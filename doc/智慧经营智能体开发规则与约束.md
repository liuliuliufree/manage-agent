# 智慧经营智能体开发规则与约束

> 适用项目：平安寿险口袋E智慧经营智能体
> 文档版本：V1.0
> 文档性质：产品、算法、后端、前端、测试、架构及业务规则团队共同遵循的开发基线
> 适用范围：方案设计、模型与工具建设、接口开发、前端交互、测试验收及生产运营

## 当前 Demo 范围覆盖说明（2026-09-21）

按项目 AGENTS.md 的最新已确认范围，Demo 仅交付一次 Goal 分析、机会发现、圈客和策略执行。每次请求最多一个 Plan，不构建或接入 Replan；NO_RESULT 停止，缺信息提示后结束本次运行，部分成功、阻断或失败也不生成新计划。用户重新提交作为独立运行。策略执行可以使用明确标识的模拟任务/分发，执行前确定性业务校验仍必须保留。

本文以下关于多次计划、重规划、追踪反馈、剩余目标调整、再次经营及跨计划复用的要求属于长期基线，不适用于当前 Demo 验收；与本说明冲突的旧 Demo 要求以 AGENTS.md 为准。动态能力选择、可信事实与规则裁决等要求继续适用。本次只调整范围，不代表代码已改动。

## 0 文档结论

智慧经营智能体必须实现为一个由代理人自然语言目标驱动、能够动态规划能力组合的经营超级Agent。

定向洞察、自动圈客、策略生成、校验分发、追踪迭代是五类可独立调用、组合、重复或跳过的通用经营能力，不是永远按固定顺序执行的五个流程节点。

事实与业务规则必须来自确定性数据、知识和规则服务。Agent负责理解目标、生成计划、组织证据和形成经营建议，但不得臆造事实、替代规则裁决或绕过执行权限。

当前Demo中的开门红、500W目标、御享分红26、御享金越年金、个险渠道和当前代理人均为示例输入。实现不得绑定这些示例。

## 1 总则

### 1.1 文档目的

本文件用于统一智慧经营智能体的产品定义和技术实现，防止项目在开发过程中退化为以下任一种形态：

- 开门红专用流程；
- 特定产品推荐器；
- 固定客户筛选工具；
- 仅生成营销话术的聊天助手；
- 把全部知识、规则和逻辑装入单一Prompt的不可治理系统；
- 以多个机械分工Agent模拟固定工作流的伪多Agent架构。

任何产品原型、技术方案、接口设计、提示词、模型训练、前端交互或测试用例，均不得与本文件中的硬约束冲突。

### 1.2 规则分级

| 等级     | 标识  | 含义                                               | 变更要求                                     |
| -------- | ----- | -------------------------------------------------- | -------------------------------------------- |
| 硬约束   | `H` | 保障业务正确性、权限边界、合规性和通用性的强制要求 | 必须实现并通过验收。例外须完成书面评审和审批 |
| 推荐原则 | `R` | 提高可维护性、可解释性、性能和用户体验的优先设计   | 原则上采用；偏离时须说明原因、风险和替代措施 |
| Demo特例 | `D` | 为当前演示准备的示例参数、渠道或产品范围           | 只能作为配置或测试数据，不得写入通用逻辑     |

### 1.3 核心术语

| 术语          | 定义                                                                                                           |
| ------------- | -------------------------------------------------------------------------------------------------------------- |
| Goal          | 代理人以自然语言表达的经营目标。结构化后包括目标类型、指标、期限、对象范围、产品或需求偏好、约束和完成标准     |
| Plan          | Agent为完成Goal动态生成的执行计划。Plan可调整能力调用顺序、重复调用能力、跳过非必要能力，并根据中间结果重规划  |
| Capability    | 可由Agent调用的通用经营能力。本基线定义五类：定向洞察、自动圈客、策略生成、校验分发、追踪迭代                  |
| Opportunity   | 基于Goal及相关证据形成的可经营机会。它描述经营问题、适配条件、证据和价值，不等同于场景标签、产品标签或客户名单 |
| Tool          | 向Agent提供确定性数据、规则计算、模型推断、知识检索或业务执行能力的受控接口                                    |
| 经营超级Agent | 负责理解Goal、生成Plan、选择和编排Capability、综合证据、形成经营建议并在必要时重规划的统一决策主体             |

## 2 核心架构原则

### H-001 目标驱动

Agent必须从代理人的自然语言经营目标出发，完成目标解析、信息缺口识别、规划和执行。系统不得要求用户必须先选择一个固定场景流程才能使用通用能力。

### H-002 五类能力不是固定五步

定向洞察、自动圈客、策略生成、校验分发、追踪迭代必须建模为独立、可组合的Capability。它们不是永远按①至⑤顺序执行的五个固定节点。

一次任务可以：

- 仅调用其中一类或几类能力；
- 跳过已有结果已经覆盖的能力；
- 多次调用同一能力；
- 根据中间结果改变调用顺序；
- 因规则阻断、数据缺失、目标变化或用户修正而重新规划。

### H-003 采用一个经营超级Agent

默认采用一个经营超级Agent统一完成Goal理解、Plan生成、能力选择、结果综合和重规划，并通过Tool、数据、模型、知识库和规则引擎获得具体能力。

不得仅因业务步骤不同而机械拆分为洞察Agent、圈客Agent、策略Agent、校验Agent等多个Agent。

只有满足下列条件之一并通过架构评审时，才可以增加独立Agent：

- 存在独立安全域或权限主体；
- 存在独立生命周期和明确自治责任；
- 存在可证明的并行自治收益，且普通Tool或Capability无法满足；
- 需要隔离风险、数据或执行权限。

### H-004 Workflow只定义问题和控制点

Workflow可以定义：

- 某阶段要解决的问题；
- 必要输入和完成条件；
- 允许调用的能力；
- 必须经过的规则或人工控制点；
- 失败处理、回退和终止条件。

Workflow不得写死：

- 某场景下固定的机会结论；
- 固定客户画像；
- 固定圈客条件；
- 固定产品适配结论；
- 固定经营策略或话术；
- 固定的五步执行顺序。

### H-005 采用 Goal → Plan → Capability

系统的标准运行关系为：

```text
代理人自然语言目标
        ↓
       Goal
        ↓
经营超级Agent生成或调整Plan
        ↓
动态选择和编排Capability
        ↓
调用Tool 数据 模型 知识 规则
        ↓
形成结果 证据 决策与下一步
        ↓
必要时重规划或进入执行
```

Plan必须是运行时产物，不得由场景名称直接映射为一个固定流程编号。

### H-006 能力必须外置

业务事实、计算、检索、模型推断、权限校验和执行动作必须通过受控能力实现。不得把所有知识、规则、流程和推理逻辑塞入一个大Prompt。

Prompt可以承载任务说明、上下文组织和输出约束，但不得成为：

- 客户事实库；
- 产品条款库；
- 渠道和人员归属系统；
- 权限裁决系统；
- 长期不可版本化的业务规则库。

### H-007 优先复用现有经营平台能力

智慧经营智能体必须优先复用现有智慧客户营销平台及其他已建设经营系统中的通用能力，不得为实现Agent场景重复建设已有的客群圈选、客群分析、营销策略配置与执行、经营追踪和营销复盘等功能。

Agent的主要职责是：

- 理解代理人的自然语言经营Goal；
- 基于Goal动态生成和调整Plan；
- 选择、组合和调用现有平台能力；
- 综合平台返回的数据、模型、知识和规则结果形成经营判断；
- 根据经营反馈持续调整后续行动和目标拆解。

现有经营平台主要承担：

- 客群标签、规则、人群包及名单生成；
- 客户和代理人画像分析；
- 产品、素材、案例、话术等经营资产管理；
- 渠道、任务、名单及策略执行；
- 客户行为、活动结果和转化结果追踪；
- 经营活动复盘及历史经验沉淀。

当现有平台已经具备相应能力时，不得通过以下方式重复实现：

- 在Prompt中重新实现已有圈客、策略或规则逻辑；
- 在Agent代码中复制已有平台业务逻辑；
- 在前端通过静态逻辑模拟已有平台能力；
- 为Demo单独建设一套与现有平台语义重复的数据加工和执行链路。

只有在确认现有平台能力无法满足当前Goal，并完成能力缺口评估后，方可新增或扩展Tool、Capability或底层服务。

智慧经营智能体与现有经营平台的关系应遵循：

```text
代理人自然语言Goal
        ↓
智慧经营超级Agent
理解目标 / 规划 / 判断 / 编排
        ↓
现有经营平台能力
圈客 / 分析 / 策略 / 执行 / 追踪 / 复盘
        ↓
业务数据、规则、知识、模型和经营资产
```

智能体的目标不是替代现有经营平台，而是将原本需要用户逐项操作的平台能力，通过自然语言目标和Agent动态编排方式组织为完整的智能经营闭环。

### R-001 分层实现

建议采用以下逻辑分层：

| 层级          | 主要职责                                                         | 不得承担的职责                                   |
| ------------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| 交互层        | 接收自然语言Goal，呈现Plan、证据、结果、确认项和执行状态         | 不在前端代码中复制圈客、权限或产品适配规则       |
| 经营超级Agent | 解析Goal，生成和调整Plan，选择Capability，综合证据，形成经营决策 | 不伪造事实，不绕过业务规则，不直接修改确定性数据 |
| 通用能力层    | 提供五类可独立调用的经营能力和统一输入输出契约                   | 不以开门红或某款产品为唯一入口                   |
| 确定性服务层  | 提供规则、权限、归属、计算、数据、知识和任务执行Tool             | 不把概率性输出伪装为确定性业务结论               |
| 数据与知识层  | 维护来源、版本、有效期、权限、血缘和质量状态                     | 不接收无来源的生成内容作为已确认事实             |

## 3 五大通用经营能力约束

五类能力的编号仅用于识别能力类别，不代表执行顺序。

### 3.1 定向洞察

**能力目的：** 识别与当前Goal相关的经营问题、机会方向、优先级和证据，为圈客或策略生成提供可解释输入。

#### H-101 输出Opportunity而非固定客群

定向洞察必须输出通用Opportunity对象或机会集合，不得直接把某场景下预设的客户画像当作唯一结论。

#### H-102 证据可追溯

每个Opportunity必须关联支持其成立的客户数据、产品知识、阶段信号、经营事实或模型结果，并标明来源、时间和适用范围。

#### H-103 机会与目标相关

每个Opportunity必须说明其与Goal的关系，包括可能贡献、适用条件、时效、主要风险和建议下一步。不能只输出泛化的营销主题。

#### R-101 优先级可解释

机会排序宜分别说明目标贡献、适配程度、时效性、可触达性、风险和数据完整度，避免仅返回无法解释的综合分。

### 3.2 自动圈客

**能力目的：** 把Opportunity转化为可评估的候选客户集合，并说明入选、排除和排序依据。

#### H-111 圈客条件由Opportunity动态形成

圈客逻辑必须由Goal和Opportunity动态形成，通过客户数据查询、特征计算、模型与规则组合执行。不得针对开门红、养老专项或某个具体产品写死一套不可复用的筛选流程。

#### H-112 候选客户不等于可执行客户

圈客结果只表示经营候选。未经校验分发，不得直接进入任务创建、客户触达或营销执行。

#### H-113 圈客过程可解释和可复现

系统必须保留：

- 查询条件；
- Opportunity到筛选条件的映射；
- 特征版本；
- 模型版本；
- 规则版本；
- 数据时间点；
- 排序依据；
- 入选和排除原因。

#### R-111 区分数据丰富度

老客户与新客户可依据数据可得性使用不同特征和置信度策略，但不得把客户新旧直接等同于价值高低、需求强弱或经营许可。

### 3.3 策略生成

**能力目的：** 针对Goal、Opportunity和客户证据形成可执行的经营决策。

#### H-121 策略生成不是话术生成

策略输出至少应回答：

- 本次经营要实现什么目标；
- 当前Opportunity是什么；
- 对客户需求的判断及其依据；
- 建议从什么问题或需求切入；
- 产品或解决方案为何适配；
- 应按什么步骤行动；
- 适合的时机、渠道和材料；
- 存在哪些风险、禁区或待确认信息；
- 下一步是什么；
- 如何判断本次经营是否取得进展。

营销话术可以是策略的一个派生结果，但不能替代经营策略。

#### H-122 事实与建议分离

产品条款、客户属性、历史行为和业务规则必须引用确定性来源。Agent生成的需求判断、优先级和行动建议必须标明为经营判断，不得表达为既成事实。

#### H-123 允许不推荐

当证据不足、产品不适配、风险过高或权限不满足时，策略必须允许输出：

- 补充信息；
- 暂缓经营；
- 更换经营方向；
- 不建议经营。

系统不得为了返回一个非空答案而强制生成营销话术。

#### R-121 提供备选方案和取舍

对于高价值或高风险客户，宜提供备选策略及适用条件，并说明预期收益、投入、风险和转换条件。

### 3.4 校验分发

**能力目的：** 在任何经营名单、任务或触达动作进入执行前，完成业务资格、归属、权限和执行边界检查，并将任务分发给合法且适当的执行主体。

#### H-131 执行前必须完成校验

所有进入执行态的对象必须完成以下检查：

- 渠道归属；
- 客户归属；
- 人员归属；
- 经营权限；
- 适用的业务限制；
- 任务执行所需的其他前置条件。

校验失败必须阻断执行，不得仅提示风险后继续。

#### H-132 确定性规则裁决

归属和权限结果必须由权威数据与规则服务返回。Agent可以解释结果和建议合法补救路径，但不得修改、猜测或覆盖裁决。

#### H-133 当前Demo渠道边界

当前Demo渠道为个险，执行人员为当前代理人。银保客户不得进入个险经营名单或任务。

该限制必须通过可配置的渠道和权限规则实现，不能只依靠：

- Prompt中的文字约束；
- 前端隐藏；
- Agent自行判断；
- 演示人员手工规避。

#### H-134 分发可审计

每次分发必须记录对象、执行人、渠道、校验结果、规则版本、时间、发起来源和任务标识。

### 3.5 追踪迭代

**能力目的：** 持续接收经营过程和结果反馈，判断Goal进展、策略有效性和下一步行动，并触发Plan调整。

#### H-141 追踪必须回到Goal

追踪指标必须关联原始Goal及其完成标准，不能只统计触达次数、页面访问量或话术使用量。

#### H-142 反馈可触发重规划

出现以下情况时，Agent必须能够再次调用洞察、圈客、策略或校验能力：

- 客户响应改变；
- 任务完成或失败；
- 目标缺口变化；
- 规则变化；
- 数据更新；
- 原有策略效果不足；
- 用户修改目标或约束。

#### H-143 反馈必须事实化

客户反馈、任务状态和业绩结果必须作为带时间、来源和关联对象的事件记录。Agent的总结不得覆盖原始记录。

#### R-141 区分相关性与因果性

策略效果评估宜至少按策略版本、客户群、渠道、时间窗口和执行完成度进行拆分，不得仅依据成交结果宣称某策略造成了结果。

### 3.6 能力组合示例

| 用户目标                             | 可能的Capability组合                         | 说明                                                           |
| ------------------------------------ | -------------------------------------------- | -------------------------------------------------------------- |
| 我这个月还差100W，先找最有把握的客户 | 洞察 → 圈客 → 校验 → 策略 → 校验 → 追踪 | 首次校验可先排除不可经营客户，策略形成后可再次检查具体执行动作 |
| 帮我看看王女士下一步怎么经营         | 策略 → 校验 → 追踪                         | 已指定客户且证据充分时，可以不做全量圈客                       |
| 上次养老客户效果不好，调整一下       | 追踪 → 洞察 → 策略 → 圈客 → 校验         | 先分析反馈，再修正机会和策略，必要时重新形成候选人群           |
| 最近有什么值得关注的机会             | 洞察                                         | 只需发现机会时，可以在洞察后结束并等待用户选择                 |

以上组合均为示例，不得转化为新的固定流程模板。

## 4 Goal与Plan规则

### 4.1 Goal结构化要求

#### H-201 保留原始目标

系统必须保存用户的原始自然语言表达，并将结构化Goal与原始表达关联，防止解析后丢失语义。

#### H-202 Goal最小结构

Goal至少应支持以下字段：

| 字段                    | 说明                                                           |
| ----------------------- | -------------------------------------------------------------- |
| goal_id                 | 目标唯一标识及版本                                             |
| original_request        | 用户原始自然语言                                               |
| goal_type               | 目标类型，例如业绩达成、客户盘点、产品经营、关系维护或经营复盘 |
| metric                  | 衡量指标，例如保额、保费、客户覆盖、有效沟通或任务完成         |
| target                  | 目标值或目标方向                                               |
| time_horizon            | 时间范围或截止日期                                             |
| audience_scope          | 客户或经营对象范围                                             |
| product_or_need_context | 产品偏好、需求方向或业务背景                                   |
| channel_and_actor       | 渠道、当前人员和授权主体                                       |
| constraints             | 预算、时间、合规、渠道、权限或其他限制                         |
| missing_information     | 缺失且可能影响Plan的信息                                       |

字段可以为空，但影响规划或执行的缺失状态必须显式表达。量化 Goal 的完成条件由
`metric + target` 推导，不重复保存同义完成标准；只有无法由 Target 表达的非量化
完成条件，在出现真实跟踪消费者后才扩展独立契约。

#### H-203 澄清门槛

只有在关键信息缺失会导致明显不同的行动、越权或不可逆执行时，才必须向用户澄清。其他情况下可以使用明确标注的假设继续规划，并允许用户修正。

#### R-201 复杂目标分解

复杂Goal宜分解为可度量的子目标，并保留子目标与总目标之间的贡献关系。

### 4.2 Plan生成与调整

#### H-211 Agent动态选择能力

Agent必须根据Goal、已有上下文、数据可用性和风险决定：

- 调用哪些Capability；
- 调用顺序；
- 哪些调用可以并行；
- 是否需要重复调用；
- 是否需要用户确认；
- 何时结束；
- 何时重规划。

#### H-212 不得把五类能力实现为固定状态机

实现和测试不得假设五类能力必然全部出现、只出现一次或按编号顺序执行。不得以五个固定节点作为唯一状态机。

#### H-213 支持局部重规划

当中间结果为空、证据冲突、规则阻断、目标变化、用户修正或外部状态更新时，Plan必须支持局部重规划，并保留已经确认的事实和有效结果。

#### H-214 外部写操作必须执行可信控制策略

涉及以下操作时，Capability 元数据或执行策略必须确定性要求必要的规则校验和用户确认；
Plan 可以展示这些要求，但不得由 Planner 或模型自行降低：

- 名单落库；
- 任务创建；
- 客户触达；
- 跨渠道分发；
- 修改客户或任务状态；
- 其他会改变外部业务状态的操作。

#### R-211 向用户展示Plan摘要

前端宜展示简化版Plan、当前步骤、关键依据、阻断原因和可选下一步，但不应暴露内部敏感推理文本。

### 4.3 Capability调用契约

| 契约部分 | 强制内容                                                                           |
| -------- | ---------------------------------------------------------------------------------- |
| 输入     | `goal_id`、`plan_id`、能力标识、授权主体、对象范围、受控输入引用和数据时间点   |
| 输出     | 结构化结果、证据引用、事实或判断类型、质量或置信信息、规则结果、错误和建议下一步   |
| 版本     | 能力版本、Tool版本、模型版本、规则版本、知识版本和关键特征版本                     |
| 状态     | 成功、部分成功、需补充信息、被规则阻断、无结果、失败。禁止用空列表同时表达多种状态 |
| 审计     | 调用时间、发起主体、输入摘要、结果摘要、外部写操作标识和关联任务                   |

## 5 知识 数据 模型与规则边界

系统必须分开管理确定性事实、业务规则、模型判断、经营经验和Agent决策。接口与前端展示也必须保留这一类型信息，避免把建议包装成事实。

| 内容类型 | 权威来源                                 | Agent权限                    | 输出要求                                   |
| -------- | ---------------------------------------- | ---------------------------- | ------------------------------------------ |
| 客户事实 | 客户主数据、保单、互动和经授权的业务数据 | 读取、归纳，不得臆造或改写   | 带来源、时间、完整度和权限状态             |
| 产品事实 | 有效产品知识、条款、销售规则和版本库     | 检索、解释，不得补写未知条款 | 带产品版本、生效范围和引用                 |
| 业务规则 | 规则引擎、权限服务、渠道和归属系统       | 调用、解释，不得覆盖裁决     | 返回规则标识、版本、结果和原因             |
| 模型判断 | 经治理的预测或排序模型                   | 调用并结合其他证据决策       | 标明模型版本、分数含义、限制和适用范围     |
| 经营经验 | 经治理的案例库、方法库和专家知识         | 可以参考，不得当作强制规则   | 标明适用条件、来源和时效                   |
| 经营决策 | 经营超级Agent基于Goal和证据动态生成      | 可以生成、解释和调整         | 明确标记为建议，列出主要依据、风险和下一步 |

### H-301 无来源内容不得作为事实

任何客户属性、产品能力、历史事件或经营结果，如果没有可追溯的确定性来源，只能标记为未知、待确认或假设，不能进入事实字段。

### H-302 业务规则优先

当Agent建议与业务规则冲突时，以规则结果为准。Agent必须停止相关执行并说明阻断原因。

### H-303 知识必须带版本和时效

产品知识、业务规则和经营知识必须包含版本、生效时间或适用时间。检索不到适用版本时，不得使用其他版本推断当前事实。

### H-304 经营经验只作参考

经营经验可以帮助Agent提出假设、排序机会或生成备选策略，但不能替代客户事实、产品知识或业务规则。具体经营决策由Agent基于当前Goal和证据动态生成。

### H-305 最小数据访问

Capability只能获取完成当前Goal所需且已获授权的数据。日志、Prompt和前端展示不得扩大敏感数据暴露范围。

### R-301 显式处理来源冲突

多个确定性来源不一致时，宜根据权威等级、更新时间和适用范围返回冲突状态，交由规则或人工处置，不应由Agent自行择一并隐藏冲突。

## 6 Opportunity通用抽象

### H-401 Opportunity与场景解耦

Opportunity不得绑定开门红、年中、年末或某款产品。场景和产品可以作为机会形成的上下文或证据，但不能成为Opportunity的结构定义。

### H-402 Opportunity必须可计算和可解释

Opportunity核心契约必须表达关联 Goal、经营问题和形成判断的证据。适配条件、限制、
优先级和时效等语义在出现真实消费者时由对应阶段的受控产物扩展，不提前堆入核心对象。

### H-403 圈客逻辑从Opportunity形成

圈客查询、特征计算或模型输入必须由 Customer Targeting Capability 基于 Opportunity
及其证据生成受控 CandidateCriteria，并记录 Opportunity 到筛选条件的映射；
可执行筛选逻辑不属于 Opportunity 核心契约。

### 6.1 Opportunity最小字段

| 字段                  | 说明                                                                                             |
| --------------------- | ------------------------------------------------------------------------------------------------ |
| `opportunity_id`      | 机会唯一标识                                                                                     |
| `goal_ref`            | 关联具体 Goal 版本                                                                               |
| `opportunity_type`    | 通用机会类型，例如保障缺口、养老现金流、家庭责任变化、资产安排、加保、续期或触达时机；类型可扩展 |
| `problem_statement`   | 待解决的经营问题，不能直接写成销售结论                                                           |
| `evidence_links`      | 支持、限制或反驳机会判断的证据引用                                                               |
| `priority`            | 可选的轻量优先级；存在时必须同时给出可解释理由                                                   |

CandidateCriteria 在圈客阶段形成，Validity/InvalidationConditions 在持续跟踪阶段形成，
下一步由 Planner 根据 Goal、Opportunity、已有 Context 和 Capability Catalog 决定。

### 6.2 示例说明

以下是Opportunity类型示例，不是固定分类：

- 家庭责任变化带来的保障调整机会；
- 退休临近带来的养老现金流规划机会；
- 现有保障与目标之间存在缺口；
- 长期未覆盖的重要客户关系维护机会；
- 已有保单或服务事件触发的后续经营机会。

这些机会可以出现在开门红、日常经营、年中盘点、年末收官、新产品上市或其他阶段。系统不能通过场景名称预设机会结论。

## 7 通用性约束

### H-501 新增场景优先组合现有能力

新增经营场景必须先证明现有Goal、Opportunity、Capability和Tool无法覆盖，方可新增基础能力或专用流程。复制一套场景工作流不得作为默认方案。

### H-502 产品和场景必须配置化

产品、阶段、目标值、渠道、人员和策略模板必须通过数据、知识或配置注入，不得写入：

- 通用编排代码；
- 前端静态分支；
- 不可维护的Prompt条件；
- 仅对某个场景生效的隐藏逻辑。

### H-503 跨场景契约保持稳定

同一Capability在不同场景下必须保持核心输入输出语义一致。扩展字段应向后兼容，并通过版本管理。

### H-504 必须进行通用性测试

至少使用以下用例验证动态规划和能力复用：

- 一个非开门红场景；
- 一个不使用御享分红26或御享金越年金的场景；
- 一个只需部分Capability的任务；
- 一个需要重复调用同一Capability的任务；
- 一个因规则阻断而重规划的任务；
- 一个用户中途修改Goal的任务。

### R-501 评估能力复用度

建议按新增场景复用的Capability、Tool、规则和接口比例，以及新增硬编码分支数量，评估架构通用性。

### 7.1 新场景接入顺序

1. 将新需求表达为Goal及完成标准。
2. 检查现有Opportunity类型和五类Capability能否覆盖。
3. 补充或更新产品知识、数据、模型、规则或Tool。
4. 只有在能力语义确实缺失时，才扩展Capability契约。
5. 使用跨场景回归用例验证没有破坏既有能力。

## 8 Demo与生产边界

Demo用于验证完整故事和关键能力，不代表生产系统可以采用场景硬编码。

| 类别     | 当前Demo设定             | 生产实现要求                                                       |
| -------- | ------------------------ | ------------------------------------------------------------------ |
| 经营阶段 | 开门红                   | 作为Goal上下文或配置输入，支持其他经营阶段                         |
| 经营目标 | 达成500W保额             | 目标指标、数值、期限和完成标准可配置、可解析                       |
| 主推产品 | 御享分红26、御享金越年金 | 从有效产品知识和配置获取，不能在Capability中写死产品名称或适配人群 |
| 渠道     | 个险                     | 通过渠道上下文和规则服务校验                                       |
| 执行人员 | 当前代理人               | 通过登录身份、人员关系和权限服务确定                               |
| 排除边界 | 银保客户不可进入个险经营 | 由确定性渠道归属和权限规则阻断，并形成审计记录                     |

### D-001 示例目标

开门红500W是演示输入，用于展示Agent如何解析目标和动态规划，不是系统内置的唯一Goal类型。

### D-002 示例产品

御享分红26和御享金越年金是演示中的产品输入。产品适配信息必须来自当期有效的产品知识，不由本基线固化。

### D-003 示例渠道和人员

Demo限定个险渠道和当前代理人，银保客户必须被排除。生产环境应采用同一规则机制支持更多渠道和人员关系。

### 8.1 Demo可以简化的内容

- 数据规模；
- 模型复杂度；
- Opportunity类型数量；
- 策略模板数量；
- 追踪周期；
- 部分Tool背后的实现。

如果Tool使用模拟数据，必须保持与生产契约一致，并清楚标记数据来源为模拟。

### 8.2 Demo不可简化的内容

- 不得把五类能力固化为不可变顺序；
- 不得绕过渠道、人员、客户归属和经营权限校验；
- 不得把示例产品知识、圈客条件或策略结论写死在代码或大Prompt中；
- 不得把模型推测展示为客户事实或业务规则；
- 不得允许银保客户进入个险经营任务；
- 不得省略关键结果的来源和证据类型。

## 9 跨团队开发基线

| 团队       | 必须落实的基线                                                                                       |
| ---------- | ---------------------------------------------------------------------------------------------------- |
| 产品       | 使用Goal和通用Capability定义需求；区分事实、判断、规则结果和建议；定义用户确认点、阻断路径和失败路径 |
| 算法       | 输出可解释的模型信号和适用范围；维护版本、评估和漂移信息；不得用模型替代权限和归属规则               |
| 后端       | 提供稳定的Capability和Tool契约；实现规则校验、幂等、审计、版本、权限和错误语义；支持重规划           |
| 前端       | 支持自然语言Goal、Plan摘要、证据与来源、阻断原因、用户确认和任务状态；不得复制业务规则               |
| 测试       | 按硬约束设计正向、逆向、越权、无数据、冲突、重复调用、重规划和跨场景用例                             |
| 架构与治理 | 评审新增Agent、新Capability、规则例外和跨域数据访问；维护规则版本、知识时效和审计可用性              |

### 9.1 前端信息要求

#### R-601 展示Goal和Plan摘要

首屏宜展示Agent理解的Goal、关键假设、准备执行的Plan和需要用户确认的内容。

#### R-602 同时展示结论和依据

Opportunity、客户和策略界面宜同时展示结论、主要依据、数据时间、限制和可展开的详细证据。

#### R-603 阻断信息必须可行动

校验失败时宜显示确定性原因和合法补救路径，例如补充授权、转交正确渠道或移出名单，而不是只显示“失败”。

### 9.2 后端与算法接口要求

- 使用稳定ID关联Goal、Plan、Opportunity、客户、策略和任务；
- 所有Capability返回统一状态语义；
- 区分“无结果”“数据不足”“规则阻断”和“系统失败”；
- 对外部写操作提供幂等键；
- 保留数据、知识、模型、特征和规则版本；
- 支持结果回放和审计查询；
- 不在日志中记录超过排障和审计所需的客户敏感信息。

## 10 禁止事项

以下事项一律禁止：

1. 把智慧经营智能体实现为开门红专用流程、特定产品推荐器或固定话术生成器。
2. 假设五类能力必须按①至⑤执行、每类只执行一次或所有任务都必须经过全部能力。
3. 因步骤不同而机械拆成多个Agent，并用Agent数量替代能力建设。
4. 在Workflow中写死Opportunity、客户画像、圈客条件、产品适配、策略答案或渠道归属。
5. 将客户事实、产品条款、经营结果或业务规则仅存放在Prompt中。
6. 由Agent猜测渠道归属、人员归属、客户归属、经营权限或规则例外。
7. 未经校验分发就创建执行任务、触达客户或交付经营名单。
8. 在个险Demo中允许银保客户进入个险经营。
9. 把经营经验或模型分数当成确定性事实或强制规则。
10. 为了获得非空结果而降低硬规则、隐藏排除原因或生成无依据的策略。
11. 为每个新场景复制一套接口、数据加工、Prompt和前端流程，除非通过通用能力缺口评审。
12. 在日志和页面中暴露超出当前Goal所需的敏感客户数据或内部敏感推理文本。
13. 用前端隐藏代替后端权限阻断。
14. 把Demo模拟数据混同为生产事实。

## 11 验收检查清单

硬约束相关检查项必须全部通过。任何未通过项均应阻止发布，或形成经批准的有期限例外。

### 11.1 架构与规划

- [ ] 系统可以直接接收自然语言经营目标，不依赖用户先选择固定流程。
- [ ] Goal保存原始表达，并形成包含指标、期限、范围、约束和完成标准的结构化表示。
- [ ] Plan由Agent在运行时生成，可以跳过、重复或重排五类Capability。
- [ ] 至少一个测试用例只调用部分Capability。
- [ ] 至少一个测试用例重复调用同一Capability。
- [ ] 至少一个测试用例因中间结果或规则阻断而重规划。
- [ ] 新增场景复用现有Capability和Tool，没有复制整套场景流程。
- [ ] 架构默认只有一个经营超级Agent；任何新增Agent均有明确的评审依据。

### 11.2 能力和业务正确性

- [ ] 定向洞察输出通用Opportunity，并提供来源、有效期和目标贡献说明。
- [ ] 圈客条件由Opportunity动态生成，可查看入选、排除和排序依据。
- [ ] 圈客结果与可执行名单在状态和接口上明确区分。
- [ ] 策略包含完整经营决策要素，而不只是营销话术。
- [ ] 证据不足或不适配时，系统可以输出暂缓、不建议经营或补充信息。
- [ ] 所有执行对象在执行前完成渠道、客户、人员和权限校验。
- [ ] 个险Demo中银保客户被确定性规则阻断，且前端不能绕过。
- [ ] 追踪结果关联原始Goal，并能触发Plan重规划。

### 11.3 数据 知识 模型和规则

- [ ] 客户和产品事实均有来源、时间和版本。
- [ ] 未知信息不会被Agent补写为事实。
- [ ] 规则服务返回规则标识、版本、结果和原因。
- [ ] Agent不能覆盖规则裁决。
- [ ] 模型输出标明模型版本、分数含义、适用范围和限制。
- [ ] 经营经验只作为参考知识，不会自动升级为硬规则。
- [ ] 接口和页面能够区分事实、规则结果、模型判断和Agent建议。
- [ ] Tool遵循最小数据访问原则，日志不存在不必要的敏感数据。

### 11.4 工程和可运营性

- [ ] Capability接口具有明确状态、错误语义、版本和幂等策略。
- [ ] 调用链可以按`goal_id`、`plan_id`、`opportunity_id`和`task_id`追踪。
- [ ] 规则、知识、模型、特征和能力版本可用于结果回放。
- [ ] 空结果、数据冲突、规则阻断、Tool失败和用户修正均有处理路径。
- [ ] 前端显示Plan摘要、主要证据、数据时间、阻断原因和合法下一步。
- [ ] 跨场景回归覆盖非开门红、非指定产品、部分能力和重复能力用例。

### 11.5 Demo专项验收

- [ ] 输入可以表达为：开门红阶段，目标500W，主推御享分红26和御享金越年金。
- [ ] 产品适配信息从当前有效知识中取得，不由本地常量或Prompt硬编码。
- [ ] Agent能够根据Goal动态形成Opportunity、候选客户和策略。
- [ ] Demo明确限定个险渠道和当前代理人。
- [ ] 银保客户不会进入个险经营名单和任务。
- [ ] 替换经营阶段、目标值或产品后，无需重写五类Capability即可运行。

## 12 规则变更与例外

### H-701 硬约束变更必须评审

任何硬约束变更必须说明：

- 业务原因；
- 影响范围；
- 合规、权限和数据风险；
- 迁移方案；
- 回归测试范围；
- 回退方案。

变更须由产品、架构、业务规则负责人及相关合规或权限责任方评审。

### H-702 临时例外必须有范围和期限

临时例外必须限定场景、人员、渠道、数据范围和有效期，并具备可关闭的技术开关及审计记录。

### H-703 冲突必须在开发前升级

任何下游设计与本基线冲突时，应在开发前升级评审，不得以Demo进度、模型效果或实现便利为由静默绕过。

### R-701 定期复核

建议随产品、渠道、监管、数据和模型变化定期复核本基线，并保持规则编号稳定，以便需求、代码、测试和审计记录引用。

## 附录 A 开发决策快速判断

| 问题                                      | 若答案为是                                     | 若答案为否                                  |
| ----------------------------------------- | ---------------------------------------------- | ------------------------------------------- |
| 这是确定性事实或业务裁决吗                | 放入权威数据、知识或规则服务，并提供版本和来源 | 继续判断是否属于模型信号或经营建议          |
| 这是可跨场景复用的经营问题吗              | 扩展现有Capability或Tool契约                   | 先确认是否只是场景配置、产品知识或展示差异  |
| 执行会改变外部状态吗                      | 先做必要规则校验和用户确认，并记录审计         | 可以继续只读分析或生成建议                  |
| 新增Agent是否对应独立安全域或自治生命周期 | 提交架构评审并定义边界                         | 保留一个经营超级Agent，以Capability承载差异 |
| 方案是否只能支持开门红和两款示例产品      | 判定不符合通用性硬约束，必须重构               | 使用跨场景用例继续验证                      |

## 附录 B 基线性架构判定

满足以下全部条件，方可判定实现遵循本基线：

```text
自然语言Goal可变化
        AND
Plan由Agent动态生成
        AND
五类Capability可选 可重排 可重复
        AND
事实与规则来自确定性来源
        AND
Opportunity与场景和产品解耦
        AND
圈客逻辑由Opportunity形成
        AND
策略输出经营决策而非只有话术
        AND
执行前完成归属和权限校验
        AND
新场景优先复用既有能力组合
```

任一条件不满足，均不能仅凭界面存在聊天入口或使用大模型而认定为“通用智慧经营智能体”。
