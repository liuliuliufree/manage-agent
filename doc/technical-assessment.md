# 智能加保经营 Demo 技术实现说明

## 一、总体判断

该故事在技术上可以实现，但需要区分三种建设深度：

| 建设形态 | 实现难度 | 典型周期（参考） | 能做到什么 |
|---|---:|---:|---|
| 领导演示版 | 中 | 2～4 周 | 使用脱敏/构造数据，完整演示机会洞察、圈客、策略、校验、模拟触达和反馈迭代 |
| 业务试点版 | 中高 | 3～6 个月 | 接入部分真实数据和一个或两个渠道，在人工审批下开展小范围真实经营 |
| 生产平台版 | 高 | 6～12 个月以上 | 打通全量数据、全渠道、权限合规、实时事件、实验评估、审计回滚和高可用体系 |

以上周期假设已有可用的客户、保单、行为和渠道系统；如果数据口径、客户授权、适当性规则或渠道接口尚未标准化，建设难点主要会出现在数据治理和系统集成，而不是大模型本身。

从技术构成看，这不是“一个大模型自动做营销”，而是五类能力的组合：

1. 数据与特征平台：汇总客户、保单、行为、授权和经营结果；
2. 规则与评分模型：计算保障缺口、机会分、意向分，并执行合规硬校验；
3. 大模型与知识库：理解经营目标、生成策略、解释原因、形成经营总结；
4. Agent 与工作流：调用数据、模型、规则、渠道和人工任务工具，维护客户旅程状态；
5. 事件与实验平台：追踪反馈，评估策略效果，在审批后迭代策略版本。

## 二、完整链路：输入、模型/工具、Agent 动作与输出

| 环节 | 主要输入数据 | 模型 / 工具 | Agent 动作 | 主要输出 | 难度判断 |
|---|---|---|---|---|---|
| 1. 目标与边界理解 | 经营目标、时间范围、目标产品方向、可用预算、营销授权要求、触达频控、适当性规则、人员资格规则 | 大模型、经营术语知识库、结构化任务模板 | 将自然语言目标拆成指标、约束、分析范围和停止条件；发现缺失参数时提示经营人员确认 | 结构化经营任务、约束清单、执行计划、任务版本 | 低到中。结构化抽取容易，难点是边界必须完整且不可被模型自行放宽 |
| 2. 多机会洞察 | 客户画像、保单与保障责任、家庭责任相关的授权信息、近期行为、历史经营结果、渠道成本、投诉/理赔状态 | SQL/指标引擎、特征计算、规则评分、聚类或机会排序模型、大模型解释 | 生成多个候选机会；计算规模、需求强度、预计响应、成本和风险；比较并推荐优先方向 | 机会卡片、候选机会排行、数据来源、更新时间、置信度、推荐理由 | Demo 中等，生产中高。核心依赖跨系统数据口径和保障缺口算法 |
| 3. 自动圈客 | 客户主数据、已有保单、保障缺口、缴费能力、主动行为、授权、频控、拒绝记录、投诉/理赔、产品适当性 | 客群查询工具、规则引擎、特征库、倾向模型/提升模型、名单去重 | 逐层筛选“有需求、可经营、值得经营”的客户；执行排除规则；为入选和未入选生成证据 | 86 名机会客户、41 名通过初筛、12 名高优先级；每人入选/排除原因 | 中高。规则可快速做，真实准确性依赖标签、模型校准和数据实时性 |
| 4. 策略与旅程生成 | 机会类型、客户画像、渠道授权与偏好、历史响应、频控、内容素材、渠道成本、可承接人员 | 大模型、RAG 知识库、合规模板库、Next Best Action 模型、工作流/状态机 | 生成递进式经营旅程和响应分支；选择渠道、时间与内容；设定转人工、等待和退出条件 | 可执行的策略包：旅程节点、渠道、内容、等待时间、分支条件、停止条件及解释 | 中。生成文本容易，难点是输出必须结构化、可执行、可校验，而不是自由文本 |
| 5. 校验与分发 | 策略包、客户授权、频控、敏感状态、产品规则、内容规则、人员资格、服务时段、渠道状态 | 确定性规则引擎、内容合规检测、适当性服务、人员匹配、流程引擎、渠道适配器 | 对每名客户逐项过闸；通过则入队，失败则拦截、暂缓或转人工；保留规则命中证据 | 校验报告、通过/拦截/暂缓决定、执行队列、人工任务、审计日志 | 高。生产难点集中在规则正确性、跨系统接口、幂等、防重复触达和审计 |
| 6. 实时追踪与动作调整 | 打开、点击、测算、浏览、咨询、拒绝、退订、投诉等事件及发生时间 | 事件总线、客户状态机、实时特征、意向评分模型、触发规则 | 更新客户状态和意向分；解释分数变化；触发继续、转人工、暂缓或退出；拒绝信号拥有最高优先级 | 客户状态时间线、68→86 的评分变化及理由、下一最佳动作、专业人员跟进任务 | 中高到高。Demo 可模拟，生产需要实时事件质量、乱序处理、去重和低延迟联动 |
| 7. 评估与受控迭代 | 触达、响应、转人工、线索、成交、成本、拒绝、退订、投诉、拦截结果、实验分组 | 指标平台、A/B 实验、统计检验/因果评估、大模型总结、策略版本管理 | 比较策略、渠道和时段效果；识别提升与风险；生成优化建议，但不直接修改生产规则 | 驾驶舱、实验结论、优化建议、待审批策略版本、发布与回滚记录 | 高。难点是归因、样本量、对照组、长期效果与合规风险的联合评价 |

## 三、需要准备的输入数据

### 1. 客户与授权数据

- 客户唯一标识、年龄段、家庭阶段等基础画像；
- 客户主动填写且已授权用于服务经营的家庭责任信息；
- 各用途、各渠道的授权状态、生效时间和失效时间；
- 客户渠道偏好、可联系时段、拒绝和退订记录。

### 2. 保单与保障数据

- 已有保单、险种、责任、保额、保费、期限和状态；
- 家庭责任与保障需求测算结果；
- 保障缺口计算口径及其版本；
- 可售产品、适用客群、限制条件和适当性规则。

### 3. 客户行为与经营数据

- 内容打开、页面浏览、测算、咨询等带时间戳事件；
- 历史触达渠道、时间、内容、次数和结果；
- 近周期频控计数、投诉、理赔和其他敏感状态；
- 历史响应、转人工、有效线索、成交、成本与负反馈。

### 4. 组织、内容与渠道数据

- 专业人员的机构、服务范围、资格、负载和在线状态；
- 已审核的素材、话术、禁限用语及版本；
- 口袋 E、绿 E 通等渠道接口能力、成本、发送限制和回执；
- 策略审批、发布、实验和回滚记录。

演示版不应使用真实敏感客户信息。建议准备 100～200 条逻辑自洽的脱敏或合成客户数据，并预置 C001、C028 等关键角色的事件脚本，以保证每次演示结果稳定、可复现。

## 四、模型与工具的职责边界

### 大模型适合做的事

- 将经营人员的自然语言目标转成结构化任务；
- 基于已计算的指标比较候选机会并生成可读解释；
- 在审核素材和规则范围内生成策略、话术草稿和分支说明；
- 汇总经营结果，生成实验解读和优化建议。

### 传统模型适合做的事

- 需求/响应倾向、意向变化、流失或负反馈风险评分；
- 渠道偏好、触达时段、下一最佳动作预测；
- 有对照组和足够样本后，使用 uplift 或因果模型判断“触达带来的增量”，避免只挑选本来就会购买的人。

演示版可先用透明的规则评分替代复杂机器学习模型，例如将保障缺口、主动测算、近期浏览、触达疲劳分别赋权。这样结果稳定，也便于领导理解。生产版再用真实历史数据训练并完成回溯验证、校准和监控。

### 必须由确定性工具完成的事

- 营销授权、触达频控、敏感期、产品适当性和人员资格校验；
- 客群查询、数值计算、名单去重、任务分发和状态流转；
- 渠道发送、回执采集、审计留痕、审批、版本发布和回滚。

上述硬约束不应仅依赖大模型判断。大模型可以解释校验结果，但不能绕过规则引擎，也不能自行改变合规规则。

## 五、Agent 的技术工作方式

Agent 本质上是一个受控的任务编排器。建议采用以下执行循环：

1. 读取目标和授权边界，形成结构化计划；
2. 调用数据查询和指标工具，获取候选机会；
3. 调用圈客、评分和规则工具，得到分层名单；
4. 调用知识库和策略生成模型，形成机器可执行的旅程定义；
5. 调用合规、适当性、频控和人员资格工具逐项校验；
6. 经审批后调用渠道或人工任务工具执行；
7. 订阅客户事件，更新状态并触发下一动作；
8. 汇总实验结果，提出新策略版本，等待人工审批发布。

每一步都应记录：输入快照、调用的工具和版本、规则命中、模型版本、置信度、输出、审批人和最终动作。这样才能做到可解释、可审计和可回放。

## 六、建议在领导 Demo 中展示的输出

建议屏幕只呈现六类核心产物，避免陷入技术细节：

1. **机会卡片**：三个候选方向及规模、需求、响应、成本、风险；
2. **可解释名单**：86→41→12 的筛选漏斗，以及 C001 的入选理由；
3. **客户旅程**：口袋 E → 绿 E 通 → 专业人员，以及继续、暂缓、退出分支；
4. **执行闸门**：C001 通过、C028 因频控被暂缓，明确展示“为什么不触达”；
5. **状态变化**：模拟客户事件后，意向分 68→86，并生成专业人员任务；
6. **受控学习**：实验结果、优化建议、人工审批、策略新版本和回滚入口。

对应的机器输出可以分别落成：机会对象、客群包、旅程 JSON、校验报告、执行任务、事件时间线、实验报告和策略版本。这些结构化产物是 Demo 从“会说”走向“会执行”的关键证据。

## 七、主要风险与降难度方案

| 风险 | 影响 | Demo 阶段的降难度方案 |
|---|---|---|
| 数据不完整或口径不一致 | 机会和保障缺口不可信 | 使用经过业务确认的合成数据集，固定指标口径并展示数据来源 |
| 模型结论不稳定 | 同一演示多次结果不同 | 数值与名单由规则/固定模型产生，大模型只负责解释；关键输出采用结构化约束 |
| 合规规则复杂 | 可能产生越权或不当推荐 | 预置确定性规则矩阵；策略先校验后执行；产品推荐保留人工确认 |
| 渠道尚未打通 | 无法展示真实闭环 | 建设渠道模拟器，模拟发送、打开、测算、拒绝等回执 |
| 实时链路成本高 | 反馈后不能及时改动作 | Demo 使用事件注入按钮驱动状态机，保留真实事件接口形态 |
| “自学习”表述过度 | 容易被理解为模型自行改规则 | 展示“提出建议→小流量实验→人工审批→版本发布→可回滚” |
| 评分缺乏解释 | 业务和合规难以接受 | 展示信号、权重/贡献、时间、有效期和排除规则，不只展示总分 |

## 八、推荐的 Demo 技术范围

为了在较短周期内获得可信效果，建议演示版采用“真实架构形态 + 模拟外部依赖”：

- 使用合成客户、保单、授权、行为和经营结果数据；
- 保障缺口、客群漏斗、频控和适当性采用确定性规则；
- 倾向分采用可解释的规则模型或轻量模型；
- 大模型生成候选机会说明、客户解释、策略草案和复盘摘要；
- 用结构化状态机执行客户旅程，不让大模型直接控制发送；
- 用渠道模拟器和事件注入完成“打开→测算→浏览→转人工/拒绝”的闭环；
- 对所有关键决策保留依据、版本和审计日志；
- 最后展示策略建议进入审批，而不是模型自动更新生产规则。

这一路径的总体难度为中等，能够真实展示 Agent 的技术形态，同时把生产阶段最重的数据治理、渠道联调和模型训练工作与领导演示解耦。

## 九、面向领导的技术总结

> 这个 Demo 的技术可行性较高。它不是依靠大模型直接决定“给谁卖什么”，而是由经营 Agent 统一编排数据分析、评分模型、合规规则、渠道工具和专业人员：大模型负责理解、生成与解释，规则引擎守住授权和合规边界，工作流负责可靠执行，客户反馈通过受控实验沉淀为下一版策略。演示版可以在数周内用脱敏数据和模拟渠道形成完整闭环；真正生产化的主要难点在数据治理、跨系统集成、实时事件、规则运营和效果归因。
