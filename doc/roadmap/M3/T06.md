
可以。**T06 Replanner 是 M3 第一次真正重新引入 LLM，但我建议把它控制得非常小。**

M2 已经有：

```text
Goal
+
Existing Context
+
Capability Catalog
↓
Planner
↓
Plan
```

而 M2-Lite 对 Planner 的核心约束本来就是：Capability 可以跳过、重复、重排，只能从 Catalog 中选择真实能力。

所以 T06 不需要新设计一个复杂的：

```text
ReplanEngine
RecoveryPlanner
PlanRepairAgent
PlanPatch
PlanDiff
```

我的建议是：

> **Replanner = Planner 在“已有 Plan 执行受阻”情况下的第二种调用方式。**

# 一、T06 只证明一个场景

M3-Lite 到目前为止，我们已经刻意规定：

```text
SUCCESS          → CONTINUE / FINISH
PARTIAL_SUCCESS  → CONTINUE / FINISH
NO_RESULT        → REPLAN
NEED_INFORMATION → ASK_USER
BLOCKED          → STOP
FAILED           → STOP
```

因此第一版 Replanner **甚至只需要处理 `NO_RESULT`**。

也就是说 T06 不需要解决：

```text
FAILED 怎么恢复
BLOCKED 怎么绕路
NEED_INFORMATION 怎么自动补信息
```

只有：

```text
某条合理业务路径正常执行了
但是没有结果
↓
基于这个新事实重新规划剩余路径
```

这已经足够证明 Replan。

---

# 二、Replanner 最小输入

M2 Planner 输入是：

```text
Goal
Current Context
Capability Catalog
```

T06 只多三个信息：

```text
Goal

Current Plan

Execution Context

Last Capability Result

Capability Catalog
```

实际上 `ExecutionContext` 已经包含：

```text
goal
current_plan
known_context
step_results
```

所以代码接口甚至可以只有：

```python
def replan(
    context: ExecutionContext,
    last_result: CapabilityResult,
    capabilities: CapabilityCatalog,
) -> Plan:
    ...
```

如果你希望依赖更明确，也可以：

```python
def replan(
    goal: Goal,
    current_plan: Plan,
    known_context: dict,
    step_results: dict,
    last_result: CapabilityResult,
    capabilities: CapabilityCatalog,
) -> Plan:
    ...
```

我更偏向第一种。

---

# 三、最关键的原则：只规划“接下来怎么办”

这是 T06 最重要的约束。

假设：

```text
Plan V1

S1 directional_insight
 ↓
S2 customer_targeting
 ↓
S3 strategy_generation
```

执行：

```text
S1 → SUCCESS
S2 → NO_RESULT
```

Replanner 不应该重新思考：

```text
我们是不是应该先做 Insight？
```

因为：

```text
S1 已经成功
Opportunity 已经产生
```

这些已经成为当前事实。

它真正应该回答：

> **在已完成 S1、且 S2 按当前条件没有结果的情况下，接下来应该怎么做？**

---

# 四、Plan V2 我建议仍然是一个完整 Plan

这里有两个选择。

### 方案 A：只输出剩余 Plan

```text
Plan V2

S4 targeting
 ↓
S5 strategy
```

### 方案 B：保留已经完成的部分

```text
Plan V2

S1 insight        completed
 ↓
S4 targeting
 ↓
S5 strategy
```

我建议 **Demo 用方案 B**。

原因非常实际：

现有 T04 已经有：

```python
if step.step_id in context.step_results:
    return False
```

所以：

```text
S1
```

即使还存在于 Plan V2，也不会再次执行。

而 Demo 展示时也更容易理解：

```text
原来做过什么
+
为什么重规划
+
接下来准备做什么
```

---

# 五、但是失败的旧 Step 不应该继续留作依赖

这是个关键细节。

原来：

```text
S1 Insight
 ↓
S2 Targeting
 ↓
S3 Strategy
```

S2：

```text
NO_RESULT
```

如果 Plan V2 写成：

```text
S1
 ↓
S2
 ↓
S4 Targeting
 ↓
S5 Strategy
```

就有问题。

因为：

```text
S4 depends_on S2
```

而 S2 是：

```text
NO_RESULT
```

按照 T04：

```text
S4 永远不会 Ready
```

所以应该改成：

```text
S1 Insight       SUCCESS
 ↓
S4 Targeting     新条件
 ↓
S5 Strategy
```

旧的：

```text
S2 NO_RESULT
```

保留在：

```text
ExecutionContext.step_results
```

作为历史事实即可。

**不要继续留在新的执行依赖链中。**

# 六、这就形成一个非常重要的模型

```text
ExecutionContext
│
├─ Historical Results
│
│   ├─ S1 → SUCCESS
│   └─ S2 → NO_RESULT
│
└─ Current Plan V2
    │
    ├─ S1 → already completed
    ├─ S4 → pending
    └─ S5 → pending
```

注意：

> `step_results` 是“发生过什么”。

而：

> `current_plan` 是“现在准备怎么办”。

这两个职责正好分开。

---

# 七、Replanner Prompt 应该非常明确地限制自由度

我建议 Prompt 的核心不是告诉模型：

> “重新规划一下。”

而是给它明确规则。

大致可以是：

```text
你正在调整一个已经开始执行的经营 Plan。

根据：
1. 当前 Goal
2. 当前 Plan
3. 已完成步骤及其结果
4. 最近一次 CapabilityResult
5. 当前已有 Context
6. 可用 Capability Catalog

生成调整后的 Plan。

要求：

- 只使用 Capability Catalog 中存在的 Capability。
- 已经成功完成且仍然有效的步骤不得重复执行。
- 最近失败路径为 NO_RESULT，说明该能力执行正常，
  但当前条件下没有获得业务结果，不等于系统故障。
- 可以跳过、重复或重新排列 Capability。
- 可以再次调用同一 Capability，
  但必须有新的执行理由。
- 不要机械补齐五类 Capability。
- 只加入完成当前 Goal 所必需的最少步骤。
- 已完成步骤可以保留在新 Plan 中，
  但不得修改其业务含义。
```

最后一句非常重要：

```text
不得修改已成功完成 Step 的业务含义
```

否则 LLM 有可能把：

```text
S1 directional_insight
```

偷偷改成：

```text
S1 customer_targeting
```

但 `step_results["S1"]` 还是原来的 Insight Result。

状态就乱了。

---

# 八、Replanner 不需要输出“为什么 Replan”

因为 PlanStep 已经有：

```text
objective
reason
```

M2 Planner 本来就允许输出这些字段。

所以新 Step：

```text
S4 customer_targeting

reason:
上一次基于 Opportunity A 的当前候选条件未找到客户，
调整目标条件后重新圈客。
```

足够了。

不要额外定义：

```text
ReplanReason
RecoveryReason
PlanChangeReason
ReplanMetadata
```

# 九、可以重复调用同一个 Capability

这是 M3 非常值得证明的一点。

例如：

```text
Plan V1

S1 directional_insight
↓
S2 customer_targeting
```

S2：

```text
NO_RESULT
```

Replanner 完全可以产生：

```text
Plan V2

S1 directional_insight     completed
↓
S3 customer_targeting
↓
S4 strategy_generation
```

注意：

```text
S2 capability_id = customer_targeting
S3 capability_id = customer_targeting
```

没有问题。

因为 Capability 本来就应该可以重复调用；M1 的设计也明确强调 Capability 可以跳过、重复和重排，而不是固定工作流。

关键是：

```text
step_id 不同
```

并且第二次调用存在新的 reason/context。

# 十、Replanner 本身可以直接复用 ChatModel

就像 M2：

```text

Planner    → ChatModel
```

一样。

T06：

```text
Replanner → ChatModel
```

第一版仍然不需要：

```text
AgentLoop
```

因为 Replanner 仍然是：

```text

↓
一次 LLM 推理
↓
结构化 Plan
```

没有：

```text
LLM ↔ Tool ↔ LLM ↔ Tool
```

# 十一、甚至可以复用 Planner 类

我觉得这比新增 `Replanner` 类更简洁。

例如当前：

```python
class Planner:

    def plan(
        self,
        goal,
        context,
        capabilities,
    ) -> Plan:
        ...
```

直接增加：

```python
class Planner:

    def plan(
        self,
        goal,
        context,
        capabilities,
    ) -> Plan:
        ...

    def replan(
        self,
        context: ExecutionContext,
        last_result: CapabilityResult,
        capabilities,
    ) -> Plan:
        ...
```

共享：

```text
ChatModel
JSON Parsing
Plan 构造
validate_plan()
```

区别只有 Prompt 和输入。

这比：

```text
Planner
Replanner
PlannerEngine
ReplanEngine
```

更符合我们的 Lite 原则。

# 十二、我只建议增加一个小型 `validate_replan()`

M2 已经有：

```python
validate_plan(
    plan,
    capability_catalog,
)
```

检查：

```text
Capability 是否存在
step_id 是否重复
dependency 是否存在
dependency 是否成环
```

这些全部继续复用。M2-Lite 原本也只要求这些轻量合法性校验。

T06 只额外检查一件事：

> **已经 SUCCESS 的旧 Step，如果被保留在新 Plan 中，不能改变 capability_id。**

例如：

```python
def validate_replan(
    old_plan,
    new_plan,
    context,
):
    validate_plan(new_plan, catalog)

    old_steps = {
        step.step_id: step
        for step in old_plan.steps
    }

    for step in new_plan.steps:

        old_step = old_steps.get(step.step_id)

        if old_step is None:
            continue

        result = context.step_results.get(
            step.step_id
        )

        if (
            result
            and result.status in SUCCESS_LIKE
            and step.capability_id
                != old_step.capability_id
        ):
            raise ValueError(
                "completed step cannot be changed"
            )
```

就够了。

甚至第一版可以不检查 objective/reason 是否改变。

只守住最关键的：

```text
step_id 对应的 Capability 身份不能变
```

# 十三、不要做 PlanPatch

很容易产生一个想法：

```text
PlanPatch

remove_steps
add_steps
replace_steps
keep_steps
dependency_changes
```

Demo 完全没必要。

让模型直接输出：

```text
完整 Plan V2
```

然后：

```python
validate_plan(plan_v2)
validate_replan(plan_v1, plan_v2)
```

即可。

如果未来 Plan 有几十、上百 Step，Patch 才有价值。

现在 Plan：

```text
2~5 个 Step
```

完整重输反而最简单。

# 十四、Plan 版本怎么处理

如果你当前 M1 `Plan` 已经具备版本字段，就直接使用，不要新增另一套 Replan ID。

概念上：

```text
Plan V1
      ↓
REPLAN
      ↓
Plan V2
```

Replan 完成以后只有一个动作：

```python
context.current_plan = plan_v2
```

然后重新进入 T04：

```text
get_next_ready_step()
```

整个循环自然恢复。

不需要：

```text
resume()
restart()
restore()
activate_plan()
switch_plan()
```

# 十五、完整运行循环现在终于闭起来了

到 T06 以后：

```python
while True:

    step = get_next_ready_step(
        context.current_plan,
        context,
    )

    result = execute_step(
        step,
        context,
        executor,
    )

    action = decide_continuation(
        context.current_plan,
        context,
        result,
    )

    if action == CONTINUE:
        continue

    if action == FINISH:
        return success_response(...)

    if action == ASK_USER:
        return clarification_response(...)

    if action == STOP:
        return stopped_response(...)

    if action == REPLAN:

        new_plan = planner.replan(
            context=context,
            last_result=result,
            capabilities=catalog,
        )

        validate_replan(
            context.current_plan,
            new_plan,
            context,
        )

        context.current_plan = new_plan

        continue
```

这段其实已经把 **M3 核心架构完整表达出来了**。

而且仍然非常小。

## M3 到 T06 的核心已经完整了

```text
                Planner
                   │
                   ▼
                Plan V1
                   │
                   ▼
            Ready Step Resolver
                   │
                   ▼
           CapabilityExecutor
                   │
                   ▼
           CapabilityResult
                   │
                   ▼
        Continuation Policy
          │      │      │
      CONTINUE  STOP   REPLAN
                         │
                         ▼
                Planner.replan()
                         │
                         ▼
                      Plan V2
                         │
                         └──────→ 回到执行循环
```

现在可以非常明确地说：

> **M2 的 Planner 负责“第一次怎么做”；M3 的 Replan 负责“事实发生变化以后，接下来怎么做”。**

并且两者还是**同一个规划能力的两个入口**，没有新造第二套 Planning Framework。

下一步 **M3-T07 就不需要再设计新的架构概念了**，而是把 `BusinessAgent + ExecutionLoop + FakeCapability + FakeReplan` 真正串起来，并用几个 Behaviour Case 验收整个 M3。
