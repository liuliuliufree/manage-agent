
那就进入 **M3-T03 + T04**。这一阶段只解决两件事：

1. **如何把一个 `PlanStep` 真正执行成一次 Capability 调用**
2. **当前 Plan 中，下一步该执行哪个 Step**

仍然坚持 Demo 原则：**不做调度器、不做状态机、不做 Workflow Engine。**

## M3-T03：PlanStep → CapabilityRequest → CapabilityResult

当前链路已经有：

```text
Plan
  ↓
PlanStep
```

我们现在补齐：

```text
PlanStep
  ↓
build_capability_request()
  ↓
CapabilityRequest
  ↓
CapabilityExecutor
  ↓
CapabilityResult
  ↓
ExecutionContext.record_result()
```

### 1. `build_capability_request()` 保持成普通函数

不要设计：

```text
CapabilityRequestBuilder
RequestFactory
ExecutionRequestAssembler
```

一个函数足够：

```python
def build_capability_request(
    step: PlanStep,
    context: ExecutionContext,
) -> CapabilityRequest:
    ...
```

它只做字段映射。

概念上：

```python
return CapabilityRequest(
    request_id=new_id(),
    capability_id=step.capability_id,
    goal_ref=...,
    plan_ref=...,
    context=context.known_context,
)
```

具体字段继续使用你 M1 已有的 `CapabilityRequest`，M3 不新增第二套请求对象。

这里有个边界要守住：

```text
PlanStep
```

描述的是：

> 我要做什么。

而：

```text
CapabilityRequest
```

描述：

> 这一次具体执行这个能力时，输入是什么。

所以它们不要合并。

---

## 2. 执行一个 Step 可以包装成一个小函数

甚至暂时不需要类：

```python
def execute_step(
    step: PlanStep,
    context: ExecutionContext,
    executor: CapabilityExecutor,
) -> CapabilityResult:

    request = build_capability_request(
        step=step,
        context=context,
    )

    result = executor.execute(request)

    context.record_result(
        step.step_id,
        result,
    )

    return result
```

于是 BusinessAgent 后面只需要：

```python
result = execute_step(
    step,
    context,
    executor,
)
```

非常清楚。

# M3-T04：如何判断下一步执行哪个 Step

这里特别容易过度设计。

我建议现在只定义一个函数：

```python
get_next_ready_step(
    plan,
    context,
)
```

返回：

```python
PlanStep | None
```

它只回答：

> 当前有没有一个可以执行且还没执行过的 Step？

---

## 3. 什么叫 Ready？

第一版只需要满足两个条件。

### 条件一：这个 Step 没执行过

```python
step.step_id not in context.step_results
```

### 条件二：它依赖的 Step 都已经成功完成

假设：

```text
S1 insight

S2 targeting
depends_on = [S1]

S3 strategy
depends_on = [S2]
```

则：

```text
S1
```

一开始 Ready。

S1 成功后：

```text
S2
```

Ready。

S2 成功后：

```text
S3
```

Ready。

仅此而已。

---

# 4. 最小实现

可以直接：

```python
def is_step_ready(
    step: PlanStep,
    context: ExecutionContext,
) -> bool:

    # 已执行
    if step.step_id in context.step_results:
        return False

    # 所有依赖都必须成功
    for dep_id in step.depends_on:

        result = context.step_results.get(dep_id)

        if result is None:
            return False

        if result.status not in {
            CapabilityStatus.SUCCESS,
            CapabilityStatus.PARTIAL_SUCCESS,
        }:
            return False

    return True
```

然后：

```python
def get_next_ready_step(
    plan: Plan,
    context: ExecutionContext,
):

    for step in plan.steps:

        if is_step_ready(step, context):
            return step

    return None
```

Demo 第一版就够了。

# 5. 为什么先用“第一个 Ready Step”？

你可能会想到：

如果两个 Step 都 Ready 呢？

例如：

```text
           ┌→ S2
S1 success
           └→ S3
```

这时候：

```text
S2
S3
```

都可以执行。

生产系统以后可能考虑：

```text
priority
parallelism
cost
latency
side effects
```

但 Demo 完全没必要。

直接：

> 按 Plan 中的出现顺序，执行第一个 Ready Step。

即可。

也就是：

```python
for step in plan.steps:
    ...
```

不要做：

```text
Task Scheduler
Priority Queue
Parallel Executor
Dependency Graph Runtime
```

---

# 6. PARTIAL_SUCCESS 怎么处理？

这里我建议先采用一个简单约定：

```text
SUCCESS
PARTIAL_SUCCESS
```

都视为：

> 这个 Step 已经完成，可以释放后继依赖。

所以：

```python
SUCCESS_STATUSES = {
    CapabilityStatus.SUCCESS,
    CapabilityStatus.PARTIAL_SUCCESS,
}
```

至于：

```text
PARTIAL_SUCCESS
```

之后要不要 Replan，

那是下一阶段 **Continuation Policy** 决定的。

不要让 `is_step_ready()` 开始承担业务决策。

---

# 7. NO_RESULT / FAILED / BLOCKED 时会发生什么？

假设：

```text
S1 Insight      SUCCESS
 ↓
S2 Targeting    NO_RESULT
 ↓
S3 Strategy
```

执行完 S2：

```python
context.step_results = {
    "s1": SUCCESS,
    "s2": NO_RESULT,
}
```

此时：

```python
get_next_ready_step(...)
```

不会返回 S3。

因为 S3 依赖：

```text
S2
```

而 S2 不是成功状态。

于是：

```text
next_ready_step = None
```

这个状态很重要。

但 **T04 不负责判断为什么没有下一步。**

它只报告：

> 当前 Plan 没有可直接执行的 Step。

下一阶段才判断：

```text
Plan 已完成？
还是卡住了？
还是需要 Replan？
还是 Ask User？
```

这样职责非常干净。

---

# 8. 暂时不要建立 Step Runtime Status

所以不要：

```python
class StepStatus(Enum):
    PENDING
    READY
    RUNNING
    SUCCESS
    FAILED
    SKIPPED
```

当前状态完全可以推导出来。

### 未执行

```python
step_id not in step_results
```

### 已成功

```python
step_results[step_id].status == SUCCESS
```

### 已失败

```python
step_results[step_id].status == FAILED
```

### Ready

动态计算：

```python
is_step_ready(...)
```

所以没必要再存一份状态。

否则容易出现：

```text
StepStatus = SUCCESS

但是

CapabilityResult = FAILED
```

两个状态源反而麻烦。

Demo 阶段坚持：

> **CapabilityResult 是 Step 执行状态的唯一事实源。**

---

# 9. 这样目前已经形成一个非常小的运行循环

现在已经可以写：

```python
while True:

    step = get_next_ready_step(
        context.current_plan,
        context,
    )

    if step is None:
        break

    execute_step(
        step=step,
        context=context,
        executor=executor,
    )
```

这段代码已经能跑：

```text
S1
↓
S2
↓
S3
```

但暂时有一个明显的问题：

如果：

```text
S2 → NO_RESULT
```

循环会：

```text
get_next_ready_step()
→ None
→ break
```

系统不知道：

> 是正常完成了，还是被卡住了。

而这恰好就是下一阶段的核心。

# 10. 所以 M3-T03/T04 的 Exit Criteria 很简单

只验证四件事：

```text
Case 1
无依赖 Step 可以执行

Case 2
依赖未完成时不能执行后续 Step

Case 3
依赖 SUCCESS 后后续 Step 变为 Ready

Case 4
依赖 NO_RESULT / FAILED / BLOCKED 时
后续 Step 不变为 Ready
```

再加一个端到端：

```text
Plan:
S1 → S2 → S3

Fake results:
SUCCESS
SUCCESS
SUCCESS

结果：
三个 Capability 按依赖顺序各执行一次
```

到这里就停止。
