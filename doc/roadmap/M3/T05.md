
可以。**T05 Continuation Policy 是 M3 的“交通灯”，不是“大脑”。**

它只回答一个问题：

> **一个 Capability 执行结束后，运行循环接下来进入什么状态？**

不负责回答：

> “如果要 Replan，新 Plan 应该是什么？”

后者全部留给 T06。

这也符合 Roadmap 对 M3 的定位：Capability 执行结果要能改变后续 Plan，并处理失败与阻断；而 M2-Lite 刻意没有实现 `CapabilityResult → Replan`。

---

# 一、T05 我建议只增加一个 Enum + 一个函数

甚至不要：

```text
ContinuationPolicyEngine
ContinuationDecision
DecisionContext
RecoveryStrategy
FailurePolicy
```

只增加：

```python
class ContinuationAction(str, Enum):
    CONTINUE = "continue"
    REPLAN = "replan"
    ASK_USER = "ask_user"
    FINISH = "finish"
    STOP = "stop"
```

然后一个普通函数：

```python
def decide_continuation(
    plan: Plan,
    context: ExecutionContext,
    last_result: CapabilityResult,
) -> ContinuationAction:
    ...
```

仅此而已。

---

# 二、为什么我增加了 `FINISH`

我们之前说：

```text
CONTINUE
REPLAN
ASK_USER
STOP
```

但真正实现时我建议把：

```text
FINISH
```

单独拿出来。

因为这两种情况业务意义完全不同：

```text
FINISH
=
Plan 正常完成
```

和：

```text
STOP
=
因为异常 / 阻断无法继续
```

否则最后 Demo 日志会出现：

```text
Execution stopped
```

但实际上是正常成功结束，很别扭。

所以最终是五种：

```text
CONTINUE
REPLAN
ASK_USER
FINISH
STOP
```

---

# 三、Demo 阶段的状态映射可以非常简单

我建议第一版直接定死：

| CapabilityResult     | Action                | 含义                            |
| -------------------- | --------------------- | ------------------------------- |
| `SUCCESS`          | `CONTINUE / FINISH` | 正常往后走                      |
| `PARTIAL_SUCCESS`  | `CONTINUE / FINISH` | Demo 暂时视作可继续             |
| `NO_RESULT`        | `REPLAN`            | 正常执行了，但当前路径没有结果  |
| `NEED_INFORMATION` | `ASK_USER`          | 缺信息，当前 Demo 不自动补      |
| `BLOCKED`          | `STOP`              | 确定性业务阻断，不允许绕过      |
| `FAILED`           | `STOP`              | 技术执行失败，Demo 暂不自动恢复 |

这里最重要的是：

> **M3-Lite 第一版只让 `NO_RESULT` 真正触发 Replan。**

这已经足够证明动态重规划。

不要为了证明“智能”，一开始让所有异常都进入 LLM。

---

# 四、为什么 `NO_RESULT → REPLAN`

这个是 M3 最核心的场景。

例如：

```text
Plan V1

S1 directional_insight
        ↓
S2 customer_targeting
        ↓
S3 strategy_generation
```

执行：

```text
S1
→ SUCCESS
→ Opportunity A
```

继续：

```text
S2
→ NO_RESULT
```

这里：

```text
NO_RESULT
```

不代表系统坏了。

它代表一个新的业务事实：

> 按照当前 Opportunity / 条件，没有找到合适客户。

所以系统应该：

```text
CapabilityResult
      ↓
NO_RESULT
      ↓
REPLAN
```

然后 T06 再决定：

```text
调整圈客条件？
换 Opportunity？
再次洞察？
还是没有可行方案？
```

这正是我们真正想证明的 Replan。

---

# 五、为什么 `NEED_INFORMATION → ASK_USER`

之前我们讨论过更高级的方案：

```text
NEED_INFORMATION(region)

↓
看看其他 Capability 能不能补 region

↓
补完以后重新执行
```

这个未来是合理的。

但对 Demo 来说有点早。

它会立刻引入：

```text
information resolver
context requirement
missing information source
自动补全策略
```

然后 M3 又变复杂了。

所以第一版明确：

```text
NEED_INFORMATION
        ↓
ASK_USER
```

例如：

```text
customer_targeting

→ NEED_INFORMATION

missing:
经营区域
```

系统：

```text
ASK_USER

“需要补充本次经营区域后才能继续圈客。”
```

等用户补信息以后，再重新进入：

```text
Goal / Context
→ Plan
```

或者以后再设计 resume。

M3-Lite 暂时不做 Resume Framework。

---

# 六、为什么 `BLOCKED → STOP`

这是很重要的安全边界。

例如：

```text
validation_distribution

→ BLOCKED
```

原因：

```text
客户属于银保渠道
当前代理人为个险渠道
```

这不是：

```text
Planner 不喜欢这个 Plan
```

而是：

```text
确定性业务规则已经判定不可执行
```

因此 Demo 第一版：

```text
BLOCKED
   ↓
STOP
```

不要：

```text
BLOCKED
↓
REPLAN
↓
LLM 想办法绕过去
```

以后 M6 真正做校验分发时，可以支持：

```text
Customer A → BLOCKED

但是

Customer B / C → 合法

↓

围绕剩余客户 Replan
```

那时候再扩。

M3-Lite 先守住：

> **阻断规则不可被 Replanner 推翻。**

---

# 七、为什么 `FAILED → STOP`，而不是自动 Retry

生产级系统肯定最终要考虑：

```text
FAILED
↓
是否瞬时异常？
↓
retry
↓
fallback
↓
alternative capability
```

但这马上会引入：

```text
retry_count
max_retry
retryable
failure_type
timeout
fallback
backoff
```

对于 Demo 都不是当前重点。

所以第一版：

```text
FAILED
↓
STOP
```

例如：

```text
customer_targeting

→ FAILED

database unavailable
```

直接：

```text
Execution STOPPED
```

测试证明：

> 系统能区分“没有客户”和“系统执行失败”。

这已经非常有价值。

---

# 八、SUCCESS 的逻辑稍微特殊一点

不能直接：

```python
SUCCESS -> CONTINUE
```

因为当前可能已经执行完最后一步了。

所以应该：

```text
SUCCESS
   ↓
还有 Ready Step？
   ├─ YES → CONTINUE
   └─ NO
       ↓
    Plan 是否全部成功完成？
       ├─ YES → FINISH
       └─ NO  → STOP
```

因此可以有一个非常小的辅助函数：

```python
SUCCESS_LIKE = {
    CapabilityStatus.SUCCESS,
    CapabilityStatus.PARTIAL_SUCCESS,
}
```

然后：

```python
def is_plan_finished(
    plan: Plan,
    context: ExecutionContext,
) -> bool:

    for step in plan.steps:

        result = context.step_results.get(
            step.step_id
        )

        if result is None:
            return False

        if result.status not in SUCCESS_LIKE:
            return False

    return True
```

---

# 九、最终 `decide_continuation()` 其实非常短

概念代码：

```python
def decide_continuation(
    plan,
    context,
    last_result,
):

    status = last_result.status

    if status == CapabilityStatus.NO_RESULT:
        return ContinuationAction.REPLAN

    if status == CapabilityStatus.NEED_INFORMATION:
        return ContinuationAction.ASK_USER

    if status == CapabilityStatus.BLOCKED:
        return ContinuationAction.STOP

    if status == CapabilityStatus.FAILED:
        return ContinuationAction.STOP

    if status in {
        CapabilityStatus.SUCCESS,
        CapabilityStatus.PARTIAL_SUCCESS,
    }:

        next_step = get_next_ready_step(
            plan,
            context,
        )

        if next_step is not None:
            return ContinuationAction.CONTINUE

        if is_plan_finished(
            plan,
            context,
        ):
            return ContinuationAction.FINISH

        return ContinuationAction.STOP
```

差不多就是这么简单。

我甚至不建议把它做成类。

---

# 十、最后这个 `STOP` 是一个兜底

你可能注意到：

```python
SUCCESS

但是：

next_ready_step is None
且
plan 没有 finished
```

理论上，如果：

* Plan DAG 合法；
* T04 的依赖判断正确；
* CapabilityResult 正确；

一般不应该发生。

所以这里：

```python
return STOP
```

其实是：

> Runtime 进入了无法继续但也不是正常结束的不一致状态。

Demo 阶段直接停止即可。

不要现在设计：

```text
ExecutionDeadlock
InvalidRuntimeState
DependencyResolutionError
```

日志写一句：

```text
No executable step but plan is incomplete.
```

够了。

# 十一、现在 BusinessAgent 的运行循环就开始有灵魂了

有了 T05 后：

```python
while True:

    step = get_next_ready_step(
        context.current_plan,
        context,
    )

    result = execute_step(
        step,
        context,
        executor,
    )

    action = decide_continuation(
        context.current_plan,
        context,
        result,
    )

    if action == CONTINUE:
        continue

    if action == FINISH:
        return success_response(...)

    if action == ASK_USER:
        return clarification_response(...)

    if action == STOP:
        return stopped_response(...)

    if action == REPLAN:
        ...
```

目前唯一还没有实现的：

```python
if action == REPLAN:
    ...
```

就是下一步 T06。

到这里架构已经非常自然。

## 到这里 M3 已经非常清晰

```text
T01 CapabilityExecutor
        ↓
执行 Capability

T02 ExecutionContext
        ↓
保存当前事实与执行结果

T03 execute_step
        ↓
PlanStep → Request → Result

T04 Ready Step Resolution
        ↓
现在能执行谁？

T05 Continuation Policy
        ↓
执行完以后怎么办？

        ┌─ CONTINUE
        ├─ FINISH
        ├─ ASK_USER
        ├─ STOP
        └─ REPLAN
               ↓
             T06
```
