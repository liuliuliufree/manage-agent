
可以。按照 Demo 阶段的原则，我建议 **M3-T01 + T02 只新增 2 个真正需要的运行时概念，而且不新增任何新的 Domain Contract**。

M1 已经有 `Goal / Plan / CapabilityRequest / CapabilityResult`，其中 `PlanStep → CapabilityRequest → CapabilityResult` 的关联关系已经定义好了；同时 Plan 本身就允许 Capability 跳过、重复、重排，并明确不应演化成第二套 Workflow Engine。
所以 M3 不应该再发明 `ExecutionRequest / ExecutionResult / ReplanContext / RuntimeState` 一堆对象。

## 1. M3 最小结构

我建议最终只有：

```text
M1 已有
────────────────────────────
Goal
Plan
PlanStep
CapabilityRequest
CapabilityResult

M3 新增
────────────────────────────
CapabilityExecutor
ExecutionContext
```

整体：

```text
PlanStep
   │
   ▼
CapabilityExecutor
   │
   ├── 构造 CapabilityRequest
   │
   ├── 找到 capability handler
   │
   └── execute()
           │
           ▼
   CapabilityResult
           │
           ▼
   ExecutionContext
```

注意：

> `CapabilityExecutor` 是执行器，不是一个新的业务协议。
> `ExecutionContext` 是运行状态，不属于 M1 Domain Contract。

# 2. M3-T01：CapabilityExecutor

这里我甚至不建议先设计什么复杂 `BaseCapability` 抽象类。

Demo 第一版，一个 callable 就够了。

```python
from typing import Callable

CapabilityHandler = Callable[
    [CapabilityRequest],
    CapabilityResult,
]
```

Catalog 解决：

```text
系统有哪些 Capability
```

Executor 解决：

```text
这个 Capability 实际由谁执行
```

所以运行时可以直接：

```python
handlers = {
    "directional_insight": fake_insight,
    "customer_targeting": fake_targeting,
    "strategy_generation": fake_strategy,
}
```

然后：

```python
class CapabilityExecutor:

    def __init__(self, handlers):
        self.handlers = handlers

    def execute(
        self,
        request: CapabilityRequest,
    ) -> CapabilityResult:

        handler = self.handlers.get(
            request.capability_id
        )

        if handler is None:
            return CapabilityResult.failed(
                request=request,
                message="capability handler not found",
            )

        try:
            return handler(request)

        except Exception as exc:
            return CapabilityResult.failed(
                request=request,
                message=str(exc),
            )
```

实际字段当然按照你 M1 已经定义好的 `CapabilityResult` 构造，不需要照抄这个示意代码。

### 为什么我不建议现在定义 `Capability` interface？

因为目前：

```text
CapabilityDefinition
```

已经负责描述：

> 这个能力是什么。

真正执行的时候 Demo 只需要：

```text
capability_id
    ↓
handler
```

如果以后 M4/M5 发现每个 Capability 都需要：

```text
initialize()
execute()
validate()
cleanup()
```

再抽象接口。

现在不要提前设计。

# 4. FakeCapability 要稍微认真一点

M3 现在并不是真的开发洞察、圈客、策略。

因此 FakeCapability 才是 M3 的主角。

最简单：

```python
def fake_insight(request):

    return CapabilityResult(
        request_id=request.request_id,
        capability_id=request.capability_id,
        status=CapabilityStatus.SUCCESS,
        outputs=[...],
    )
```

但是我更推荐一个非常小的可配置 Fake：

```python
class FakeCapability:

    def __init__(self, results):
        self.results = list(results)
        self.call_count = 0

    def __call__(self, request):
        self.call_count += 1
        return self.results.pop(0)
```

因为这样以后 M3 可以非常容易测试：

```text
第一次 targeting
→ NO_RESULT

Replan

第二次 targeting
→ SUCCESS
```

配置：

```python
fake_targeting = FakeCapability([
    no_result,
    success,
])
```

这对 M3 的测试价值很大，但复杂度几乎为零。

# 6. 四个字段分别干什么

### `goal`

始终知道：

```text
我们最终想完成什么
```

不复制 Goal。

---

### `current_plan`

表示当前真正执行的 Plan：

```text
Plan V1
```

Replan 后直接变成：

```text
Plan V2
```

所以字段叫：

```python
current_plan
```

而不是：

```python
plan
```

语义会更清楚。

---

### `known_context`

这个就是 M2：

```python
context = {
    "opportunity_refs": [],
    "customer_refs": [],
    "strategy_refs": [],
}
```

的自然延续。

第一版不要定义：

```text
PlanningContext
BusinessContext
OpportunityContext
CustomerContext
RuntimeKnowledge
```

直接：

```python
dict[str, Any]
```

即可。

比如：

```python
known_context = {
    "opportunity_refs": ["opp_001"],
}
```

随后圈客成功：

```python
known_context = {
    "opportunity_refs": ["opp_001"],
    "customer_refs": [
        "customer_001",
        "customer_002",
    ],
}
```

以后如果事实证明这个 dict 已经失控，再把它升级成正式 Contract。

Demo 阶段没必要。

---

### `step_results`

这是 M3 真正需要新增的东西。

例如：

```python
{
    "step_01": CapabilityResult(
        status="SUCCESS",
        ...
    ),

    "step_02": CapabilityResult(
        status="NO_RESULT",
        ...
    ),
}
```

这样 Replanner 才能知道：

```text
S1 已经执行成功
S2 没有结果
```

而不是只看到一个最终 Context。

我暂时**不建议**写：

# 8. 为什么既要 known_context 又要 step_results？

这两个不能混。

假设：

```text
Targeting
→ NO_RESULT
```

那么：

### `known_context`

可能仍然是：

```python
{
    "opportunity_refs": ["opp_01"],
    "customer_refs": [],
}
```

表示：

> 当前我们有什么。

但是：

### `step_results`

保存：

```text
targeting_01
→ NO_RESULT
```

表示：

> 我们刚才尝试过什么，以及发生了什么。

这两个信息对于 Replan 都重要。

所以：

```text
known_context
=
当前事实

step_results
=
执行历史
```

这个区分我建议保留。

# 14. 一个完整例子

初始：

```python
context = ExecutionContext(
    goal=goal,
    current_plan=plan_v1,
    known_context={},
)
```

执行：

```text
Step 1
directional_insight
```

Executor 构造：

```text
CapabilityRequest
```

FakeCapability 返回：

```text
CapabilityResult

status = SUCCESS

outputs =
    Opportunity A
```

然后：

```python
context.record_result(
    "step_01",
    result,
)
```

同时应用层把产物加入：

```python
context.known_context[
    "opportunity_refs"

```

此时：

```text
ExecutionContext

Goal
 └─ 500W NBEV

Current Plan
 └─ Plan V1

Known Context
 └─ Opportunity A

Step Results

```

然后执行第二步：

```text
customer_targeting
```

返回：

```text
NO_RESULT
```

于是：

```text
Known Context
 └─ Opportunity A

Step Results
 ├─ step_01 → SUCCESS

```

这时候 **T01/T02 的任务已经完成了。**

```text
REPLAN？

```

# 15. 所以我建议把 M3 最小契约正式定成这样

```text
┌─────────────────────────────┐
│      ExecutionContext       │
├─────────────────────────────┤
│ goal                        │
│ current_plan                │
│ known_context               │
│ step_results                │
└─────────────────────────────┘


CapabilityHandler
    =
CapabilityRequest
    ↓
CapabilityResult


┌─────────────────────────────┐
│     CapabilityExecutor      │
├─────────────────────────────┤
│ handlers                    │
│                             │
│ execute(request)            │
│        ↓                    │
│ CapabilityResult            │
└─────────────────────────────┘
```

**仅此而已。**

我认为这个粒度很适合现在的 Demo：已经足以支撑下一步 Replan，但还没有提前引入 Workflow Engine、复杂 State、Repository、Retry Framework 或 Capability 生命周期。下一步可以直接设计 **M3-T03/T04：从 `PlanStep` 到一次真实 Capability 调用，以及“下一步哪个 Step 可执行”的最小逻辑**。
