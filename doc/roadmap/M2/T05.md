
可以。进入 **M2-T05 Planner** 后，我们第一次真正让 LLM 决定：

> **针对当前 Goal，在现有上下文和当前可用 Capability 下，下一步应该做哪些业务动作，以及它们之间是什么依赖关系。**

但边界仍然非常严格：

```text
Planner 可以决定：
选择哪些 Capability
是否跳过某些 Capability
是否重复某个 Capability
步骤之间的依赖
每一步要解决什么问题

Planner 不可以决定：
业务事实是真是假
权限是否通过
规则是否放行
Capability 是否真实存在
Capability 版本号
Tool 怎么调用
外部写操作是否可以绕过控制点
```

规范本身要求 Plan 由 Agent 根据 Goal、上下文、数据可用性和风险动态选择 Capability，并支持跳过、重复、重排和局部重规划，而不是固定五步状态机。

---

# 一、Planner 的位置

现在 M2 链路已经完整到这里：

```text
BusinessRequest
      ↓
GoalInterpreter
      ↓
GoalInterpretation
      ↓
GoalAssembler
      ↓
Goal
      ↓
ClarificationGate
      │
      ├─ REQUIRE_CLARIFICATION → 用户
      │
      └─ CONTINUE
              ↓
       CapabilityCatalog
              │
              ▼
           Planner       ← T05
              │
              ▼
          PlanDraft
              │
              ▼
       PlanValidator      ← T06
              │
              ▼
             Plan
```

这里特别重要的是：

> **Planner 输出的是 `PlanDraft`，不是正式 `Plan`。**

和前面的：

```text
GoalInterpreter → GoalInterpretation
GoalAssembler   → Goal
```

完全同一个思想：

```text
LLM负责语义决策
确定性代码负责系统事实与结构合法性
```

---

# 二、Planner 应该直接使用 ChatModel

M2-T05 我仍建议：

```text
Planner
    ↓
ChatModel
```

而不是：

```text
Planner
    ↓
AgentLoop
    ↓
ChatModel
```

原因是当前 Planner 做的是一次：

```text
structured inference
```

输入：

```text
Goal
Current Context
Capability Catalog
```

输出：

```text
PlanDraft
```

目前：

```text
不执行 Tool
不运行 Capability
不需要多 Turn Tool Loop
```

所以没必要强行使用 AgentLoop。

真正到了 M3：

```text
Plan
↓
Capability Tool
↓
CapabilityResult
↓
Replan
```

才需要现有 Agent Runtime 发挥作用。

---

# 三、Planner 的输入不应该只有 Goal

如果只有：

```python
planner.plan(goal)
```

模型很容易不知道：

> 当前已经有什么？

于是重复调用不必要的 Capability。

因此建议引入一个很轻的 Application DTO：

```python
@dataclass(frozen=True)
class PlanningContext:
    available_refs: tuple[ContextRef, ...] = ()

    assumptions: tuple[Assumption, ...] = ()

    missing_information: tuple[MissingInformation, ...] = ()
```

于是 Planner 的输入逻辑上是：

```python
planner.plan(
    goal=goal,
    context=planning_context,
    catalog=capability_catalog,
)
```

---

# 四、PlanningContext 和 RuntimeContext 不一样

这是一个重要边界。

`RuntimeContext`：

```text
谁在使用系统
当前渠道
授权主体
请求时间
```

回答的是：

> 当前运行环境是什么？

而：

`PlanningContext`：

```text
已经有什么Opportunity
已经有什么Customer
已经有什么Evidence
已经有什么Strategy
哪些信息仍然缺失
使用了哪些Assumption
```

回答的是：

> Planner 当前掌握哪些业务上下文？

所以：

```text
RuntimeContext ≠ PlanningContext
```

当然：

```text
Goal.channel_and_actor
```

已经吸收了可信 Runtime Context 中与 Goal 有关的部分。

Planner 不需要再次拿整份 RuntimeContext。

---

# 五、为什么 `available_refs` 很重要

比如用户说：

> 围绕刚才那个养老机会帮我找一下客户。

PlanningContext：

```python
available_refs=(
    ContextRef(
        ref_type="opportunity",
        ref_id="opp_001",
    ),
)
```

Capability Catalog：

```text
customer_targeting

required_context:
goal
opportunity
```

Planner 就能直接：

```text
customer_targeting
```

而不需要重新：

```text
directional_insight
→ customer_targeting
```

这就是动态规划真正开始发挥作用的地方。

# 六、M2 当前 available_refs 可以很少

因为现在还没进入 M3。

第一版甚至大部分时候：

```python
available_refs=()
```

完全正常。

但这个 Contract 要先存在。

否则到了 M3 我们突然加入：

```text
已有 Opportunity
已有 Customer
已有 Feedback
```

Planner 输入结构又需要推翻。

---

# 七、Planner 输出应该是 `PlannerDecision`

这里我建议比简单：

```text
PlanDraft
```

再多一层非常轻的结果。

因为有一种情况必须被表达：

> **当前系统根本没有能力完成这个 Goal。**

例如用户说：

> 看一下经营任务进展。

但是：

```text
tracking_iteration.available = False
```

Planner 不能：

```text
随便找另一个 Capability 顶替
```

所以建议：

```python
class PlanningDecisionType(str, Enum):
    PLAN = "plan"
    NO_FEASIBLE_PLAN = "no_feasible_plan"
```

然后：

```python
@dataclass(frozen=True)
class PlannerDecision:
    decision: PlanningDecisionType

    plan_draft: "PlanDraft | None" = None

    reason: str | None = None
```

这里的 `reason` 是简短的业务说明，不是模型的内部推理过程。

例如：

```text
NO_FEASIBLE_PLAN

reason:
当前经营追踪能力尚未接入，
现有Capability无法可靠回答任务进展问题。
```

这比让 Planner 编造一个 Plan 好很多。

---

# 八、什么时候应该 NO_FEASIBLE_PLAN

这里和：

```text
Clarification
```

要区分。

例如：

```text
用户：
“业绩做到500W。”

Metric 不明确。
```

属于：

```text
REQUIRE_CLARIFICATION
```

甚至不会进入 Planner。

而：

```text
用户：
“看看任务进展。”

Goal 已经很清楚。

但 Tracking Capability unavailable。
```

属于：

```text
NO_FEASIBLE_PLAN
```

区别是：

```text
Clarification
=
目标本身还不够清晰

NO_FEASIBLE_PLAN
=
目标很清晰，但系统当前没能力完成
```

---

# 九、正式定义 PlanDraft

M1 的正式 Plan 有：

```text
plan_id
version
goal_ref
status
created_at
Capability version
...
```

这些不能让 LLM 决定。

所以 Planner 输出的应该只是：

```python
@dataclass(frozen=True)
class PlanDraft:
    steps: tuple["PlanStepDraft", ...]
```

极其简单。

---

# 十、PlanStepDraft

建议：

```python
@dataclass(frozen=True)
class PlanStepDraft:
    step_id: str

    capability_id: str

    objective: str
    reason: str

    depends_on: tuple[str, ...] = ()

    input_refs: tuple[ContextRef, ...] = ()

    expected_outputs: tuple[str, ...] = ()

    side_effect_intent: "SideEffectIntent" = (
        SideEffectIntent.READ_ONLY
    )
```

这里和 M1 `PlanStep` 非常接近。

但少了：

```text
capability_version
status
control_points
```

因为这些属于正式 Plan 的确定性组装。

---

# 十一、为什么 Draft 里仍然需要 step_id

因为 Planner 必须能够表达：

```text
S2 depends_on S1
```

所以需要本次 Draft 内的临时引用 ID。

例如：

```json
{
  "steps": [
    {
      "step_id": "s1",
      "capability_id": "directional_insight"
    },
    {
      "step_id": "s2",
      "capability_id": "customer_targeting",
      "depends_on": ["s1"]
    }
  ]
}
```

这个：

```text
s1 / s2
```

只是 Draft 内部 ID。

正式 PlanValidator 后可以继续使用，或者重新生成正式 step_id。

---

# 十二、`objective` 和 `reason` 继续保留

例如：

```text
Capability:
customer_targeting
```

`objective`：

> 围绕当前养老现金流 Opportunity 寻找优先候选客户。

`reason`：

> 当前目标要求进一步定位具体经营对象，且已有有效 Opportunity 可直接用于圈客。

这里的 `reason` 应当：

```text
短
业务化
可展示
```

不要要求模型输出：

> “请详细解释你一步一步如何思考得到这个计划。”

我们只需要**结果层 rationale**，不需要暴露内部推理。规范也只要求向用户展示 Plan 摘要和关键依据，而不是内部敏感推理文本。

---

# 十三、`side_effect_intent` 很值得在 T05 加入

T04 我们已经发现：

```text
validation_distribution
```

既可能只做验证，也可能进入任务分发。

所以仅仅 Catalog 中：

```text
side_effect_level=MAY_WRITE
```

还不够。

Planner 这次究竟想干什么，需要显式表达。

建议：

```python
class SideEffectIntent(str, Enum):
    READ_ONLY = "read_only"
    EXTERNAL_WRITE = "external_write"
```

例如：

用户：

> 看看王女士是不是我能经营的客户。

```text
validation_distribution

side_effect_intent:
READ_ONLY
```

而：

> 校验后帮我形成经营任务。

则：

```text
validation_distribution

side_effect_intent:
EXTERNAL_WRITE
```

随后 T06 PlanValidator 看见：

```text
EXTERNAL_WRITE
```

就必须插入：

```text
RULE_CHECK
USER_CONFIRMATION
```

等必要 ControlPoint。

这样**安全控制不是 LLM 自己保证的**。

---

# 十四、Planner 不直接生成 ControlPoint

这是我建议的一个重要边界。

不要让 LLM：

```json
{
  "requires_user_confirmation": true
}
```

然后就认为安全控制完成。

更合理：

```text
Planner：
我准备执行外部写动作。

↓ side_effect_intent

PlanValidator：
既然是WRITE，
那根据系统规则必须加入控制点。
```

即：

```text
LLM 声明意图
代码施加约束
```

---

# 十五、Planner 的核心任务其实只有四件事

虽然由 LLM 完成，但语义可以非常清楚：

```text
理解当前 Goal 想得到什么结果

        ↓

检查当前已经有什么 Context

        ↓

从 Catalog 中选择最少且合适的 Capability

        ↓

确定业务依赖关系并形成 PlanDraft
```

这里的关键词是：

> **最少且合适。**

不是：

> “为了显得完整尽量使用五个 Capability。”

---

# 十六、Planner Prompt 的核心原则

我建议 Prompt 不要写得特别大。

核心约束可以压缩成：

```text
你负责为当前经营Goal生成下一步业务计划。

你只能从提供的Capability Catalog中选择可用能力。

根据当前Goal和已有Context选择最少且足够的Capability。
Capability可以被跳过、重复、重排，不存在固定执行顺序。

不要因为某个Capability通常产生另一个Capability需要的输入，
就无条件重复生成已有Context。

如果某Capability所需Context当前不存在，
可以选择能够合理产生该Context的Capability；
如果当前Catalog无法获得关键Context或完成Goal，
返回NO_FEASIBLE_PLAN。

不得生成客户事实、产品事实、权限结果、规则结果或Opportunity结论。

不得输出Tool名称、API、SQL、Prompt或实现细节。

外部写意图必须显式标记，
但不得自行认为规则已通过或用户已确认。
```

我认为这已经覆盖 80% 核心风险。

---

# 十七、最危险的 Prompt 写法

绝对不要：

> “智慧经营包括五个阶段：定向洞察、自动圈客、策略生成、校验分发、追踪迭代，请按照这些步骤……”

哪怕后面再补一句：

> “可以灵活调整。”

模型仍然会高度倾向：

```text
1
2
3
4
5
```

所以 Planner Prompt 应该先给：

```text
Goal
Context
```

然后给：

```text
Capability Catalog
```

Catalog 只是一个**无序能力集合**。

甚至序列化给模型时，都不建议固定使用：

```text
1.
2.
3.
4.
5.
```

避免无意识位置暗示。

可以按：

```json
{
  "capabilities": {
    "customer_targeting": {...},
    "directional_insight": {...},
    ...
  }
}
```

这种无业务序号结构。

---

# 十八、Planner 如何处理 Required Context

例如：

```text
strategy_generation

requires:
goal
customer
```

当前：

```text
Goal ✓
Customer ✗
Opportunity ✓
```

Planner 不应该：

```text
strategy_generation
```

直接假设 customer 存在。

它应该查看 Catalog：

```text
customer_targeting

requires:
goal
opportunity

produces:
candidate_set
```

于是合理生成：

```text
S1 customer_targeting
S2 strategy_generation

S2 depends_on S1
```

这就是动态依赖。

---

# 十九、但也不要写一个 Dependency Solver

非常重要。

Application 不需要：

```python
while missing_context:
    search capability graph...
```

这种复杂算法。

这仍然让 LLM 根据：

```text
Goal
Context
Catalog
```

进行语义规划。

T06 只负责验证：

> 你规划出来的东西是否合法？

而不是代码替代 Planner 完成业务规划。

---

# 二十、PlanValidator 后面会怎么验证 Context Dependency

T05 可以先定义输出，T06 再实现。

例如 Planner 输出：

```text
S1 strategy_generation

input:
customer_123
```

Catalog：

```text
requires:
goal
customer
```

PlanningContext：

```text
customer_123 exists
```

合法。

另一种：

```text
S1 strategy_generation

无 customer
```

也没有任何依赖 Step 能产生 customer context。

则：

```text
PlanValidator Reject
```

这能防止模型“跳步”靠的是幻觉，而不是动态规划。

---

# 二十一、`expected_outputs` 仍然应该由 Planner 提议

例如：

```text
directional_insight

expected_outputs:
opportunity
```

或者：

```text
customer_targeting

expected_outputs:
candidate_set
```

这有两个价值。

第一，Plan 可以告诉用户：

> 这一步打算得到什么。

第二，M3 执行后可以比较：

```text
Expected
vs
CapabilityResult
```

支持后续 Replan。

但 T06 应检查：

```text
expected_outputs
```

必须是 Catalog `produces` 的合法子集。

---

# 二十二、不要让 Planner 自己生成 Opportunity ID 等未来结果引用

例如：

```text
S1 Insight
produces opp_001

S2 Targeting
input_ref=opp_001
```

这时 `opp_001` 还不存在。

不要让模型制造未来实体 ID。

因此对于未来步骤之间的依赖：

```text
S2 depends_on = S1
```

就够。

具体执行后：

```text
S1 CapabilityResult
→ opp_real_827
```

M3 再将真实输出传给 S2。

也就是说：

> `input_refs` 只引用已经存在的 Context。

> 未来产物通过 `depends_on` 表达。

这条很关键。

---

# 二十三、一个完整 Planner 输入

例如 Goal：

```text
完成500W NBEV
当前主推产品 A、B
```

PlanningContext：

```text
available_refs = ()
assumptions = ()
missing_information =
  - 开门红截止日期暂未确定
    non-blocking
```

Capability Catalog：

```text
directional_insight
customer_targeting
strategy_generation
validation_distribution
tracking_iteration
```

Planner 可能输出：

```text
S1
directional_insight

objective:
识别当前Goal下优先经营机会

depends_on:
[]


S2
customer_targeting

objective:
围绕已识别机会寻找候选经营对象

depends_on:
[S1]


S3
strategy_generation

objective:
为优先经营对象形成具体策略

depends_on:
[S2]
```

这个计划是合理的。

但注意：

> **不能把这个结果写成 Golden Exact Plan。**

因为不同 Goal Context 下合理 Plan 可能不同。

# 二十四、什么 Planner 场景可以做精确 Golden Test？

一些非常明确的简单问题可以。

例如：

### 用户只问

> 最近有什么值得关注的经营机会？

预期：

```text
directional_insight
```

可以作为强行为测试。

---

### 用户问

> 围绕刚才这个 Opportunity 找客户。

已有 Opportunity。

预期：

```text
customer_targeting
```

---

### 用户问

> 王女士下一步怎么经营？

已有 Customer + 足够 Evidence。

预期：

```text
strategy_generation
```

---

### 用户问

> 看看之前任务进展。

Tracking available。

预期：

```text
tracking_iteration
```

这些场景可以强力验证：

> Planner 没有“五步强迫症”。

---

# 二十五、复杂 Goal 不建议 Exact Match

比如：

> 完成500W NBEV。

不要测试：

```python
assert capability_ids == [
    "directional_insight",
    "customer_targeting",
    "strategy_generation",
]
```

这种测试太脆。

更合理的是评估：

```text
没有无关Capability

没有 unavailable Capability

步骤依赖合法

没有把五类能力全部机械加入

能够解释每个Step和Goal关系

最终路径可以产生当前请求所需结果
```

这里有一部分属于：

```text
Behaviour Evaluation
```

而不是纯单元测试。

---

# 二十六、FakeModel 和真实模型测试必须分开

你们已经有：

```text
src/model/fake.py
```

非常适合 T05。

### Contract / Application Tests

用 FakeModel。

例如 Fake 返回：

```text
合法 PlanDraft
未知 Capability
循环依赖
非法 JSON
external_write
```

这些测试必须：

```text
deterministic
```

---

### Planner Behaviour Evaluation

少量真实模型。

建立一个固定评估集：

| 场景                    | 期望规划特征                |
| ----------------------- | --------------------------- |
| 只看机会                | 只选 Insight                |
| 已有 Opportunity 找客户 | Targeting，无重复 Insight   |
| 已有客户求策略          | Strategy，无 Targeting      |
| 看进展                  | Tracking                    |
| Tracking unavailable    | NO_FEASIBLE_PLAN            |
| 复杂目标                | 合理组合，不机械全五类      |
| 外部任务创建            | 标记 write intent           |
| 缺 Context 可由能力产生 | 先补 Context 再执行目标能力 |

这是 M2 第一次应该开始维护一个小型：

```text
Planner Eval Set
```

# 二十七、结构化输出建议

Planner 也必须严格 Structured Output。

例如：

```json
{
  "decision": "plan",
  "steps": [
    {
      "step_id": "s1",
      "capability_id": "directional_insight",
      "objective": "识别当前目标下值得优先经营的机会",
      "reason": "当前尚缺少可用于进一步定位客户的经营机会上下文",
      "depends_on": [],
      "input_refs": [],
      "expected_outputs": [
        "opportunity"
      ],
      "side_effect_intent": "read_only"
    }
  ]
}
```

或者：

```json
{
  "decision": "no_feasible_plan",
  "reason": "当前系统未提供可用的经营追踪能力"
}
```

---

# 二十八、和 T02 一样做 bounded repair

流程：

```text
ChatModel
↓
Planner raw JSON
↓
Schema parse
↓
成功
```

失败：

```text
第一次 invalid
↓
一次 repair
↓
仍然 invalid
↓
PlannerError
```

不要无限 repair。

也不要 invalid JSON 后：

```text
随便正则提取几个 capability_id
```

那会破坏 Contract。

---

# 二十九、Planner Error 和 NO_FEASIBLE_PLAN 不一样

这是必须区分的。

```text
NO_FEASIBLE_PLAN
```

是业务规划结果：

> 系统正常工作，但现有能力不足。

而：

```text
PlannerError
```

是：

> 模型调用失败 / 输出无法解析 / Application 出错。

和我们 T06：

```text
NO_RESULT ≠ FAILED
```

其实是完全相同的设计哲学。

---

# 三十、Planner 不负责解决非阻塞 MissingInformation

例如：

```text
开门红截止日期未知
```

ClarificationGate 已经决定：

```text
CONTINUE
```

Planner 可以看到：

```text
missing_information
```

然后在计划中规避依赖精确日期的行为。

但 Planner 不应该：

```text
“我猜截止日期是3月31日。”
```

也不应该修改 Goal。

如果某一步真的必须需要日期：

Planner 可以：

```text
NO_FEASIBLE_PLAN
```

或者后续 M3 才考虑通过知识能力获取。

M2 不要偷偷扩大 Planner 权限。

---

# 三十一、Assumption 也必须提供给 Planner

比如 Goal 中：

```text
Assumption:
暂以当前代理人的全部可经营客户作为分析范围
```

Planner 需要看到。

否则它可能误认为：

```text
audience scope 已经由用户明确确认
```

所以 Planning Prompt 中应该清楚区分：

```text
Confirmed Goal

Assumptions

Missing Information
```

模型不能把三者混成一块 Context。

# 三十二、第一版建议的代码结构

不必过度拆分，概念上：

```text
src/application/
├─ request.py
├─ goal_interpreter.py
├─ goal_assembler.py
├─ capability_catalog.py
└─ planner.py
```

`planner.py` 可以先包含：

```text
PlanningContext
PlanningDecisionType
PlanningDecision
PlanDraft
PlanStepDraft
Planner
```

如果文件明显过长，再拆：

```text
planning/
  contract.py
  planner.py
```

不要为了架构图漂亮提前拆十几个文件。

# 三十三、M2-T05 的重要不变量

这一阶段我建议正式锁住以下内容：

| 编号  | Planner 不变量                                                     |
| ----- | ------------------------------------------------------------------ |
| PL-01 | Planner 只从当前 Catalog 选择 Capability                           |
| PL-02 | 不得选择`available=False` 的 Capability                          |
| PL-03 | Capability 可跳过、重复、重排                                      |
| PL-04 | Planner 应选择满足当前 Goal 的最少合理能力组合                     |
| PL-05 | 已存在 Context 不应通过重复 Capability 再生成                      |
| PL-06 | Required Context 不存在时，不得假装存在                            |
| PL-07 | 可通过其他 Capability 产生的 Context 可以通过依赖 Step 获得        |
| PL-08 | Planner 不生成客户/产品/规则等业务事实                             |
| PL-09 | Planner 不生成 Tool、SQL、API、Prompt 等实现细节                   |
| PL-10 | Planner 不生成 Capability Version，由 Catalog/Validator解析        |
| PL-11 | Planner 不生成未来业务实体 ID                                      |
| PL-12 | 外部写意图必须明确标记，但控制点由确定性 Validator 施加            |
| PL-13 | 当前能力无法完成 Goal 时返回 NO_FEASIBLE_PLAN，不得编造 Capability |
| PL-14 | `reason` 是简洁业务理由，不保存/要求内部推理过程                 |
| PL-15 | Planner 只产生 PlanDraft，不直接产生正式 Plan                      |

# 三十四、T05 的完成标准

T05 做完以后，我们应该已经能够稳定运行：

```text
Goal
+
PlanningContext
+
CapabilityCatalog
        ↓
      Planner
        ↓
┌───────────────────┐
│ PLAN              │
│                   │
│ PlanDraft         │
│   S1 Capability A │
│   S2 Capability B │
│      depends S1   │
└───────────────────┘
```

或者：

```text
┌──────────────────────────┐
│ NO_FEASIBLE_PLAN         │
│                          │
│ 当前系统无合适Capability │
└──────────────────────────┘
```

但此时我们仍然**不相信 PlanDraft 本身一定合法**。

这正是下一步 **M2-T06 Plan Validator** 的职责：

```text
PlanDraft
      ↓
检查 Capability 是否真实存在/可用
检查 expected output
检查 required context
检查 depends_on
检查 cycle
解析 Capability version
对 write intent 强制加入 ControlPoint
生成 plan_id/version/goal_ref
      ↓
正式 Plan
```

所以 **T05 是“LLM 提议怎么做”，T06 才是“系统允许这个计划成为正式计划”。** 这会是 M2 中另一条非常重要的信任边界。
