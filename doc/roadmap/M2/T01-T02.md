
可以，我们从 **M2-T01 + M2-T02** 开始，把它们直接推到“可以交给 Codex 实现”的设计深度。

这两个任务其实共同解决一个问题：

> **用户说了一句话之后，系统如何在不污染可信业务上下文、不提前做经营决策的前提下，把自然语言转换成一个“待组装的 Goal 解释结果”。**

所以这一阶段的边界应该非常清楚：

```text
M2-T01
建立 Application 入口和可信 Runtime Context

           ↓

M2-T02
让 LLM 只理解用户表达

           ↓

GoalInterpretation

           ↓
       M2-T03
Deterministic Goal Assembler
           ↓
          Goal
```

注意：**T02 结束时还没有最终 Goal。**

这是我认为这一阶段最重要的设计。

---

# 一、M2-T01：Application Layer 的第一个入口

M1 已经确定了依赖：

```text
Application
   ├── Domain
   └── Agent / Model
```

所以现在第一次真正出现：

```text
src/application/
```

但这一层目前不要设计成庞大的 Service 层。

M2-T01 暂时只需要解决：

```text
谁发起请求？
用户说了什么？
当前可信运行上下文是什么？
这是不是对已有 Goal 的继续修改？
```

因此建议第一版只有两个核心对象：

```text
BusinessRequest

RuntimeContext
```

---

# 二、为什么不能只有一个 `user_message: str`

最简单的入口当然是：

```python
def handle(user_message: str):
    ...
```

但对于这个项目来说明显不够。

因为：

> 当前代理人是谁？

> 当前渠道是什么？

> 当前请求时间是什么？

> 用户是不是正在修改之前的 Goal？

这些信息都不应该由 LLM 从用户文本里猜。

例如用户只说：

> “开门红500W，主推御享分红26和御享金越年金。”

如果只把一句话交给 LLM，它很可能顺便生成：

```text
channel = 个险
actor = 当前代理人
```

而这两个信息实际上应该来自可信登录上下文。

规范也明确要求渠道、人员、授权以及后续权限判断不能由 Agent 臆造或覆盖。:chatgpt-content-reference{index="0"}

因此系统入口从第一天就应该把：

```text
User-provided information
```

和：

```text
Trusted runtime information
```

分开。

---

# 三、BusinessRequest 第一版

我建议：

```python
@dataclass(frozen=True)
class BusinessRequest:
    request_id: str

    user_request: str

    runtime_context: "RuntimeContext"

    existing_goal_ref: GoalRef | None = None
```

第一版就这几个字段。

不要马上加入：

```text
conversation_history
session_state
memory
previous_plan
customer_context
attachments
```

以后需要时再增加。

---

# 四、`request_id` 和 Goal ID 不一样

需要特别明确：

```text
request_id
```

表示：

> 这一次用户输入。

而：

```text
goal_id
```

表示：

> 业务目标本身。

比如：

```text
Request 001
“我要完成500W NBEV”

        ↓

Goal 001 v1
```

后来：

```text
Request 009
“500W改成400W，优先老客户”

        ↓

Goal 001 v2
```

所以：

```text
request_id != goal_id
```

以后 Trace、审计会很依赖这个区分。

---

# 五、RuntimeContext 应该保持非常克制

第一版建议：

```python
@dataclass(frozen=True)
class RuntimeContext:
    actor_ref: str | None
    channel_ref: str | None
    authorization_ref: str | None

    request_time: datetime
```

目前这样就够。

这里有一个重要原则：

> `RuntimeContext` 只是“当前可信运行上下文”，不是业务数据大礼包。

所以不要：

```python
RuntimeContext(
    actor_ref=...,
    customer_profile=...,
    all_products=...,
    sales_history=...,
    ...
)
```

客户、产品等数据后面都应该通过受控 Capability / Tool 获取。

否则 Application 入口会很快变成一个万能 Context。

---

# 六、为什么 RuntimeContext 可以存在 `None`

例如内部单元测试，或者某些匿名只读场景：

```python
actor_ref=None
channel_ref=None
```

不应该导致：

```text
BusinessRequest 无法建立
```

而应该在后面的：

```text
GoalAssembler
ClarificationGate
Validation
```

判断：

> 当前缺失会不会影响接下来的行动？

这延续 M1 的原则：

> 信息缺失不是异常；关键是必须显式知道它缺失。:chatgpt-content-reference{index="1"}

---

# 七、`existing_goal_ref` 是 M2-T01 非常值得提前保留的字段

因为用户不一定每次创建新 Goal。

例如：

```text
第一轮：
“开门红完成500W NBEV”
```

产生：

```text
Goal 001 v1
```

用户随后说：

> “改成400W，而且优先经营老客户。”

这一句话单独来看是不完整的。

如果没有：

```text
existing_goal_ref
```

Goal Interpreter 很容易把它理解成一个全新 Goal。

正确应该：

```text
BusinessRequest
├─ user_request
│    “改成400W，而且优先老客户”
│
└─ existing_goal_ref
     Goal 001 v1
```

然后后续 M2-T03 才决定：

```text
Goal 001 v2
```

---

# 八、但是 existing Goal 不应该直接塞进 T02 Prompt

这里值得谨慎一点。

T02 的职责是：

> 理解当前用户表达。

如果直接把整个旧 Goal 给它，并让它：

> “输出新的完整 Goal”

就会让：

```text
理解
+
合并
+
可信上下文决策
+
版本更新
```

全部重新塞回 LLM。

所以建议：

```text
现有 Goal
```

可以作为解析上下文，但 T02 输出应该明确区分：

```text
用户新表达了什么
```

而不是：

```text
最终 Goal 应该是什么
```

这个区别非常关键。

---

# 九、T01 最终的边界

因此 M2-T01 最终实际上建立：

```text
┌────────────────────────────┐
│ BusinessRequest            │
│                            │
│ request_id                 │
│ user_request               │
│ existing_goal_ref          │
│ runtime_context            │
└──────────────┬─────────────┘
               │
               ▼
          GoalInterpreter
```

而 RuntimeContext 保持：

```text
Trusted
Non-LLM-generated
Explicit
Minimal
```

---

# 十、进入 M2-T02：Goal Interpreter 到底负责什么

建议正式定义：

> **Goal Interpreter 负责从用户自然语言中提取“用户明确表达或语言上可以合理解析出的经营意图”，不负责补全权威事实、不负责形成最终 Goal、不负责规划 Capability。**

换句话说，它回答：

> **“用户刚才到底表达了什么？”**

而不是：

> **“系统最终应该相信什么？”**

更不是：

> **“接下来应该怎么做？”**

---

# 十一、Goal Interpreter 的输入

第一版可以概念化为：

```python
@dataclass(frozen=True)
class GoalInterpretationRequest:
    user_request: str

    existing_goal: Goal | None = None
```

注意这里没有：

```text
runtime_context
```

是不是意味着模型完全不知道渠道？

不一定。

我建议第一版区分两类上下文：

```text
LLM 可以看到的 context
```

和：

```text
LLM 有权决定的 field
```

即使 Prompt 中为了帮助理解可以告诉模型：

> 当前登录环境为个险代理人。

它也**不能输出这件事作为解析所得用户事实**。

但为了最大化边界清晰，M2 第一版甚至可以不把 RuntimeContext 交给 Interpreter，而在 T03 才 merge。

我更倾向这个方案。

也就是：

```text
T02 输入

user_request
+
existing Goal semantic snapshot（如需要）

不输入可信身份上下文
```

这样最干净。

---

# 十二、GoalInterpretation 不应该复用 Goal 本体

这是 T02 的另一个关键设计。

不要：

```python
GoalInterpreter.parse(...) -> Goal
```

而应该：

```python
GoalInterpreter.parse(...) -> GoalInterpretation
```

因为这两者代表不同的可信级别。

`Goal` 是：

```text
系统认可的业务领域对象
```

而：

`GoalInterpretation` 是：

```text
LLM 对用户语言的结构化解释
```

二者绝对不能同权。

---

# 十三、GoalInterpretation 第一版建议结构

我建议不要完全复制 Goal。

而是围绕：

```text
用户明确说了什么
用户修改了什么
哪些地方仍然不清楚
```

建模。

例如：

```python
@dataclass(frozen=True)
class GoalInterpretation:
    goal_type: str | None = None

    metric: "MetricInterpretation | None" = None
    target: "TargetInterpretation | None" = None

    time_expression: str | None = None
    audience_expression: str | None = None

    product_mentions: tuple[str, ...] = ()
    need_mentions: tuple[str, ...] = ()

    constraints: tuple["ConstraintInterpretation", ...] = ()

    unresolved_items: tuple["UnresolvedItem", ...] = ()
```

注意故意没有：

```text
goal_id
version
channel_and_actor
success_criteria
missing_information
assumptions
```

因为这些不是 LLM 解析用户一句话时应该拥有最终决定权的字段。

---

# 十四、为什么没有 `original_request`

因为：

```text
original_request
```

已经在：

```text
BusinessRequest.user_request
```

中存在。

T03 Goal Assembler 直接把它带入 Goal。

没有必要让模型再返回一次：

```json
{
  "original_request": "..."
}
```

否则模型甚至可能改写用户原文。

---

# 十五、MetricInterpretation

建议：

```python
@dataclass(frozen=True)
class MetricInterpretation:
    raw_expression: str
    normalized_code: str | None = None
```

例如：

```text
用户：
“500W新业务价值”
```

可能：

```text
raw_expression = "新业务价值"
normalized_code = "NBEV"
```

这里需要谨慎：

如果：

```text
NBEV ↔ 新业务价值
```

是系统已经明确允许的语言归一化，可以解析。

但如果出现模糊指标：

> “业绩做到500W”

模型不应该擅自：

```text
normalized_code = NBEV
```

而应该：

```text
normalized_code = None
```

并产生：

```text
UnresolvedItem
```

---

# 十六、TargetInterpretation

建议：

```python
@dataclass(frozen=True)
class TargetInterpretation:
    raw_expression: str

    value: float | None = None
    unit: str | None = None
    direction: str | None = None
```

例如：

```text
“500W”
```

输出：

```text
value=500
unit="万元"
direction="at_least"
```

但这里有一个需要谨慎的点：

“希望达成500W”

能否自动解释为：

```text
at_least
```

我认为可以。

这是语言语义转换，不是业务事实补全。

但：

```text
“业绩更高一点”
```

不能变成：

```text
value = 500
```

---

# 十七、TimeExpression 先不要让 LLM 算日期

T02 这里继续坚持 M1 原则。

例如：

```text
“开门红阶段”
```

Interpreter 只返回：

```text
time_expression = "开门红阶段"
```

不要：

```text
start_at = ...
end_at = ...
```

即使模型“知道”大概什么时间。

真正日期应该以后由：

```text
业务日历
配置
知识 Tool
```

确定。

所以这里不要复用：

```text
TimeHorizon
```

而是：

```text
raw time expression
```

这能非常有效地阻断幻觉。

---

# 十八、AudienceExpression 同理

例如：

```text
“我的老客户”
```

T02：

```text
audience_expression = "我的老客户"
```

而不是：

```text
customer_type = existing
ownership = current_agent
channel = individual
```

因为后面的：

```text
“我的”
```

涉及真实客户归属。

这需要可信系统解释。

---

# 十九、Product Mentions 也只是 Mention

例如：

```text
御享分红26
御享金越年金
```

T02 可以：

```python
product_mentions=(
    "御享分红26",
    "御享金越年金",
)
```

但不要马上：

```text
product_id = PRD000123
```

除非产品 ID 是通过确定性 Entity Resolver / Knowledge Tool 查出来的。

这其实可以为后面留下：

```text
raw mention
→ entity resolution
→ authoritative ref
```

的路径。

---

# 二十、Need Mentions

比如用户说：

> “我主要想做养老规划。”

可以：

```python
need_mentions=("养老规划",)
```

但：

> “50岁客户”

不能自动生成：

```text
need_mentions=("养老",)
```

因为那已经属于经营判断。

这应该留给：

```text
Opportunity
```

---

# 二十一、ConstraintInterpretation

这里建议简单：

```python
@dataclass(frozen=True)
class ConstraintInterpretation:
    raw_expression: str
    constraint_type: str | None = None
    value: object | None = None
```

比如：

> 优先老客户。

输出：

```text
constraint_type = customer_preference
value = existing_customer
```

但：

> 银保客户不能做。

如果用户这么说，也只是：

```text
user-stated constraint
```

绝不能因此升级成业务规则。

真正 Rule 必须来自规则服务。

---

# 二十二、UnresolvedItem 非常重要

这是 T02 防止模型“为了 JSON 完整而乱填”的关键。

建议：

```python
@dataclass(frozen=True)
class UnresolvedItem:
    field: str
    raw_expression: str | None
    reason: str
```

例如：

用户：

> “这个月把业绩做到500W。”

模型无法确定：

```text
业绩 = NBEV？
保费？
件数？
```

正确：

```python
UnresolvedItem(
    field="metric",
    raw_expression="业绩",
    reason="用户未明确具体业绩指标",
)
```

而不是猜：

```text
metric=NBEV
```

---

# 二十三、T02 不负责 MissingInformation

这里要区别：

```text
UnresolvedItem
```

和 M1 的：

```text
MissingInformation
```

两者相似，但层级不同。

`UnresolvedItem`：

> LLM 在理解这句话时没有解析清楚。

`MissingInformation`：

> 系统组装最终 Goal 后确认存在的业务信息缺口。

例如用户没说渠道：

T02：

```text
不一定产生 unresolved_item
```

因为用户本来就没必要说渠道。

T03 发现 RuntimeContext 也没有渠道：

```text
MissingInformation(
    field="channel_and_actor.channel_ref",
    ...
)
```

所以一定不要混。

---

# 二十四、如何支持 Goal 修改

这是 T02 一个特别重要的场景。

原 Goal：

```text
Goal 001 v1

target = 500W
audience = all manageable customers
```

用户：

> 改成400W，优先老客户。

GoalInterpretation 应该表达：

```text
target:
400W

constraints:
优先老客户
```

但不应该重新生成：

```text
metric = NBEV
product context = ...
time horizon = ...
```

因为用户这一轮根本没说。

也就是说：

> **GoalInterpretation 最好采用 PATCH 语义，而不是完整对象语义。**

这个设计我很推荐。

---

# 二十五、因此 GoalInterpretation 本质上其实是 Goal Patch

可以把它理解成：

```text
用户当前这句话，
对 Goal 提出了哪些新增/修改信息？
```

例如：

```text
“改成400W”
```

Interpretation：

```json
{
  "target": {
    "value": 400,
    "unit": "万元"
  }
}
```

而不是：

```json
{
  "goal_type": "...",
  "metric": "...",
  "target": 400,
  "products": [...]
}
```

把旧数据重新生成一遍。

这样风险小很多。

---

# 二十六、但我暂时不建议把类命名成 `GoalPatch`

为什么？

因为新建 Goal 时，它也是同一个解析结果。

例如第一次：

```text
“500W NBEV”
```

实际上也是：

```text
空 Goal
+
当前 interpretation
```

所以：

```text
GoalInterpretation
```

语义更通用。

但在实现规则上采用：

> **partial / patch semantics**

即可。

---

# 二十七、Goal Interpreter 应该看到旧 Goal 的哪些内容？

如果 existing_goal 存在，我建议给 LLM：

```text
Current Goal Summary
```

而不是整个领域对象 JSON 无脑塞进去。

例如：

```text
当前目标：
- 指标：NBEV
- 目标值：500万元
- 时间：开门红阶段
- 客户范围：当前可经营客户
- 产品背景：A、B
```

用户：

> “改成400W，优先老客户。”

模型就能理解：

```text
400W
```

是在修改 target。

但一定在 System Prompt 中明确：

> 只输出当前用户明确新增、修改或取消的字段；不得重复或猜测未被当前表达修改的字段。

---

# 二十八、需要支持字段“清除”

例如用户说：

> 不限定产品了。

这不是：

```text
product_mentions = ()
```

那么简单，因为：

```text
()
```

可能意味着：

> 用户没有提产品。

也可能意味着：

> 用户明确删除已有产品约束。

所以 GoalInterpretation 需要区分：

```text
UNSPECIFIED
```

和：

```text
CLEAR
```

这是 M2-T02 中一个非常重要的工程问题。

---

# 二十九、我建议为可修改字段引入一个轻量 PatchField

比如：

```python
class UpdateAction(str, Enum):
    SET = "set"
    CLEAR = "clear"
```

然后：

```python
@dataclass(frozen=True)
class FieldUpdate:
    action: UpdateAction
    value: object | None = None
```

于是：

用户：

> “主推御享分红26。”

```text
SET
["御享分红26"]
```

用户：

> “不限定产品。”

```text
CLEAR
```

用户完全没提产品：

```text
对应字段 = None
```

这三种语义是不一样的：

```text
None
=
本轮未涉及

SET
=
本轮明确设置

CLEAR
=
本轮明确清除
```

我认为这个设计值得从 M2 第一版就做。

---

# 三十、GoalInterpretation 可以进一步调整成这样

概念上：

```python
@dataclass(frozen=True)
class GoalInterpretation:
    goal_type: FieldUpdate | None = None

    metric: FieldUpdate | None = None
    target: FieldUpdate | None = None

    time_expression: FieldUpdate | None = None
    audience_expression: FieldUpdate | None = None

    product_mentions: FieldUpdate | None = None
    need_mentions: FieldUpdate | None = None

    constraints: FieldUpdate | None = None

    unresolved_items: tuple[UnresolvedItem, ...] = ()
```

如果觉得所有字段都包一层太重，也可以第一版只对：

```text
product
need
constraint
audience
```

这种可显式删除的字段做 Patch。

不过从一致性来说，我倾向统一。

---

# 三十一、LLM 输出 Schema

T02 我建议要求非常严格。

例如：

```json
{
  "goal_type": {
    "action": "set",
    "value": "performance_achievement"
  },
  "metric": {
    "action": "set",
    "raw_expression": "NBEV",
    "normalized_code": "NBEV"
  },
  "target": {
    "action": "set",
    "raw_expression": "500W",
    "value": 500,
    "unit": "万元",
    "direction": "at_least"
  },
  "time_expression": {
    "action": "set",
    "value": "开门红阶段"
  },
  "product_mentions": {
    "action": "set",
    "value": [
      "御享分红26",
      "御享金越年金"
    ]
  },
  "unresolved_items": []
}
```

注意没有：

```text
goal_id
actor
channel
start_date
end_date
plan
opportunity
recommended_product
```

这些都不属于 T02。

---

# 三十二、Prompt 的核心约束

Goal Interpreter Prompt 不需要非常长。

核心应该是五条语义：

```text
你负责理解用户当前表达中的经营目标信息，
不负责制定经营计划。

只提取用户当前明确表达或可以直接从语言语义规范化得到的信息。

不得补充客户、渠道、人员、权限、产品事实、日期等外部事实。

如果信息存在歧义，保留原表达并放入 unresolved_items，不要猜测。

若存在已有 Goal，只输出当前用户明确新增、修改或清除的内容，不要重新生成未改变字段。
```

这比堆大量 Demo few-shot 更重要。

---

# 三十三、可以提供 Few-shot，但必须跨场景

例如至少包括三种：

```text
500W NBEV绩效目标

单客户：
“看看王女士下一步怎么经营”

修改型：
“改成400W，不限定产品了”
```

不要所有例子都是：

```text
开门红 + 两款 Demo 产品
```

否则模型行为会悄悄场景化。

---

# 三十四、Goal Interpreter 的输出要经过确定性 Schema Validation

流程：

```text
ChatModel
   ↓
raw structured output
   ↓
JSON/schema parse
   ↓
GoalInterpretation
```

如果解析失败：

```text
第一次
↓
一次 bounded repair
↓
仍失败
↓
InterpretationFailure
```

这里不要直接产生：

```text
CapabilityResult.FAILED
```

因为 Goal Interpreter 目前还不是 Capability。

可以是 Application 层自己的错误：

```text
GoalInterpretationError
```

或者普通 exception，由 BusinessAgent 捕获。

不要把 M1 Capability Status 滥用到所有系统对象。

---

# 三十五、我甚至建议 M2 第一版“不使用 AgentLoop”

这里再次确认。

T02：

```text
Goal Interpreter
↓
ChatModel
```

即可。

因为它不需要 Tool。

如果为了“这是 Agent 项目”，强制：

```text
AgentLoop
↓
ChatModel
```

没有实际收益。

这也能保持现有 `AgentLoop` 足够纯粹。

# 三十六、T01 + T02 建议的代码边界

概念上：

```text
src/
├─ model/
├─ agent/
├─ domain/
└─ application/
   ├─ request.py
   └─ goal/
      ├─ interpretation.py
      └─ interpreter.py
```

也可以简单：

```text
application/

```

不要为了目录漂亮过度拆文件。

# 三十七、T01 + T02 测试非常关键

这阶段至少应该锁住下面这些行为：

| 输入                             | 关键期望                                            |
| -------------------------------- | --------------------------------------------------- |
| “完成500W NBEV”                | 正确提取 metric/target                              |
| “业绩做到500W”                 | metric 不明确，进入 unresolved                      |
| “开门红阶段”                   | 保留 raw expression，不生成日期                     |
| “我的老客户”                   | 保留 audience expression，不推断真实归属            |
| “我想做养老”                   | need mention=养老                                   |
| “50岁客户”                     | 不自动生成“养老需求”                              |
| “主推产品A”                    | product mention=A，不生成产品ID/产品事实            |
| “我现在是银保渠道”             | 可以识别这是用户陈述，但不能成为可信 RuntimeContext |
| existing Goal + “改成400W”     | 只输出 target update                                |
| existing Goal + “不限定产品了” | 输出 CLEAR，而不是“本轮没提产品”                  |
| existing Goal + “就这样”       | 不重新生成整个 Goal                                 |
| Invalid model JSON               | 有限修复/明确失败                                   |

其中有一个我特别建议写成长期 Regression：

```text
输入：
“50岁男性客户”

结果：
不得出现 need_mentions = ["养老"]
```

因为它直接检验：

> **Interpreter 有没有偷偷开始做 Opportunity 判断。**

# 三十八、T02 最大的 Anti-pattern

最危险的实现其实是：

```text
一个超级 Prompt：

请根据用户输入，
输出：
Goal
Plan
Opportunity
推荐客户
推荐产品
策略……
```

这样 Demo 会非常快。

但：

```text
T01 ~ T08
```

几乎全部失效。

M2 应该反其道而行：

```text
Goal Interpreter
只负责 Goal Interpretation
```

之后：

```text
Goal Assembler
```

之后：

```text
Planner
```

不同阶段权限不同。

这不是为了“架构漂亮”，而是为了限制 LLM 能偷偷决定什么。

# 三十九、T01 + T02 的不变量

我建议正式锁定：

**I-01**：自然语言和 Trusted Runtime Context 是两个独立输入源。
**I-02**：RuntimeContext 不由 LLM 创建或修改。
**I-03**：GoalInterpreter 输出 `GoalInterpretation`，不直接输出 Domain `Goal`。
**I-04**：Interpretation 采用 partial/patch semantics。
**I-05**：未提及字段与明确清除字段必须可区分。
**I-06**：Interpreter 不生成 Goal ID/version。
**I-07**：Interpreter 不生成 actor/channel/authorization 的可信值。
**I-08**：Interpreter 不解析需要外部权威知识才能确定的事实。
**I-09**：歧义进入 `unresolved_items`，不能猜。
**I-10**：Interpreter 不输出 Plan、Capability 或 Opportunity。
**I-11**：已有 Goal 只用于帮助理解变更语义，不允许模型无理由重写旧字段。
**I-12**：结构化输出必须通过确定性 Schema Validation。

## T01 + T02 做完以后应该得到什么

还不是：

```text
Goal
```

而是这样：

```text
BusinessRequest
│
├── user_request
├── existing_goal_ref
└── RuntimeContext
        │
        │
        └───────────────┐
                        │ 留给 T03
user_request            │
      ↓                 │
GoalInterpreter          │
      ↓                 │
GoalInterpretation      │
                        │
      ┌─────────────────┘
      ↓
下一阶段 T03
GoalAssembler
```

举我们的 Demo：

```text
用户输入：
“当前处于开门红阶段，
希望完成500W NBEV，
主推御享分红26和御享金越年金。”
```

T02 最理想的结果只是：

```text
goal_type:
    SET performance_achievement

metric:
    SET NBEV

target:
    SET 500万元

time_expression:
    SET “开门红阶段”

product_mentions:
    SET
    - 御享分红26
    - 御享金越年金

unresolved:
    []
```

而与此同时，系统另一个完全独立的对象保存：

```text
RuntimeContext

actor_ref:
agent_001

channel_ref:
individual_insurance

authorization_ref:
...
```

**直到 T03，这两条信息流才第一次汇合。**

我认为这是 M2 前半段最重要的架构边界。下一步进入 **M2-T03** 时，我们就可以专门解决最有意思的问题：**如何把一个“不可信但有语义价值的 LLM Interpretation”和一个“可信但语义有限的 RuntimeContext”确定性地合并成最终 Goal，并决定什么时候必须问用户。**
