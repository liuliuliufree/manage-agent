
进入 **M2-T06：Plan Validator**。这一阶段的定位可以非常明确：

> **Planner 负责“提出一个计划”，Plan Validator 负责“证明这个计划在当前系统中合法、安全、可执行”，然后才把它升级成正式 `Plan`。**

这也是 M2 里第二条重要信任边界：

```text
LLM Planner
    ↓
PlanDraft          ← 建议
    ↓
Plan Validator     ← 确定性代码
    ↓
Plan               ← 系统认可
```

规范要求 Plan 可以动态选择、跳过、重复、重排 Capability，同时外部写操作必须经过规则校验和用户确认；所以这些不能依靠 Planner “自觉”，必须由确定性层兜底。

---

# 一、先明确 Plan Validator 不是什么

它不是第二个 Planner。

所以它不能看到：

```text
PlanDraft:
S1 directional_insight
S2 strategy_generation
```

然后自己觉得：

> “中间好像少了 customer_targeting，我帮你补一个。”

不允许。

同样不能：

```text
重新排列步骤
新增 Capability
删除 Planner 选择的步骤
改 objective
重写 reason
```

否则实际上就有两套 Planner。

Plan Validator 只允许做两类动作：

```text
验证
+
确定性补全
```

例如：

```text
capability_id
      ↓
绑定真实 capability_version

external_write
      ↓
强制加入 RULE_CHECK / USER_CONFIRMATION

draft step id
      ↓
形成正式 PlanStep

Goal
      ↓
绑定 goal_id + version
```

---

# 二、T06 的输入应该固定下来

建议：

```python
validate_plan(
    draft: PlanDraft,
    goal: Goal,
    context: PlanningContext,
    catalog: CapabilityCatalog,
) -> PlanValidationResult
```

所以 Validator 只依赖四类信息：

```text
PlanDraft
Goal
PlanningContext
CapabilityCatalog
```

不需要：

```text
ChatModel
AgentLoop
Tool
数据库
业务规则服务
```

整个 T06 应该是**纯确定性逻辑**。

---

# 三、第一层校验：Draft 自身结构

最基础的先验证：

```text
step_id 唯一
depends_on 指向真实 step
不存在 self dependency
不存在 cycle
Plan 不为空
```

例如：

```text
S1 depends_on S2
S2 depends_on S1
```

直接：

```text
INVALID_PLAN
DEPENDENCY_CYCLE
```

这里实现一个几十行的 DAG cycle detection 足够。

不要引入：

```text
NetworkX
LangGraph
Workflow Engine
```

---

# 四、第二层：Capability 是否真实存在

Planner 只能选择 Catalog 中存在的 Capability。

例如 Planner 幻觉：

```text
wealth_customer_analysis
```

但 Catalog 中只有：

```text
directional_insight
customer_targeting
strategy_generation
validation_distribution
tracking_iteration
```

Validator：

```text
UNKNOWN_CAPABILITY
```

直接拒绝。

不能：

```text
“这个名字看起来挺合理，先接受。”
```

这条是防 Planner hallucination 的第一道硬墙。

---

# 五、第三层：Capability 当前是否 Available

Catalog：

```text
tracking_iteration

available = False
reason = 当前未接入经营追踪服务
```

Planner 却生成：

```text
S1 tracking_iteration
```

Validator：

```text
CAPABILITY_UNAVAILABLE
```

拒绝。

虽然 Planner 本应该输出：

```text
NO_FEASIBLE_PLAN
```

但不能把安全性寄托在模型一定做对。

也就是说：

> Planner 的 Prompt 约束是第一道防线，Validator 是最终防线。

---

# 六、第四层：绑定 Capability Version

这一步完全由系统完成。

Planner Draft：

```text
capability_id:
directional_insight
```

Catalog：

```text
directional_insight
version = 1.3
```

正式 Plan：

```text
CapabilityRef(
    capability_id="directional_insight",
    version="1.3",
)
```

所以正式 `PlanStep` 建议从：

```python
capability_id: str
```

升级成：

```python
@dataclass(frozen=True)
class CapabilityRef:
    capability_id: str
    version: str
```

然后：

```python
class PlanStep:
    capability_ref: CapabilityRef
```

这里版本号永远不能由 LLM 输出。

---

# 七、第五层：验证 `expected_outputs`

假设 Catalog：

```text
directional_insight

produces:
- opportunity
- evidence
```

Planner 却生成：

```text
expected_outputs:
- customer
```

Validator 应该：

```text
INVALID_EXPECTED_OUTPUT
```

因为 Planner 不能擅自扩大 Capability 契约。

合法的是：

```text
expected_outputs = ("opportunity",)
```

它是：

```text
Catalog.produces
```

的子集。

---

# 八、这里 T04 暴露出一个需要小修订的地方

我们之前把 Capability 的输入简单建模成：

```python
required_context: tuple[str, ...]
```

但真正做 Validator 时会发现，有些 Capability 不是简单的 AND。

例如 Strategy：

```text
一定需要 Goal

并且可能需要：
具体 customer
或者 candidate_set
```

所以如果简单写：

```text
required_context=("goal", "customer")
```

那么：

```text
Targeting → candidate_set
          ↓
Strategy
```

在结构上反而无法验证。

因此我建议在 T06 正式把 Capability Context Requirement 稍微升级一下。

---

# 九、引入轻量 `ContextRequirement`

不用复杂 DSL。

第一版只支持：

```python
@dataclass(frozen=True)
class ContextRequirement:
    required_all: tuple[str, ...] = ()
    required_any: tuple[str, ...] = ()
```

语义：

```text
required_all
=
全部必须满足

required_any
=
至少一个满足
```

比如 Strategy：

```python
ContextRequirement(
    required_all=("goal",),
    required_any=(
        "customer",
        "candidate_set",
    ),
)
```

Targeting：

```python
ContextRequirement(
    required_all=(
        "goal",
        "opportunity",
    ),
)
```

Insight：

```python
ContextRequirement(
    required_all=("goal",),
)
```

这样当前五类 Capability 已经足够表达。

暂时不要引入：

```text
AND/OR AST
Nested Expression
Context DSL
```

---

# 十、Goal 可以视作永远存在的 Context

因为 Planner 本身就是：

```text
Goal → Plan
```

所以 Validator 初始化时可以：

```text
available_context_types = {"goal"}
```

然后加入：

```text
PlanningContext.available_refs
```

比如：

```text
opp_001
customer_123
```

变成：

```text
goal
opportunity
customer
```

---

# 十一、第六层：验证现有 `input_refs`

Planner 可以引用已经存在的 Context：

```python
input_refs=(
    ContextRef(
        ref_type="opportunity",
        ref_id="opp_001",
    ),
)
```

Validator 必须检查：

```text
opp_001
```

是否真的存在于：

```text
PlanningContext.available_refs
```

否则：

```text
UNKNOWN_CONTEXT_REF
```

拒绝。

这能阻止 Planner 幻觉：

```text
customer_999
opp_abc
```

这样的 ID。

---

# 十二、Planner 不能引用未来实体

例如 Planner 输出：

```text
S1 Insight

S2 Targeting
input_refs = opp_future_001
```

这是非法。

因为：

```text
opp_future_001
```

此刻并不存在。

正确表达应该是：

```text
S2 depends_on = S1
```

然后等 M3 真执行 S1：

```text
CapabilityResult
→ opportunity_id = opp_827
```

再把真实 ID 输入 S2。

所以：

> **已有数据通过 `input_refs` 表达；未来数据通过 `depends_on` 表达。**

这一条非常值得固定。

---

# 十三、第七层：验证 Capability Context Dependency

这是 T06 最核心的一部分。

Validator 需要回答：

> 每个 Step 执行时，它需要的业务 Context 是否真的能够获得？

例如：

```text
PlanningContext:

Goal ✓
Opportunity ✗
Customer ✗
```

Plan：

```text
S1 directional_insight
produces opportunity

S2 customer_targeting
depends_on S1
requires opportunity
```

合法。

因为：

```text
S1
↓
Opportunity
↓
S2
```

---

再比如：

```text
S1 strategy_generation
```

而 Context 中：

```text
Customer ✗
CandidateSet ✗
```

也没有任何 dependency step 能产生。

那么：

```text
UNSATISFIED_CONTEXT
```

拒绝。

---

# 十四、Validator 怎么计算 Context？

不用做复杂 Solver。

直接按照 Plan 的拓扑结构走一遍。

概念上：

```text
Initial Context
    =
Goal
+
PlanningContext existing refs
```

然后对每个 Step：

```text
Step Context
=
Initial Context
+
所有 ancestor steps 的 produces
```

检查：

```text
required_all ⊆ Step Context
```

以及：

```text
required_any 至少命中一个
```

如果满足：

```text
该 Step 合法
```

然后把当前 Capability 的：

```text
produces
```

加入它的后继可用 Context。

---

# 十五、这里一定要看 ancestor，而不是所有前面的 Step

比如：

```text
       S1 Insight
       /        \
      /          \
S2 Targeting A   S3 Other
                     │
                     ▼
                 S4 Strategy
```

如果：

```text
S4 depends_on = S3
```

它不能偷偷使用：

```text
S2
```

产生的 Context。

除非：

```text
S4 depends_on = (S2, S3)
```

这让：

```text
depends_on
```

不仅表达执行顺序，也表达明确的数据可见关系。

这对以后并行执行很重要。

---

# 十六、不要要求 Planner 精确填写所有 `input_refs`

例如：

```text
S1 Insight
→ Opportunity

S2 Targeting depends_on S1
```

这就足够。

Planner 不需要：

```text
S2.input_refs = S1.output.opportunity
```

这种不存在的 Future Reference。

所以：

```text
depends_on
```

负责 future context。

```text
input_refs
```

只负责 already-existing context。

保持非常清楚。

---

# 十七、第八层：Side Effect Validation

这是安全上最重要的一层。

Catalog：

```text
strategy_generation
side_effect_level = READ_ONLY
```

Planner：

```text
side_effect_intent = EXTERNAL_WRITE
```

直接：

```text
SIDE_EFFECT_NOT_SUPPORTED
```

不能允许。

---

而：

```text
validation_distribution
side_effect_level = MAY_WRITE
```

Planner：

```text
side_effect_intent = READ_ONLY
```

合法。

例如只是：

> 看看这个客户当前能不能经营。

---

如果 Planner：

```text
validation_distribution
side_effect_intent = EXTERNAL_WRITE
```

也合法。

但这时候 Validator 必须插入安全控制。

---

# 十八、ControlPoint 必须由 Validator 加

M1 已经有：

```text
RULE_CHECK
USER_CONFIRMATION
```

对于：

```text
EXTERNAL_WRITE
```

Validator 应确定性产生：

```python
control_points=(
    ControlPoint(
        control_type=ControlPointType.RULE_CHECK,
        description="执行外部业务写操作前必须通过适用业务规则校验",
    ),
    ControlPoint(
        control_type=ControlPointType.USER_CONFIRMATION,
        description="改变外部业务状态前需要用户明确确认",
    ),
)
```

Planner 没写：

```text
我需要用户确认
```

也没关系。

系统必须自动加。

这正是当前规范要求的：名单落库、任务创建、客户触达、跨渠道分发、修改状态等外部写操作必须经过规则校验和用户确认。

---

# 十九、Planner 也不能通过伪装绕过 ControlPoint

例如：

```text
capability = validation_distribution
objective = 创建任务
side_effect_intent = READ_ONLY
```

这里存在语义矛盾。

代码很难完全判断自然语言 `objective` 是否暗含写操作。

所以第一版：

```text
side_effect_intent
```

仍然依赖 Planner 正确声明。

但是实际到了 M3 执行真正 Tool 时，还必须有第二层：

> **任何实际 External Write Tool 自己再次要求 Rule Check + Confirmation Token。**

所以安全模型应该是：

```text
Planner intent
        ↓
Plan Validator control point
        ↓
Execution-layer hard enforcement
```

多层防护。

T06 不是唯一安全边界。

---

# 二十、Plan Validator 不调用真实业务规则

注意：

```text
RULE_CHECK ControlPoint
```

不代表 T06 真的去检查：

> 银保客户是不是禁止。

T06 只声明：

> 这个动作执行前必须校验规则。

真正：

```text
Rule Tool
↓
RULE_RESULT
```

发生在 M3/M6。

所以 Plan Validator 不依赖业务规则系统。

---

# 二十一、第九层：Goal Version Binding

正式 Plan 必须绑定：

```python
GoalRef(
    goal_id=goal.goal_id,
    version=goal.version,
)
```

Planner 完全不参与。

这样以后：

```text
Goal v1
→ Plan p1 v1

Goal v2
→ Plan p2 / 新Plan版本
```

都有明确关系。

规范要求 Goal、Plan、Opportunity、任务等都使用稳定 ID 支持回放和审计。

---

# 二十二、Plan ID / Version 怎么生成？

M2 当前只有首次规划。

所以第一版非常简单：

```text
new plan_id
version = 1
```

不要现在为了未来 Replan 做很多复杂逻辑。

M3 到时候再支持：

```text
plan_id = same
version += 1
supersedes_version = ...
```

目前 Contract 已经预留这些字段就够。

---

# 二十三、正式 PlanStep Status

Planner 不输出。

Validator 产生：

```text
PLANNED
```

所以正式：

```python
PlanStep(
    ...,
    status=PlanStepStatus.PLANNED,
)
```

至于：

```text
READY
RUNNING
COMPLETED
```

属于 M3 Execution。

---

# 二十四、Plan Status

正式首次 Plan：

```text
ACTIVE
```

也是 Validator 确定。

Planner 不允许：

```text
plan_status=completed
```

这种输出。

---

# 二十五、Validation Failure 应该结构化

不要只：

```python
raise ValueError("invalid plan")
```

因为 T07 还需要决定：

> 是否把错误反馈给 Planner 进行一次修复。

建议：

```python
class PlanValidationErrorCode(str, Enum):
    EMPTY_PLAN = "empty_plan"
    DUPLICATE_STEP_ID = "duplicate_step_id"
    UNKNOWN_DEPENDENCY = "unknown_dependency"
    DEPENDENCY_CYCLE = "dependency_cycle"

    UNKNOWN_CAPABILITY = "unknown_capability"
    CAPABILITY_UNAVAILABLE = "capability_unavailable"

    INVALID_INPUT_REF = "invalid_input_ref"
    UNSATISFIED_CONTEXT = "unsatisfied_context"

    INVALID_EXPECTED_OUTPUT = "invalid_expected_output"

    SIDE_EFFECT_NOT_SUPPORTED = "side_effect_not_supported"
```

然后：

```python
@dataclass(frozen=True)
class PlanValidationError:
    code: PlanValidationErrorCode
    message: str
    step_id: str | None = None
```

---

# 二十六、这些 Error 不属于 `CapabilityError`

这个边界要保持。

M1：

```text
CapabilityError
```

描述的是：

> Capability 执行发生什么问题。

现在：

```text
PlanValidationError
```

描述的是：

> Planner 提议的计划结构不合法。

二者完全不同。

不要所有 Error 都塞进一个通用：

```text
SystemError
```

---

# 二十七、PlanValidationResult

建议：

```python
class PlanValidationStatus(str, Enum):
    VALID = "valid"
    INVALID = "invalid"


@dataclass(frozen=True)
class PlanValidationResult:
    status: PlanValidationStatus

    plan: Plan | None = None

    errors: tuple[PlanValidationError, ...] = ()
```

不建议：

```text
PARTIAL_VALID
```

Plan 要么：

```text
成为正式 Plan
```

要么：

```text
不能成为正式 Plan
```

保持简单。

---

# 二十八、Validator 遇到错误要一次返回多少？

建议：

> 尽量一次返回所有确定性可发现问题。

例如 Planner 同时：

```text
用了 unknown capability
+
依赖不存在 step
+
expected output 非法
```

不要第一次只返回一个。

可以：

```text
errors=[
    UNKNOWN_CAPABILITY,
    UNKNOWN_DEPENDENCY,
    INVALID_EXPECTED_OUTPUT,
]
```

这样 T07 做一次 Repair 时更高效。

---

# 二十九、但某些校验需要分阶段

例如：

```text
Capability 不存在
```

那么它的：

```text
required_context
produces
```

自然无法继续验证。

所以可以有三层：

```text
Structural Validation
       ↓
Capability Validation
       ↓
Semantic Context Validation
```

前面关键结构坏掉，后面相关校验跳过。

避免产生一堆连锁伪错误。

```text

500W NBEV
```

PlanningContext：

```text
只有 Goal
```

Planner Draft：

```text

expected:
opportunity

S2
customer_targeting
depends_on:
S1
expected:
candidate_set

S3
strategy_generation
```

```text

```

Catalog：



绝不能自动：


用户：

Planner：

```text
EXTERNAL_WRITE
```

Catalog：

```text

```

```text
VALID
```


# 三十五、Plan Validator 到底能“修改”哪些东西？

这条边界建议正式固定。

| 可以确定性补充                 | 不可以改变           |
| ------------------------------ | -------------------- |
| plan_id                        | Capability 选择      |
| plan version                   | Step 依赖            |
| goal_ref                       | objective            |
| capability version             | reason               |
| initial Plan/Step Status       | expected output 语义 |
| 必须的 ControlPoint            | side-effect intent   |
| 正式 step ID（如决定重新生成） | 新增/删除业务 Step   |

也就是说：

> **Validator 可以 enrich，但不能 re-plan。**

---

# 三十六、是否重新生成正式 Step ID？

我倾向第一版：

```text
保留 Planner temporary step_id
```

只要它：

```text
唯一
格式合法
```

即可。

没必要：

```text
s1 → step_a7f349
```

让调试变复杂。

正式 Plan 本身已经有：

```text
plan_id
```

所以：

```text
(plan_id, step_id)
```

足够唯一。

以后持久化真有需求再调整。

---

# 三十七、T06 不做 Planner Repair

这个要留给 T07。

流程：

```text
T05 Planner
      ↓
PlanDraft
      ↓
T06 Validator
      ↓
INVALID
```

T06 到这里结束。

不要：

```text
Validator
↓
自己再次调用 Planner
↓
再验证
```

否则 Component 边界混乱。

T07 BusinessAgent 才负责：


# 三十九、T06 的架构不变量

建议最终锁定：

**PV-01**：Plan Validator 完全确定性，不调用 LLM。
**PV-02**：Validator 只能验证/补全，不得新增、删除或重排业务 Step。
**PV-03**：只有 Catalog 中存在且 available 的 Capability 才能进入正式 Plan。
**PV-04**：Capability Version 由系统绑定，不由 Planner 提供。
**PV-05**：`input_refs` 只能引用当前已经存在的 Context。
**PV-06**：未来 Capability 产物通过 `depends_on` 表达，不允许 Planner 伪造未来实体 ID。
**PV-07**：Capability Required Context 必须来自已有 Context 或祖先 Step 的声明产物。
**PV-08**：平行且无依赖关系的 Step 不得隐式共享未来产物。
**PV-09**：Expected Output 必须属于 Capability Contract。
**PV-10**：Plan 不允许 Dependency Cycle。
**PV-11**：不支持写操作的 Capability 不得声明 External Write。
**PV-12**：External Write 必须由 Validator 强制加入必要 ControlPoint。
**PV-13**：Validator 不执行真实业务规则，仅声明必须经过规则控制。
**PV-14**：Validation Error 与 Capability Error 完全分离。
**PV-15**：正式 Plan 必须绑定当前 Goal ID/version。
