
可以。基于 M1 已经确定的 Contract，我建议把 **M2 定义为“经营超级 Agent 的首次认知与规划阶段”**，范围严格控制在：

> **自然语言经营诉求 → Goal → 动态 Plan**

先不执行 Capability，也先不根据执行结果 Replan。这样 M2 能非常清楚地验证：LLM 是否真的在“理解目标和规划”，而不是把 Demo 五步重新复述一遍。

---

# 一、M2 在整个 Roadmap 中的位置

现在已经有：

```text
M0
Model + Agent Runtime
        ↓
M1
Domain Contract
Goal / Evidence / Opportunity
Capability / Result / Plan
        ↓
M2
Application Layer
自然语言 → Goal → Plan
        ↓
M3
执行 Capability
Result → Replan
```

所以 M2 的核心不是增加新的 Domain Model，而是开始使用 M1。

我建议 M2 最终只实现这条链：

```text
User Request
     │
     ▼
Goal Interpreter
     │
     ▼
Goal Draft
     │
     ├──── Trusted Runtime Context
     │
     ▼
Goal Assembler / Validator
     │
     ▼
Goal
     │
     ▼
Planner
     │
     ├──── Capability Catalog
     │
     ▼
Plan Draft
     │
     ▼
Plan Validator
     │
     ▼
Plan
```

---

# 二、M2 最重要的架构原则

M1 已经决定：

```text
Application
   ├── Domain
   └── Agent → Model
```

M2 就正式开始建立：

```text
src/application/
```

但这里要避免一个误区：

> `Goal Interpreter` 和 `Planner` 是两个 Application Component，不是两个 Agent。

仍然只有一个：

```text
经营超级 Agent
```

未来可以有：

```text
BusinessAgent
  ├── interpret_goal()
  ├── plan()
  ├── execute()      # M3
  └── replan()       # M3
```

内部两次模型调用完全没有问题。

不要因此变成：

```text
GoalAgent
PlannerAgent
InsightAgent
...
```

---

# 三、M2 我建议拆成 8 个任务

| Task   | 目标                                | 核心产物                             |
| ------ | ----------------------------------- | ------------------------------------ |
| M2-T01 | 建立 Application Layer 边界         | RequestContext / 调用入口            |
| M2-T02 | Goal Interpreter                    | Natural Language → 结构化解析结果   |
| M2-T03 | Goal Assembler & Clarification Gate | 解析结果 + Trusted Context → Goal   |
| M2-T04 | Capability Catalog                  | 告诉 Planner 当前“能做什么”        |
| M2-T05 | Planner                             | Goal → Plan Draft                   |
| M2-T06 | Plan Validator                      | 确定性校验 LLM Plan                  |
| M2-T07 | BusinessAgent Facade                | 一次调用完成 Request → Goal → Plan |
| M2-T08 | Dynamic Planning Tests              | 证明没有退化成固定五步               |

这八个任务基本正好组成一次完整 M2。

---

# 四、M2-T01：先建立 Application Request Context

这是 M2 第一件应该做的。

因为自然语言并不是 Goal 的唯一来源。

例如用户说：

> 开门红阶段完成500W NBEV。

但是：

```text
当前渠道 = 个险
当前代理人 = agent_001
```

不是这句话告诉我们的。

它来自可信 Runtime Context。

所以 Application 的入口最好不是：

```python
interpret_goal(text: str)
```

而是类似：

```text
BusinessRequest

user_request
runtime_context
existing_goal(optional)
```

概念上：

```python
@dataclass(frozen=True)
class BusinessRequest:
    user_request: str
    runtime_context: RuntimeContext

    existing_goal_ref: GoalRef | None = None
```

`RuntimeContext` 至少可以承载：

```text
actor_ref
channel_ref
authorization_ref
request_time
```

以后再扩。

---

# 五、非常重要：LLM 不直接生成最终 Goal

这是我认为 M2 最关键的设计决定。

不要：

```text
User text
   ↓
LLM
   ↓
Goal(...)
```

因为最终 Goal 中存在不同权威等级的信息。

应该：

```text
                  User Request
                       │
                       ▼
                     LLM
                       │
                       ▼
              Goal Interpretation
                       │
                       │
Trusted Context ───────┤
                       │
                       ▼
              Deterministic Merge
                       │
                       ▼
                     Goal
```

也就是说：

> **LLM 负责“理解”，代码负责“组装可信 Goal”。**

---

# 六、M2-T02：Goal Interpreter

Goal Interpreter 只解析用户表达中确实存在的语义。

例如：

> 当前处于开门红阶段，希望完成500W NBEV，主推御享分红26和御享金越年金。

LLM 可以提取：

```text
goal_type:
performance_achievement

metric:
NBEV

target:
500万元

time_horizon.raw:
开门红阶段

products:
御享分红26
御享金越年金
```

但它**不能输出**：

```text
actor_ref = agent_001
channel = 个险
```

除非用户真的明确说了，而且即使用户说了，也不能把它直接当作可信身份信息。

---

# 七、所以最好存在一个 Application DTO：GoalInterpretation

这不是 Domain。

只是 LLM 输出的临时结构。

例如：

```text
GoalInterpretation
├─ goal_type
├─ metric
├─ target
├─ time_expression
├─ audience_expression
├─ product_mentions
├─ need_mentions
├─ constraints
├─ explicit_assumptions
└─ unresolved_items
```

它的生命周期非常短：

```text
LLM output
↓
validate
↓
assemble Goal
↓
结束
```

不要把它持久化成核心领域对象。

---

# 八、Goal Interpreter 应采用严格结构化输出

这里不应该让模型输出：

> “我认为这个用户的目标应该是……”

然后我们再解析自然语言。

应该要求：

```json
{
  "goal_type": "...",
  "metric": {},
  "target": {},
  "time_horizon": {},
  "..."
}
```

然后：

```text
LLM JSON
↓
Schema validation
↓
GoalInterpretation
```

模型格式不合法：

```text
第一次输出
↓
validation failed
↓
有限一次 repair
↓
仍失败 → FAILED
```

不要无限：

```text
LLM → 修复 → LLM → 修复 → ...
```

这会把 Application 又变成隐藏 Agent Loop。

---

# 九、这里该用 ChatModel 还是 AgentLoop？

我的建议是：

> **M2 的 Goal Interpreter 和初版 Planner 优先直接建立在 `ChatModel` 契约之上，而不是为了形式统一强行走 AgentLoop。**

原因很简单。

Goal Interpreter 是：

```text
structured inference
```

Planner 第一版也是：

```text
structured inference
```

它们目前不需要：

```text
Tool Call
多 Turn
Tool Execution
```

所以如果：

```text
Goal Interpreter
↓
强行 AgentLoop
↓
其实一个 Tool 都没有
```

意义不大。

而 M3 真正进入：

```text
Plan
↓
Capability Tool
↓
Result
↓
Replan
```

才是 `AgentLoop` 真正发挥作用的地方。

这也保持了：

```text
该简单时简单
```

的原则。

---

# 十、M2-T03：Goal Assembler

Goal Assembler 是纯确定性代码。

职责：

```text
GoalInterpretation
+
RuntimeContext
+
ID/version
+
MissingInformation
+
Assumptions
        ↓
Goal
```

例如：

LLM：

```text
goal_type = performance_achievement
metric = NBEV
target = 500W
time = 开门红阶段
```

Runtime：

```text
actor_ref = agent_001
channel_ref = individual_insurance
```

Assembler：

```text
Goal

original_request = ...
goal_type = ...
metric = ...
target = ...

channel_and_actor:
    actor_ref = agent_001
    channel = individual_insurance

time_horizon:
    raw_expression = 开门红阶段
    start = None
    end = None

missing_information:
    time_horizon.end
```

---

# 十一、来源优先级也应该在这里固定

例如用户说：

> 我现在是银保渠道……

但 RuntimeContext：

```text
channel = individual_insurance
```

最终：

```text
channel_and_actor
```

不能让 LLM/User Text 覆盖 Runtime。

建议固定：

```text
Trusted Runtime Context
        >
Authoritative Business Context
        >
Explicit User Statement
        >
LLM Interpretation
        >
Assumption
```

至少涉及：

```text
身份
渠道
权限
```

必须如此。

如果用户陈述和可信上下文冲突，可以保留：

```text
constraint / unresolved conflict
```

但不能修改真实身份上下文。

---

# 十二、Clarification Gate 放在 Goal Assembler 后面

例如：

> 帮我看看王女士下一步怎么经营。

假设系统中有：

```text
王女士 A
王女士 B
王女士 C
```

这时候如果不明确具体客户：

```text
Strategy
```

可能完全不同。

所以：

```text
Goal
↓
MissingInformation
↓
Clarification Gate
```

判断：

```text
当前是否可以继续规划？
```

不是所有 MissingInformation 都要问。

仍遵守 M1：

```text
missing but non-critical
        ↓
显式 assumption
        ↓
继续

critical / permission / irreversible
        ↓
需要澄清
```

---

# 十三、我建议 M2 不把“澄清”设计成 Capability

至少目前不要。

澄清是：

```text
Application Control
```

不是：

```text
Business Capability
```

所以：

```text
Need Clarification
↓
BusinessAgent 返回问题
```

而不是：

```text
call clarify_user capability
```

否则所有简单交互都会被工具化。

---

# 十四、M2-T04：Capability Catalog

Planner 如果要动态规划，必须知道：

> **系统现在到底有什么能力？**

不能把能力描述永远写死在 Planner Prompt。

因此需要一个非常轻的：

```text
CapabilityCatalog
```

例如：

```text
directional_insight
    description:
    识别与Goal相关的经营问题和机会

customer_targeting
    description:
    基于Opportunity寻找候选经营对象

strategy_generation
    description:
    为具体对象形成经营策略

validation_distribution
    description:
    完成渠道、归属、权限等校验并支持合法执行

tracking_iteration
    description:
    获取经营反馈和Goal进展
```

来源就是 M1：

```text
CapabilityDefinition
```

所以：

```text
Planner
↓
读取 CapabilityDefinition[]
↓
决定本次使用哪些
```

---

# 十五、Capability Catalog 不应该告诉 Planner “顺序”

错误：

```text
directional_insight
order=1

customer_targeting
order=2

strategy_generation
order=3
```

这会让动态规划从第一天就死掉。

Capability Catalog 只描述：

```text
我能解决什么问题
我需要哪些类型输入
我可能产生哪些结果
有什么重要限制
```

不描述：

```text
我是第几步
```

---

# 十六、M2-T05：Planner

Planner 的输入我建议非常清楚：

```text
PlanningContext

Goal

Available Capabilities

Existing confirmed context
```

M2 第一版：

```text
Existing confirmed context
```

甚至可以非常少，因为还没有 Capability Result。

于是：

```text
Goal
+
Capability Catalog
↓
LLM Planner
↓
Plan Draft
```

---

# 十七、Planner Prompt 不应该教模型“五步怎么走”

这是 M2 最大的风险。

错误 Prompt：

> 你需要按照定向洞察、自动圈客、策略生成、校验分发、追踪迭代五步生成计划……

这等于所有 M1 白做。

正确语义应该是：

> 根据 Goal 和当前上下文，从可用 Capability 中选择完成当前需求所需的最少且合适的能力。能力可以跳过、重复、重排；不要调用与当前目标无关的能力。

Capability 的描述通过 Catalog 注入。

---

# 十八、Planner 输出 PlanDraft，而不是直接信任成 Plan

和 Goal 一样：

```text
LLM
↓
PlanDraft
↓
Deterministic Validator
↓
Plan
```

PlanDraft 可以包含：

```text
steps
  - temporary_step_id
  - capability_id
  - objective
  - reason
  - depends_on
  - input refs
  - expected outputs
```

Application 再补：

```text
plan_id
version
goal_ref
created_at
```

所以仍然坚持：

> **LLM 负责语义决策，代码负责身份、可信上下文和结构不变量。**

---

# 十九、M2-T06：Plan Validator

这个组件非常重要，而且完全确定性。

至少校验：

```text
所有 capability_id 必须存在于 Catalog

所有 depends_on 必须存在

不能形成 cycle

step_id 唯一

Plan 必须引用当前 Goal version

不能生成 Tool 名代替 Capability

不能空 Plan，除非 Planner 明确判断 Goal 已满足/无需动作
```

其中：

```text
“养老机会是不是对的”
```

不是 Validator 能判断的。

Validator 只保证：

> **Plan structurally legitimate。**

---

# 二十、是否允许 Planner 生成空 Plan？

我建议允许，但必须有明确语义。

比如用户说：

> 刚才那个目标取消。

或者：

> 我只是问目标是什么意思，不需要经营动作。

未来可能：

```text
Plan steps = ()
```

合法。

但第一版如果用户明确提出经营需求：

```text
steps=()
```

最好视为 Planner 输出异常。

可以先要求：

```text
active Goal → 至少一个 Step
```

等后面真出现空 Plan 场景再放宽。

---

# 二十一、M2-T07：BusinessAgent Facade

到这里才出现真正意义上的：

```text
BusinessAgent
```

但它依然很薄。

第一版大概：

```text
BusinessAgent.handle(request)

    ↓

GoalInterpreter

    ↓

GoalAssembler

    ↓

ClarificationGate
     │
     ├─ need clarification
     │      ↓
     │   return
     │
     └─ continue

    ↓

Planner

    ↓

PlanValidator

    ↓

BusinessAgentResponse
```

注意：

```text
BusinessAgent
```

不是：

```text
又一个新的 AgentLoop 实现
```

它是 Application Orchestrator。

底层仍然：

```text
ChatModel
AgentLoop
```

只有一套。

---

# 二十二、BusinessAgentResponse 第一版也要很简单

例如：

```text
BusinessAgentResponse

goal

plan

clarification

warnings
```

暂时没有：

```text
Opportunity
Customer
Strategy
Task
```

因为这些属于 M3/M4 以后。

# 二十三、M2 最重要的五个测试场景

这次不是再测 dataclass，而是第一次真正测 LLM 行为。

### Case A：经典 Demo

输入：

> 开门红阶段完成500W NBEV，主推两款产品。

预期可能：

```text
Insight
↓
Targeting
↓
Strategy
```

注意：

**可以是这个结果，但测试不能要求必须是五步。**

---

### Case B：具体客户策略

> 帮我看看王女士下一步怎么经营。

预期：

```text
strategy_generation
```

或者如果证据不足：

```text
需要信息获取/洞察
↓
strategy_generation
```

但绝不能机械：

```text
Insight
Targeting
Strategy
Validation
Tracking
```

---

### Case C：只想看经营机会

> 最近有什么值得关注的经营机会？

合理 Plan：

```text
directional_insight
```

只有一步。

这是 M2 非常重要的 Golden Test。

---

### Case D：只做追踪

> 看看我上周安排的客户经营任务现在进展怎么样。

合理 Plan：

```text
tracking_iteration
```

而不是重新圈客。

---

### Case E：信息冲突

用户：

> 我是银保代理人……

Runtime：

```text
channel = individual_insurance
```

Goal 中的可信：

```text
channel_and_actor
=
Runtime Context
```

不能让 LLM 覆盖。

# 二十四、FakeModel 在 M2 会非常重要

你们 M0 已经有：

```text
src/model/fake.py
```

这会让 M2 非常好测。

建议至少准备：

```text
Fake Goal Interpretation

Fake Plan
Invalid JSON
Unknown Capability
Cycle Dependency
Missing Required Field
```

这样大量 Application Tests 都不需要真实 OpenAI 调用。

真实模型只用于：

```text
少量 integration / behaviour evaluation
```

否则测试会：

```text
不稳定
慢
有成本
难以复现
```

---

# 二十五、M2 暂时不要做什么

这个范围要非常严格：

| 暂时不做              | 原因              |
| --------------------- | ----------------- |
| 真正执行 Plan         | M3                |
| Capability Tool 调用  | M3                |
| Result-driven Replan  | M3                |
| Opportunity 真正生成  | M4                |
| 真实圈客              | 后续              |
| Strategy 真实生成     | 后续              |
| 任务创建              | 后续              |
| Tracking 数据接入     | 后续              |
| 多 Agent              | 无需求            |
| Memory / 长期会话系统 | 尚未出现实际需求  |
| Planner Workflow DSL  | 与动态 Agent 冲突 |
| LangGraph             | 当前不需要        |

所以 M2 完成的时候，界面上甚至只需要看到：

```text
我理解你的目标是……

当前计划：

1. 识别与目标相关的经营机会
2. 基于机会寻找候选客户
3. 为优先客户形成经营策略
```

**但是还不真正执行。**

这完全可以接受。

---

# 二十六、M2 的 Exit Criteria

我建议最后只用这几个标准判断是否完成：

```text
Natural Language
        ↓
结构化 Goal
```

稳定。

```text
Goal + Capability Catalog
        ↓
动态 Plan
```

稳定。

并且：

```text
具体客户问题
→ 不做圈客

只看机会
→ 只调用 Insight

只看进展
→ 只调用 Tracking

复杂经营目标
→ 可以组合多个 Capability

Capability 顺序
→ 不由固定编号决定
```

同时：

```text
未知 Capability
cycle dependency
invalid output
```

都能被确定性代码拒绝。

满足这些条件，我才认为 M2 完成。

---

## M2 最核心的架构其实可以压缩成一句话

> **LLM 可以理解 Goal、选择 Capability 和生成 Plan；但最终 Goal 和 Plan 必须经过确定性 Application 层组装与验证，LLM 不拥有身份、规则和结构不变量的最终解释权。**

因此下一步最适合从 **M2-T01 + T02** 开始：先把 `BusinessRequest / RuntimeContext / GoalInterpretation` 三者之间的关系设计清楚，再决定 Goal Interpreter 的 Prompt 和结构化输出 Schema。这样 M2 不会一上来就变成“写一个巨大 Planner Prompt”。
