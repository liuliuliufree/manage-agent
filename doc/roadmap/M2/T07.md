
进入 **M2-T07：BusinessAgent Facade**。这一阶段不再新增“智能能力”，而是把前面已经确定的组件组合成一个真正可调用的智慧经营 Application。

一句话定义：

> **BusinessAgent 是智慧经营超级 Agent 的 Application Facade：它负责组织 Goal 理解、可信组装、澄清判断、动态规划、计划校验和有限修复，但 M2 阶段绝不执行 Capability。**

---

# 一、先明确 BusinessAgent 和 AgentLoop 的区别

现在系统里会第一次同时存在两个名字里带 Agent 的东西：

```text
BusinessAgent
```

和：

```text
AgentLoop
```

必须避免职责混淆。

```text
BusinessAgent
Application Layer
────────────────────
理解经营请求
形成 Goal
判断是否澄清
形成 Plan
返回业务结果


AgentLoop
Runtime Layer
────────────────────
模型多 Turn
Tool Calling
Tool Execution
Trace / Turn
终止控制
```

M2 阶段甚至：

> **BusinessAgent 可以完全不调用 AgentLoop。**

它内部的：

```text
GoalInterpreter → ChatModel

Planner → ChatModel
```

已经足够。

到了 M3：

```text
BusinessAgent
    ↓
正式 Plan
    ↓
AgentLoop
    ↓
Capability Tool
```

两者才真正接起来。

# 三、这里需要先修正 T01 的一个工程问题

T01 中我们设计：

```python
BusinessRequest(
    user_request=...,
    existing_goal_ref=...
)
```

但现在真正运行到 T07 会发现：

> **只有 `existing_goal_ref` 不够，因为当前 M2 明确还不做数据库/Repository。**

例如：

```text
existing_goal_ref = goal_001 v1
```

GoalInterpreter 和 GoalAssembler 实际需要：

```text
Goal 001 v1
```

的内容。

但我们现在没有：

```text
GoalRepository
```

也不应该为了 M2 临时造一个。

所以我建议 T07 采用：

```python
BusinessAgent.handle(
    request,
    context,
)
```

其中新增一个 Application DTO：

```python
@dataclass(frozen=True)
class BusinessAgentContext:
    existing_goal: Goal | None = None
    planning_context: PlanningContext | None = None
```

这样：

```text
BusinessRequest
=
当前这次用户请求

BusinessAgentContext
=
调用方已经解析好的当前业务状态
```

---

# 四、为什么这比 Repository 更合理

M2 当前重点是：

```text
理解
+
规划
```

不是：

```text
持久化
状态存储
数据库
```

所以现在：

```text
调用方
    ↓
resolve existing Goal
    ↓
BusinessAgentContext
    ↓
BusinessAgent
```

即可。

未来如果有：

```text
GoalRepository
ConversationStateStore
```

也只是调用 BusinessAgent 之前进行解析。

BusinessAgent 自身不需要因此改变。

# 五、existing_goal_ref 和 actual Goal 必须一致

如果：

```text
request.existing_goal_ref
=
goal_001 v2
```

但是：

```text
context.existing_goal
=
goal_001 v1
```

这是 Application 调用错误。

BusinessAgent 应直接：

```text
INVALID_REQUEST
```

不能：

```text
“差一个版本而已，先用 v1。”
```

同理：

```text
existing_goal_ref != None
```

但：

```text
existing_goal = None
```

也应该明确失败。

否则 Goal Patch 有可能应用在错误版本上。

# 六、为什么还需要 `planning_context`

因为 T05 Planner 已经支持：

```text
已有 Opportunity
已有 Customer
已有 Evidence
```

例如：

> 围绕刚才那个养老机会找客户。

调用方可能已经知道：

```python
PlanningContext(
    available_refs=(
        ContextRef(
            ref_type="opportunity",
            ref_id="opp_001",
        ),
    )
)
```

BusinessAgent 不应该自己去数据库找：

```text
opp_001
```

当前 M2 只消费调用方给它的：

```text
PlanningContext
```

以后 M3 再逐步构建运行状态。

# 七、BusinessAgent 的依赖应该全部显式注入

我建议它大概持有：

```python
        ...
```

注意没有：

```text
ChatModel

RuleEngine
```

为什么？

因为：

```text
GoalInterpreter
```

自己知道如何调用 ChatModel。

```text

```

自己知道如何调用 ChatModel。

BusinessAgent 只负责编排 Application Component。

# 八、BusinessAgent 不需要继承任何 Agent 基类

不要：

```python
class BusinessAgent(AgentLoop):
```

也不要：

```python
class BusinessAgent(BaseAgent):
```

除非当前项目本身已经有非常明确且合适的抽象。

当前架构语义上：

```text
BusinessAgent
```

只是一个 Application Facade / Orchestrator。

不需要为了名字叫 Agent 就强行继承 Agent Runtime。

# 九、BusinessAgent Response 需要统一

我建议定义四种稳定结果：

```python
class BusinessAgentStatus(str, Enum):
    PLAN_READY = "plan_ready"
    CLARIFICATION_REQUIRED = "clarification_required"
    NO_FEASIBLE_PLAN = "no_feasible_plan"
    FAILED = "failed"
```

基本覆盖 M2 所有出口。

# 十、`PLAN_READY`

这是 M2 的正常成功路径：

```text
User
 ↓
Goal
 ↓
Plan
```

返回：

```python
BusinessAgentResponse(
    request_id="req_001",
    status=BusinessAgentStatus.PLAN_READY,

    goal=goal,
    plan=plan,
)
```

此时表达的是：

> **系统已经理解 Goal，并形成了合法 Plan。**

但不要说：

> “经营任务已经完成。”

因为 M2 根本还没有执行 Plan。

# 十一、`CLARIFICATION_REQUIRED`

例如：

> 这个月业绩做到500W。

T03 判断：

```text
metric 不明确
required_before_planning=True
```

BusinessAgent 必须在这里直接停止：

```text
Goal
↓
ClarificationGate
↓
CLARIFICATION_REQUIRED
```

绝对不能继续：

```text
Planner
```

否则 Planner 只能猜：

```text
500W NBEV？
500W保费？
```

# 十二、一个非常重要的设计：Goal 可以有效，但暂时不 Planning-ready

也就是说：

```text
Goal
```

不必因为：

```text

```

存在就成为非法对象。

例如：

```text

target = 500W
metric = None

missing_information:
metric 未明确
```

这个 Goal 依然是：

> **一个合法的、但尚不足以规划的 Domain Artifact。**

于是 BusinessAgent 可以返回：

```text
CLARIFICATION_REQUIRED

```

用户随后回答：

> NBEV。

下一次：

```text
BusinessRequest:
"NBEV"

existing_goal_ref:
goal_001 v1
```

```text
metric = SET NBEV
```

T03：

```text
Goal 001 v2
```

然后：

```text
ClarificationGate
→ CONTINUE
```

这套链非常自然。

# 十四、`NO_FEASIBLE_PLAN`

这是 Planner 明确判断：

> Goal 很清楚，但当前 Capability Catalog 无法完成。

例如：

用户：

> 看一下之前经营任务进展。

Goal 合法。

但：

```text
tracking_iteration.available = False
```

Planner：

```text
NO_FEASIBLE_PLAN
```

BusinessAgent 应直接返回：

```python
BusinessAgentResponse(
    status=BusinessAgentStatus.NO_FEASIBLE_PLAN,
    goal=goal,
    plan=None,
    message=(
        "当前经营追踪能力尚不可用，"
        "现有能力无法可靠完成该请求。"
    ),
)
```

这里不要进入：

```text
PlanValidator
```

因为没有 PlanDraft。

# 十五、`FAILED` 应该只代表系统处理失败

例如：

```text
GoalInterpreter 模型调用失败

Planner 输出连续两次无法解析

PlanDraft 第一次非法
repair 后仍然非法

Application 输入上下文版本不匹配
```

这些属于：

```text
FAILED
```

不要和：

```text
NO_FEASIBLE_PLAN
```

混。

这个设计延续了之前所有状态设计：

```text
业务没有结果
≠
系统坏了
```

# 十六、建议再定义一个 ApplicationFailure

不要把：

```text
CapabilityError
```

拿过来用。

Capability 甚至还没执行。

建议：

```python
class ApplicationFailureStage(str, Enum):
    REQUEST_VALIDATION = "request_validation"
    GOAL_INTERPRETATION = "goal_interpretation"
    GOAL_ASSEMBLY = "goal_assembly"
    PLANNING = "planning"
    PLAN_VALIDATION = "plan_validation"
```

然后：

```python
@dataclass(frozen=True)
class ApplicationFailure:

    code: str
    message: str
    retryable: bool = False
```

比如：

```text

code:
PLAN_REPAIR_EXHAUSTED
```

# 十八、BusinessAgent 的主流程

第一版伪代码可以非常接近：

```python
def handle(
    request: BusinessRequest,
    context: BusinessAgentContext,
) -> BusinessAgentResponse:

    validate_request_context(request, context)

    interpretation = goal_interpreter.interpret(
        user_request=request.user_request,
        existing_goal=context.existing_goal,
    )

    goal = goal_assembler.assemble(
        request=request,
        interpretation=interpretation,
        existing_goal=context.existing_goal,
    )

    clarification = clarification_gate.evaluate(goal)

    if clarification.requires_clarification:
        return clarification_response(...)

    planning_context = build_planning_context(
        goal=goal,
        existing=context.planning_context,
    )

    decision = planner.plan(
        goal=goal,
        context=planning_context,
        catalog=capability_catalog,
    )

    if decision.is_no_feasible_plan:
        return no_feasible_plan_response(...)

    validation = plan_validator.validate(
        draft=decision.plan_draft,
        goal=goal,
        context=planning_context,
        catalog=capability_catalog,
    )

    if validation.valid:
        return plan_ready_response(...)

    repaired_draft = planner.repair(...)

    repaired_validation = plan_validator.validate(...)

    if repaired_validation.valid:
        return plan_ready_response(...)

    return plan_validation_failed_response(...)
```

这基本就是 T07。

# 十九、这里最关键的是“bounded repair”

Plan Validator 发现：

```text
UNKNOWN_CAPABILITY
```

或者：

```text
UNSATISFIED_CONTEXT
```

不代表第一次 Planner 输出错误后立刻整个请求失败。

可以允许：

> **一次语义 Repair。**

流程：

```text
Planner Draft v1
      ↓
Validator
      ↓
INVALID
      ↓
Planner Repair
      ↓
Draft v2
      ↓
Validator
```

如果：

```text
VALID
```

继续。

如果：

```text
INVALID
```

停止：

```text
FAILED
PLAN_REPAIR_EXHAUSTED
```

不要：

```text
while invalid:
    call_llm_again()
```

无限修。

---

# 二十、为什么只建议 Repair 一次

因为如果模型已经收到：

```text
Goal
Context
Catalog
Validation Errors
Original Draft
```

仍然无法产生一个合法 Plan：

> 继续调用同一个模型很可能只是反复震荡。

这时候应该暴露问题，而不是烧很多 Turn 把错误藏起来。

---

# 二十一、Repair 到底给 Planner 什么

只需要：

```text
Goal

PlanningContext

CapabilityCatalog

Original PlanDraft

PlanValidationError[]
```

例如：

```text
Validation errors:

step s1:
UNKNOWN_CAPABILITY
"customer_value_prediction" does not exist.

Available capabilities:
...
```

然后要求：

> 在保持原 Goal 不变的情况下修正 PlanDraft。

不要给：

```text
Stack trace
内部异常
Validator代码
完整系统Prompt
```

---

# 二十二、Repair 也不能改变 Goal

非常重要。

错误：

```text
Plan 无法完成
↓
Planner Repair
↓
顺手把500W改成300W
```

不允许。

Planner 只能改：

```text
PlanDraft
```

不能修改：

```text
Goal
```

如果发现：

> 当前 Goal 本身有问题。

应该下一轮：

```text
Clarification / Goal Update
```

而不是 Planner 偷改目标。

---

# 二十三、Goal Interpreter 自己的 Structured Output Repair 怎么算？

这里其实有两个不同层级的 repair。

### 类型 A：格式 Repair

例如：

```text
GoalInterpreter
返回非法JSON
```

GoalInterpreter 内部可以：

```text
第一次 parse fail
↓
一次 schema repair
↓
仍失败 → InterpreterError
```

Planner 同理。

这属于：

```text
Component-local structured output repair
```

---

### 类型 B：Plan Semantic Repair

JSON 完全合法：

```text
capability_id = abc_xyz
```

但系统里不存在。

这是：

```text
PlanValidator semantic failure
```

由 BusinessAgent 触发一次：

```text
Planner Repair
```

这两种不要混。

---

# 二十四、所以最多会调用 Planner 几次？

正常：

```text
1 次
```

Semantic Invalid：

```text
第一次 Plan
+
一次 Repair
=
2 次
```

不要第三次。

Planner 内部如果第一次 JSON 格式错误，内部可以做一次格式 repair，但这是另一个维度。

---

# 二十五、T07 不要做 Replan

名字很像，但这里必须区别：

```text
Repair
```

和：

```text
Replan
```

### Repair

发生在：

```text
Plan 还没有正式成立
```

因为 Planner Draft 不合法。

目标是：

> 让一个提议满足 Contract。

---

### Replan

发生在 M3：

```text
Plan 已经正式执行
↓
CapabilityResult
NO_RESULT / BLOCKED / FAILED...
↓
重新决定后续业务路径
```

它是真正的经营动态调整。

所以：

```text
M2 = Plan Repair
M3 = Business Replan
```

不要提前混。

---

# 二十六、BusinessAgent 是否应该把 Plan Validation Errors 返回用户？

通常：

> 不应该。

例如：

```text
DEPENDENCY_CYCLE
UNKNOWN_CAPABILITY
```

这些是系统内部规划错误。

用户没有必要看到：

> “模型生成了循环 DAG。”

最终用户可以看到：

```text
“当前无法形成可靠的经营计划，请重试。”
```

详细 Validation Error：

```text
Trace / Log
```

保留。

---

# 二十七、哪些内容可以进入 warnings？

例如：

```text
开门红具体结束日期尚未确认
```

但：

```text
ClarificationGate = CONTINUE
```

这可以进入：

```text
warnings
```

最终前端可以展示：

> 当前计划基于“开门红阶段”的原始时间表达，尚未解析精确截止日期。

再比如：

```text
Assumption:
暂以全部可经营客户作为分析范围
```

也可以作为 warning/assumption 展示。

这样用户能够纠正。

---

# 二十八、不要把内部 Validation Error 当 warning

例如：

```text
第一次 Planner 用了 unknown capability
第二次 Repair 成功
```

最终响应：

```text
PLAN_READY
```

用户没有必要看到：

> “Planner 第一版计划犯了错。”

这属于：

```text
Trace
```

而不是业务 warning。

---

# 二十九、BusinessAgent 现在已经可以成为未来唯一超级 Agent 入口

未来 UI/API 不应该直接分别调用：

```text
GoalInterpreter
Planner
PlanValidator
```

而是：

```text
UI / API
    ↓
BusinessAgent.handle()
```

Application 内部如何拆组件是实现细节。

以后 M3：

```text
BusinessAgent.handle()
```

还可以逐渐支持：

```text
Goal
↓
Plan
↓
Execution
↓
Result
↓
Replan
```

对上层 API 来说入口可以保持稳定。

# 三十、但不要现在强行定义一个巨大 `run()` 方法

M2 第一版：

```python

```

只负责：

```text

```

```text

```

是否扩展，还是：


现在不要提前设计完整生命周期。

```text
tracking_iteration.available=False
```

Planner：

```text
NO_FEASIBLE_PLAN
```

BusinessAgent：

```text
status:
NO_FEASIBLE_PLAN

goal:
合法

plan:
None

message:
当前经营追踪能力尚未接入，暂时无法可靠回答该请求。
```

这不是：

```text
FAILED
```

系统没有坏。

# 三十六、T07 测试应该重点测 orchestration

这次不是再测 Goal/Plan Contract，而是：

```text
组件有没有被正确调用？
该停止的时候有没有停止？
Repair 有没有上限？
```

我建议至少覆盖：

| 场景                             | 核心断言                                    |
| -------------------------------- | ------------------------------------------- |
| 正常 Goal + 合法 Draft           | `PLAN_READY`                              |
| Goal 需要澄清                    | Planner 0 次调用                            |
| Planner NO_FEASIBLE              | Validator 0 次调用                          |
| Draft 第一次合法                 | Planner 1 次                                |
| Draft invalid → repair valid    | Planner 2 次、Validator 2 次                |
| Draft invalid → repair invalid  | `FAILED`，不允许第三次 Planner            |
| GoalInterpreter 最终失败         | 后续组件均不调用                            |
| existing_goal_ref/version 不匹配 | 模型 0 次调用，直接失败                     |
| Goal Patch                       | 新 Goal version 被传给 Planner              |
| Plan Ready                       | Plan.goal_ref 必须对应刚生成的 Goal version |

这张表基本就是 T07 的自动化验收。

# 三十七、尤其要测试“短路”

这是 Application Orchestration 最容易写错的地方。

例如：

```text
Clarification required
```

必须确保：

```python
planner.call_count == 0
plan_validator.call_count == 0
```

同样：

```text
NO_FEASIBLE_PLAN
```

应该：

```python
plan_validator.call_count == 0
```

不要虽然最后返回正确，但背后还白调用了一堆模型。

# 三十八、Trace 怎么处理？

M0 已经有 Runtime Trace。

M2 当前没有通过 AgentLoop 运行，所以可以暂时只做 Application Log：

```text
request_id
goal_id/version
planner attempt count
final status
```

不要为了 M2 强行让 Application 复用：

```text
Agent Trace/Turn
```

因为它们目前描述的是 Agent Runtime。

未来 M3 BusinessAgent 真正进入 AgentLoop 后，再建立：

```text
request_id
goal_id
plan_id
trace_id
```

关联。

# 三十九、BusinessAgent 不应返回 LLM 原始内容

最终：

```text
GoalInterpretation raw JSON
Planner raw JSON
Repair prompt
```

都属于内部实现。

正式 Response 只返回：

```text
Goal
Plan
Clarification
用户可理解的信息
```

这样上层不依赖模型中间格式。

# 四十、T07 建议锁定的不变量

| 编号  | BusinessAgent 不变量                                                |
| ----- | ------------------------------------------------------------------- |
| BA-01 | BusinessAgent 是 Application Orchestrator，不是第二套 Agent Runtime |
| BA-02 | M2 阶段 BusinessAgent 不执行任何 Capability                         |
| BA-03 | GoalInterpreter、Planner 等组件通过依赖注入组合                     |
| BA-04 | existing Goal 由调用方解析提供，M2 不新增 Repository                |
| BA-05 | `existing_goal_ref` 与实际 Goal 必须严格匹配                      |
| BA-06 | Clarification Required 时必须立即短路，不调用 Planner               |
| BA-07 | NO_FEASIBLE_PLAN 是正常业务结果，不是系统失败                       |
| BA-08 | PlanDraft 必须经过 PlanValidator 才能成为正式 Plan                  |
| BA-09 | Semantic Plan Repair 最多一次                                       |
| BA-10 | Repair 只能修改 PlanDraft，不得修改 Goal                            |
| BA-11 | Repair 与 M3 Replan 是不同概念                                      |
| BA-12 | 内部 Plan Validation Error 不直接暴露给业务用户                     |
| BA-13 | 最终 Plan 必须绑定本轮最新 Goal version                             |
| BA-14 | Response 不暴露 Prompt、Raw Model Output 或内部推理文本             |
| BA-15 | BusinessAgent 是未来 UI/API 的统一智慧经营入口                      |

# 四十一、T07 完成之后，M2 第一次可以完整运行

此时你已经拥有真正可以 Demo 的：

```text
用户：
“最近有哪些经营机会值得关注？”

               ↓

        BusinessAgent

               ↓

Goal:
发现近期值得关注的经营机会

               ↓

Plan:
执行定向洞察

               ↓

“我已理解你的经营目标。
接下来我准备先识别与当前目标相关、
且有数据依据的经营机会。”
```

虽然它还**没有执行洞察**，但已经证明三件很关键的事：

```text
自然语言真的形成了结构化 Goal

Plan 真的是运行时动态产生

系统没有依赖固定五步 Workflow
```

因此 T07 做完后，M2 实际只剩 **T08 Dynamic Planning / Behaviour Evaluation**：不再设计新组件，而是用一组针对 Planner 和整个 `BusinessAgent` 的跨场景测试，主动攻击它是否又悄悄学成了“固定五步”，并正式定义 M2 的 Release Gate。
