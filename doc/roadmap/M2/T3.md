
进入 **M2-T03：Goal Assembler + Clarification Gate**。

这一阶段我建议把目标压缩成一句话：

> **把 T02 得到的“LLM 对用户表达的解释”，与可信 Runtime Context、已有 Goal 确定性合并，形成系统真正认可的 Domain `Goal`；同时判断哪些信息缺失必须现在澄清，哪些可以带着明确假设继续规划。**

这里开始第一次出现“系统相信什么”的问题，所以 T03 必须以**确定性代码为主，LLM 不再拥有最终裁决权**。

---

# 一、T03 在链路中的位置

现在已经有两条完全不同的信息流：

```text
用户自然语言
    ↓
GoalInterpreter
    ↓
GoalInterpretation
```

以及：

```text
登录 / 系统环境
    ↓
RuntimeContext
```

如果是修改已有目标，还有第三条：

```text
Existing Goal vN
```

T03 才第一次把三者汇合：

```text
GoalInterpretation ───────┐
                          │
RuntimeContext ───────────┼──→ GoalAssembler ──→ Goal Candidate
                          │
Existing Goal ────────────┘
                                      │
                                      ▼
                              Clarification Gate
                                 /           \
                                /             \
                         可以继续           必须澄清
                            │                  │
                            ▼                  ▼
                          Goal          ClarificationRequest
```

---

# 二、首先确定一个非常关键的原则

**GoalAssembler 不是另一次 LLM 调用。**

不要：

```text
Interpretation
+
RuntimeContext
+
Existing Goal
    ↓
LLM
    ↓
Final Goal
```

这样等于又把刚刚建立的信任边界交回模型。

正确应该是：

```text
Interpretation
+
Trusted Context
+
Existing Goal
        ↓
Deterministic Merge Rules
        ↓
Goal
```

也就是说：

> T02 负责理解语义，T03 负责确定事实与状态。

---

# 三、T03 我建议拆成两个 Application Component

不是两个 Agent。

```text
GoalAssembler
```

负责：

> 根据明确优先级形成 Goal。

```text
ClarificationGate
```

负责：

> 判断这个 Goal 当前是否已经足够进入 Planner。

概念上：

```python
goal = goal_assembler.assemble(
    request=request,
    interpretation=interpretation,
    existing_goal=existing_goal,
)

decision = clarification_gate.evaluate(goal)
```

不要现在再造：

```text
GoalService
GoalManager
GoalEngine
GoalWorkflow
```

两个组件就够。

---

# 四、GoalAssembler 第一件事：明确来源优先级

这个顺序非常重要。

对于同一个字段，并不是“最后出现的值覆盖之前的值”。

我建议至少分成四类来源：

```text
1. Trusted Runtime Context
2. Existing Confirmed Goal
3. Explicit User Update
4. Assumption
```

但它们并不是所有字段都用同一优先级。

核心思想是：

> **不同字段有不同 authority。**

---

# 五、身份和渠道类字段：Runtime Context 优先级最高

例如：

```text
actor_ref
channel_ref
authorization_ref
```

来源优先级：

```text
Trusted Runtime Context
        >
其他任何来源
```

即使用户说：

> “我是银保渠道。”

而系统可信上下文：

```text
channel_ref = individual_insurance
```

最终 Goal：

```text
channel_ref = individual_insurance
```

同时可以记录：

```text
用户表达与可信运行上下文存在冲突
```

但不能：

```text
channel_ref = bancassurance
```

规范要求渠道、人员、授权以及规则判断由确定性来源处理，Agent 不能自行覆盖。:chatgpt-content-reference{index="0"}

---

# 六、用户目标字段：Explicit User Update 优先

例如：

```text
target
product_or_need_context
audience preference
time expression
constraints
```

如果已有 Goal：

```text
target = 500W
```

用户明确：

> “改成400W。”

那么：

```text
Explicit User Update
        >
Existing Goal
```

结果：

```text
Goal v2.target = 400W
```

---

# 七、未提及 ≠ 清除

这就要利用 T02 的 Patch Semantics。

假设 Goal v1：

```text
metric = NBEV
target = 500W
products = A, B
```

用户说：

> 改成400W。

Interpretation：

```text
target = SET 400W

metric = None
products = None
```

这里：

```text
None
```

意思是：

> 本轮没有涉及。

所以最终：

```text
metric = NBEV        # 保留
target = 400W        # 更新
products = A, B      # 保留
```

而不是：

```text
metric = None
products = ()
```

---

# 八、CLEAR 必须真的清除

如果用户说：

> 不限定产品了。

T02：

```text
product_mentions:
    action = CLEAR
```

Assembler：

```text
Goal v1:
products = A, B

        ↓

Goal v2:
product_or_need_context.products = ()
```

这和：

```text
用户本轮没提产品
```

必须是两种完全不同的行为。

---

# 九、我建议把 Merge Rule 做成明确代码，而不是大量 if 散落

不过暂时也不用搞复杂规则引擎。

可以很简单地抽一个：

```python
def apply_update(
    current_value,
    update: FieldUpdate | None,
):
    if update is None:
        return current_value

    if update.action == UpdateAction.SET:
        return update.value

    if update.action == UpdateAction.CLEAR:
        return None
```

对于集合：

```python
CLEAR → ()
```

对于可选标量：

```python
CLEAR → None
```

这已经足够。

---

# 十、New Goal 和 Existing Goal Update 应该统一处理

我建议不要写两套逻辑：

```text
create_goal()
update_goal()
```

大量重复。

概念上可以理解为：

### 新建

```text
Base Goal = empty
+
GoalInterpretation
+
RuntimeContext
```

### 修改

```text
Base Goal = existing Goal
+
GoalInterpretation Patch
+
RuntimeContext refresh
```

所以核心：

```text
base
+ patch
+ trusted context
→ new Goal
```

一致。

---

# 十一、Goal ID / Version 由 Assembler 管，不由 LLM 管

规则非常简单。

### 新 Goal

```text
existing_goal = None
```

则：

```text
new goal_id
version = 1
```

### 修改已有 Goal

```text
existing_goal = goal_001 v3
```

则：

```text
goal_id = goal_001
version = 4
```

LLM 永远不生成：

```text
goal_id
version
```

---

# 十二、`original_request` 怎么处理修改型 Goal？

这是值得认真处理的。

M1 中我们说：

```text
original_request
```

必须保留。

但 Goal v2 如果用户只是说：

> 改成400W。

如果简单写：

```text
original_request = "改成400W"
```

会丢失最初上下文。

如果继续保留：

```text
original_request = "开门红完成500W..."
```

又无法体现当前修改。

所以这里建议稍微修正 Goal Contract：

```text
original_request
```

表示：

> 创建该 Goal 时的原始诉求。

再增加一个非常轻的：

```text
latest_user_request
```

或者更推荐在 Application/Audit 层通过：

```text
source_request_id
```

关联具体请求。

为了不污染 M1 Domain，我更倾向：

```text
Goal.original_request
```

继续不变。

Goal v2 额外关联：

```text
source_request_id
```

如果 M1 当前没有这个字段，可以现在评估是否值得加入：

```python
source_request_id: str | None
```

我认为值得。

这样：

```text
Goal 001 v1
original_request = "完成500W..."
source_request_id = req_001

Goal 001 v2
original_request = "完成500W..."
source_request_id = req_009
```

审计时通过 request 找到：

> “改成400W。”

# 十三、GoalAssembler 不负责解析外部业务知识

例如用户说：

> 开门红期间。

Assembler 看到：

```text
time_expression="开门红期间"
```

不应该：

```text
start_at = ...
end_at = ...
```

除非输入中已经有可信的：

```text
BusinessCalendarContext
```

当前 T03 还没有。

所以仍然：

```text
TimeHorizon(
    raw_expression="开门红期间",
    start_at=None,
    end_at=None,
)
```

然后形成：

```text
MissingInformation
```

这继续贯彻“无来源内容不得作为事实”的原则。:chatgpt-content-reference{index="1"}

---

# 十四、Product mention 也不能在 Assembler 中凭字符串成为 authoritative product ref

T02：

```text
product_mentions = ["御享分红26"]
```

T03 第一版可以暂时：

```text
product_refs=("御享分红26",)
```

但必须把它理解为：

> user-provided product reference / raw mention

而不是：

> 已确认产品主数据 ID。

更理想的长期路径：

```text
“御享分红26”
      ↓
Entity Resolution Tool
      ↓
product_id + version
```

但这不是 T03 当前范围。

---

# 十五、MissingInformation 在 T03 才真正产生

这是 T02 `UnresolvedItem` 和 T03 `MissingInformation` 的分水岭。

GoalAssembler 应综合：

```text
Interpretation unresolved
+
RuntimeContext missing
+
Goal required semantics
+
field conflicts
```

生成：

```text
MissingInformation[]
```

例如：

用户：

> “业绩做到500W。”

T02：

```text
UnresolvedItem(
    field="metric",
    reason="业绩指标不明确"
)
```

T03：

```text
MissingInformation(
    field="metric",
    reason="用户表达中的‘业绩’无法确定为具体业务指标",
    impact="无法准确计算目标完成进度及后续机会贡献",
    required_before_execution=...
)
```

注意：

> T02 描述语言理解问题。

> T03 描述业务 Goal 缺口。

---

# 十六、并不是所有 unresolved 都一定变 MissingInformation

比如：

用户说：

> 最近帮我看看有什么经营机会。

“最近”到底是：

```text
7天
30天
90天
```

可能 unresolved。

但 Planner 完全可以：

```text
明确采用默认最近30天作为假设
```

或者之后 Capability 使用平台默认时间窗口。

所以可能转成：

```text
Assumption
```

而不是：

```text
必须澄清
```

这就是 T03 第二个重要工作：**Missing vs Assumption 的分类。**

---

# 十七、什么时候用 Assumption？

建议原则是：

```text
信息缺失
+
采用合理默认值
+
不会导致明显不同的经营方向
+
不会导致越权
+
不会触发不可逆外部动作
```

才允许：

```text
Assumption
```

例如：

> “最近有哪些经营机会？”

可以假设：

```text
recent = 平台默认分析周期
```

只要：

```text
revisable = true
```

并在 Plan/UI 中明确。

规范允许对于不会导致明显不同行动、越权或不可逆执行的信息，用明确标注假设继续规划。:chatgpt-content-reference{index="2"}

---

# 十八、什么情况绝不能假设？

至少三大类。

### 1. 身份 / 权限

不能假设：

```text
actor = 当前代理人
```

如果 RuntimeContext 根本没有 actor。

---

### 2. 关键对象身份

例如：

> 帮我看看王女士。

系统中有三个王女士。

不能随机选一个。

---

### 3. 不可逆执行所需信息

例如：

```text
要给客户创建经营任务
```

但：

```text
channel
ownership
permission
```

不明确。

绝不能：

```text
先假设通过。
```

---

# 十九、Clarification Gate 就负责判断这一点

建议输出不是 bool。

而是明确 Decision：

```python
class ClarificationDecision(str, Enum):
    CONTINUE = "continue"
    REQUIRE_CLARIFICATION = "require_clarification"
```

配：

```python
@dataclass(frozen=True)
class ClarificationResult:
    decision: ClarificationDecision

    blocking_items: tuple[MissingInformation, ...] = ()
    non_blocking_items: tuple[MissingInformation, ...] = ()
```

以后如果需要：

```text
warnings
```

再加。

---

# 二十、Clarification Gate 第一版规则可以非常简单

例如：

```python
blocking = tuple(
    item
    for item in goal.missing_information
    if item.required_before_execution
)
```

但不能只靠：

```text
required_before_execution
```

因为当前阶段还没执行。

比如：

```text
metric 不明确
```

对于：

> 帮我发现经营机会

可能不阻塞 Planner。

对于：

> 我要完成500W“业绩”

则很可能会导致完全不同的规划，因此应该现在问。

所以建议 `MissingInformation` 再增加一个概念：

```text
required_before_planning
```

这值得现在修订 M1。

---

# 二十一、我建议 MissingInformation 升级为两个 Gate

当前：

```python
required_before_execution: bool
```

建议改成：

```python
@dataclass(frozen=True)
class MissingInformation:
    field: str
    reason: str
    impact: str | None = None

    required_before_planning: bool = False
    required_before_execution: bool = False
```

这会很有价值。

例如：

### 指标不明确

```text
required_before_planning = True
```

因为：

```text
NBEV
保费
客户数
```

会明显改变经营规划。

---

### 开门红具体截止日期未知

可能：

```text
required_before_planning = False
required_before_execution = False
```

第一轮可以先规划。

---

### actor_ref 缺失

只读洞察时可能：

```text
required_before_planning = False
```

但：

```text
required_before_execution = True
```

---

# 二十二、不过 `required_before_execution` 不等于现在可以忽略

Planner 必须看得到这些缺失。

例如：

```text
actor missing
```

Plan 可以：

```text
Insight
```

但不应该规划：

```text
task_creation
```

绕过这个缺失。

后面 M2-T05 Planner Context 应该携带：

```text
missing_information
assumptions
```

所以 Planner 可以主动避免越界路径。

---

# 二十三、Clarification Gate 第一版判断流程

概念上：

```text
Goal Candidate
      ↓
有没有 required_before_planning？
      │
   ┌──┴──┐
   │     │
  有     无
   │     │
   ▼     ▼
问用户   有没有可合理假设的缺失？
          │
      ┌───┴───┐
      │       │
     有       无
      │       │
      ▼       ▼
 加 Assumption   Continue
      │
      ▼
 Continue
```

但：

> **Assumption 应该由 Assembler 根据明确默认策略产生，不建议 Clarification Gate 临时用 LLM 发明。**

# 二十四、澄清问题本身是否让 LLM 生成？

第一版我建议：

> 可以用模板确定性生成。

例如：

```text
metric missing
→
“你提到的‘业绩500W’具体指 NBEV、保费，还是其他指标？”
```

因为 MissingInformation 已经有：

```text
field
reason
impact
```

完全可以生成简单问题。

暂时不要为了问一句话再调用 LLM。

以后为了自然语言体验可以让 LLM润色，但不是核心。

# 二十五、ClarificationRequest 可以非常轻

例如：

```python
@dataclass(frozen=True)
class ClarificationQuestion:
    field: str
    question: str
    options: tuple[str, ...] = ()


@dataclass(frozen=True)
class ClarificationRequest:
    request_id: str
    goal_ref: GoalRef | None
    questions: tuple[ClarificationQuestion, ...]
```

但我甚至建议现在不急着把它放 Domain。

这是 Application DTO。

因为：

```text
用户澄清交互
```

不是智慧经营核心领域对象。

# 二十六、已有 Goal 修改时发生冲突怎么办？

例如：

Goal v1：

```text
metric = NBEV
```

用户说：

> “目标改成500W保费。”

这不是真正冲突。

这是明确 Update：

```text
metric = premium
target = 500W
```

正常生成 Goal v2。

---

但是：

用户说：

> “我是银保渠道，继续做。”

RuntimeContext：

```text
channel = individual_insurance
```

这就是 Authority Conflict。

我建议不改 Runtime value，同时在 Goal 中：

```text
channel_and_actor = individual_insurance
```

增加：

```text
MissingInformation / Warning
```

更准确的可能是：

```text
ContextConflict
```

但 M2 第一版不值得引入新 Domain Object。

可以作为 Application warning：

```text
warnings=(
    "用户声明的渠道与当前可信登录上下文不一致",
)
```

重要的是：

> 不让用户文本覆盖可信上下文。

# 二十七、是否需要给每个 Goal 字段保存 provenance？

这是一个值得讨论的问题。

理论上非常漂亮：

```text
target:
  value: 500
  source: user_request

channel:
  value: individual
  source: runtime_context
```

但我现在不建议把整个 Goal 改造成：

```text
FieldValue[T]
```

这种重型结构。

因为 T03 还没有实际证明需要这么复杂。

第一版：

```text
Goal
+
source_request_id
+
assumptions
+
missing_information
```

已经足够。

Evidence 阶段才需要强来源治理。

# 二十八、SuccessCriteria 应该由谁生成？

这是 T03 一个容易忽略的问题。

例如：

```text
metric=NBEV
target=500W
```

可以确定性生成：

```text
NBEV >= 500W
```

所以建议：

> **对于简单 quantitative Goal，SuccessCriterion 由 Assembler 确定性派生。**

不要再让 LLM输出：

```text
success_criteria
```

例如：

```python
if metric and target:
    success_criteria = (
        SuccessCriterion(
            criterion_type="metric_threshold",
            metric_code=metric.code,
            operator=target.direction,
            value=target.value,
        ),
    )
```

当然实际 `direction` 到 operator 需要轻量映射。

# 二十九、非量化 Goal 呢？

例如：

> 帮我看看王女士下一步怎么经营。

没有：

```text
metric
target
```

那 SuccessCriterion 可以：

```text
形成一个有依据的下一步经营策略
```

这里是否让 LLM 生成？

我建议 M2 第一版：

```text
success_criteria = ()
```

完全可以。

不要为了填满 Goal 而发明一个主观完成条件。

之后 Planner/Capability 真正成熟后，再设计非量化 Goal 的完成语义。

这符合：

> 字段可以为空，不能为了结构完整补造信息。

# 三十、T03 第一版 GoalAssembler API

可以很清楚：

```python
class GoalAssembler:

    def assemble(
        self,
        request: BusinessRequest,
        interpretation: GoalInterpretation,
        existing_goal: Goal | None = None,
    ) -> Goal:
        ...
```

它内部只做：

```text
1. 确定 goal_id / version
2. 取得 base Goal
3. apply interpretation patch
4. 注入 trusted runtime context
5. 生成 derived fields
6. 生成 MissingInformation
7. 生成 Assumptions
8. 创建 immutable Goal
```

不要做：

```text
Tool Call
LLM Call
Database Query
```

GoalAssembler 应该是非常好测的纯函数/近纯函数。

---

# 三十一、ClarificationGate API

```python
class ClarificationGate:

    def evaluate(
        self,
        goal: Goal,
    ) -> ClarificationResult:
        ...
```

或者干脆先做函数：

```python
evaluate_goal_readiness(goal)
```

不要现在为了 OO 完整度强建 class。

项目整体如果偏函数式，就用函数。

# 三十三、模糊指标场景

用户：

> 这个月业绩做到500W。

T02：

```text
target=500W

metric unresolved:
“业绩”无法明确映射具体指标
```

T03：

```text
MissingInformation:

field=metric

impact=
不同指标将明显影响目标衡量和后续经营规划

required_before_planning=True
```

Clarification：

```text
REQUIRE_CLARIFICATION
```

问题：

> “这里的500W业绩具体指 NBEV、保费，还是其他指标？”

不进入 Planner。

# 三十四、单客户策略场景

用户：

> 看看王女士下一步怎么经营。

假设已有确定性实体解析还没做。

```text
audience_expression="王女士"
```

如果系统当前没有 customer ref：

T03：

```text
AudienceScope(
    scope_type="specific_customer",
    reference=None,
    raw_expression="王女士",
)
```

如果不能唯一确认：

```text
MissingInformation(
    field="audience_scope.reference",
    reason="尚未唯一定位具体客户",
    required_before_planning=True,
)
```

因为给错客户生成策略显然不可接受。

# 三十五、Goal 修改场景

原来：

```text
Goal 001 v1
target=500
products=A,B
```

新请求：

> 改成400W，不限定产品了，优先老客户。

T02：

```text
target:
SET 400W

product_mentions:
CLEAR

constraints:
SET 优先老客户
```

T03：

```text
Goal 001 v2

target=400
products=()
constraints:
customer_preference=existing_customer

其他未提字段全部继承 v1
```

这就是我们设计 Patch Semantics 的价值。

# 三十六、T03 的测试建议

这一阶段单元测试会非常有价值。

至少应该包含：

```text
A. New Goal +完整 Interpretation
→ Goal v1
```

```text
B. Existing Goal + SET target
→ 同 goal_id
→ version + 1
→ 只有 target 修改
```

```text
C. Existing Goal + CLEAR product
→ product context 被显式清除
```

```text
D. 未涉及字段
→ 保留旧值
```

```text
E. 用户 channel 与 runtime channel 冲突
→ runtime 胜出
```

```text
F. Runtime actor 缺失
→ 显式 MissingInformation
```

```text
G. 模糊 metric
→ required_before_planning=True
→ Clarification
```

```text
H. 时间截止日未知但不影响第一轮规划
→ non-blocking missing
→ Continue
```

```text
I. unique customer unresolved
→ planning blocked
```

```text
J. Assumption 不得覆盖 Runtime Fact
```

# 三十七、T03 建议锁定的不变量

我建议正式记录：

**A-01**：GoalAssembler 不调用 LLM。
**A-02**：最终 Goal 只能由确定性组装逻辑创建。
**A-03**：身份、渠道、授权等可信字段只能来自 Runtime/权威来源。
**A-04**：用户明确更新的 Goal 字段覆盖旧 Goal 对应业务目标字段。
**A-05**：未提及字段继承 Existing Goal，不视为清除。
**A-06**：`CLEAR` 与未提及必须严格区分。
**A-07**：Goal 修改生成新版本，不修改旧实例。
**A-08**：无法解析的外部事实保持未知，不由 Assembler 推断。
**A-09**：LLM `UnresolvedItem` 在 T03 转译为 MissingInformation 或显式 Assumption。
**A-10**：只有会明显改变规划的缺失才阻断 Planner。
**A-11**：身份、权限、关键对象歧义和不可逆执行信息不得通过 Assumption 绕过。
**A-12**：ClarificationGate 是确定性 Application Control，不是新 Agent/Capability。

## 到这里，M2 前半段已经形成非常清楚的“信任升级链”

```text
用户原话
│
│ 非结构化、用户提供
▼
GoalInterpretation
│
│ LLM解释，有语义价值但非权威事实
▼
GoalAssembler
│
├── Existing Goal
├── Trusted Runtime Context
├── Merge Rules
├── Missing / Assumption
│
▼
Goal
│
│ 系统认可的领域目标
▼
Clarification Gate
│
├── BLOCK PLANNING → 问用户
│
└── CONTINUE
       ↓
      Planner
```

这个设计里有一个非常漂亮的边界：

> **LLM 有权说“我理解用户表达了什么”，但没有权说“系统最终应该相信什么”。**

下一步进入 **M2-T04 Capability Catalog** 后，我们就从“理解 Goal”正式跨入“动态规划”：先建立 Planner 可以看到的能力目录，然后 T05 才真正让 LLM 决定当前 Goal 应该调用哪些 Capability。
