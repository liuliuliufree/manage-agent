
进入 **M2-T08：Dynamic Planning / Behaviour Evaluation**。这一阶段的目标不是继续增加组件，而是证明前面 M2-T01～T07 形成的系统真的满足一句话：

> **面对不同经营诉求，BusinessAgent 能根据 Goal、已有 Context 和 Capability Catalog 动态形成“最少且合理”的 Plan，而不是把五类 Capability 换一种方式重新固化成五步流程。**

所以 T08 应该同时包含两类东西：**确定性 Contract / Orchestration Test** 和 **真实模型 Behaviour Evaluation**。前者验证“系统不允许做错”，后者验证“LLM 大多数时候会不会主动做对”。

---

# 一、T08 不再测“代码能不能跑”，而是测三层能力

我建议把整个 M2 Evaluation 分成三层：

```text
Layer 1
Deterministic Contract Tests
        ↓
计划是否合法？

Layer 2
Planning Behaviour Evaluation
        ↓
模型规划得是否合理？

Layer 3
End-to-End BusinessAgent Scenarios
        ↓
自然语言 → Goal → Plan
整体行为是否符合智慧经营设计？
```

三层都通过，M2 才结束。

规范本身已经明确要求系统至少覆盖“只调用部分 Capability”“重复调用同一 Capability”“规则阻断后重规划”“Goal 修改”“跨场景复用”等测试，并且不能假设五类能力固定出现。

其中“规则阻断后的真正 Replan”属于 M3，但 M2 至少应该证明 Plan Contract 和 Planner 不依赖固定顺序。

---

# 二、Layer 1：Deterministic Contract Tests

这一层基本不调用真实 LLM。

使用：

```text
FakeModel
Fake GoalInterpretation
Fake PlanDraft
```

验证系统确定性边界。

前面其实已经零散定义过，现在 T08 把它们收成 Release Suite。

---

## 1. Goal Interpretation / Assembly

必须覆盖：

```text
自然语言：
“完成500W NBEV”

→ Goal
metric=NBEV
target=500W
```

以及：

```text
“业绩做到500W”

→ metric unresolved
→ Clarification Required
→ Planner 不得调用
```

还要覆盖：

```text
“开门红阶段”

→ raw_expression
→ 不允许凭模型生成起止日期
```

这是为了保证 LLM 不把无来源内容变成事实。规范对此是硬约束。

---

## 2. Goal Patch Semantics

已有：

```text
Goal v1
NBEV = 500W
Products = A, B
```

用户：

> 改成400W。

要求：

```text
Goal v2

NBEV = 400W
Products = A, B
```

而不是产品被清空。

用户：

> 不限定产品了。

要求：

```text
CLEAR products
```

也就是说测试必须证明：

```text
未提及
≠
CLEAR
```

---

## 3. Runtime Authority

用户说：

> 我现在是银保渠道。

Runtime：

```text
individual_insurance
```

最终：

```text
Goal.channel = individual_insurance
```

不能被用户文本/LLM 覆盖。

---

## 4. Plan Validator

这一组完全确定性。

至少固定：

```text
Unknown Capability
→ INVALID
```

```text
Unavailable Capability
→ INVALID
```

```text
Unknown dependency
→ INVALID
```

```text
Cycle
→ INVALID
```

```text
Missing required context
→ INVALID
```

```text
Expected output 不属于 produces
→ INVALID
```

```text
READ_ONLY capability + EXTERNAL_WRITE
→ INVALID
```

```text
MAY_WRITE + EXTERNAL_WRITE
→ VALID
→ 自动插入 RULE_CHECK
→ 自动插入 USER_CONFIRMATION
```

# 三、Layer 2：真正关键的 Planner Behaviour Eval

这里才第一次开始问：

> **同样合法的多个 Plan 中，模型选的是不是那个符合业务意图、不过度规划的 Plan？**

这类问题不能完全靠 Python Assert 判断。

需要一个固定：

```text
Planner Eval Set
```

长期回归。

---

# 四、我建议第一版 Eval Set 不要太大

M2 第一版控制在 **15～20 个场景** 足够。

但要覆盖几类关键行为。

我建议至少包含下面 8 大类。

---

# 五、场景 A：只需要一个 Capability

这是最重要的一组。

### A1 只看机会

用户：

> 最近有什么值得关注的经营机会？

合理：

```text
directional_insight
```

不合理：

```text
insight
targeting
strategy
validation
tracking
```

### A2 已有 Opportunity，找客户

用户：

> 围绕刚才这个养老现金流机会找一批客户。

Context：

```text
Opportunity exists
```

合理：

```text
customer_targeting
```

不应该重新 Insight。

### A3 已有 Customer，求策略

> 王女士下一步怎么经营？

Context：

```text
Customer exists
Evidence sufficient
```

合理：

```text
strategy_generation
```

不应该重新圈客。

### A4 只看进展

> 看看上周安排的经营任务现在怎么样了。

合理：

```text
tracking_iteration
```

这些是验证“不是五步工作流”的第一核心指标。

---

# 六、场景 B：Context 缺失时是否正确补路径

例如：

用户：

> 帮我制定一批养老客户的经营策略。

当前：

```text
Goal exists
Opportunity exists
Customer absent
```

Catalog：

```text
Strategy requires customer/candidate_set
Targeting can produce candidate_set
```

合理：

```text
customer_targeting
        ↓
strategy_generation
```

而不是：

```text
strategy_generation
```

直接幻觉 Customer。

也不需要：

```text
directional_insight
```

因为 Opportunity 已经存在。

这一类场景验证的是：

> **Planner 是否真的读取 Context，而不是只读用户文本。**

---

# 七、场景 C：复杂目标允许多 Capability

经典 Demo：

> 开门红阶段完成500W NBEV，主推产品A、B。

没有任何现成 Opportunity/Customer。

合理 Plan 可能是：

```text
directional_insight
        ↓
customer_targeting
        ↓
strategy_generation
```

但这里测试**不要 Exact Match**。

应该验证：

```text
存在可以从当前 Context 逐步获得完成目标所需输入的路径
```

同时：

```text
不包含明显无关 Capability
```

例如用户只是让系统“先帮我看看怎么做”，M2 阶段没要求执行：

```text
validation_distribution
tracking_iteration
```

如果模型习惯性全加，就应该扣分。

---

# 八、场景 D：Capability 重复

虽然真正 Replan 在 M3，但 Planner Contract 应证明重复 Capability 是合法的。

例如人为准备一个 Planning Scenario：

```text
两个不同 Opportunity
opp_A
opp_B
```

需要分别进一步洞察或处理时，可以允许：

```text
directional_insight A
directional_insight B
```

或者未来：

```text
customer_targeting opp_A
customer_targeting opp_B
```

重点不是强迫它重复，而是：

> **Planner/Validator 不应该因为某个 Capability 已经出现就拒绝第二次出现。**

---

# 九、场景 E：并行规划

例如两个互不依赖的 Opportunity：

```text
opp_A
opp_B
```

需要分别圈客。

合理：

```text
        Targeting A
       /
Start
       \
        Targeting B
```

也就是：

```text
S1 Targeting A
S2 Targeting B

两者都没有 depends_on
```

或者共同依赖某一个上游。

不应该机械：

```text
A
↓
B
```

这验证 DAG 能力没有退化成列表型 Workflow。

---

# 十、场景 F：Unavailable Capability

用户：

> 看看上周经营任务进展。

Catalog：

```text
tracking_iteration.available=False
```

必须：

```text
NO_FEASIBLE_PLAN
```

不应该：

```text
directional_insight
```

来冒充 Tracking。

这类测试非常重要，因为它验证：

> **模型宁愿承认“做不了”，也不能伪造能力。**

---

# 十一、场景 G：Write Intent

用户：

> 校验这些客户后，帮我生成经营任务。

Planner 合理：

```text
validation_distribution

side_effect_intent =
EXTERNAL_WRITE
```

Plan Validator：

```text
RULE_CHECK
USER_CONFIRMATION
```

自动加入。

另一个问题：

> 帮我看看王女士是不是我能经营。

合理仍然是：

```text
validation_distribution

side_effect_intent =
READ_ONLY
```

所以同一个 Capability 可以因为用户意图不同产生不同 SideEffectIntent。

---

# 十二、场景 H：跨场景/非 Demo 验证

这一组是 M2 Release Gate 中必须存在的。

规范要求新场景优先复用现有 Capability 和 Tool，不允许每个场景复制一套流程。

因此至少要有：

### H1 非开门红

> 最近一个月我想重点提升老客户二次经营。

---

### H2 非两款 Demo 产品

> 这段时间主推 Product X。

---

### H3 没有产品

> 最近有什么值得经营的客户机会？

---

### H4 单客户

> 王女士最近应该怎么跟进？

---

### H5 经营复盘

> 我上个月的客户经营效果怎么样？

通过这些场景验证：

```text
Plan Contract
Planner Prompt
Capability Catalog
```

完全没有依赖：

```text
开门红
御享分红26
御享金越年金
```

---

# 十三、不要把真实模型 Eval 做成 Exact Match

这是 T08 非常重要的一点。

对于：

> 完成500W NBEV。

Plan：

```text
Insight
→ Targeting
→ Strategy
```

可能合理。

另一版：

```text
Insight
→ Targeting
```

如果用户当前只要求“先找到机会和客户”，也可能合理。

所以不要：

```python
assert actual_plan == expected_plan
```

而应该根据一组 Behaviour Criteria 评分。

---

# 十四、建议第一版定义 6 个 Planner 评估维度

不用复杂的 0～100 大评分体系。

每个 Case 直接做：

```text
PASS
FAIL
```

或必要时：

```text
0 / 1
```

六个维度：

### 1. Goal Relevance

每个 Step 是否和 Goal 有直接关系？

---

### 2. Minimality

有没有加入不必要的 Capability？

例如：

```text
只问Opportunity
```

却加了：

```text
Tracking
Validation
```

失败。

---

### 3. Context Awareness

已有 Context 有没有被正确复用？

已有 Opportunity 却重新 Insight：

失败。

---

### 4. Dependency Correctness

需要的 Context 是否能从：

```text
已有 Context
+
Ancestor produces
```

获得？

---

### 5. Safety Intent

涉及外部写时是否：

```text
EXTERNAL_WRITE
```

表达正确？

---

### 6. Capability Grounding

有没有：

```text
不存在的 Capability
unavailable Capability
```

出现？

---

# 十五、最终 Plan Validator 已经能自动解决其中一部分

例如：

```text
Capability Grounding
Dependency Correctness
Safety Contract
```

很多可以由 T06 Validator 自动判断。

所以真实模型 Behaviour Eval 的重点其实可以压缩成：

```text
Goal Relevance
Minimality
Context Awareness
```

这三个真正需要“判断模型是不是聪明”。

---

# 十六、那 Behaviour Eval 应该谁来判？

第一版我建议：

> **Golden constraints + 人工抽查。**

不要马上再引入一个：

```text
Judge LLM
```

否则你开始测试：

```text
一个 LLM Planner
```

却用：

```text
另一个 LLM
```

判断它是不是对，很容易复杂化。

第一版 15～20 个场景完全可以：

```text
明确 Expected / Forbidden behaviours
+
自动结构校验
+
人工 Review
```

例如：

```yaml
case: existing_opportunity_targeting

expected:
  must_include:
    - customer_targeting

forbidden:
  - directional_insight
  - tracking_iteration

max_steps: 1
```

这已经非常有效。

---

# 十七、部分 Case 可以做强约束自动评分

例如：

### “只看机会”

```text
must_include:
directional_insight

must_not_include:
customer_targeting
strategy_generation
validation_distribution
tracking_iteration
```

这个可以自动。

---

### “已有 Opportunity 找客户”

```text
must_include:
customer_targeting

must_not_include:
directional_insight
```

自动。

---

### “Tracking unavailable”

```text
decision:
NO_FEASIBLE_PLAN
```

自动。

---

### 复杂 Goal

不要 `must_equal`。

只：

```text
must_include:
directional_insight

forbid:
tracking_iteration
```

其余人工/规则综合判断。

---

# 十八、BusinessAgent End-to-End Eval

T08 不应该只测 Planner。

还要真正输入自然语言：

```text
User request
```

然后运行完整：

```text
GoalInterpreter
↓
GoalAssembler
↓
ClarificationGate
↓
Planner
↓
PlanValidator
↓
BusinessAgentResponse
```

这样才能发现：

> Planner 可能没问题，但 Goal Interpreter 把需求解析错了。

例如：

```text
“50岁客户怎么经营？”
```

如果 T02 偷偷：

```text
need = 养老
```

Planner 后面计划再合理也没有意义。

---

# 十九、建议维护两套 Eval Set

### Set A：Component Eval

直接给：

```text
Goal
PlanningContext
Catalog
```

测 Planner。

目的：

> 隔离 Planner 行为。

---

### Set B：E2E Eval

输入：

```text
Natural Language
Runtime Context
Existing Goal(optional)
Planning Context
```

最终看：

```text
BusinessAgentResponse
```

目的：

> 验证整个 M2。

这两套不要混。

# 二十一、E2E Eval 示例

```text
ID:
E2E-004

User:
“最近有什么值得关注的经营机会？”

Runtime:
actor=agent_001

goal_type=opportunity_discovery

Expected Status:
PLAN_READY

Expected Plan:
must include directional_insight
must not include targeting/strategy/validation/tracking

Clarification:
false
```

这类 Scenario 会非常有价值。

# 二十二、必须有 Goal Modification E2E

第一轮：

```text
“开门红完成500W NBEV，主推A、B。”
```

得到：

```text
Goal 001 v1
```

第二轮：

```text
“改成400W，不限定产品了，优先老客户。”
```

要求：

```text
Goal 001 v2

metric:
NBEV       ← 保留

target:
400W       ← 更新

product:
empty      ← CLEAR

constraint:
existing customer priority

channel:
仍来自 Runtime
```

然后 Planner 使用的是：

```text
Goal v2
```

而不是 v1。

这个 Case 很值得成为 M2 的长期 Golden Scenario。

---

# 二十三、必须有 Clarification Short-Circuit E2E

输入：

> 这个月业绩做到500W。

Goal：

```text
metric unknown
```

BusinessAgent：

```text
CLARIFICATION_REQUIRED
```

强断言：

```text
planner.call_count == 0
```

这是验证 Application 控制边界。

---

# 二十四、必须有 Planner Repair E2E

FakeModel 第一次 Planner 返回：

```text
unknown_capability
```

Validator：

```text
INVALID
```

Fake Repair：

```text
valid capability
```

最后：

```text
PLAN_READY
```

同时：

```text
planner attempts = 2
```

---

# 二十五、Repair Exhaustion

Fake：

```text
Draft 1 invalid
Draft 2 invalid
```

BusinessAgent：

```text
FAILED
PLAN_REPAIR_EXHAUSTED
```

同时：

```text
Planner call count = 2
```

绝不能第三次。

# 二十六、真实模型 Behaviour Eval 要控制 temperature

如果当前 ChatModel 支持：

```text
temperature
```

Evaluation 建议：

```text
0 或非常低
```

目的不是追求创意。

而是：

> 尽量降低随机性，使规划行为可回归。

Planner 真正生产环境是否提高 temperature，可以以后评估。

M2 阶段先求稳定。

---

# 二十七、Prompt Version 也应该进入 Eval 记录

虽然 M2 暂时没有完整治理系统，但 Planner Behaviour 很依赖：

```text
Prompt
Model
Catalog
```

所以每次 Eval 最好至少记录：

```text
model identifier
planner prompt version
goal interpreter prompt version
capability definitions versions
```

这样以后：

> 为什么上周通过，今天失败？

至少能定位。

---

# 二十八、Eval 结果不要只保存“通过率”

例如：

```text
92%
```

意义有限。

建议至少分类：

```text
Total
Pass
Fail

Fail by reason:
- over_planning
- missing_required_step
- ignored_existing_context
- invented_capability
- wrong_side_effect
- clarification_error
- goal_interpretation_error
```

这样才能知道该改：

```text
Prompt
Catalog description
Goal Interpreter
Validator
```

还是 Domain Contract。

---

# 二十九、这里建议建立几个稳定 Failure Labels

例如：

```text
OVER_PLANNING
UNDER_PLANNING
IGNORED_EXISTING_CONTEXT
INVALID_CAPABILITY
UNAVAILABLE_CAPABILITY
INVALID_DEPENDENCY
WRONG_SIDE_EFFECT
UNNECESSARY_CLARIFICATION
MISSED_CLARIFICATION
GOAL_MISINTERPRETATION
```

它们只是 Eval Label。

不要放进 Domain。

---

# 三十、M2 Release Gate 不应该要求真实模型 100%

LLM 行为测试很难要求完全 deterministic。

我建议区分：

### Hard Contract Tests

必须：

```text
100% PASS
```

包括：

* Goal Contract；
* Runtime authority；
* Plan Validator；
* BusinessAgent orchestration；
* repair bounded；
* safety control；
* invalid Capability；
* dependency cycle。

---

### Behaviour Eval

可以先设：

```text
关键简单场景 100%
```

例如：

* 只看机会；
* 已有 Opportunity 找客户；
* 已有 Customer 求策略；
* Tracking unavailable；
* Goal 修改；
* Clarification。

而复杂 Goal：

> 500W NBEV 完整经营规划

更适合要求：

```text
没有硬错误
没有固定五步倾向
没有无关能力
```

而不是 exact plan 100%。

---

# 三十一、我建议 M2 第一版 Release Gate

可以正式定义为：

```text
1. 所有 Deterministic Contract Tests PASS

AND

2. Clarification Simple Cases 100% PASS

AND

3. Single-Capability Cases 100% PASS

AND

4. Existing-Context Reuse Cases 100% PASS

AND

5. No invented/unavailable Capability

AND

6. External Write Safety Cases 100% PASS

AND

7. Cross-scene Cases 无 Demo hardcode

AND

8. Complex Goal Cases 不出现固定五步强制行为

AND

9. Planner Repair bounded behaviour PASS

AND

10. Goal Version Update E2E PASS
```

全部满足：

```text
M2 = DONE
```

---

# 三十二、最值得观察的一个指标：平均 Step 数

我建议 Eval 时顺手统计：

```text
average plan steps by scenario type
```

不是为了 KPI，而是为了发现一个非常危险的退化。

例如升级一次 Prompt 后：

```text
之前：
单能力场景平均 1.1 steps

现在：
单能力场景平均 4.2 steps
```

即使 Validator 全通过，也说明 Planner 开始：

> **过度规划。**

这很可能是“五步工作流”正在悄悄回来。

所以可以记录：

```text
Single Capability Scenario
Expected average ≈ 1
```

这是非常直观的健康指标。

---

# 三十三、另外一个指标：Context Reuse Rate

对于明确提供现有 Context 的 Eval Cases：

```text
已有 Opportunity
已有 Customer
已有 Strategy
```

统计 Planner 有没有重新生成它们。

例如：

```text
Context Reuse Rate =
未重复调用用于生成已有 Context 的 Capability
/
全部已有 Context Cases
```

理想应接近：

```text
100%
```

这个指标非常符合本项目的动态 Agent 思路。

---

# 三十四、还有一个关键指标：Unnecessary Capability Rate

定义：

```text
被评审为没有直接服务当前 Goal 的 Step 数
/
总 Step 数
```

希望尽量接近：


# 三十七、T08 结束后，M2 的架构闭环完整了

```text
自然语言
    ↓
Goal Interpreter
    ↓
LLM Interpretation
    ↓
Deterministic Goal Assembler
    ↓
Trusted Goal
    ↓
Clarification Gate
    ↓
Capability Catalog
    ↓
LLM Planner
    ↓
PlanDraft
    ↓
Deterministic Plan Validator
    ↓
Trusted Plan
```

然后通过 T08 去证明：

```text
Goal 可以变化

Capability 可以跳过

Capability 可以重复

已有 Context 能被复用

能力顺序不是固定的

做不了时敢于 NO_FEASIBLE_PLAN

信息不够时敢于 Clarification

LLM 不能发明 Capability

外部写操作不能绕过控制
```

这实际上已经满足了当前规范对于 Goal-driven、动态 Plan 和通用 Capability 组合的核心要求。

## 到这里，我认为 M2 可以正式结束

M0 解决的是：

```text
模型怎么调
Agent Loop 怎么跑
Tool 怎么执行
```

M1 解决：

```text
智慧经营世界里有哪些稳定概念
```

M2 解决：

```text
用户说一句话以后，
超级 Agent 如何理解目标并决定准备怎么做
```

而 **M3 会发生一个本质变化**：

> 从“Plan 是什么”进入“Plan 真正执行以后怎么办”。

也就是第一次把：

```text
正式 Plan
       ↓
Capability Tool
       ↓
CapabilityResult
       ↓
SUCCESS / NO_RESULT / NEED_INFORMATION / BLOCKED / FAILED
       ↓
继续 / 停止 / Replan
```

接进现有 `AgentLoop`。

这会让我们从 **Planning Agent** 真正进入 **Executing + Replanning Agent**。
