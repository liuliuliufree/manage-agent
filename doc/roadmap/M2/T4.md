
可以。**M2-T04 Capability Catalog** 的核心任务，是给 Planner 一张“我现在能做什么”的受控能力地图，但不告诉它“必须按什么顺序做”。

> **Catalog 回答的是：系统有哪些 Capability、各自解决什么问题、需要什么上下文、可能产生什么结果、是否涉及外部状态。它不回答：当前 Goal 应该先调用谁、后调用谁。**

这一区分很重要。规范明确要求五类 Capability 可以跳过、重复、重排，而不是固定状态机。

---

# 一、T04 在 M2 中的位置

现在链路是：

```text
BusinessRequest
      ↓
GoalInterpreter
      ↓
GoalInterpretation
      ↓
GoalAssembler
      ↓
Goal
      ↓
ClarificationGate
      │
      ├── REQUIRE_CLARIFICATION
      │
      └── CONTINUE
              ↓
      Capability Catalog   ← T04
              │
              ▼
           Planner          ← T05
              ↓
             Plan
```

所以 Planner 最终不是凭 Prompt 中的常识规划，而是接收：

```text
Goal
+
Current Context
+
Capability Catalog
```

再做动态选择。

---

# 二、Catalog 和 M1 的 `CapabilityDefinition` 是什么关系？

M1 已经有：

```python
@dataclass(frozen=True)
class CapabilityDefinition:
    capability_id: str
    version: str
    name: str
    description: str
    input_schema_version: str
    output_schema_version: str
```

这个定义是对的，但对于 Planner 来说还不够。

Planner 至少还需要知道：

```text
这个 Capability 什么时候有用？
需要什么业务上下文？
会产生什么？
有哪些重要限制？
会不会改变外部状态？
```

我不建议因此把 `CapabilityDefinition` 越堆越大。

更干净的方式是：

```text
Domain
CapabilityDefinition
        │
        ▼
Application
PlanningCapability
        │
        ▼
CapabilityCatalog
        │
        ▼
Planner
```

也就是说：

> `CapabilityDefinition` 是稳定领域身份；
> `PlanningCapability` 是给 Planner 看的能力说明。

---

# 三、建议新增 `PlanningCapability`

第一版我建议：

```python
@dataclass(frozen=True)
class PlanningCapability:
    capability_id: str
    capability_version: str

    name: str
    purpose: str

    required_context: tuple[str, ...] = ()
    optional_context: tuple[str, ...] = ()

    produces: tuple[str, ...] = ()

    limitations: tuple[str, ...] = ()

    side_effect_level: "SideEffectLevel" = SideEffectLevel.READ_ONLY
```

这里每个字段都有非常明确的规划意义。

---

# 四、`purpose`

不要只是：

```text
“定向洞察”
```

Planner 真正需要理解：

> 这个能力到底解决什么问题？

比如：

```text
directional_insight

purpose:
基于当前Goal和已有证据识别值得进一步经营的问题、
机会方向和优先级，并形成可解释Opportunity。
```

而：

```text
customer_targeting

purpose:
基于已经形成的Opportunity，
寻找符合机会条件的候选经营对象并解释入选、排除和排序依据。
```

注意这里描述的是：

```text
业务问题
```

而不是：

```text
调用步骤。
```

---

# 五、`required_context` 最容易设计错

这里绝对不要写：

```text
customer_targeting
requires_capability = directional_insight
```

因为这样等于把固定流程重新编码进 Catalog。

应该表达：

```text
customer_targeting
requires_context = opportunity
```

两者差异非常大。

错误：

```text
Insight
必须先执行
      ↓
Targeting
```

正确：

```text
Targeting
需要 Opportunity
```

Opportunity 可以来自：

```text
当前会话已有结果
历史已确认结果
用户已有明确经营机会
Directional Insight
其他可信业务系统
```

所以我们表达的是：

> **数据/语义依赖**

而不是：

> **前驱 Capability 依赖。**

---

# 六、这也意味着 Planner 真正需要解决“上下文缺口”

例如：

用户：

> 围绕这个养老现金流机会帮我找一批客户。

Context 中已经有：

```text
opp_001
```

Planner 完全可以：

```text
customer_targeting
```

一步完成。

不应该因为 Catalog 写了：

```text
Insight → Targeting
```

又重复执行 Insight。

---

# 七、第一版 Context Type 不要设计得太复杂

可以先用稳定字符串：

```text
goal
evidence
opportunity
customer
candidate_set
strategy
validation_result
task
feedback
progress
```

例如：

```python
required_context=("goal", "opportunity")
```

暂时不要做：

```text
ContextType Registry
Ontology
复杂泛型系统
```

真正发现 typo 或类型治理问题后，再收敛 Enum。

---

# 八、`produces`

这告诉 Planner：

> 如果调用这个 Capability，我大概能得到什么东西？

例如：

```text
directional_insight
→ opportunity
→ evidence
```

```text
customer_targeting
→ candidate_set
→ evidence
```

```text
strategy_generation
→ strategy
→ evidence
```

这样 Planner 未来就可以推理：

```text
我现在需要 strategy

strategy_generation 需要 customer

当前没有 customer

customer_targeting 可以产生 candidate_set/customer context

...
```

这才是真正的动态规划基础。

---

# 九、但不要让 Planner 变成自动拼积木算法

这里也需要控制。

我们不是要：

```text
Output A
→ match Input B
→ 自动生成 Workflow Graph
```

Planner 仍然由 LLM 根据 Goal 做语义规划。

Catalog 的：

```text
required_context
produces
```

只是帮助模型：

* 避免无效调用；
* 解释为什么需要某一步；
* 检查上下文是否足够。

不是在 Application 里开发一个：

```text
Capability Dependency Solver
```

现在没有必要。

---

# 十、`optional_context`

这个字段也很有价值。

比如：

```text
strategy_generation
```

可能必须有：

```text
goal
customer
```

但以下信息：

```text
opportunity
evidence
product_context
prior_feedback
```

属于：

```text
有则更好
```

所以：

```python
required_context=(
    "goal",
    "customer",
)

optional_context=(
    "opportunity",
    "evidence",
    "feedback",
)
```

这能让 Planner 明白：

> 缺少 Opportunity 不一定意味着不能生成 Strategy。

这正好避免机械五步。

---

# 十一、`limitations` 不是 Business Rules

比如 Targeting 可以告诉 Planner：

```text
结果仅代表候选客户，
不代表客户具备当前渠道经营权限。
```

这是 Capability 的**语义限制**。

合法。

但是 Catalog 不应该塞：

```text
银保客户不能进入个险
年龄必须...
某产品必须...
```

这些属于业务规则。

规范要求确定性规则继续存在于规则/权限服务，而不是 Prompt 或能力描述里。

所以：

```text
limitations
=
能力边界
```

不是：

```text
rules
=
具体业务裁决
```

---

# 十二、Planner 还需要知道 Capability 会不会改变外部状态

这一点很重要。

建议：

```python
class SideEffectLevel(str, Enum):
    READ_ONLY = "read_only"
    MAY_WRITE = "may_write"
```

暂时两个就够。

不要一开始：

```text
LOW
MEDIUM
HIGH
CRITICAL
```

没必要。

例如：

```text
directional_insight
READ_ONLY

customer_targeting
READ_ONLY

strategy_generation
READ_ONLY

tracking_iteration
READ_ONLY
```

而：

```text
validation_distribution
MAY_WRITE
```

因为它可能最终涉及：

```text
名单落库
任务创建
分发
```

---

# 十三、但是 `MAY_WRITE` 不代表每次调用都会写

这一点必须明确。

例如：

```text
validation_distribution
```

可能这次用户只是问：

> 这个客户我能不能经营？

那只需要：

```text
validation
```

完全只读。

所以：

```text
MAY_WRITE
```

只是告诉 Planner：

> **这个能力可能进入受控外部写路径，如果规划到了写操作，需要 ControlPoint。**

真正 Plan 是否需要：

```text
RULE_CHECK
USER_CONFIRMATION
```

由 Planner + Plan Validator 在具体动作层判断。

---

# 十四、一个值得考虑的小修订：`validation_distribution` 是否太大？

这里第一次出现一个值得记下、但**现在不要改**的问题。

目前 Capability 是：

```text
validation_distribution
```

它实际上包含两种性质不同的行为：

```text
validation
=
确定性校验
=
read only
```

和：

```text
distribution
=
执行
=
可能 write
```

长期可能发现应该拆成：

```text
execution_validation

business_distribution
```

但是当前规范已经定义五类通用 Capability，所以 **M2 不应该擅自改变这个基线**。

先用：

```text
side_effect_level=MAY_WRITE
```

处理即可。

等真实 M3/M6 实现证明这个组合确实造成困难，再提交架构调整。

# 十六、Catalog 和 Tool Registry 完全不是一回事

这个边界一定要明确。

未来可能有：

```text
CapabilityCatalog
```

给：

```text
Planner
```

看。

而：

```text
Tool Registry
```

给：

```text
Agent Runtime
```

执行。

两者关系：

```text
Planner World
────────────────────────

Capability Catalog
        ↓
directional_insight


Execution World
────────────────────────

Tool Registry
        ↓
directional_insight_tool
        ↓
handler
```

不要：

```text
CapabilityCatalog
=
ToolRegistry
```

否则 Planner 会开始看到：

```text
JSON Schema
handler function
HTTP endpoint
```

这些完全不该进入业务规划。

# 十七、Capability Catalog 也不负责实现映射

即：

```text
capability_id
→
具体 Tool
```

这个映射属于未来 M3：

```text
Capability Invocation / Adapter
```

T04 只管：

> Planner 认知。

# 十八、Availability 要不要现在做？

这是一个现实问题。

例如系统定义有：

```text
tracking_iteration
```

但当前 Demo 环境：

```text
tracking backend 尚未接入
```

如果 Catalog 还告诉 Planner：

> 你可以使用 tracking_iteration。

Planner 会生成一个不可执行 Plan。

所以我建议 T04 第一版就加入非常轻的：

```python
available: bool = True
```

以及：

```python
unavailable_reason: str | None = None
```

例如：

```text
tracking_iteration

available = False

reason =
当前Demo尚未接入经营追踪数据服务
```

---

# 十九、但是 Availability 不是业务权限

比如：

```text
customer_targeting.available = True
```

只代表：

> 当前系统部署环境具备这个能力。

不代表：

> 当前代理人有权限查某个客户。

那仍然属于：

```text
业务权限 / Rule
```

一定不要混。

# 二十、Planner 应该看到 unavailable Capability 吗？

我的建议是：

> **看得到，但明确标记 unavailable。**

而不是完全删掉。

为什么？

例如用户问：

> 看一下任务进展。

如果 Tracking 当前没接好。

如果 Catalog 完全不告诉 Planner Tracking 存在，模型可能乱选：

```text
directional_insight
```

或者自己编一个 Capability。

如果它看到：

```text
tracking_iteration
available=false
```

就能正确形成：

```text
当前系统暂时无法完成该请求
```

而不是规划一个假的替代路径。

# 二十二、五类 Capability 第一版 Catalog

这一张表其实非常关键。

### ① `directional_insight`

```text
purpose
识别与当前Goal相关的经营问题、机会方向、
优先级和支持证据，并形成Opportunity。

required
- goal

optional
- evidence
- feedback
- progress

produces
- opportunity
- evidence

side effect
READ_ONLY
```

limitations：

> 输出的是 Opportunity，而不是固定客户名单或最终产品销售结论。

---

### ② `customer_targeting`

```text
purpose
基于Opportunity形成候选对象范围，
执行圈选、评估和排序并解释依据。

required
- goal
- opportunity

optional
- evidence

produces
- candidate_set
- evidence

side effect
READ_ONLY
```

limitations：

> 候选客户不等于可执行客户；不得跳过后续权限/渠道校验。

这与现有规范一致。

---

### ③ `strategy_generation`

```text
purpose
针对明确经营对象、Goal和已有证据，
形成下一步经营策略。

required
- goal
- customer/object_scope

optional
- opportunity
- evidence
- feedback
- product_or_need_context

produces
- strategy
- evidence

side effect
READ_ONLY
```

limitations：

> Strategy 是经营建议，不是业务事实或权限裁决。

---

### ④ `validation_distribution`

```text
purpose
对拟执行经营动作完成渠道、人员、客户归属、
权限及业务限制校验，并在满足控制要求时支持合法分发。

required
- goal
- customer/object_scope
- intended_action

optional
- strategy
- evidence

produces
- validation_result
- rule_result
- task/distribution_result（条件性）

side effect
MAY_WRITE
```

limitations：

> Agent 不能覆盖规则结果；外部写操作必须经过必要规则校验和用户确认。

规范明确要求外部写操作设置控制点。

---

### ⑤ `tracking_iteration`

```text
purpose
获取Goal、客户经营任务和触达结果的最新进展与反馈，
形成后续重规划所需上下文。

required
- goal

optional
- task
- customer
- strategy
- prior feedback

produces
- progress
- feedback
- evidence

side effect
READ_ONLY
```

limitations：

> 观察到的变化或相关性不得自动解释成因果关系。

# 二十六、Capability Version 的一个小修订

这里暴露出 T07 Plan Contract 的一个值得修正点。

我们原来：

```python
PlanStep(
    capability_id="directional_insight"
)
```

但 Catalog 已经明确：

```text
capability_id
+
capability_version
```

为了可回放，我建议在 **Plan Validator 最终生成正式 Plan 时绑定 Capability Version**。

因此可以把：

```python
capability_id: str
```

升级为：

```python
@dataclass(frozen=True)
class CapabilityRef:
    capability_id: str
    version: str
```

然后：

```python
PlanStep:
    capability_ref: CapabilityRef
```

PlanDraft 仍然允许 LLM 只输出：

```text
capability_id
```

然后 T06 PlanValidator：

```text
capability_id
↓
CapabilityCatalog
↓
resolve active version
↓
CapabilityRef
```

这比让 LLM 生成版本号合理得多。

# 三十、给 Planner 的 Catalog 不一定要直接塞 dataclass

T05 真正给 LLM 时，可以序列化成一个简洁结构：

```json
[
  {
    "id": "directional_insight",
    "purpose": "识别与当前Goal相关的经营机会",

    "available": true
  },
  {
    "id": "customer_targeting",
    "purpose": "基于Opportunity寻找候选经营对象",

  }

```

不是把 Python 内部对象整个 dump 给模型。

# 三十一、T04 建议锁定这些不变量

**CAT-01**：Catalog 描述 Capability，不描述固定执行顺序。
**CAT-02**：Capability 依赖通过所需业务上下文表达，不通过前驱 Capability 表达。
**CAT-03**：Catalog 不包含 Tool handler、Prompt、API endpoint 等执行细节。
**CAT-04**：Catalog 不存具体场景、具体产品和客户筛选规则。
**CAT-05**：Catalog 不承担业务权限裁决。
**CAT-06**：Planner 只能选择 Catalog 中存在的 Capability。
**CAT-07**：不可用 Capability 必须明确标记，不允许 Planner 假设其可执行。
**CAT-08**：Capability 的输出描述用于规划，不代表结果一定产生。
**CAT-09**：`required_context` 表达语义数据依赖，不表达固定 Workflow 依赖。
**CAT-10**：Capability Version 由 Catalog/系统解析，不由 LLM 猜测。
**CAT-11**：Potential write Capability 必须向 Planner 暴露 side-effect 属性。
**CAT-12**：Capability Catalog 和 Tool Registry 保持独立。
