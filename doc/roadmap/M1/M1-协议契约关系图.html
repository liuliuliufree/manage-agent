智慧经营智能体 · M1 Domain Contract

M1 领域协议契约关系图

M1 固定的是智慧经营的“业务语言”，而非固定流程：Goal 定义要达成什么，Plan 动态组合 Capability，Capability 通过 Tool 获得数据、规则、模型和知识，并以 Evidence 与明确状态返回可审计结果。

01 · 依赖边界

Application 是未来唯一的组合点；Domain、Agent Runtime 与 Model 保持独立。

M1-T01
业务语义

Domain

Goal、Plan、Opportunity、Evidence、Capability 契约。
不导入 LLM、Tool Calling、Prompt、Trace。

通用运行时

Agent Runtime

Agent Loop、Tool 调用、Trace、Turn、生命周期。
不感知 NBEV、客户、产品或机会。

模型通信

Model

LLM 配置与流式响应。
不知道 Agent 与业务领域。

Application → Domain Application → Agent → Model Domain ↮ Agent / Model 业务 ID 与 Trace ID 分离

02 · M1 对象关系

箭头描述稳定引用与输入输出，不表示五个 Capability 的固定执行顺序。

核心关系
01

原始经营请求

自然语言保留为 original_request；M1 不负责解析它。

02

Goal

版本化的“要达成什么”。信息不全时显式记录缺失与假设。

03

Plan

围绕 Goal 的轻量步骤依赖图；每步只选择一个 Capability。

04

Capability Request / Result

稳定业务请求与结果信封，承接上下文、输出、状态、规则与审计元数据。

05

Opportunity + Evidence

Opportunity 指向 Goal 版本，并通过 EvidenceLink 保留支持、限制和冲突依据。

这五个环节通过哪些字段连接？

原始经营请求
→
Goal
原文由 Goal.original_request 保留；这是内容承载，不是跨对象 ID 引用。
Goal
→
Plan
Plan.goal_ref.goal_id = Goal.goal_id，且 Plan.goal_ref.version = Goal.version；Plan 必须服务于一个明确 Goal 版本。
PlanStep
↔
CapabilityRequest
PlanStep.capability_id 与 CapabilityRequest.capability_id 选择同一能力；请求以 plan_ref(plan_id, version) 回指 Plan，并另带 goal_ref。
CapabilityRequest
→
CapabilityResult
CapabilityResult.request_id = CapabilityRequest.request_id，capability_id 也保持一致；这是一次调用的主关联键。
Result / Opportunity
→
Evidence
结果通过 evidence_refs、outputs[].evidence_refs 与 rule_result_refs 引用 Evidence.evidence_id；Opportunity 通过 evidence_links[].evidence_id 引用，并以 goal_link 回指 Goal。

不变量：Capability 可跳过、重复和重排；Plan 只校验依赖存在且无环，不演变成第二套 Workflow Engine。

03 · 协议内部细节

字段按已实现的 M1 dataclass 契约归纳；斜体说明为字段的业务语义或校验规则。

M1-T02 ～ T07

Goal

版本化意图

描述代理人要达成的经营目标；回答 What，不携带 Tool、Workflow 或经营结论。

identity
goal_id、version ≥ 1；revise() 新建版本，旧实例不变。
request
original_request 不可为空，始终保留原始自然语言；goal_type 不可为空。
objective
metric、target(value / unit / comparator)、time_horizon。
business scope
audience_scope、product_or_need_context、channel_and_actor。
guarded context
constraints、success_criteria、missing_information、assumptions。
未知不能脑补GoalRef(goal_id, version)

Evidence

可追溯依据

承载可以被引用和审计的事实、规则、模型信号、知识或经验；不把 Agent judgement 伪装成事实。

identity & summary
evidence_id 与非空 summary。
evidence_type
customer_fact、product_fact、business_fact、rule_result、model_signal、experience。
source
source_id、source_type 必填；可含 version、retrieved_at。
validity & quality
effective_period（起止不可倒置）、quality(confidence / completeness / note)。
content
payload 保存结构化内容；引用时使用 evidence_id。
来源必填模型信号 ≠ 客户事实

Opportunity

证据驱动机会

描述与某一 Goal 版本相关的可经营问题与条件，不等同于客户标签、产品答案或可执行名单。

identity & goal
opportunity_id；goal_link(goal_id, version) 必须引用具体 Goal 版本。
problem
opportunity_type 与非空 problem_statement。
evidence_links
至少一条；角色为 supports、limits 或 contradicts，不丢弃反证。
conditions
goal_contributions、conditions、candidate_logic；候选逻辑不是查询或权限裁决。
priority & next
priority(level / score / factors) 的解释因素必填；另含 validity 与 next_action_hint。
必须有 EvidenceLink跨场景可复用

Capability Request / Result

统一业务信封

将“要解决的经营问题”封装为稳定的业务请求和结果；它不执行实现，也不依赖 Tool、Trace、AgentLoop 或 ChatModel。

definition
CapabilityDefinition(capability_id, name, description, version)；描述可替换的业务能力。
request identity
request_id、capability_id、强制 goal_ref；可选 plan_ref。
request context
ActorContext 的 trusted_source 必填；可带对象范围、证据引用、属性和约束。
outputs
CapabilityOutput 包含 output_id、类型、摘要、载荷与 Evidence 引用；结果可带质量。
result semantics
status、rule_result_refs、missing_information、errors、limitations。
audit bridge
execution_meta 保留 trace_id 字符串引用、实现引用和起止时间，Domain 不导入 Agent Trace。
GoalRef / PlanRefEvidence / Rule Result refs实现可替换

Plan / PlanStep

轻量依赖计划

围绕 Goal 的当前能力组合与依赖关系；不是固定五步，也不是含分支、循环、重试策略的 Workflow DSL。

plan identity
plan_id、version ≥ 1、goal_ref、status、supersedes_version。
step selection
PlanStep(step_id, capability_id)：一个步骤选择一个 Capability；步骤可省略、重复或重排。
dependency
depends_on 仅引用已有 step_id；不允许自身依赖、重复 step ID 或循环。
context & control
context_refs 传递已知上下文；control_points 仅定义 rule_check 与 user_confirmation。
life cycle
Plan：active / completed / blocked / superseded / cancelled；Step：planned / ready / running / completed / skipped / blocked / cancelled。
DAG 校验可局部 Replan不引入工作流引擎

04 · Capability 与 Tool：两个层次

稳定业务语义与具体技术/业务接口必须分开，Application 才负责把它们组合起来。

M1-T05
为什么做

Capability

经营问题类型。例如定向洞察、自动圈客、策略生成、校验分发、追踪迭代；它们可独立、组合、重复或跳过。

Application 编排
如何调用

CapabilityRequest → Result

稳定的外部信封。承接 Goal / Plan 引用、上下文、结果、状态、证据、规则结果与执行元数据。

一个或多个
如何实现

Tool

受控接口。提供确定性数据、规则计算、模型推断、知识检索或业务执行；属于 Agent Runtime 侧的技术/业务接口。

Capability 不等于固定流程节点

不能因为出现“策略生成”就要求它一定排在洞察、圈客之后；Plan 只记录当前需要的组合与依赖。

Tool 不等于领域语义

例如查询客户、读取产品知识、校验渠道归属都可以是 Tool；主 Agent 不需要知道其内部实现。

05 · CapabilityResult 状态与错误语义

空结果、信息不足、规则阻断与运行失败具有不同处理语义，不能用同一个空列表或异常代替。

M1-T06
SUCCESS

成功完成；不得同时携带 errors。

PARTIAL_SUCCESS

部分完成；必须说明 errors、缺失信息或 limitations。

NEED_INFORMATION

信息不足；必须携带 missing_information。

BLOCKED

规则明确阻断；必须关联至少一条 rule_result_ref。

NO_RESULT

正常执行但没有发现结果；合法且不等同于失败。

FAILED

运行失败；必须携带至少一条结构化 CapabilityError。

06 · M1 契约守住的边界

这些规则分别由类型不变量、依赖校验和架构评审共同保证。

M1-T08
允许

可表达的变化

  • Goal 缺期限或指标，但将缺失信息显式保留。
  • Goal 与 Plan 均通过新版本表达修改或重规划。
  • 只执行一个 Capability，或在同一 Plan 中重复能力。
  • Plan 形成串行或并行 DAG，只要依赖存在且无环。
  • Opportunity 同时保留支持、限制和反对依据。
禁止混淆

不可越过的边界

  • 把模型分数、经验或 Agent 建议说成客户事实。
  • 没有 EvidenceLink 就形成正式 Opportunity。
  • 规则 BLOCKED 后以模型高分或建议绕过执行边界。
  • 把五类 Capability 固化为每次都必经的流程。
  • 让 Domain 依赖 Tool、Trace、AgentLoop 或 ChatModel。
