
进入 T07。这个阶段最关键的不是“怎么把五个 Capability 排成步骤”，而是要确保：

> **Plan 是 Agent 在某个 Goal 下、基于当前已知事实形成的“当前行动意图”，不是一套预定义 Workflow。**

规范已经明确：Plan 必须在运行时生成，可以决定调用哪些 Capability、顺序、并行、重复、确认、终止和重规划；同时不能把五类能力实现成固定状态机。:chatgpt-content-reference{index="0"}

我建议先把一个设计原则钉死：**Plan 表达“现在准备做什么”，AgentLoop 负责“怎么运行”，Capability 负责“具体完成什么业务动作”。**

---

# 一、Plan 在系统中的准确位置

现在整体关系已经可以收敛成：

```text
Goal
│
│ 我想完成什么
▼
Plan
│
│ 基于当前信息，准备采取哪些业务动作
▼
PlanStep
│
│ 每一步选择一个 Capability
▼
CapabilityRequest
│
▼
CapabilityResult
│
├── SUCCESS
├── PARTIAL_SUCCESS
├── NEED_INFORMATION
├── BLOCKED
├── NO_RESULT
└── FAILED
│
▼
Agent 判断是否继续 / 结束 / Replan
```

这里必须区分三件东西：

```text
PlanStep
=
“计划做什么”

CapabilityRequest
=
“这一次具体怎么调用”

CapabilityResult
=
“这次调用实际发生了什么”
```

例如：

```text
PlanStep:
    对退休现金流机会执行候选客户圈选
```

真正执行时才生成：

```text
CapabilityRequest:
    goal_001
    plan_001
    opportunity=opp_003
    object_scope=...
```

所以 **Plan 不保存 Tool 参数细节，也不保存 Runtime 的 Turn/Trace。**

---

# 二、Plan 应该是运行时业务 Artifact

我建议：

```python
@dataclass(frozen=True)
class Plan:
    plan_id: str
    version: int

    goal_ref: GoalRef

    status: "PlanStatus"

    steps: tuple["PlanStep", ...]

    created_at: datetime
    supersedes_version: int | None = None
```

这里最值得注意的是：

```text
plan_id + version
```

而不是每次 Replan 都生成完全无关系的新 Plan。

例如：

```text
Goal v1

Plan p001 v1
    Insight
    Targeting
    Strategy
```

圈客返回：

```text
NO_RESULT
```

Agent 决定调整：

```text
Plan p001 v2
    Insight（已完成，保留）
    Targeting（旧步骤失效）
    Insight（新增局部洞察）
    Targeting（新条件）
```

也就是说：

> **Replan 通常创建新的 Plan version，并保留仍然有效的已有结果，而不是把整个运行历史推倒重来。**

这正符合当前规范对局部重规划的要求。:chatgpt-content-reference{index="1"}

---

# 三、PlanStatus 和 CapabilityStatus 必须分开

T06 已经有：

```text
CapabilityStatus
```

现在 Plan 自己需要一套很小的状态。

我建议第一版：

```python
class PlanStatus(str, Enum):
    ACTIVE = "active"
    COMPLETED = "completed"
    BLOCKED = "blocked"
    SUPERSEDED = "superseded"
    CANCELLED = "cancelled"
```

不要引入：

```text
FAILED
```

作为主要 Plan 状态。

因为某个 Capability `FAILED`：

```text
≠
整个 Plan 失败
```

Agent 可能完全可以：

```text
换 Tool
换 Capability
调整路径
```

继续完成 Goal。

所以：

```text
Capability FAILED
        ↓
可能触发 Replan
        ↓
新 Plan 仍然 ACTIVE
```

这正体现 Agentic Planning，而不是传统流程失败即终止。

# 四、PlanStep 是核心

我建议第一版：

```python
@dataclass(frozen=True)
class PlanStep:
    step_id: str

    capability_id: str

    objective: str
    reason: str

    depends_on: tuple[str, ...] = ()

    input_refs: tuple["ContextRef", ...] = ()

    expected_outputs: tuple[str, ...] = ()

    control_points: tuple["ControlPoint", ...] = ()

    status: "PlanStepStatus" = PlanStepStatus.PLANNED
```

这里每个字段都有明确职责。

---

# 五、`objective` 和 `reason` 要同时保留

例如：

```text
Capability:
customer_targeting
```

本身太抽象。

所以需要：

```text
objective:
围绕养老现金流机会寻找优先经营客户
```

同时：

```text
reason:
当前500W目标存在较大缺口，上一阶段识别出养老现金流机会，
需要进一步确定具体经营对象
```

两者区别：

```text
objective
=
这一步要完成什么
```

```text
reason
=
为什么当前要做这一步
```

以后前端展示 Plan 时：

> “接下来我会从养老现金流机会中筛选优先客户，因为……”

就可以直接来源于 Plan，而不需要重新让 LLM 即兴解释。

---

# 六、不要用 `step_order`

这个点非常重要。

不建议：

```python
step_order: int
```

然后：

```text
1 Insight
2 Targeting
3 Strategy
4 Validation
5 Tracking
```

这太容易重新退化成 Workflow。

应该用：

```python
depends_on: tuple[str, ...]
```

例如：

```text
step_a
Insight
depends_on=()

step_b
Targeting
depends_on=("step_a",)

step_c
Strategy
depends_on=("step_b",)
```

但也可以：

```text
step_b
Targeting opportunity A
depends_on=("step_a",)

step_c
Targeting opportunity B
depends_on=("step_a",)
```

于是：

```text
          Insight
          /     \
         /       \
 Targeting A   Targeting B
```

B 和 C 可以并行。

这正好表达规范里“哪些调用可以并行”，而无需建 Workflow Engine。:chatgpt-content-reference{index="2"}

---

# 七、重复 Capability 不需要 Loop 语法

比如第一次圈客没有结果：

```text
step_02
customer_targeting
→ NO_RESULT
```

重新规划以后：

```text
step_05
customer_targeting
```

即可。

所以：

```text
step_02.capability_id
==
step_05.capability_id
```

完全合法。

不要设计：

```python
repeat=True
max_loop=3
while_condition=...
```

这些属于 Workflow Engine。

Plan 中的重复调用应该表现为：

> **不同的 Step，调用同一个 Capability。**

这样历史也最清楚。

---

# 八、`input_refs` 不存具体 Tool 参数

建议做一个非常轻的引用：

```python
@dataclass(frozen=True)
class ContextRef:
    ref_type: str
    ref_id: str
```

比如：

```text
ContextRef(
    ref_type="opportunity",
    ref_id="opp_001",
)
```

或者：

```text
ContextRef(
    ref_type="customer",
    ref_id="customer_123",
)
```

因此 PlanStep 可以说：

```text
这一步依赖：

opp_001
customer_123
```

真正运行时，由 Application 把这些引用转成：

```text
CapabilityRequest.context
CapabilityRequest.object_scope
```

这样 Plan 不会被 Capability API 细节污染。

---

# 九、`expected_outputs` 是计划预期，不是结果

例如：

```python
expected_outputs=(
    "candidate_set",
    "ranking_explanation",
)
```

只是告诉：

> 这一步为什么存在，完成标准是什么。

实际结果可能：

```text
NO_RESULT
```

也可能：

```text
PARTIAL_SUCCESS
只有 candidate_set
没有完整 ranking explanation
```

于是 Agent 才能比较：

```text
Expected
vs
Actual
```

决定是否 Replan。

---

# 十、外部写操作怎么办：ControlPoint

这是 T07 唯一值得加入的一点“控制逻辑”。

规范明确要求名单落库、任务创建、客户触达、跨渠道分发、修改状态等外部写操作必须经过规则校验和用户确认。:chatgpt-content-reference{index="3"}

但是不要写：

```python
if approval:
    ...
else:
    ...
```

进 Plan DSL。

建议只表达控制要求：

```python
class ControlPointType(str, Enum):
    RULE_CHECK = "rule_check"
    USER_CONFIRMATION = "user_confirmation"
```

```python
@dataclass(frozen=True)
class ControlPoint:
    control_type: ControlPointType
    description: str
    required: bool = True
```

例如任务创建：

```text
PlanStep
capability:
validation_distribution

control_points:
    RULE_CHECK
    USER_CONFIRMATION
```

Plan 只声明：

> **这一步执行前/过程中必须满足这些控制条件。**

到底怎么确认、由哪个 Tool 校验，属于 Application / Capability。

---

# 十一、PlanStepStatus 也需要和 CapabilityStatus 分开

建议：

```python
class PlanStepStatus(str, Enum):
    PLANNED = "planned"
    READY = "ready"
    RUNNING = "running"
    COMPLETED = "completed"
    SKIPPED = "skipped"
    BLOCKED = "blocked"
    CANCELLED = "cancelled"
```

为什么没有：

```text
FAILED
```

第一版我倾向于没有。

因为 Capability 调用失败以后，这个 Step 最终可能：

```text
重新执行成功
```

也可能：

```text
被 Replan 替换
```

所以 runtime 的失败可以记录在 CapabilityResult 和 Trace 中。

Step 最终是：

```text
COMPLETED
SKIPPED
BLOCKED
CANCELLED
```

如果未来发现确实需要表示“步骤永久失败”，再加入 `FAILED`。

---

# 十二、READY 不需要 Agent 手动写

语义上：

```text
PLANNED
```

当：

```text
所有 depends_on 都已经满足
+
必要前置条件满足
```

就可以进入：

```text
READY
```

这可以由 Application 层计算。

第一版甚至可以不持久化 READY，仅动态判断。

所以 Python Contract 中：

```text
READY
```

可保留，但不要因此马上写：

```text
PlanScheduler
PlanExecutor
DAGEngine
```

目前没有必要。

---

# 十三、最重要的一条：Plan 不负责执行

不要出现：

```python
plan.execute()
step.execute()
plan.next()
```

这些会让 Domain 开始承担 Runtime 职责。

Plan 只是：

> **不可变的业务运行意图描述。**

Application：

```text
读取 Plan
↓
寻找可执行 Step
↓
构造 CapabilityRequest
↓
交给 Agent Runtime
↓
得到 CapabilityResult
↓
更新运行状态 / 必要时生成 Plan v2
```

所以依赖关系继续保持：

```text
Domain
Plan / Goal / Evidence
       ↑
Application
Planner / BusinessAgent
       ↓
Agent Runtime
```

# 十四、Plan Version 如何进行局部重规划

这是 T07 必须提前想清楚的。

假设：

```text
Plan v1

S1 Insight
S2 Targeting
S3 Strategy
```

执行结果：

```text
S1 COMPLETED
S2 NO_RESULT
```

Agent 判断：

> 当前圈客条件过窄，需要重新洞察。

不要修改 v1：

```text
S2.condition = ...
```

而是：

```text
Plan v2
```

其中：

```text
S1
保留为已完成有效步骤

S2
保留历史，但不再继续

S4
重新 Insight

S5
重新 Targeting
```

概念上：

```text
Plan v1
S1 ✓
S2 NO_RESULT
S3 未执行

        ↓ Replan

Plan v2
S1 ✓  ← retained
S4 Insight
S5 Targeting
S6 Strategy
```

这个设计保证：

> 已确认事实和有效结果被保留，而失败路径不会污染新计划。

符合 H-213。:chatgpt-content-reference{index="4"}

第一版我建议**不需要**。

有人可能会想建：

```text
RETAINED
REPLACED
INVALIDATED
NEW
```

目前先不要。

Plan v2 可以通过：

```text
step_id
```

是否复用，以及：

```text

```

和执行历史推断。

如果 M3 实际实现 Replan 后发现确实难以追踪，再引入：

```text
replaced_step_id
```

之类的字段。

现在不要提前设计。

# 十六、Plan 与 CapabilityRequest 的转换关系

这是非常关键的一步。

Plan 中：

```text
PlanStep

capability_id:
customer_targeting

objective:
围绕 opp_001 寻找候选客户

input_refs:
opp_001
```

真正执行时 Application 转成：

```text
CapabilityRequest

goal_001 v1

plan_ref:
plan_001 v1

customer_targeting

context:
opportunity_refs=(opp_001,)

manageable_customers
```

所以：

```text
PlanStep ≠ CapabilityRequest
```

前者是：

> declarative intent

> executable invocation

这个边界建议以后一直守住。

# 二十、Plan 里明确不要出现这些东西

这是 T07 最需要控制住的地方：

| 不应该进入 Plan   | 原因                           |
| ----------------- | ------------------------------ |
| SQL / API 参数    | 属于 Tool                      |
| Prompt            | 属于 Capability/Application    |
| LLM Message       | 属于 Agent Runtime             |
| Trace / Turn      | 属于 Runtime                   |
| 固定五步骤号      | 会退化成 Workflow              |
| `if / else` DSL | 会造第二套 Workflow Engine     |
| `while / loop`  | 重复应通过 Replan/新 Step 表达 |
| retry 次数        | Runtime/Application 决定       |
| 客户业务事实      | 属于 Evidence/Data             |
| 权限裁决结果      | 属于 Rule Result               |
| 产品适配答案      | 属于 Strategy / Decision       |

这是本阶段唯一需要的一张清单。

# 二十一、T07 的不变量

建议正式固定：

**P-01**：Plan 必须关联明确的 Goal version。
**P-02**：Plan 是运行时 Artifact，不由场景名称直接映射固定流程。
**P-03**：PlanStep 选择 Capability，不直接选择底层 Tool。
**P-04**：步骤关系通过 `depends_on` 表达，不通过固定序号表达。
**P-05**：允许只出现部分 Capability。
**P-06**：允许同一个 Capability 出现多次。
**P-07**：PlanStep 不等于 CapabilityRequest。
**P-08**：Plan 不实现 `if/else/loop/retry` DSL。
**P-09**：外部写操作必须显式声明必要 ControlPoint。
**P-10**：Replan 生成新 Plan version，不静默修改旧计划。
**P-11**：重规划应尽可能保留已经确认的事实和有效结果。
**P-12**：Plan 不负责执行，执行属于 Application + Agent Runtime。

# 二十二、T07 最值得写的单元测试

第一组：

```text
只含 strategy_generation
→ 合法
```

第二组：

```text
insight
targeting
insight
→ 合法
```

第三组：

```text
一个 Insight
两个 Targeting 同时依赖它
→ 合法
```

这验证并行结构。

第四组：

```text

→ 非法
```

```text

→ 非法
```

这里可以做一个非常轻的 DAG validation，但**不要因此引入图工作流框架**。

第六组：

```text

→ 应在具体 Plan 生成/审查阶段判定不合格
```

第七组：

```text

→ v1 可保留历史
→ v2 与同一 Goal version 或更新 Goal version 关联
```
