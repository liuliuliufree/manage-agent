
进入 T05。这个阶段我建议我们解决的核心问题是：

> **“智慧经营系统中的一个业务动作，究竟如何被超级 Agent 调用、执行、返回结果？”**

前面 T01～T04 定义的基本都是“名词”：

```text
Goal          我要完成什么
Evidence      我知道什么
Opportunity   我判断有什么机会
```

T05 开始第一次定义“动作”：

```text
Capability    我能够完成哪一类经营任务
```

并把它真正接到你现在已经存在的：

```text
AgentLoop → Tool
```

上。

---

# 一、先解决 Capability 和 Tool 的关系

规范里的语义定义是：

```text
Capability
=
一类稳定、通用的经营能力

Tool
=
向 Agent 提供数据、规则、模型、
知识或业务执行能力的受控接口
```

标准运行关系也是：

```text
Goal
 ↓
Plan
 ↓
Capability
 ↓
Tool / Data / Model / Knowledge / Rule
```

:chatgpt-content-reference{index="0"}

但是项目级 `AGENTS.md` 又明确要求：

> 除主 Agent 外，业务能力和外部能力统一按可插拔 Tool 设计，通过统一工具协议完成注册、发现、参数校验和调用。:chatgpt-content-reference{index="1"}

这两者并不冲突。

我建议正式确定：

```text
语义层

Capability
“自动圈客”
“定向洞察”
“策略生成”


运行层

Tool
“Agent 如何调用这个能力”
```

也就是说：

> **Capability 是业务概念，Tool 是运行协议。**

---

# 二、所以不要再造 `CapabilityLoop`

这是 T05 最重要的架构决策之一。

现在已经有：

```text
AgentLoop
    ↓
Tool Registry
    ↓
Tool Execution
```

不要再出现：

```text
AgentLoop
    ↓
CapabilityEngine
    ↓
CapabilityRegistry
    ↓
CapabilityExecutor
    ↓
ToolRegistry
```

这样马上产生两套：

- 注册机制；
- 参数校验；
- 调用生命周期；
- 错误处理；
- Trace；
- 执行抽象。

没有必要。

更自然的是：

```text
                  Main Business Agent
                         │
                         │ Tool Call
                         ▼
          ┌──────────────────────────────┐
          │ Capability Tool Adapter      │
          │                              │
          │ directional_insight          │
          │ customer_targeting           │
          │ strategy_generation          │
          │ validation_distribution      │
          │ tracking_iteration           │
          └──────────────┬───────────────┘
                         │
                         ▼
                   Capability
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
          Data Tool   Model Tool   Rule Tool
```

不过第一版甚至不必真的出现：

```text
CapabilityToolAdapter
```

这种类。

可能只需要：

```python
Tool(
    name="directional_insight",
    schema=...,
    handler=directional_insight,
)
```

等真实重复代码出现，再抽 Adapter。

---

# 三、Capability 是稳定业务接口

Capability 最重要的价值不是“多包一层函数”。

而是稳定住：

> **Agent 在业务层面能做什么。**

当前基线定义五类：

```text
directional_insight

customer_targeting

strategy_generation

validation_distribution

tracking_iteration
```

它们是：

> Capability category / semantic contract

不是固定 workflow node。

规范明确要求它们可以只调用部分、重复调用、跳过和重排。:chatgpt-content-reference{index="2"}

因此应该允许：

```text
Plan A

directional_insight
↓
customer_targeting
↓
strategy_generation
```

以及：

```text
Plan B

strategy_generation
↓
validation_distribution
```

以及：

```text
Plan C

tracking_iteration
↓
directional_insight
↓
customer_targeting
```

Capability 本身不关心自己是不是：

```text
第1步
第2步
第3步
```

---

# 四、T05 建议先定义两个对象

第一版不用太复杂：

```text
CapabilityRequest

CapabilityResult
```

外加一个非常轻的：

```text
CapabilityDefinition
```

关系：

```text
CapabilityDefinition
描述“我是谁、能干什么”

CapabilityRequest
描述“这一次让我干什么”

CapabilityResult
描述“这一次干出了什么”
```

---

# 五、CapabilityDefinition

建议：

```python
@dataclass(frozen=True)
class CapabilityDefinition:
    capability_id: str
    version: str

    name: str
    description: str

    input_schema_version: str
    output_schema_version: str
```

例如：

```python
CapabilityDefinition(
    capability_id="directional_insight",
    version="1.0",
    name="定向洞察",
    description="识别与当前经营Goal相关的机会方向、优先级和证据",
    input_schema_version="1.0",
    output_schema_version="1.0",
)
```

注意：

```text
capability_id
```

应该稳定。

不要：

```text
opening_campaign_insight
pension_insight
dividend_product_insight
```

否则只是换个名字复制场景。

---

# 六、第一版暂时不做 Capability Enum

这里我建议和 OpportunityType 一样：

```python
capability_id: str
```

而不是：

```python
class CapabilityType(Enum):
    ...
```

原因不是五类会频繁变化，而是：

> 我们现在还在搭通用机制，没有必要让 runtime code 对具体业务 Capability 枚举产生编译级依赖。

未来可以建立：

```text
Capability Registry
```

进行受控注册。

但不是 M1 现在做。

---

# 七、CapabilityRequest 是真正的调用契约

基线已经明确 Capability 输入至少应该包含：

- `goal_id`
- `plan_id`
- 上下文
- 对象范围
- 授权主体
- 数据时间点
- 所需输出
- 约束

:chatgpt-content-reference{index="3"}

我建议第一版整理成：

```python
@dataclass(frozen=True)
class CapabilityRequest:
    request_id: str

    goal_ref: GoalRef
    plan_ref: PlanRef | None

    capability_id: str

    context: "CapabilityContext"

    object_scope: "ObjectScope | None"
    actor_context: "ActorContext"

    constraints: tuple["CapabilityConstraint", ...] = ()
    requested_outputs: tuple[str, ...] = ()
```

---

# 八、为什么 `goal_ref` 一定要有版本

与 Opportunity 相同：

```python
@dataclass(frozen=True)
class GoalRef:
    goal_id: str
    version: int
```

否则：

```text
Goal v1 = 500W
Goal v2 = 400W
```

你无法知道本次 Capability 调用到底服务于哪个目标。

---

# 九、PlanRef 可以暂时允许为空

因为 T07 才正式定义 Plan。

所以第一版：

```python
@dataclass(frozen=True)
class PlanRef:
    plan_id: str
    version: int
```

但是：

```python
plan_ref: PlanRef | None
```

是合理的。

为什么？

因为 M1 单元测试或者未来直接测试 Capability 时，不应该为了调用：

```text
directional_insight
```

必须先制造一个假 Plan。

到 M2 真正由 Planner 调用时，再要求 production path 带 PlanRef。

---

# 十、CapabilityContext 不应该变成万能 dict

最偷懒的设计是：

```python
context: dict[str, Any]
```

第一版可能很好用，半年后基本不可治理。

但另一方面，也不能现在把所有上下文都建模。

建议做一个很薄的结构：

```python
@dataclass(frozen=True)
class CapabilityContext:
    evidence_refs: tuple[str, ...] = ()
    opportunity_refs: tuple[str, ...] = ()
    prior_result_refs: tuple[str, ...] = ()
    business_context: dict[str, Any] | None = None
```

这里有意区分：

```text
结构化的核心上下文引用
```

和：

```text
暂时无法稳定建模的业务扩展上下文
```

例如自动圈客：

```text
evidence_refs
opportunity_refs
```

就是非常重要的输入。

策略生成：

```text
customer_ref
opportunity_ref
evidence_refs
```

也可以通过 object_scope/context 组合。

---

# 十一、ObjectScope 表示“这次能力处理谁”

Goal 的 `AudienceScope` 表达：

> 用户整体目标针对谁。

而 CapabilityRequest 的 `ObjectScope` 表达：

> **这一次 Capability Call 具体处理什么对象。**

两者不要混。

例如：

```text
Goal AudienceScope
=
当前代理人全部可经营客户
```

到了策略阶段：

```text
Capability ObjectScope
=
customer_123
```

所以建议：

```python
@dataclass(frozen=True)
class ObjectScope:
    object_type: str
    refs: tuple[str, ...] = ()
    expression: str | None = None
```

例如：

```python
ObjectScope(
    object_type="customer",
    refs=("customer_123",),
)
```

或者圈客：

```python
ObjectScope(
    object_type="audience",
    expression="current_actor_manageable_customers",
)
```

---

# 十二、ActorContext 必须由可信上下文提供

建议：

```python
@dataclass(frozen=True)
class ActorContext:
    actor_ref: str
    channel_ref: str | None = None
    authorization_ref: str | None = None
```

这一块一定不要让模型生成。

来源应该是：

```text
Authentication
Runtime Context
Authorization System
```

Agent 只读取。

因为权限和归属不能由 Agent 猜测或覆盖。:chatgpt-content-reference{index="4"}

---

# 十三、Data Time Point 很重要，但不要单独散落

规范要求 Capability 输入带数据时间点。

我建议放到：

```python
CapabilityContext
```

里：

```python
@dataclass(frozen=True)
class CapabilityContext:
    as_of: datetime | None = None

    evidence_refs: tuple[str, ...] = ()
    opportunity_refs: tuple[str, ...] = ()
    prior_result_refs: tuple[str, ...] = ()

    business_context: dict[str, Any] | None = None
```

于是每一次调用都可以明确：

> “我是基于什么时间点的数据做判断的？”

以后回放非常关键。

---

# 十四、CapabilityConstraint 与 Goal Constraint 不一样

Goal：

```text
优先老客户
```

是 Goal-level Constraint。

Capability 可能把它翻译成：

```text
本次圈客：
只允许在某客户范围内查询
最多返回100人
```

所以 CapabilityRequest 可以有运行时约束：

```python
@dataclass(frozen=True)
class CapabilityConstraint:
    key: str
    value: Any
    source: str
```

例如：

```python
CapabilityConstraint(
    key="max_candidates",
    value=100,
    source="plan",
)
```

或者：

```python
CapabilityConstraint(
    key="customer_type_preference",
    value="existing_customer",
    source="goal",
)
```

---

# 十五、requested_outputs 非常有价值

为什么？

因为同一个 Capability 不一定每次都需要返回所有东西。

比如：

> 最近有什么值得关注的经营机会？

洞察可能只需要：

```text
Opportunity
```

而完整经营：

```text
Opportunity
+
Priority explanation
+
Candidate logic
```

所以可以：

```python
requested_outputs=(
    "opportunities",
    "priority_explanation",
    "candidate_logic",
)
```

第一版它只是 hint。

不能让 Agent 通过：

```text
requested_outputs
```

绕过 Capability 的硬要求。

比如 Evidence 必须存在，那么即便没 request：

```text
evidence
```

Capability 仍必须生成/关联。

---

# 十六、CapabilityResult

这是 T05 另一个核心。

规范要求输出包括：

- 结构化结果；
- 证据引用；
- 事实/判断类型；
- 质量或置信信息；
- 规则结果；
- 错误；
- 建议下一步；
- 版本；
- 审计。:chatgpt-content-reference{index="5"}

我建议先定义：

```python
@dataclass(frozen=True)
class CapabilityResult:
    result_id: str
    request_id: str

    capability_id: str
    capability_version: str

    status: str

    outputs: tuple["CapabilityOutput", ...]

    evidence_refs: tuple[str, ...] = ()
    rule_result_refs: tuple[str, ...] = ()

    quality: "ResultQuality | None" = None

    errors: tuple["CapabilityError", ...] = ()
    next_action_hints: tuple["NextActionHint", ...] = ()

    execution_meta: "CapabilityExecutionMeta | None" = None
```

这里：

```text
status
errors
```

具体语义暂时留到 T06。

T05 先把位置留出来。

---

# 十七、为什么 Outputs 不能只是 `dict`

例如：

```python
outputs: dict[str, Any]
```

太宽松。

但现在又不能定义：

```text
InsightResult
TargetingResult
StrategyResult
```

五套完全不同 Envelope。

我建议：

```python
@dataclass(frozen=True)
class CapabilityOutput:
    output_type: str
    ref: str | None = None
    value: Any | None = None
```

例如洞察：

```python
CapabilityOutput(
    output_type="opportunity",
    ref="opp_001",
)
```

圈客：

```python
CapabilityOutput(
    output_type="candidate_set",
    ref="candidate_set_001",
)
```

策略：

```python
CapabilityOutput(
    output_type="strategy",
    ref="strategy_001",
)
```

这样 Envelope 稳定。

而每一种：

```text
Opportunity
CandidateSet
Strategy
```

仍然拥有自己的领域 Contract。

---

# 十八、不要把实际领域对象全塞进 Result

比如：

```python
CapabilityResult(
    outputs=(整个Opportunity对象, 整个Customer对象, ...)
)
```

第一版看似方便。

但是后面：

- API；
- 存储；
- 回放；
- 异步；
- Trace；

都会变麻烦。

更稳的是：

```text
Result
 ├── output refs
 ├── evidence refs
 ├── rule refs
 └── meta
```

具体对象由对应领域层/应用层管理。

当然当前纯内存 Demo 中，可以允许：

```python
value
```

存在。

所以 `CapabilityOutput` 同时保留：

```text
ref
value
```

但设计上优先 ref。

---

# 十九、ResultQuality

和 Evidence 一样：

不要把所有东西都硬塞一个 confidence。

建议：

```python
@dataclass(frozen=True)
class ResultQuality:
    confidence: float | None = None
    completeness: float | None = None
    limitations: tuple[str, ...] = ()
```

例如圈客：

```text
completeness = 0.75

limitations:
新客户历史数据不足
```

策略：

```text
limitations:
客户最新预算信息缺失
```

---

# 二十、CapabilityExecutionMeta

这个字段不要替代现有 Trace。

这是需要特别注意的。

现有：

```text
Trace
Turn
ToolExecution
```

负责：

> 程序怎么运行的。

CapabilityExecutionMeta 只负责**业务级调用元数据**。

例如：

```python
@dataclass(frozen=True)
class CapabilityExecutionMeta:
    started_at: datetime
    completed_at: datetime | None = None

    trace_id: str | None = None

    tool_versions: tuple[str, ...] = ()
    model_versions: tuple[str, ...] = ()
    rule_versions: tuple[str, ...] = ()
    knowledge_versions: tuple[str, ...] = ()
    feature_versions: tuple[str, ...] = ()
```

重点：

```text
trace_id
```

把业务调用和 runtime trace 关联起来。

但不要复制：

```text
Turn
ToolExecution
LLM messages
```

到 Domain。

最终关系变成：

```text
Application
────────────────────────────

Planner
Business Agent
Capability invocation


Runtime
────────────────────────────

AgentLoop

Model
────────────────────────────

ChatModel
```

而运行时：

```text

       │
       ▼

       │
       ▼

       │
       ▼

       │
       ▼

       ├── Data Tool

       └── Knowledge Tool
```

# 二十二、这里还有一个非常关键的问题：Capability 能不能调用 LLM？

答案：

> **可以，但 Agent 不需要知道。**

例如：

```text
strategy_generation
```

内部可能需要 LLM。

而：

```text
validation_distribution
```

可能完全是确定性逻辑。

甚至：

```text
customer_targeting
```

可能只是现有营销平台 API。

主 Agent 只看到：

```text
Capability Contract
```

不知道：

```text
local Python
external API
another LLM call
existing marketing platform
```

这正好符合项目约束：

> Tool 内部可以是本地函数、外部服务适配器或独立大模型调用，主 Agent 不感知具体实现。:chatgpt-content-reference{index="6"}

---

# 二十三、但是不要机械变成多个 Agent

例如：

```text
DirectionalInsightAgent
TargetingAgent
StrategyAgent
ValidationAgent
```

仍然不推荐。

即使 Strategy 内部调用一次 LLM：

```text
strategy_generation capability
    ↓
LLM
```

它仍然只是一个 Capability 实现。

不是一个独立 Agent。

除非未来真的出现：

- 独立生命周期；
- 独立安全边界；
- 自治循环；
- 明确并行自治价值。

否则保持单一经营超级 Agent。规范对此有明确约束。:chatgpt-content-reference{index="7"}

# 二十五、用“定向洞察”跑一次

输入：

```text
Goal
500W NBEV
```

Application 构造：

```python
request = CapabilityRequest(
    request_id="req_001",

    goal_ref=GoalRef(
        goal_id="goal_001",
        version=1,
    ),

    plan_ref=None,

    capability_id="directional_insight",

    context=CapabilityContext(
        as_of=...,
        evidence_refs=(),
    ),

    object_scope=ObjectScope(
        object_type="audience",
        expression="current_actor_manageable_customers",
    ),

    actor_context=ActorContext(
        actor_ref="agent_001",
        channel_ref="individual_insurance",
    ),

    requested_outputs=(
        "opportunities",
    ),
)
```

得到：

```text
CapabilityResult

status
    success

outputs
    opportunity → opp_001
    opportunity → opp_002

evidence_refs
    ev_001
    ev_002
    ev_003

execution_meta
    trace_id
    knowledge_version
    model_version
```

主 Agent 下一次看到的应该是：

```text
形成2个Opportunity

opp_001
养老现金流规划机会

opp_002
家庭长期财富安排机会
```

而不是底层：

```text
查了哪个SQL
调用了哪个HTTP API
模型prompt是什么
用了几个Turn
```

这些属于 Trace。

# 二十六、再用校验能力验证架构

```text
Capability:
validation_distribution
```

内部完全可能不需要 LLM：

```text
customer
↓
channel rule service
↓
ownership service
↓
permission service
↓
BLOCKED
```

但对于主 Agent 来说仍然是：

```text
CapabilityRequest
↓

```

所以五种 Capability 虽然实现完全不同：

```text
Insight → LLM + Knowledge

Targeting → Data Platform

Strategy → LLM + Knowledge

Validation → Rule Engine

Tracking → Event/Data Service
```

对 Agent 来说调用契约完全一致。

**这正是 Capability 抽象真正的价值。**

# 二十七、T05 的架构不变量

建议正式记下这 12 条：

| 编号 | 不变量                                                  |
| ---- | ------------------------------------------------------- |
| C-01 | Capability 表达稳定经营能力，不表达固定工作流节点       |
| C-02 | Capability 与 Tool 语义分离，但运行时复用统一 Tool 协议 |
| C-03 | 不新增第二套 Capability Loop / Execution Engine         |
| C-04 | CapabilityRequest 必须关联 Goal 版本                    |
| C-05 | 生产 Plan 调用最终必须可关联 Plan 版本                  |
| C-06 | Actor/Channel 来自可信 Runtime Context，不由 LLM 猜测   |
| C-07 | Capability 输出统一使用 Result Envelope                 |
| C-08 | Result 必须能够关联 Evidence、Rule、版本和 Trace        |
| C-09 | 不同 Capability 可以有完全不同内部实现                  |
| C-10 | Capability 内部使用 LLM 不等于新增独立 Agent            |
| C-11 | Capability 不直接依赖固定场景、具体产品                 |
| C-12 | Capability 的实现细节不得泄漏给主 Agent                 |
