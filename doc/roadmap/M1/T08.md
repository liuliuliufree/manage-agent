
进入 T08。到这一阶段，M1 不再增加新的领域对象，而是专门做一件事：

> **证明 T01～T07 形成的这些 Contract，不仅“能用”，而且能够阻止项目未来沿着错误方向演化。**

所以 T08 不是普通的“测几个 dataclass 能不能创建”，而应该分成三层：

```text
Layer 1  Contract Test
         ↓
字段、不变量、引用关系是否合法

Layer 2  Architecture/Semantic Test
         ↓
有没有把事实、判断、规则、Plan、Capability 边界搞混

Layer 3  Cross-scenario Regression
         ↓
换目标、换场景、换产品、跳步骤以后，
这套抽象还能不能成立
```

当前规范本身也把“部分 Capability、重复 Capability、规则阻断后重规划、用户修改 Goal、跨场景复用”等列为必须验证的内容。:chatgpt-content-reference{index="0"}

# 一、先定义 T08 的最终验收目标

T08 结束后，我们要敢于回答下面这些问题：

| 问题                                               | 必须做到 |
| -------------------------------------------------- | -------- |
| Goal 信息不全时会不会偷偷补事实？                  | 不会     |
| Evidence 会不会把模型分数包装成客户事实？          | 不会     |
| Opportunity 会不会退化成“某产品目标客户”？       | 不会     |
| Capability 会不会变成五个固定 Workflow 节点？      | 不会     |
| `NO_RESULT` 和系统报错能不能区分？               | 能       |
| 规则明确 BLOCKED 时 Agent 有没有机会绕过？         | 没有     |
| Plan 是否允许只调用一个 Capability？               | 允许     |
| Plan 是否允许重复调用同一 Capability？             | 允许     |
| Plan 是否支持并行依赖而非固定顺序？                | 支持     |
| 换掉开门红和两款 Demo 产品后 Contract 是否仍成立？ | 成立     |

这就是 M1 的 Exit Gate。

# 二、T08-01：Goal Contract 攻击测试

第一类专门攻击 T02。

## Case G01：缺失信息合法存在

输入：

```text
“最近有什么值得关注的经营机会？”
```

期望：

```text
metric = None
target = None

Goal 创建成功
```

不允许：

```text
target = 自动生成某个经营指标
```

因为规范要求字段可以为空，但缺失状态必须显式表达。:chatgpt-content-reference{index="1"}

---

## Case G02：时间不能脑补

输入：

```text
“开门红阶段完成500W NBEV”
```

在没有权威开门红日期配置的情况下：

```python
TimeHorizon(
    raw_expression="开门红阶段",
    start_at=None,
    end_at=None,
)
```

同时存在：

```python
MissingInformation(
    field="time_horizon.end_at",
    ...
)
```

测试必须防止：

```text
2026-10-01 ~ 2027-03-31
```

这种无来源日期进入 Fact。

---

## Case G03：Goal 不得包含 Plan 字段

可以直接做结构测试：

```python
assert not hasattr(goal, "next_capability")
assert not hasattr(goal, "workflow_id")
assert not hasattr(goal, "tool_name")
```

当然这不是完美防御，但非常直观。

Goal 永远回答：

```text
What
```

而不是：

```text
How
```

---

## Case G04：Goal 版本不可覆盖

```text
Goal v1
target = 500

用户修改目标

Goal v2
target = 400
```

测试：

```text
goal_id 相同
version 不同
v1 仍然保持500
```

不要：

```python
goal.target = 400
```

---

# 三、T08-02：Evidence Contract 攻击测试

这一组非常关键。

规范要求系统区分客户事实、产品事实、业务规则、模型判断、经营经验和 Agent 决策。:chatgpt-content-reference{index="2"}

## Case E01：Fact 必须有 Source

非法：

```python
Evidence(
    evidence_type=CUSTOMER_FACT,
    source=EvidenceSource(
        source_id=""
    )
)
```

应该直接 Contract Validation 失败。

---

## Case E02：模型结果不能升级为 Fact

输入：

```text
养老需求模型评分 = 0.82
```

合法：

```text
MODEL_SIGNAL
```

非法：

```text
CUSTOMER_FACT:
客户有养老需求
```

这个测试非常值得保留。

---

## Case E03：Agent Judgment 不是 Evidence

应该确保：

```python
EvidenceType.AGENT_JUDGEMENT
```

根本不存在。

例如：

> 客户存在养老规划机会。

应该出现在：

```text
Opportunity
```

而不是 Evidence。

---

## Case E04：经营经验不能变规则

```text
EXPERIENCE:
临近退休客户通常更容易从现金流切入
```

不能变成：

```text
RULE_RESULT:
临近退休客户必须销售年金
```

规范也明确规定经营经验只能作为参考，不能替代事实和业务规则。:chatgpt-content-reference{index="3"}

---

## Case E05：规则必须带来源和版本

```text
RULE_RESULT
```

如果：

```text
source_id = channel_eligibility
version = None
```

第一版是否完全禁止 `None` 可以讨论，但至少业务执行路径必须要求版本存在。

否则未来无法审计：

> 到底是哪版规则拦住客户的？

---

# 四、T08-03：Opportunity Contract 攻击测试

这里主要防止 Demo 逻辑渗入领域模型。

## Case O01：Opportunity 没 Evidence

例如：

```text
“养老机会”
```

但：

```python
evidence_links=()
```

如果把它标记为正式形成的 Opportunity，应该判非法。

规范明确要求 Opportunity 必须关联形成依据。:chatgpt-content-reference{index="4"}

---

## Case O02：产品名不能成为 OpportunityType

不建议仅靠代码 regex 禁止产品名，因为未来无法维护。

这属于：

> Semantic Architecture Test。

例如测试 fixture：

```text
opportunity_type = "yuxiang_jinyue_customer"
```

预期：

```text
Architecture Review Fail
```

原因不是字符串本身违法，而是：

> Opportunity 被产品化了。

---

## Case O03：Product recommendation 不能进入 problem_statement

错误：

```text
客户适合购买御享金越年金
```

正确：

```text
客户存在长期养老现金流规划空间
```

这个最好作为团队的 **Golden / Anti-pattern Case**，而不是试图用程序自动理解文本是否合法。

---

## Case O04：支持证据和反对证据同时存在

例如：

```text
SUPPORTS
养老需求评分0.82

CONTRADICTS
客户明确表示暂不考虑养老配置
```

两者必须都保留。

不能因为系统想生成一个漂亮 Opportunity，就把 `CONTRADICTS` 删除。

规范同样要求冲突来源不得由 Agent 静默择一。:chatgpt-content-reference{index="5"}

---

# 五、T08-04：Capability Contract 攻击测试

这里验证 T05。

## Case C01：五类能力使用统一 Request/Result

例如：

```text
directional_insight
strategy_generation
validation_distribution
```

内部实现可以完全不同，但外部都必须：

```text
CapabilityRequest
        ↓
CapabilityResult
```

不能出现：

```text
InsightRequest
StrategySpecialRequest
ValidationMagicResponse
```

各自重新发明 Envelope。

---

## Case C02：Capability 不等于固定步骤号

测试：

```text
strategy_generation
```

可以独立请求。

不能要求：

```text
必须先存在 insight_result
必须先存在 targeting_result
```

除非当前具体策略场景真的缺这些信息。

---

## Case C03：Capability 内部实现可替换

Fake 两个实现：

```text
Implementation A
纯 Python Function

Implementation B
调用 Fake ChatModel
```

二者对调用方暴露完全相同：

```text
CapabilityRequest → CapabilityResult
```

这就证明 Capability 并没有和 LLM 强绑定。

---

# 六、T08-05：Status Contract 攻击测试

这一组可以写成真正非常严格的单元测试。

### `SUCCESS + error`

非法：

```python
status=SUCCESS
errors=(some_error,)
```

---

### `FAILED + no error`

非法：

```python
status=FAILED
errors=()
```

---

### `BLOCKED + no rule`

非法：

```python
status=BLOCKED
rule_result_refs=()
```

---

### `NEED_INFORMATION + no missing information`

非法。

---

### `NO_RESULT + empty output`

合法。

这是非常重要的：

```text
没有客户
≠
系统异常
```

---

### `PARTIAL_SUCCESS + no limitation/error/missing`

非法或者至少强 warning。

因为必须说明：

> 部分成功究竟部分在哪里。

---

# 七、T08-06：最关键的 Rule Boundary Test

这个建议单独测试。

场景：

```text
Customer A

MODEL_SIGNAL:
价值评分 0.99

Opportunity:
非常值得经营

Strategy:
强烈建议优先触达
```

随后：

```text
RULE_RESULT:
channel_eligibility = BLOCKED
```

最终：

```text
CapabilityResult.status = BLOCKED
```

系统不能出现任何：

```text
override = True
```

或者：

```text
因为模型评分高，所以允许继续
```

规范对此是硬约束。:chatgpt-content-reference{index="6"}

这是智慧经营项目里非常值得长期保留的 Regression Test。

---

# 八、T08-07：Plan Contract 攻击测试

这是 T08 里面最重要的一组之一。

## Case P01：只执行部分 Capability

合法：

```text
Plan

S1 strategy_generation
```

应该通过。

规范明确要求至少有一个“只调用部分 Capability”的测试。:chatgpt-content-reference{index="7"}

---

## Case P02：重复 Capability

合法：

```text
S1 directional_insight
S2 customer_targeting
S3 directional_insight
```

不能因为：

```text
directional_insight 已经出现过
```

拒绝。

规范同样要求覆盖重复 Capability。:chatgpt-content-reference{index="8"}

---

## Case P03：能力顺序改变

合法：

```text
tracking_iteration
↓
directional_insight
↓
strategy_generation
```

测试不能假定：

```text
Insight < Targeting < Strategy < Validation < Tracking
```

---

## Case P04：并行 DAG

合法：

```text
          S1 Insight
           /      \
          /        \
S2 Targeting A    S3 Targeting B
```

即：

```python
S2.depends_on = ("S1",)
S3.depends_on = ("S1",)
```

---

## Case P05：不存在的依赖

非法：

```python
S3.depends_on = ("S999",)
```

---

## Case P06：循环依赖

非法：

```text
S1 depends S2
S2 depends S1
```

这里可以实现一个极轻量的 DAG validator。

只验证：

```text
不存在 dependency cycle
```

不要因此引入 LangGraph、DAG Engine 或 Workflow Framework。

---

# 九、T08-08：Replan Contract Test

虽然真正 Replan 是 M3，但 M1 可以验证数据结构支持。

初始：

```text
Plan v1

S1 Insight           COMPLETED
S2 Targeting         NO_RESULT
S3 Strategy          未执行
```

产生：

```text
Plan v2
```

要求：

```text
plan_id 相同
version = 2
supersedes_version = 1
```

并且：

```text
已确认的 S1 结果仍然可以被 v2 引用
```

而不是：

```text
所有东西重新生成一次
```

这就是“局部重规划”的结构基础。规范明确要求重规划时保留已经确认的事实和有效结果。:chatgpt-content-reference{index="9"}

---

# 十、T08-09：最值得做的跨场景攻击测试

这一组不是普通 unit test，而是 M1 最重要的“架构验收”。

我们故意不用 Demo。

### 场景 A：日常单客户

用户：

> 帮我看看王女士下一步怎么经营。

要求：

```text
Goal
↓
Plan
↓
Strategy Capability
```

不需要：

```text
Insight → Targeting
```

---

### 场景 B：没有产品背景

用户：

> 最近有哪些客户经营机会值得关注？

Goal 中：

```text
product_or_need_context = None
```

系统结构必须仍然成立。

---

### 场景 C：换其他产品

把：

```text
御享分红26
御享金越年金
```

全部替换成：

```text
Product X
Product Y
```

如果领域 Contract 或测试大量报错：

> 说明 Demo 产品已经偷偷进入架构。

---

### 场景 D：非绩效型 Goal

例如：

> 帮我看看近期沉默客户有没有值得重新经营的机会。

这时：

```text
metric = None
target = None
```

仍应正常建 Goal、Plan 和 Opportunity。

---

### 场景 E：Goal 中途变化

原来：

```text
500W NBEV
```

用户：

> 调成400W，优先老客户。

结果：

```text
Goal v2
```

而不是：

```text
修改 Goal v1
```

后面的 Plan 必须能够基于新 Goal 版本。

# 十一、建议 T08 将测试代码按三组组织

即使目前代码目录尚未最终确定，我倾向于概念上：

```text
tests/
│
├─ domain/
│  ├─ test_goal.py
│  ├─ test_evidence.py
│  ├─ test_opportunity.py
│  ├─ test_capability.py
│  └─ test_plan.py
│
├─ contract/
│  ├─ test_capability_result_status.py
│  └─ test_plan_dependency.py
│
└─ architecture/
   └─ test_generic_scenarios.py
```

这里不要机械照搬，如果当前测试目录已经有规范，就遵循现有项目结构。

其中：

```text
domain/
```

主要验证数据结构。

```text
contract/
```

主要验证协议不变量。

```text
architecture/
```

主要验证：

> “换场景以后，我们是不是偷偷写成了固定 Workflow？”

# 十二、需要区分哪些东西可以自动测试，哪些不能

这是 T08 很重要的现实问题。

并不是所有架构原则都应该试图写成 Python assert。

例如：

| 原则                      | 自动化测试程度      |
| ------------------------- | ------------------- |
| FAILED 必须有 Error       | 高                  |
| BLOCKED 必须有 RuleResult | 高                  |
| Plan 不能循环依赖         | 高                  |
| Goal version >= 1         | 高                  |
| Fact 必须有 Source        | 高                  |
| Opportunity 不应绑定产品  | 中低                |
| Strategy 不应硬编码 Demo  | 中低                |
| 不应机械拆多个 Agent      | Review              |
| Prompt 不得存业务规则     | Review              |
| 不能重建已有营销平台能力  | Architecture Review |

所以 T08 最好明确：

```text
Machine-enforced invariant
```

和：

```text
Review-enforced invariant
```

两类。

不要为了自动化测试覆盖率，写一堆脆弱的：

```python
assert "御享" not in some_string
```

这种测试。

它测试的不是架构，只测试某几个关键词。

# 十三、我建议 M1 最终形成一张 Contract Matrix

这张表后面非常有价值。

| 对象             | 必须保证                               | 明确禁止                           |
| ---------------- | -------------------------------------- | ---------------------------------- |
| Goal             | 原始请求、结构化目标、版本、缺失/假设  | Tool、Workflow、经营结论           |
| Evidence         | 类型、来源、时间、版本                 | Agent 判断冒充 Fact                |
| Opportunity      | Goal关联、Evidence、问题判断、候选逻辑 | 固定产品答案、固定客群标签         |
| Capability       | 稳定业务动作、统一 Request/Result      | 固定 Workflow 节点、第二套 Runtime |
| CapabilityResult | 明确 Status、Evidence、Rule、Error     | 空列表表示所有失败                 |
| Plan             | 动态 Capability 组合、依赖关系、版本   | 固定五步、if/else/loop DSL         |
| Agent Runtime    | Loop、Tool、Trace                      | NBEV、客户、产品等业务语义         |

这其实就是整个 M1 最浓缩的结果。

# 十四、T08 的 M1 Release Gate

我建议最后把 M1 的完成标准直接定义成以下逻辑：

```text
Goal Contract Tests PASS

AND

Evidence Contract Tests PASS

AND

Opportunity Contract Tests PASS

AND

Capability Contract Tests PASS

AND

Status Contract Tests PASS

AND

Plan Contract Tests PASS

AND

Partial Capability Scenario PASS

AND

Repeated Capability Scenario PASS

AND

Rule Block Scenario PASS

AND

Non-Demo Scenario PASS

AND

Goal Version Change Scenario PASS
```

全部成立：

```text
M1 = DONE
```

任何一个核心硬约束没通过，都不要急着进入：

```text
M2 Goal Parser / Planner
```

否则 LLM 接入以后，只会把已有结构问题放大。

# 十五、M1 到这里真正完成了什么

实际上现在已经拥有完整的领域契约链：

```text
Natural Language
      │
      │ M2
      ▼
┌─────────────┐
│    Goal     │
│ 我要完成什么 │
└──────┬──────┘
       │
       ▼
┌─────────────┐
│    Plan     │
│ 当前准备怎么做│
└──────┬──────┘
       │
       ▼
┌──────────────────┐
│ CapabilityRequest│
└─────────┬────────┘
          ▼
┌─────────────┐
│ Capability  │
│ 经营业务动作 │
└─────────┬───┘
          ▼
 Data / Knowledge / Model / Rule
          │
          ▼
┌──────────────────┐
│ CapabilityResult │
│ Status + Outputs │
└───────┬──────────┘
        │
        ├──── Evidence
        │
        ├──── Opportunity
        │
        └──── Rule Result
```

而更关键的是，每一层的职责现在都比较干净。

**M1 的成果不是“写了十几个 dataclass”，而是给后面的 LLM 划出了不可越过的业务边界。**

这非常重要，因为到了 M2，模型可以负责：

```text
理解
规划
选择
组织
解释
```

但它不能重新发明：

```text
事实是什么
规则能否绕过
什么叫成功
什么叫没有结果
Goal 和 Plan 的边界
```

这些已经由 M1 的 Contract 固定下来。

因此，T08 做完以后，我认为 **M1 可以正式结束**。下一阶段 M2 就不再继续扩充领域模型，而应该进入第一个真正运行起来的链路：

```text
Natural Language
        ↓
Goal Parser
        ↓
Goal
        ↓
Planner
        ↓
Plan
```

这会是智慧经营超级 Agent 第一次真正站在你现有 `AgentLoop` 之上开始工作。
