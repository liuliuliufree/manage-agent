
进入 T04。这里我建议先把 Opportunity 的一句话定义定死：

> **Opportunity = 针对某个 Goal，基于一组可追溯 Evidence 形成的“可经营问题/机会判断”，并描述谁可能适配、为什么值得关注、有哪些限制、如何进一步圈客或行动。**

它不是客户标签，不是产品推荐，不是圈客名单，更不是业务规则。规范本身要求 Opportunity 与场景、产品解耦，同时必须包含形成条件、证据、目标贡献、适配对象、限制、优先级、有效期和下一步，并能进一步形成圈客逻辑。:chatgpt-content-reference{index="0"}

---

# 1. 先确定 Opportunity 在整个链路的位置

现在领域关系可以明确为：

```text
Goal
 │
 │ 我想完成什么？
 ▼
Evidence
 │
 │ 当前已知什么？
 ▼
Opportunity
 │
 │ 基于这些依据，
 │ 存在什么值得经营的问题/机会？
 ▼
Candidate Logic
 │
 │ 什么样的人可能符合？
 ▼
自动圈客
```

最重要的是中间这条：

```text
Evidence → Opportunity
```

例如：

```text
Evidence
- 客户逐渐接近退休年龄
- 当前保障中养老现金流配置较弱
- 近期多次关注退休收入
- 养老需求模型信号较高

            ↓

Opportunity

退休阶段的长期养老现金流
可能存在进一步规划空间
```

而不是：

```text
客户年龄52岁
      ↓
养老客户
      ↓
推荐御享金越年金
```

后面这种写法实际上把**事实 → 标签 → 产品答案**直接写死了。

---

# 2. Opportunity 首先必须是 Judgment，而不是 Fact

这是和 T03 最重要的衔接。

T03 中：

```text
CUSTOMER_FACT
PRODUCT_FACT
BUSINESS_FACT
RULE_RESULT
MODEL_SIGNAL
EXPERIENCE
```

都可以成为 Evidence。

但是：

> “存在养老现金流经营机会”

是一个基于 Evidence 的**经营判断**。

因此应该：

```text
Opportunity
    └── evidence_links
```

而绝对不要：

```text
EvidenceType.OPPORTUNITY
```

否则结论又会反过来成为自己的证据。

规范同样要求系统区分事实、模型判断和 Agent 决策，Agent 可以综合证据形成判断，但不能把生成结果重新包装成确定性事实。:chatgpt-content-reference{index="1"}

---

# 3. Opportunity 第一版核心结构

我建议：

```text
Opportunity
│
├── identity
│   ├── opportunity_id
│   └── version
│
├── goal_link
│
├── opportunity_type
│
├── problem_statement
│
├── evidence_links
│
├── goal_contribution
│
├── eligibility
│
├── exclusions
│
├── priority
│
├── validity
│
├── candidate_logic
│
└── next_actions
```

和当前规范定义基本一致，但我们把几个模糊字段进一步结构化。规范给出的最小字段本身就是 `goal_link / opportunity_type / problem_statement / evidence / eligibility / exclusions / priority / validity / candidate_logic / next_actions`。:chatgpt-content-reference{index="2"}

# 4. `opportunity_id + version`

和 Goal 一样：

```python
opportunity_id: str
version: int
```

因为 Opportunity 也可能变化。

例如第一次：

```text
Opportunity v1

养老现金流规划机会
```

后来实际触客发现：

```text
客户明确没有养老需求
但非常关注子女财富安排
```

那么不应该静默修改原 Opportunity。

可以形成：

```text
Opportunity A
状态失效

Opportunity B
新的家庭财富安排机会
```

或者 Opportunity 本身产生新版。

具体生命周期到追踪阶段再完善，但 **M1 从第一版保留 version** 很有价值。

---

# 5. `goal_link`

这里不要只保存：

```python
goal_id
```

建议：

```python
@dataclass(frozen=True)
class GoalLink:
    goal_id: str
    goal_version: int
```

因为：

```text
Goal v1 = 500W
Goal v2 = 400W
```

某个 Opportunity 可能是基于 v1 产生的。

以后复盘的时候必须知道：

> 这个经营机会究竟是围绕哪个版本目标产生的？

---

# 6. `opportunity_type`

和 `goal_type` 一样，我暂时不建议固定成 Enum。

第一版：

```python
opportunity_type: str
```

例如：

```text
retirement_cashflow_gap

family_protection_gap

wealth_transfer_need

relationship_reactivation

coverage_adjustment
```

但是这些只是：

> 可扩展的分类 code。

不能把：

```text
开门红养老客户
御享分红客户
```

定义为类型。

因为同一个：

```text
retirement_cashflow_gap
```

完全可以发生在：

```text
开门红
日常经营
年中经营
客户生日经营
保单检视
```

等不同场景。

规范明确规定 Opportunity 不得绑定开门红、年中、年末或具体产品。:chatgpt-content-reference{index="3"}

---

# 7. `problem_statement` 是 Opportunity 的灵魂

这是我认为 T04 最重要的字段。

Opportunity 不是：

```text
养老客户
```

而应该回答：

> **当前究竟存在什么值得解决的经营问题？**

例如：

```text
客户逐步进入退休准备阶段，
但现有保障与资产安排中缺少清晰的长期养老现金流方案，
可能存在进一步养老规划空间。
```

所以：

```python
problem_statement: str
```

可以是自然语言。

这里没有必要过度结构化，因为它本身就是经营判断的核心语义。

但是必须建立一个硬约束：

> `problem_statement` 不得直接写成产品销售结论。

错误：

```text
客户适合购买御享金越年金。
```

正确：

```text
客户存在长期养老现金流规划空间。
```

至于：

> 哪款产品能解决？

应该进入后面的 Strategy。

# 8. Evidence 不只是 `evidence_ids`

这里我建议相比上一轮再提升一点。

如果简单：

```python
evidence_ids: tuple[str, ...]
```

有一个问题：

系统不知道某条证据到底是：

```text
支持这个机会
限制这个机会
还是与这个机会冲突
```

因此建议定义：

```python
class EvidenceRole(str, Enum):
    SUPPORTS = "supports"
    LIMITS = "limits"
    CONTRADICTS = "contradicts"
```

然后：

```python
@dataclass(frozen=True)
class EvidenceLink:
    evidence_id: str
    role: EvidenceRole
    rationale: str | None = None
```

于是 Opportunity 可以出现：

```text
SUPPORTS
- 年龄52岁
- 三次咨询退休收入
- 模型养老需求评分0.82

LIMITS
- 客户当前新增保险预算有限

CONTRADICTS
- 客户最近一次明确表示暂不考虑养老产品
```

Agent 不能把最后一条偷偷删掉。

这个设计正好支持 T03 所说的“来源冲突不能静默隐藏”。规范也要求多确定性来源冲突时显式处理，而不是由 Agent 自行择一。:chatgpt-content-reference{index="4"}

---

# 9. `goal_contribution`

Opportunity 为什么值得关心，最终必须回到 Goal。

规范明确要求机会必须说明和 Goal 的关系，而不能只是泛化营销主题。:chatgpt-content-reference{index="5"}

建议：

```python
@dataclass(frozen=True)
class GoalContribution:
    contribution_type: str
    description: str
    estimated_value: float | None = None
    unit: str | None = None
```

例如：

```python
GoalContribution(
    contribution_type="revenue_potential",
    description="该机会可能贡献当前NBEV目标",
)
```

如果将来真的有可信模型估计：

```python
estimated_value=30
unit="万元NBEV"
```

也可以。

但没有模型时：

```text
estimated_value = None
```

绝不能让 LLM 随手生成：

```text
预计贡献30W
```

---

# 10. `eligibility` 和 `exclusions`

两者含义要区分清楚。

## Eligibility

表达：

> 什么条件下，这个 Opportunity 更可能成立？

例如：

```text
接近退休规划阶段
存在稳定收入或资产
当前养老现金流准备不足
```

---

## Exclusions

表达：

> 什么情况下这个 Opportunity 不应继续成立，或者必须进一步检查？

例如：

```text
客户已经具备充分养老现金流安排
客户明确表示当前无相关需求
数据严重不足
```

但是注意：

```text
银保客户不能进入个险任务
```

严格来说不是 Opportunity 本身的经营适配条件，而是：

```text
执行阶段业务规则
```

所以 Opportunity 最多可以表示：

```text
需要渠道资格校验
```

真正裁决必须留给 Validation Capability。

这样就不会把业务权限规则偷偷塞进 Opportunity。

---

# 11. Eligibility 第一版不要建复杂 DSL

这里很容易过度设计。

先做一个非常轻的：

```python
@dataclass(frozen=True)
class OpportunityCondition:
    key: str
    operator: str
    value: object
    description: str | None = None
```

例如：

```python
OpportunityCondition(
    key="retirement_stage",
    operator="is",
    value=True,
    description="客户进入退休准备阶段",
)
```

或者：

```python
OpportunityCondition(
    key="existing_retirement_cashflow",
    operator="less_than",
    value="sufficient",
)
```

这里：

```text
key
```

应该是**业务语义字段**。

不要直接：

```text
table_a.col_x
```

否则 Domain 会和数据库绑定。

---

# 12. `candidate_logic` 与 eligibility 不完全一样

这两个容易混淆。

### eligibility

描述的是：

> 这个机会理论上适合什么样的对象？

### candidate_logic

描述的是：

> 为了寻找这类对象，目前可以把这些适配条件如何转译成圈客条件？

比如 Opportunity：

```text
退休现金流规划机会
```

eligibility：

```text
临近退休阶段
当前养老现金流准备不足
具备进一步长期规划基础
```

candidate_logic：

```text
customer.age >= 某业务阈值
AND
existing_retirement_cashflow == insufficient
AND
...
```

但是 M1 我不建议把 candidate_logic 直接设计成 SQL DSL。

第一版可以：

```python
@dataclass(frozen=True)
class CandidateLogic:
    conditions: tuple[OpportunityCondition, ...]
    logic: str = "all"
```

以后如果智慧客户营销平台已有自己的圈客规则格式：

```text
CandidateLogic
       ↓
Adapter
       ↓
现有平台Query/Rule DSL
```

而不是让 Domain 直接绑定某个平台。

这点和“优先复用现有营销平台的圈客能力”也保持一致。:chatgpt-content-reference{index="6"}

---

# 13. `priority` 不应该只是一个 score

错误设计：

```python
priority = 0.87
```

因为代理人会问：

> 为什么0.87？

规范要求 Opportunity 排序最好能分别解释目标贡献、适配程度、时效、可触达性、风险和数据完整度，而不是一个不可解释综合分。:chatgpt-content-reference{index="7"}

所以建议：

```python
@dataclass(frozen=True)
class PriorityFactor:
    name: str
    assessment: str
    rationale: str
    evidence_ids: tuple[str, ...] = ()


@dataclass(frozen=True)
class OpportunityPriority:
    level: str
    factors: tuple[PriorityFactor, ...]
```

例如：

```text
Priority = HIGH

目标贡献:
HIGH

适配程度:
HIGH

时效性:
MEDIUM

可触达性:
HIGH

风险:
LOW

数据完整度:
MEDIUM
```

以后真有模型分数，可以作为一个 factor。

但不能让 score 取代解释。

---

# 14. `validity`

Opportunity 不是永久成立。

比如：

```text
客户即将退休
```

半年以后可能情况完全不同。

建议：

```python
@dataclass(frozen=True)
class OpportunityValidity:
    valid_from: datetime | None = None
    valid_until: datetime | None = None
    invalidation_conditions: tuple[str, ...] = ()
```

例如：

```text
失效条件：

客户明确表示无相关需求
客户已经完成养老规划
关键客户事实发生变化
相关产品/业务背景失效
```

后面 M7 Tracking 才能知道：

> 是否需要重新判断 Opportunity。

---

# 15. `next_actions`

这里暂时不要直接依赖 Capability。

因为 T05 我们还没有正式定义 Capability Contract。

所以先设计：

```python
@dataclass(frozen=True)
class NextActionHint:
    action_type: str
    reason: str
    required_information: tuple[str, ...] = ()
```

比如：

```python
NextActionHint(
    action_type="customer_targeting",
    reason="需要进一步定位符合该机会条件的候选客户",
)
```

或者：

```python
NextActionHint(
    action_type="collect_information",
    reason="当前证据不足以形成可靠圈客条件",
    required_information=(
        "客户养老准备情况",
    ),
)
```

等 T05 Capability 定义以后：

```text
NextActionHint
        ↓
Planner
        ↓
CapabilityCall
```

而不是 Opportunity 直接控制执行流程。

# 16. 第一版 Python Contract

综合起来，我建议 T04 第一版大概到这个程度：

```python
from dataclasses import dataclass
from datetime import datetime
from enum import Enum
from typing import Any


class EvidenceRole(str, Enum):
    SUPPORTS = "supports"
    LIMITS = "limits"
    CONTRADICTS = "contradicts"


@dataclass(frozen=True)
class GoalLink:
    goal_id: str
    goal_version: int


@dataclass(frozen=True)
class EvidenceLink:
    evidence_id: str
    role: EvidenceRole
    rationale: str | None = None


@dataclass(frozen=True)
class GoalContribution:
    contribution_type: str
    description: str
    estimated_value: float | None = None
    unit: str | None = None


@dataclass(frozen=True)
class OpportunityCondition:
    key: str
    operator: str
    value: Any
    description: str | None = None


@dataclass(frozen=True)
class CandidateLogic:
    conditions: tuple[OpportunityCondition, ...] = ()
    logic: str = "all"


@dataclass(frozen=True)
class PriorityFactor:
    name: str
    assessment: str
    rationale: str
    evidence_ids: tuple[str, ...] = ()


@dataclass(frozen=True)
class OpportunityPriority:
    level: str
    factors: tuple[PriorityFactor, ...] = ()


@dataclass(frozen=True)
class OpportunityValidity:
    valid_from: datetime | None = None
    valid_until: datetime | None = None
    invalidation_conditions: tuple[str, ...] = ()


@dataclass(frozen=True)
class NextActionHint:
    action_type: str
    reason: str
    required_information: tuple[str, ...] = ()


@dataclass(frozen=True)
class Opportunity:
    opportunity_id: str
    version: int

    goal_link: GoalLink

    opportunity_type: str
    problem_statement: str

    evidence_links: tuple[EvidenceLink, ...]

    goal_contribution: GoalContribution | None

    eligibility: tuple[OpportunityCondition, ...]
    exclusions: tuple[OpportunityCondition, ...]

    priority: OpportunityPriority | None

    validity: OpportunityValidity | None

    candidate_logic: CandidateLogic | None

    next_actions: tuple[NextActionHint, ...]
```

看起来类型不少，但每个对象都非常薄。

关键在于没有引入：

```text
OpportunityService
OpportunityManager
OpportunityRepository
OpportunityEngine
```

这些当前都还没有必要。

# 17. 用 Demo 场景验证一下

比如开门红 Goal 下形成一个：

```text
retirement_cashflow_gap
```

可以是：

```python
opportunity = Opportunity(
    opportunity_id="opp_001",
    version=1,

    goal_link=GoalLink(
        goal_id="goal_001",
        goal_version=1,
    ),

    opportunity_type="retirement_cashflow_gap",

    problem_statement=(
        "部分客户逐步进入退休准备阶段，"
        "但当前长期养老现金流安排可能不足，"
        "存在进一步养老规划空间。"
    ),

    evidence_links=(
        EvidenceLink(
            evidence_id="ev_001",
            role=EvidenceRole.SUPPORTS,
        ),
        EvidenceLink(
            evidence_id="ev_002",
            role=EvidenceRole.SUPPORTS,
        ),
    ),

    goal_contribution=GoalContribution(
        contribution_type="goal_support",
        description="可作为当前NBEV目标的重要潜在经营来源之一",
    ),

    eligibility=(
        OpportunityCondition(
            key="retirement_stage",
            operator="is",
            value=True,
        ),
    ),

    exclusions=(),

    priority=OpportunityPriority(
        level="high",
        factors=(
            PriorityFactor(
                name="timeliness",
                assessment="high",
                rationale="客户正处于养老规划窗口",
            ),
        ),
    ),

    validity=None,

    candidate_logic=CandidateLogic(
        conditions=(
            OpportunityCondition(
                key="retirement_stage",
                operator="is",
                value=True,
            ),
        )
    ),

    next_actions=(
        NextActionHint(
            action_type="customer_targeting",
            reason="进一步定位符合该机会的候选客户",
        ),
    ),
)
```

注意这里完全没有：

```text
御享金越年金
```

不是遗漏。

这是故意的。

因为当前 Opportunity 解决的是：

> **有什么值得经营的问题？**

不是：

> **卖什么？**

后者应该在 Strategy 阶段结合产品事实、客户事实等进一步形成。

# 19. T04 建议正式确定 12 条不变量

| 编号 | Opportunity 不变量                                                     |
| ---- | ---------------------------------------------------------------------- |
| O-01 | Opportunity 必须关联明确的 Goal 版本                                   |
| O-02 | Opportunity 是经营判断，不是确定性事实                                 |
| O-03 | `problem_statement` 描述经营问题，不直接写产品推荐答案               |
| O-04 | Opportunity 必须具有可追溯 Evidence                                    |
| O-05 | Supporting / Limiting / Contradicting Evidence 不得静默丢弃            |
| O-06 | Opportunity Type 不绑定具体经营阶段或产品                              |
| O-07 | 产品名、场景名可以作为上下文或 Evidence，但不能成为 Opportunity Schema |
| O-08 | Priority 必须可解释，不能只有单一综合分                                |
| O-09 | Candidate Logic 是逻辑表达，不直接绑定 SQL 或具体数据平台              |
| O-10 | Candidate Logic 只产生候选客户，不代表客户拥有经营权限                 |
| O-11 | Opportunity 的规则限制不能替代后续确定性 Validation                    |
| O-12 | Opportunity 必须允许失效、修正或被新 Evidence 推翻                     |

其中 O-10 特别关键。规范明确规定圈客得到的只是候选客户，未经校验分发绝不能直接进入任务执行。:chatgpt-content-reference{index="8"}

# 20. T04 的测试重点

这一轮依然不需要 LLM，也不需要真实数据。

建议至少验证四组核心场景：

```text
Case A
Opportunity 引用 Customer Fact + Model Signal
→ 合法

Case B
Opportunity 没有任何 Evidence
→ 不允许作为正常已形成机会

Case C
Opportunity 类型 = retirement_cashflow_gap
Goal 从“开门红”换成“日常客户盘点”
→ Opportunity Contract 无需变化

Case D
存在 SUPPORTS + CONTRADICTS Evidence
→ 两类 Evidence 均必须被保留

Case E
candidate_logic 包含筛选条件
→ 合法
但不得因此产生“可执行客户”

Case F
Opportunity 直接把“御享金越年金”作为 opportunity_type
→ Contract/Review 应判定为不符合领域建模原则
```

---

## 至此，T04 的真正成果

现在我们的领域语言已经形成了一条相当清晰的链：

```text
Goal
“我要完成什么”
        ↓
Evidence
“当前有什么可信依据”
        ↓
Opportunity
“依据这些信息，有什么经营问题值得抓”
        ↓
Candidate Logic
“哪些对象可能属于这个机会”
```

而且最重要的是还**没有进入执行层**。

接下来进入 **T05 Capability Contract** 时，就终于可以解决：

```text
Goal + Context
       ↓
Capability Call
       ↓
组织 Tool
       ↓
Capability Result
       ↓
Evidence / Opportunity / Candidate / Strategy...
```

也就是说，**T01~T04 是在定义智慧经营的“名词”，T05 开始定义智慧经营的“动作”。**
