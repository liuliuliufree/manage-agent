
可以，T03 正式启动。这个阶段我建议把目标定义得很清楚：

> **建立一套统一的 Evidence Contract，让后面的 Opportunity、圈客、Strategy、Validation 都能回答：这个结论依据什么、依据属于什么性质、从哪里来、什么时候有效。**

并且先修正我们之前的一个初步设想：

> **`AGENT_JUDGEMENT` 不作为 Evidence。**

规范要求系统区分确定性事实、业务规则、模型判断、经营经验和 Agent 决策；Agent 决策是“基于 Goal 和证据形成的建议”，而不是证据本身。:chatgpt-content-reference{index="0"}

所以关系应该是：

```text
Evidence[]
    ↓
Agent 综合分析
    ↓
Opportunity / Strategy / Decision
    ↓
引用 evidence_id
```

而不是：

```text
Agent说了一句话
↓
把这句话包装成 Evidence
↓
再用它证明自己
```

这条边界非常重要。

---

# 一、T03 首先解决三个问题

Evidence Contract 不负责保存“所有业务数据”。

它只需要回答三个问题：

```text
① 这条依据是什么性质？

② 它从哪里来，现在是否适用？

③ 后面的经营判断如何引用它？
```

规范明确要求 Opportunity 的证据必须能追溯到客户数据、产品知识、阶段/经营事实或模型结果，并带来源、时间和适用范围。:chatgpt-content-reference{index="1"}

因此 Evidence 本质上应该是一个：

> **标准化的“证据引用 + 必要摘要”，而不是业务数据仓库副本。**

---

# 二、先确定 Evidence 的类型体系

这里和 `GoalType` 不一样。

`GoalType` 我们之前不建议马上写死 Enum，因为未来经营目标类型还会扩展。

但是 Evidence 的一级性质是规则规定的稳定边界，我反而建议第一版直接 Enum。

```python
class EvidenceType(str, Enum):
    CUSTOMER_FACT = "customer_fact"
    PRODUCT_FACT = "product_fact"
    BUSINESS_FACT = "business_fact"
    RULE_RESULT = "rule_result"
    MODEL_SIGNAL = "model_signal"
    EXPERIENCE = "experience"
```

分别来看。

| EvidenceType      | 含义                      | 典型例子                       | 能否直接作为确定性事实 |
| ----------------- | ------------------------- | ------------------------------ | ---------------------- |
| `CUSTOMER_FACT` | 客户相关确定性事实        | 年龄、保单、历史互动           | 是                     |
| `PRODUCT_FACT`  | 产品相关确定性事实        | 产品期限、条款、适用规则       | 是                     |
| `BUSINESS_FACT` | 经营过程/阶段的确定性事实 | 已完成180W、本月已触达3次      | 是                     |
| `RULE_RESULT`   | 权威规则服务的裁决结果    | 客户属于银保，不可进入个险任务 | 是，且裁决优先         |
| `MODEL_SIGNAL`  | 模型输出                  | 养老需求倾向0.82               | 否，只是信号           |
| `EXPERIENCE`    | 经治理的经营经验          | 某类客户更适合某切入方式       | 否，仅参考             |

这里增加 `BUSINESS_FACT`，主要是为了容纳：

```text
经营阶段事实
任务状态
触达结果
业绩结果
历史经营事件
```

否则后面 M7 的追踪事件没有自然位置。

---

# 三、为什么没有 `AGENT_JUDGEMENT`

例如：

```text
客户52岁
```

是：

```text
CUSTOMER_FACT
```

---

```text
养老需求倾向分 = 0.82
```

是：

```text
MODEL_SIGNAL
```

---

```text
产品支持长期领取
```

是：

```text
PRODUCT_FACT
```

---

由这些内容得出：

> 该客户目前可能存在养老现金流规划机会。

这个不是 Evidence。

这是：

```text
Opportunity / Agent Judgment
```

它应该这样引用：

```text
Opportunity
    evidence_ids:
      - ev_001
      - ev_002
      - ev_003
```

这样系统天然能区分：

```text
事实是什么
模型说什么
Agent最终判断什么
```

这也正好落实规范“不把建议包装成事实”的要求。:chatgpt-content-reference{index="2"}

---

# 四、Evidence 不应该只是一段 text

最简单但非常危险的设计是：

```python
Evidence(
    text="客户适合养老规划"
)
```

这种设计后面完全不可治理。

我建议 Evidence 第一版至少长这样：

```python
@dataclass(frozen=True)
class Evidence:
    evidence_id: str

    evidence_type: EvidenceType

    subject_ref: str | None
    field: str | None
    value: object | None
    summary: str

    source: "EvidenceSource"

    observed_at: datetime | None = None
    effective_period: "EffectivePeriod | None" = None

    quality: "EvidenceQuality | None" = None
```

先解释每一个字段。

---

# 五、`evidence_id`

一定要有稳定 ID。

例如：

```text
ev_customer_age_001
ev_policy_123
ev_model_987
```

当然生产环境不要靠语义字符串生成，最终可以 UUID。

它存在的最大意义是：

```text
Opportunity
CustomerRecommendation
Strategy
ValidationResult
```

以后统一只需要保存：

```python
evidence_ids = (...)
```

而不是复制 Evidence 内容。

最终会形成：

```text
Goal
 │
 ▼
Opportunity
 │
 ├── evidence: ev001
 ├── evidence: ev002
 └── evidence: ev003
```

---

# 六、`subject_ref`

这个字段回答：

> 这条证据在说谁 / 什么？

例如：

```python
subject_ref="customer_123"
```

或者：

```python
subject_ref="product_456"
```

或者：

```python
subject_ref="task_789"
```

甚至：

```python
subject_ref="agent_001"
```

这里不要设计：

```python
customer_id
product_id
task_id
```

三个字段。

否则 Evidence 会不断随着业务对象增加字段。

统一：

```text
subject_ref
```

更加通用。

---

# 七、`field + value + summary`

这里建议同时保留**机器可消费结构**和**人可读摘要**。

例如客户年龄：

```python
Evidence(
    evidence_type=EvidenceType.CUSTOMER_FACT,
    subject_ref="customer_001",
    field="age",
    value=52,
    summary="客户当前年龄为52岁",
    ...
)
```

模型信号：

```python
Evidence(
    evidence_type=EvidenceType.MODEL_SIGNAL,
    subject_ref="customer_001",
    field="retirement_need_score",
    value=0.82,
    summary="养老现金流需求模型评分为0.82",
    ...
)
```

为什么两个都要？

因为：

```text
field/value
```

给代码和 Agent 使用。

```text
summary
```

给解释、页面、审计使用。

---

# 八、Source 单独做 Value Object

我认为这个值得拆。

```python
@dataclass(frozen=True)
class EvidenceSource:
    source_type: str
    source_id: str
    version: str | None = None
    record_ref: str | None = None
```

例如：

```python
EvidenceSource(
    source_type="customer_data",
    source_id="customer_profile_service",
    version="2026-09-01",
    record_ref="customer_001",
)
```

模型：

```python
EvidenceSource(
    source_type="model",
    source_id="retirement_need_model",
    version="v3.2",
)
```

规则：

```python
EvidenceSource(
    source_type="rule_service",
    source_id="channel_eligibility_rule",
    version="v12",
)
```

规范明确要求客户和产品事实有来源、时间和版本，规则返回标识和版本，模型也要带模型版本和适用信息。:chatgpt-content-reference{index="3"}

---

# 九、`record_ref` 不等于复制原始数据

例如客户保单事实来自：

```text
policy_service
```

Evidence 可以记录：

```text
source_id = policy_service
record_ref = policy_123
```

但是不要把：

```text
整张保单
整份客户画像
整个模型输入
```

直接塞入 Evidence。

Evidence 应该只是当前 Goal 所需要的最小信息。

这也符合规范的最小数据访问要求：Capability 只能获取完成当前 Goal 所需、且获授权的数据。:chatgpt-content-reference{index="4"}

---

# 十、时间需要区分两个概念

我建议不要只设计一个：

```python
timestamp
```

因为 Evidence 有两个不同时间语义。

## observed_at

表示：

> 这条事实是什么时候观察/取得的。

例如：

```text
2026-09-17 10:00
```

---

## effective_period

表示：

> 这条知识或规则什么时候有效。

```python
@dataclass(frozen=True)
class EffectivePeriod:
    valid_from: datetime | None = None
    valid_to: datetime | None = None
```

例如产品知识：

```text
产品条款版本 V5
2026-07-01 起生效
```

规则：

```text
个险渠道规则 v12
2026-09-01 起生效
```

这非常重要，因为规范明确规定：

> 检索不到适用版本时，不能拿另一个版本推断当前事实。:chatgpt-content-reference{index="5"}

所以：

```text
source.version
+
effective_period
```

最好从 T03 就存在。

---

# 十一、Quality 不要简单等于 confidence

这里值得注意。

不是所有 Evidence 都有“置信度”。

比如：

```text
客户出生日期来自客户主数据
```

不存在：

```text
confidence=0.97
```

这种概念。

但模型有。

所以我建议：

```python
@dataclass(frozen=True)
class EvidenceQuality:
    confidence: float | None = None
    completeness: float | None = None
    limitations: tuple[str, ...] = ()
```

例如模型：

```python
EvidenceQuality(
    confidence=0.82,
    limitations=(
        "新客户历史行为数据不足",
    ),
)
```

经营经验：

```python
EvidenceQuality(
    limitations=(
        "仅适用于退休临近客户群",
    ),
)
```

客户事实可能：

```python
EvidenceQuality(
    completeness=1.0,
)
```

也可以干脆：

```python
quality=None
```

合法。

不要为了字段完整给所有事实造“置信度”。

---

# 十二、RULE_RESULT 需要特殊对待

虽然统一放进 Evidence Contract，但 Rule Result 是特殊类型。

例如：

```python
Evidence(
    evidence_id="ev_rule_001",
    evidence_type=EvidenceType.RULE_RESULT,
    subject_ref="customer_001",
    field="channel_eligibility",
    value="blocked",
    summary="客户属于银保渠道，不可进入当前个险经营任务",
    source=EvidenceSource(
        source_type="rule_service",
        source_id="channel_eligibility",
        version="v12",
    ),
)
```

这种 Evidence 与：

```text
MODEL_SIGNAL
```

不是同等权重。

如果：

```text
模型：客户价值很高
规则：禁止经营
```

最终必须：

```text
BLOCKED
```

Agent 不能自己做：

```text
综合权重后放行
```

规范对这一点是硬约束：Agent 建议与规则冲突时，以规则为准。:chatgpt-content-reference{index="6"}

所以后面 T05/T06 Capability Result 需要单独保留：

```text
rule_results
```

而不是把规则仅仅当成普通 Evidence 加权。

---

# 十三、经营经验也不能升级成 Fact

比如案例库告诉我们：

> 临近退休客户从现金流切入通常更容易沟通。

可以：

```text
EXPERIENCE
```

但不能经过一次 LLM 总结以后变成：

```text
客户需要养老金产品
```

规范明确要求经营经验只能用于提出假设、排序或生成备选策略，不能替代客户事实、产品事实和业务规则。:chatgpt-content-reference{index="7"}

所以：

```text
EXPERIENCE
   ↓
可以影响 Agent Judgment

但不能变成
   ↓
CUSTOMER_FACT
```

---

# 十四、Evidence 不负责表达“结论”

这也是我们应该给 T03 立的一条非常重要的不变量。

错误：

```python
Evidence(
    evidence_type=CUSTOMER_FACT,
    summary="客户是高潜养老客户"
)
```

因为：

```text
高潜
养老需求
```

已经是业务判断。

正确应该拆成：

```text
Evidence 1
客户年龄52岁
CUSTOMER_FACT

Evidence 2
现有保障中无养老年金
CUSTOMER_FACT

Evidence 3
近三次沟通关注退休收入
CUSTOMER_FACT / BUSINESS_FACT

Evidence 4
养老需求模型评分0.82
MODEL_SIGNAL
```

然后：

```text
Opportunity:

该客户存在较高养老现金流规划机会

evidence_ids:
    ev1
    ev2
    ev3
    ev4
```

这样：

> **证据和结论真正分开了。**

# 十五、来源冲突怎么办

这一点建议 T03 就定义原则，但暂时不要开发复杂解决引擎。

例如：

```text
Source A:
客户职业 = 企业高管

Source B:
客户职业 = 自由职业
```

不允许：

```text
Agent感觉A比较可信，所以用A
```

而应该能被表达成：

```text
Evidence A
Evidence B
```

然后上层进入：

```text
CONFLICT
```

或者：

```text
NEED_INFORMATION
```

具体状态后面 T06 再确定。

规范已经明确要求多个确定性来源不一致时，应显式返回冲突，不由 Agent 自行择一隐藏。:chatgpt-content-reference{index="8"}

# 十六、T03 第一版 Python 类型，我建议就控制在 4 个

不要一下建很多抽象。

```python
EvidenceType

Evidence

EvidenceSource

EffectivePeriod

EvidenceQuality
```

严格说是五个，但只有两个是核心：

```text
Evidence
EvidenceSource
```

其余非常薄。

完整概念可以是：

```python
from dataclasses import dataclass
from datetime import datetime
from enum import Enum
from typing import Any


class EvidenceType(str, Enum):
    CUSTOMER_FACT = "customer_fact"
    PRODUCT_FACT = "product_fact"
    BUSINESS_FACT = "business_fact"
    RULE_RESULT = "rule_result"
    MODEL_SIGNAL = "model_signal"
    EXPERIENCE = "experience"


@dataclass(frozen=True)
class EvidenceSource:
    source_type: str
    source_id: str
    version: str | None = None
    record_ref: str | None = None


@dataclass(frozen=True)
class EffectivePeriod:
    valid_from: datetime | None = None
    valid_to: datetime | None = None


@dataclass(frozen=True)
class EvidenceQuality:
    confidence: float | None = None
    completeness: float | None = None
    limitations: tuple[str, ...] = ()


@dataclass(frozen=True)
class Evidence:
    evidence_id: str
    evidence_type: EvidenceType

    subject_ref: str | None
    field: str | None
    value: Any | None
    summary: str

    source: EvidenceSource

    observed_at: datetime | None = None
    effective_period: EffectivePeriod | None = None
    quality: EvidenceQuality | None = None
```

第一版我觉得做到这里就够。

假设后面分析客户 A。

### 客户事实

```python
ev_age = Evidence(

        source_type="customer_data",
        source_id="customer_profile_service",

    ),

```

### 产品事实

```python
ev_product = Evidence(
    evidence_id="ev_002",
    evidence_type=EvidenceType.PRODUCT_FACT,
    subject_ref="product_x",
    field="benefit_pattern",
    value="long_term_cashflow",

        source_type="product_knowledge",

```

### 模型信号

```python
ev_model = Evidence(
    evidence_id="ev_003",

```

# 十八、T03 的核心不变量可以正式定下来

| 编号 | 不变量                                                       |
| ---- | ------------------------------------------------------------ |
| E-01 | Evidence 必须有稳定`evidence_id`                           |
| E-02 | Evidence 必须声明类型，事实、规则、模型和经验不能混淆        |
| E-03 | 确定性事实必须存在可追溯 Source                              |
| E-04 | 无来源内容不得标记为 Fact                                    |
| E-05 | 产品知识、规则、经营知识必须支持版本/有效期                  |
| E-06 | 模型结果始终是`MODEL_SIGNAL`，不得自动升级为 Fact          |
| E-07 | 经营经验始终是参考依据，不得自动升级为 Rule                  |
| E-08 | Agent Judgment 不属于 Evidence，而是引用 Evidence 的上层结果 |
| E-09 | Rule Result 不能被 Agent 或模型覆盖                          |
| E-10 | 来源冲突必须显式保留，不允许 Agent 静默选择                  |
| E-11 | Evidence 只保存当前 Goal 所需的最小信息，不复制完整源数据    |
| E-12 | Evidence 与页面展示都必须能保留来源、时间和适用范围          |

这基本就是 T03 的 Contract Constitution。

# 十九、T03 应该怎么测试

这一阶段暂时不用接任何真实系统。

用纯单元测试就够。

可以至少验证这些场景：

```text
客户事实 + 合法 Source
→ 可以创建

客户事实没有 source_id
→ 非法

模型信号 confidence=0.82
→ 合法

MODEL_SIGNAL
→ 不能变成 CUSTOMER_FACT

规则结果 blocked
→ 可以明确保留规则版本

经营经验
→ 可以存在
→ 但 EvidenceType 必须仍是 EXPERIENCE

同一字段两个确定性 Evidence 冲突
→ 两条证据都保留
→ 不允许自动覆盖

Evidence
→ 不允许 evidence_type = AGENT_JUDGEMENT
```

最后这一项尤其重要。

## 到这里，T03 的核心设计其实已经成立

现在领域模型开始变成：

```text
Goal
 │
 │  我要完成什么
 │
 ▼
未来 Plan / Capability
 │
 ▼
Evidence
 │
 │  我知道什么、依据是什么
 │
 ▼
Opportunity
 │
 │  基于这些依据，我判断有什么机会
 ▼
Strategy / Decision
```

而且这时已经形成一个非常关键的系统原则：

> **事实不会因为进入 LLM 而失去来源，模型结果不会因为被 LLM 总结而变成事实，Agent 结论也不会因为表达得很肯定就变成 Evidence。**

这正是后面整个智慧经营 Agent 可解释、可审计的基础。

下一步进入 **T04 Opportunity Contract** 时，我们就可以正式利用这套设计，解决一个非常具体的问题：

> **Agent 如何把若干 Evidence 组织成一个“经营机会”，但又不把机会写死成养老客户、财富传承客户这样的 Demo 标签。**
