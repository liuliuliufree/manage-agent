可以，我们这一步直接把 **M1-T01「领域边界」** 和 **M1-T02「Goal Contract」** 定成可进入实现的版本。

先给结论：我建议把当前架构从“两层”进一步明确成 **三层依赖关系**，而不是简单地“业务层压在 Agent Runtime 上”。

## M1-T01：确定领域边界

当前已有：

```text
src/model/
    LLM 调用层

src/agent/
    通用 Agent Runtime
```

下一步新增的业务概念，建议独立成为 **Domain 层**：

```text
                    未来 M2
              智慧经营 Application
                 /          \
                ↓            ↓
        Business Domain    Agent Runtime
                │              │
                │              ↓
                │           Model
                │
                └── 不依赖 Agent / Model
```

也就是说，我建议最终依赖方向是：

```text
Application
   ├──→ Domain
   └──→ Agent
          └──→ Model
```

而不是：

```text
Domain → Agent → Model
```

### 为什么要这样？

因为 `Goal`、`Opportunity` 这些东西，本质上是**智慧经营领域概念**。

一个 Goal：

> 本月完成500W NBEV

无论将来我们：

- 用 LLM 解析；
- 用规则解析；
- 从页面表单产生；
- 从 API 接收；

它依然是同一个 Goal。

所以 Goal 不应该知道：

```text
ChatModel
ToolCall
Turn
Trace
LLM Message
```

这些概念。

同理，现有 `AgentLoop` 也不应该知道：

```text
NBEV
开门红
客户
产品
个险
Opportunity
```

项目原则本来也要求底层 Agent 机制不感知具体业务。:chatgpt-content-reference{index="0"}

---

### 因此我们正式确定四类职责

| 层              | 负责什么                                          | 明确不负责什么                   |
| --------------- | ------------------------------------------------- | -------------------------------- |
| `model`       | LLM通信、流式响应、模型配置                       | Goal、业务规则、客户             |
| `agent`       | Agent Loop、Tool调用、Trace、Turn、生命周期       | 开门红、NBEV、Opportunity        |
| `domain`      | Goal、Opportunity、Evidence 等智慧经营业务语义    | LLM、Tool Calling、Prompt、Trace |
| `application` | 未来超级Agent：Goal解析、Plan生成、Capability编排 | 不承载客户事实和确定性规则本身   |

其中：

```text
domain
```

我们现在开始做。

```text
application
```

留到 M2。

---

## 建议的代码边界

现阶段我倾向于新增：

```text
src/
├─ model/
├─ agent/
└─ domain/
```

而不是现在就建：

```text
src/business_agent/
src/super_agent/
src/workflow/
```

因为 M1 还没有真正的经营 Agent。

`domain` 只是：

> **描述智慧经营世界中的东西。**

后面大概才会逐渐出现：

```text
src/domain/
├─ goal.py
├─ opportunity.py
├─ evidence.py
├─ capability.py
└─ plan.py
```

具体文件拆分后续可以随着实现调整，现在不必强制锁死。

---

# T01 的五条架构不变量

这几条我建议直接作为 M1 的 Architecture Test / Code Review 标准。

### ① Domain 不依赖 Agent

禁止：

```python
# domain/goal.py

from src.agent.tool import Tool
from src.agent.trace import Trace
```

Goal 本身不知道 Agent Runtime 存在。

---

### ② Agent 不依赖 Domain

同样禁止：

```python
# agent/loop.py

from src.domain.goal import Goal
```

否则以后这个 Agent Runtime 就不能再作为通用框架复用。

---

### ③ Model 是最底层

保持：

```text
agent → model
```

但：

```text
model
```

不知道 Agent 和业务世界。

---

### ④ Application 才是组合点

未来：

```text
经营超级Agent
```

可以同时知道：

```text
Goal
Plan
Capability

以及

AgentLoop
Tool
Trace
```

因此 Application 才是真正把：

```text
业务语义
+
Agent Runtime
```

接起来的地方。

---

### ⑤ 业务状态与 Runtime 状态分开

现在已经有：

```text
Trace
Turn
ToolExecution
```

未来还会出现：

```text
Goal
Plan
Opportunity
Task
```

这两套 ID 不应该混。

例如：

```text
goal_id != trace_id
plan_id != trace_id
```

关系应该是：

```text
Goal
  │
  └── Plan
        │
        └── Agent Run
               │
               └── Trace
```

也就是说：

> Trace 记录“这次程序是怎么运行的”。

而：

> Goal / Plan 记录“业务上正在做什么”。

这两个语义一定要守住。

---

# 到这里，M1-T01 可以认为已经确定

最终架构决策是：

```text
┌────────────────────────────────────┐
│ Application                        │
│ 智慧经营超级Agent（M2开始建设）      │
│ Goal理解 / Plan / Capability编排    │
└──────────────┬───────────┬─────────┘
               │           │
               ▼           ▼
        ┌────────────┐  ┌────────────┐
        │   Domain   │  │ Agent      │
        │            │  │ Runtime    │
        │ Goal       │  │ Loop       │
        │ Opportunity│  │ Tool       │
        │ Evidence   │  │ Trace      │
        │ Plan       │  │ Event      │
        └────────────┘  └─────┬──────┘
                              │
                              ▼
                       ┌────────────┐
                       │   Model    │
                       └────────────┘
```

这里没有循环依赖。

# M1-T02：正式定义 Goal Contract

接下来 Goal。

规范已经规定 Goal 至少要支持：

```text
goal_id
original_request
goal_type
metric
target
time_horizon
audience_scope
product_or_need_context
channel_and_actor
constraints
success_criteria
missing_information
```

并且字段允许为空，但缺失必须显式表达。:chatgpt-content-reference{index="1"}

不过这里有一个重要原则：

> **Goal Contract 描述“用户究竟想完成什么”，而不是“系统准备怎么完成”。**

所以 Goal 里面绝对不要出现：

```text
call_insight = true
need_targeting = true
next_tool
workflow_step
capability_order
```

这些属于 Plan。

---

# 一、Goal 的第一版结构

我建议逻辑模型定成：

```text
Goal
│
├── identity
│     ├── goal_id
│     └── version
│
├── request
│     └── original_request
│
├── intention
│     ├── goal_type
│     ├── metric
│     └── target
│
├── context
│     ├── time_horizon
│     ├── audience_scope
│     ├── product_or_need_context
│     └── channel_and_actor
│
├── constraints
│
├── success_criteria
│
├── missing_information
│
└── assumptions
```

这里我比规范多加一个：

```text
assumptions
```

理由是规则明确允许：对于不会导致明显不同行动、越权或不可逆执行的信息缺失，可以基于**明确标注的假设**继续规划。:chatgpt-content-reference{index="2"}

既然假设会影响后面的 Plan，就不能只存在 Prompt 里。

---

# 二、identity

## `goal_id`

代表这个经营目标的稳定身份。

例如：

```text
goal_123
```

---

## `version`

代表 Goal 的版本。

例如：

```text
goal_id = goal_123

version = 1
```

用户之后说：

> 500W太高了，调整成400W。

应该得到：

```text
goal_id = goal_123
version = 2
```

而不是直接覆盖 v1。

所以：

```text
Goal v1
目标500W

        ↓ 用户修改

Goal v2
目标400W
```

后面的：

```text
Plan
Opportunity
Task
Feedback
```

才能知道自己是基于哪一个 Goal 产生的。

---

# 三、original_request

必须完整保存：

```text
当前处于开门红阶段，我希望达成的NBEV为500W，
当前主推产品为御享分红26、御享金越年金。
```

不能只保留解析后的：

```text
target = 500
```

因为后面可能发现：

> 原解析遗漏了某些语义。

规范也明确要求结构化 Goal 必须和原始自然语言关联。:chatgpt-content-reference{index="3"}

建议：

```text
original_request
```

创建后不可修改。

用户说新话以后：

```text
新版本 Goal
```

保存新的原始请求或者变更请求，而不是改旧数据。

---

# 四、goal_type

这一字段表达：

> **用户当前想解决什么经营问题。**

例如可能是：

```text
PERFORMANCE_ACHIEVEMENT
CUSTOMER_REVIEW
PRODUCT_OPERATION
RELATIONSHIP_MAINTENANCE
OPPORTUNITY_DISCOVERY
STRATEGY_ADVICE
OPERATION_REVIEW
```

但这里我不建议现在把 enum 完全锁死。

因为规范本身说的是“例如”，不是穷举。:chatgpt-content-reference{index="4"}

所以 Contract 应允许未来扩展。

例如：

```text
goal_type:
    code: performance_achievement
```

而不是写成永远不可扩展的五选一。

---

# 五、metric

`metric` 表达：

> 用什么指标衡量 Goal。

例如：

```text
metric:
    code: NBEV
```

或者：

```text
metric:
    code: premium
```

也可能不存在：

> 帮我看看王女士下一步怎么经营。

这时候：

```text
metric = null
```

是完全合法的。

不要为了填字段：

```text
metric = customer_conversion
```

自己猜一个。

---

# 六、target

target 不能简单设计成：

```python
target: float
```

因为 Goal 不一定是金额。

可能是：

```text
500W NBEV
```

也可能是：

```text
覆盖100位客户
```

甚至：

```text
提升转化率
```

因此逻辑上建议至少支持：

```text
target:
    type
    value
    unit
    direction
```

例如：

```text
target:
    type: quantitative
    value: 500
    unit: 万
    direction: at_least
```

而：

> 最近有什么值得关注的机会？

可能是：

```text
target = null
```

也是合法 Goal。

---

# 七、time_horizon

这个字段很值得谨慎。

比如用户说：

> 开门红阶段完成500W。

如果系统没有权威的：

```text
开门红开始/结束日期
```

就不能擅自写：

```text
2026-10-01 ~ 2027-03-31
```

应该允许：

```text
time_horizon:
    raw: 开门红阶段
    start: null
    end: null
```

然后：

```text
missing_information
```

说明尚未解析成确定日期。

未来可以通过知识/配置 Tool 解析。

这是“事实必须有来源”的直接体现。:chatgpt-content-reference{index="5"}

---

# 八、audience_scope

表达：

> Goal 针对谁。

例如：

```text
当前代理人全部可经营客户
```

或者：

```text
王女士
```

或者：

```text
我的老客户
```

第一版不用急着定义特别复杂的 DSL。

它只需要能够表达：

```text
scope_type
scope_reference
raw_expression
```

概念即可。

真正：

> “哪些客户满足这个 Scope”

属于以后 Capability / Tool 的事情。

Goal 不负责自己查客户。

---

# 九、product_or_need_context

这个字段非常重要，因为：

> 产品不是 Goal 的固定组成。

比如：

```text
主推御享分红26、御享金越年金
```

只是这次 Goal 的业务背景。

可以表达：

```text
product_context:
    - 御享分红26
    - 御享金越年金
```

也可以是：

```text
need_context:
    - 养老规划
```

甚至两者都没有。

因此这里不要变成：

```python
product_1
product_2
```

更不能把两款 Demo 产品写进类型系统。

Demo 产品必须作为输入，而不是通用逻辑。:chatgpt-content-reference{index="6"}

---

# 十、channel_and_actor

这一个字段有非常特殊的性质。

例如：

```text
channel = 个险
actor = 当前登录代理人
```

可能根本不是用户在 Prompt 里说的。

而是来自：

```text
登录上下文
权限上下文
渠道上下文
```

所以这里需要明确：

> **Goal 不等于纯粹的 LLM 解析结果。**

Goal 实际上是：

```text
User Request
+
Trusted Runtime Context
+
明确的缺失状态
```

组合出来的。

尤其：

```text
channel
actor
```

绝对不能由 LLM 猜。

规范要求渠道、人员、客户归属和经营权限最终由确定性来源处理。:chatgpt-content-reference{index="7"}

---

# 十一、constraints

这里表达用户或业务上下文施加的限制。

例如：

```text
只经营个险渠道
```

或者：

```text
优先经营老客户
```

或者：

```text
暂时不触达已拒绝客户
```

注意未来要区分：

```text
User Constraint
```

和：

```text
Business Rule
```

例如：

> 我优先想找老客户。

是 Constraint。

而：

> 银保客户不能进入当前个险任务。

是 Rule。

**绝不能因为两者看起来都是“限制”，就在 Goal 里混为同一种确定性规则。**

等 T03 Evidence / Rule 类型建立后，这个边界会继续加强。

---

# 十二、success_criteria

这是非常容易被忽略，但对于以后 Tracking 极其重要的字段。

例如：

```text
metric = NBEV
target = 500W
```

那么：

```text
success_criteria:
    NBEV >= 500W
```

以后 M7：

```text
当前180W
```

才能判断：

```text
36%
```

并重新得到：

```text
remaining_gap = 320W
```

而如果用户问：

> 帮我看看王女士下一步怎么经营。

success criteria 可能完全不同：

```text
形成一个有证据支撑的下一步经营策略
```

所以成功条件也不是永远是一个金额。

---

# 十三、missing_information

这个字段不要简单定义为：

```text
["time"]
```

我建议第一版就稍微结构化一点：

```text
MissingInformation

field
reason
impact
required_before_execution
```

例如：

```text
field:
    time_horizon.end

reason:
    用户未明确具体结束日期，
    当前上下文也没有提供开门红日期配置

impact:
    无法准确判断目标完成期限

required_before_execution:
    false
```

意味着：

> 可以先规划，但这是一个明确缺失项。

另一个例子：

```text
field:
    channel_and_actor.actor

impact:
    无法进行经营权限校验

required_before_execution:
    true
```

意味着：

> 可以进行部分只读分析，但在执行任务前必须补齐。

这刚好与规范的“澄清门槛”保持一致：只有信息缺失会导致明显不同行动、越权或不可逆执行时，才必须阻断并询问用户。:chatgpt-content-reference{index="8"}

---

# 十四、assumptions

例如：

```text
assumption:
    本轮暂以当前登录代理人的全部个险可经营客户
    作为候选分析范围

reason:
    用户未特别限定客户范围

revisable:
    true
```

这一项必须明确：

> assumption ≠ fact。

后面用户随时可以修改。

---

# 十五、Goal 的核心不变量

我建议正式确定下面 8 条。

### G-01 原始表达不可丢失

```text
original_request
```

必填。

---

### G-02 Goal 可以不完整

允许：

```text
metric = null
time_horizon = null
```

不能为了结构完整而臆造字段。

---

### G-03 缺失必须显式表达

重要缺失信息进入：

```text
missing_information
```

---

### G-04 假设必须显式表达

系统继续规划所使用的默认前提进入：

```text
assumptions
```

不能偷偷藏在 Prompt 中。

---

### G-05 Goal 不包含 Plan

禁止：

```text
next_capability
tool_to_call
workflow
```

Goal 回答：

> **我要完成什么？**

Plan 才回答：

> **怎么完成？**

---

### G-06 Goal 不包含经营结论

例如禁止：

```text
opportunity = 养老客户
```

因为那是分析结果。

Goal 可以有：

```text
need_context = 养老
```

前提是用户明确说了。

---

### G-07 Demo内容不能变成 Schema

下面任何内容都不能成为 Goal 类型中的特殊字段：

```text
开门红
500W
御享分红26
御享金越年金
个险
```

它们只是值。规范也明确要求这些示例不得绑定到实现。:chatgpt-content-reference{index="9"}

---

### G-08 Goal 修改必须可版本化

任何影响经营语义的修改：

```text
目标
范围
期限
产品方向
关键约束
```

都产生新的版本。

旧 Goal 不被覆盖。

---

# 十六、用我们的 Demo 验证一下

输入：

> 当前处于开门红阶段，我希望达成的NBEV为500W，当前主推的产品为御享分红26、御享金越年金。

Goal 大概应该表达成：

```text
Goal

goal_id:
    goal_xxx

    1


original_request:
    当前处于开门红阶段，
    我希望达成的NBEV为500W，
    当前主推的产品为御享分红26、御享金越年金。


goal_type:
    performance_achievement

    NBEV

    type: quantitative
    value: 500
    unit: 万
    direction: at_least


time_horizon:
    raw: 开门红阶段
    start: null
    end: null

    当前代理人可经营客户

    products:
      - 御享分红26
      - 御享金越年金

    channel: 个险
    actor: 当前登录代理人

    []

    NBEV >= 500W

    []
```

这里注意：

`个险 / 当前代理人`

不是从这句话解析出来的。

它应该由：

```text
Trusted Runtime Context
```

注入。

# 再拿另外两个 Goal 攻击一下这个 Contract

### Case B

> 帮我看看王女士下一步怎么经营。

完全可以：

```text
goal_type:
    strategy_advice

metric:
    null

target:
    null

audience_scope:
    specific_customer: 王女士

product_or_need_context:
    null
```

合法。

---

### Case C

> 最近有什么值得关注的机会？

也可以：

```text
goal_type:
    opportunity_discovery

metric:
    null

target:
    null

time_horizon:
    recent

audience_scope:
    current_actor_manageable_customers
```

仍然合法。

这说明：

> Goal Contract 没有被“500W开门红”绑架。

# 到这里，M1-T01 和 M1-T02 可以形成第一个正式决策

**T01 架构决策：**

```text
Application → Domain
Application → Agent → Model

Domain 独立
```

`Domain` 不依赖 `Agent / Model`，`Agent` 也不感知智慧经营领域。

**T02 Goal 决策：**

```text
Goal
=
原始经营诉求
+
结构化目标
+
可信业务上下文
+
显式缺失信息
+
显式假设
+
版本
```

它只描述：

> **“经营者想完成什么。”**

绝不描述：

> **“Agent准备怎么完成。”**

---

下一步我建议我们不要立刻进入 T03，而是先做一个很小但重要的动作：**把 Goal Contract 再往下一层落成 Python 类型设计**，也就是具体讨论 `Goal`、`Target`、`TimeHorizon`、`MissingInformation` 等哪些应该是独立 Value Object，哪些先保持简单字段。

这一步完成之后，T02 才真正能够交给开发实现。

# 具体实现

那我们就把 **M1-T02 再落一层，直接定成可实现的 Python 类型设计**。

我建议第一版遵循一个原则：**只把真正具有独立语义和校验规则的字段拆成 Value Object，其余先保持简单，避免过度建模。**

```text
Goal
├─ GoalType
├─ Metric
├─ Target
├─ TimeHorizon
├─ AudienceScope
├─ ProductOrNeedContext
├─ ChannelAndActor
├─ Constraint[]
├─ SuccessCriterion[]
├─ MissingInformation[]
└─ Assumption[]
```

但第一版并不需要把上面所有东西都做成复杂 class。

## 1. Goal 本体

我建议 `Goal` 本身作为不可随意修改的领域对象：

```python
@dataclass(frozen=True)
class Goal:
    goal_id: str
    version: int

    original_request: str

    goal_type: str | None
    metric: "Metric | None"
    target: "Target | None"

    time_horizon: "TimeHorizon | None"
    audience_scope: "AudienceScope | None"
    product_or_need_context: "ProductOrNeedContext | None"
    channel_and_actor: "ChannelAndActor | None"

    constraints: tuple["Constraint", ...]
    success_criteria: tuple["SuccessCriterion", ...]

    missing_information: tuple["MissingInformation", ...]
    assumptions: tuple["Assumption", ...]
```

这里我比较建议：

```python
frozen=True
```

因为 Goal 一旦形成，就不应该：

```python
goal.target = 400
```

而应该：

```text
Goal v1 → Goal v2
```

这样以后 Plan、Opportunity、Task 都能准确知道自己基于哪个 Goal 版本。

---

## 2. `goal_type` 第一版先不要做死 Enum

这是一个容易踩坑的地方。

我暂时不建议：

```python
class GoalType(Enum):
    PERFORMANCE = ...
    STRATEGY = ...
```

因为现在对于 Goal 分类体系，我们还没有业务验证。

第一版可以简单：

```python
goal_type: str | None
```

例如：

```python
"performance_achievement"
"strategy_advice"
"opportunity_discovery"
```

等后面实际跑出足够多场景，再决定是否收敛成：

```text
受控枚举 / Registry / 配置
```

也就是说：

> **M1 先稳定语义，不提前稳定分类全集。**

---

## 3. Metric

Metric 可以做一个很轻的 Value Object。

```python
@dataclass(frozen=True)
class Metric:
    code: str
    display_name: str | None = None
```

例如：

```python
Metric(
    code="NBEV",
    display_name="新业务价值",
)
```

为什么不直接：

```python
metric = "NBEV"
```

因为以后很可能出现：

```text
code
单位
口径版本
指标定义
```

但现在先不要全部塞进去。

---

## 4. Target

这个建议一定拆出来。

不要：

```python
target: float
```

建议：

```python
@dataclass(frozen=True)
class Target:
    target_type: str
    value: object | None
    unit: str | None = None
    direction: str | None = None
```

比如：

```python
Target(
    target_type="quantitative",
    value=500,
    unit="万元",
    direction="at_least",
)
```

未来也允许：

```python
Target(
    target_type="directional",
    value=None,
    direction="increase",
)
```

所以它可以覆盖：

> 达到500W

以及：

> 提升转化率

这种不同 Goal。

---

## 5. TimeHorizon

这个也值得独立。

```python
@dataclass(frozen=True)
class TimeHorizon:
    raw_expression: str | None = None
    start_at: datetime | None = None
    end_at: datetime | None = None
```

比如：

```python
TimeHorizon(
    raw_expression="开门红阶段",
    start_at=None,
    end_at=None,
)
```

这非常重要，因为它保留了：

> 用户到底说了什么

同时不会假装：

> 系统已经知道“开门红”的准确日期。

未来如果通过业务配置解析出来：

```python
start_at = ...
end_at = ...
```

再形成更完整的 Goal 版本即可。

---

## 6. AudienceScope

第一版也不要设计成复杂查询 DSL。

建议：

```python
@dataclass(frozen=True)
class AudienceScope:
    scope_type: str
    reference: str | None = None
    raw_expression: str | None = None
```

例如：

### 当前全部可经营客户

```python
AudienceScope(
    scope_type="manageable_customers",
)
```

### 王女士

```python
AudienceScope(
    scope_type="specific_customer",
    reference="customer_xxx",
    raw_expression="王女士",
)
```

这里一个原则：

> `AudienceScope` 描述对象范围，不负责真正执行查询。

查询属于未来 Capability / Tool。

---

## 7. ProductOrNeedContext

这里我建议不要创建一个巨大对象。

简单一点：

```python
@dataclass(frozen=True)
class ProductOrNeedContext:
    product_refs: tuple[str, ...] = ()
    need_refs: tuple[str, ...] = ()
    raw_expression: str | None = None
```

例如：

```python
ProductOrNeedContext(
    product_refs=(
        "御享分红26",
        "御享金越年金",
    ),
)
```

第一版甚至可以先用业务名称。

后面接真实产品知识库以后，再变成：

```text
product_id
product_version
```

而 Goal Contract 本身不需要变化。

---

## 8. ChannelAndActor

这个值得单独建模，因为它来自可信 Runtime Context，而不是纯 LLM。

```python
@dataclass(frozen=True)
class ChannelAndActor:
    channel_ref: str | None
    actor_ref: str | None
```

例如：

```python
ChannelAndActor(
    channel_ref="individual_insurance",
    actor_ref="agent_123",
)
```

注意这里不保存：

```text
是否有权限
是否可以经营某客户
```

这些属于后面的规则校验结果。

`ChannelAndActor` 只表示：

> 当前是谁、在哪个业务上下文里发起这个 Goal。

---

## 9. Constraint

第一版保持通用：

```python
@dataclass(frozen=True)
class Constraint:
    constraint_type: str
    value: object
    source: str
```

例如用户说：

> 优先老客户。

可以表达：

```python
Constraint(
    constraint_type="customer_preference",
    value="existing_customer",
    source="user",
)
```

这里 `source` 很重要，因为以后可能来自：

```text
user
runtime_context
configuration
```

但还是那句话：

> **Constraint 不是 Business Rule。**

像“银保客户不能进入个险名单”不应该塞进这里当用户 Goal 的 Constraint。

---

## 10. SuccessCriterion

这个也应该是独立对象。

```python
@dataclass(frozen=True)
class SuccessCriterion:
    criterion_type: str
    metric_code: str | None = None
    operator: str | None = None
    value: object | None = None
    description: str | None = None
```

例如：

```python
SuccessCriterion(
    criterion_type="metric_threshold",
    metric_code="NBEV",
    operator=">=",
    value=500,
)
```

而：

> 给王女士形成下一步经营建议

可能是：

```python
SuccessCriterion(
    criterion_type="deliverable",
    description="形成有依据的下一步经营策略",
)
```

这样以后 Tracking 不会天然只支持数字指标。

---

## 11. MissingInformation

这个我建议认真一点。

```python
@dataclass(frozen=True)
class MissingInformation:
    field: str
    reason: str
    impact: str | None = None
    required_before_execution: bool = False
```

例如：

```python
MissingInformation(
    field="time_horizon.end_at",
    reason="尚未取得开门红阶段对应的确定截止日期",
    impact="暂时无法准确计算剩余经营时间",
    required_before_execution=False,
)
```

以及：

```python
MissingInformation(
    field="channel_and_actor.actor_ref",
    reason="当前没有可信登录人员上下文",
    impact="无法完成经营权限校验",
    required_before_execution=True,
)
```

这个结构以后对 Planner 非常有用。

Planner 可以判断：

```text
可以继续分析
```

还是：

```text
必须先澄清 / 获取可信上下文
```

---

## 12. Assumption

建议也单独建模：

```python
@dataclass(frozen=True)
class Assumption:
    field: str | None
    description: str
    reason: str | None = None
    revisable: bool = True
```

比如：

```python
Assumption(
    field="audience_scope",
    description="暂以当前代理人的全部可经营客户作为分析对象",
    reason="用户没有进一步限定客户范围",
)
```

这能保证未来页面、日志、Plan 都知道：

> 哪些内容是事实，哪些只是为了继续工作而采用的假设。

---

## 13. 第一版不要做 `GoalBuilder` 太复杂

我建议 M1 只提供一个很轻的构造入口。

例如：

```python
goal = Goal(...)
```

以及必要的验证：

```text
goal_id不能为空
version >= 1
original_request不能为空
target有value时target_type必须存在
missing_information.field不能为空
```

先不要做：

```text
GoalFactory
GoalBuilder
GoalAssembler
GoalRepository
GoalService
GoalManager
```

这些都没有真实问题支撑。

符合你们当前原则：

> 新增抽象必须能说明它解决的当前问题。:chatgpt-content-reference{index="0"}

---

## 14. Goal 本身也不要负责复杂业务校验

例如不要：

```python
goal.validate_business_permissions()
```

也不要：

```python
goal.resolve_campaign_period()
```

Goal 内部校验只负责：

> **自身结构是否合法。**

比如：

```text
original_request 是否为空
version是否合法
Target结构是否合法
```

而：

```text
开门红到底是什么日期
当前产品是否有效
代理人有没有权限
```

都应该交给未来 Tool / Capability。

---

```python
goal = Goal(

        target_type="quantitative",
        value=500,

        direction="at_least",
    ),
    time_horizon=TimeHorizon(
        raw_expression="开门红阶段",
    ),
    audience_scope=AudienceScope(
        scope_type="manageable_customers",
    ),
    product_or_need_context=ProductOrNeedContext(
        product_refs=(
            "御享分红26",

    ),
    channel_and_actor=ChannelAndActor(
        channel_ref="individual_insurance",
        actor_ref="current_agent",
```

注意这个对象本身完全不知道：

```text
AgentLoop
```

## 我建议 M1-T02 最终只实现这些类型

第一轮控制在：

```text
Goal
Metric
Target
TimeHorizon
AudienceScope
ProductOrNeedContext
ChannelAndActor
Constraint
SuccessCriterion
MissingInformation
Assumption
```

看起来有 11 个，但绝大多数只是很薄的 Value Object。

**不要再往下拆。**

尤其现在不要做：

```text
Campaign
Product
Customer
AgentIdentity
MetricDefinition
BusinessPeriod
```

那些属于后面真实业务能力需要时再建。

---

## T02 的单元测试建议直接定下来

至少有四组。

**Case A：完整绩效目标**

```text
开门红 + 500W NBEV + 两款产品
```

能正常创建。

**Case B：信息不完整**

```text
最近有什么值得关注的机会？
```

`metric / target` 为 `None` 仍然合法。

**Case C：单客户策略**

```text
帮我看看王女士下一步怎么经营
```

能表达 `specific_customer`，不要求 target。

**Case D：禁止隐式补事实**

用户只有：

```text
开门红阶段
```

系统没有可信时间配置时：

```text
start_at=None
end_at=None
```

而不是自动编日期。
