
进入 T06。这个阶段其实是在给未来的 Replan 建“交通信号灯”。

前面我们已经有：

```text
CapabilityRequest
        ↓
    Capability
        ↓
CapabilityResult
```

T06 要解决的是：

> **超级 Agent 收到 `CapabilityResult` 后，怎么准确知道“成功了、没结果、缺信息、被规则拦住了，还是系统真的坏了”？**

规范明确要求 Capability 统一区分“成功、部分成功、需补充信息、规则阻断、无结果、失败”，并且后续 Plan 要能因为空结果、证据冲突、规则阻断等情况重新规划。:chatgpt-content-reference{index="0"}

---

# 一、先正式定义 6 个 Status

这 6 个我建议直接做稳定 Enum，因为它们已经属于系统协议，而不是业务分类。

```python
from enum import Enum


class CapabilityStatus(str, Enum):
    SUCCESS = "success"
    PARTIAL_SUCCESS = "partial_success"
    NEED_INFORMATION = "need_information"
    BLOCKED = "blocked"
    NO_RESULT = "no_result"
    FAILED = "failed"
```

暂时**不要再加**：

```text
TIMEOUT
CANCELLED
RETRYING
PENDING
```

因为：

- `TIMEOUT` 是失败原因，不是业务结果；
- `RETRYING` 是 Application/Runtime 行为；
- `PENDING` 将来真有异步 Capability 再引入；
- `CANCELLED` 当前没有真实需求。

保持第一版克制。

---

# 二、六种状态最重要的是语义不能重叠

建议直接把这个表当成 Contract。

| Status               | 含义                                     | Capability 是否正常执行 | 有无业务结果 | 是否意味着系统错误 |
| -------------------- | ---------------------------------------- | ----------------------: | -----------: | -----------------: |
| `SUCCESS`          | 要求的业务目标已经完成                   |                      是 |           有 |                 否 |
| `PARTIAL_SUCCESS`  | 得到有效结果，但并未完整满足要求         |                 是/部分 |           有 |             不一定 |
| `NEED_INFORMATION` | 缺少继续可靠处理所需的信息               |                      是 |     可有部分 |                 否 |
| `BLOCKED`          | 确定性业务规则阻止继续                   |                      是 |         可有 |                 否 |
| `NO_RESULT`        | 请求合法且执行正常，但业务上没有找到结果 |                      是 |   无核心结果 |                 否 |
| `FAILED`           | Capability 本身无法正常完成              |                      否 |       不可靠 |                 是 |

这张表很关键。

---

# 三、`NO_RESULT` 和 `FAILED` 必须彻底区分

例如自动圈客：

```text
查询成功
↓
符合 Opportunity 的客户数 = 0
```

这是：

```text
NO_RESULT
```

绝对不是：

```text
FAILED
```

因为系统一点问题都没有。

相反：

```text
客户平台 HTTP 500
```

才是：

```text
FAILED
```

如果这两个混在一起，未来 Planner 会做出完全错误的动作。

---

# 四、`NEED_INFORMATION` 也不是 FAILED

例如 Strategy Capability：

```text
客户历史保障：有
客户家庭结构：有
客户最新资金预算：未知
```

如果这条信息会显著影响经营策略：

```text
NEED_INFORMATION
```

而不是：

```text
FAILED
```

这意味着系统实际上工作正常，只是在告诉 Planner：

> **现在证据还不够，我不应该硬编一个答案。**

这正符合当前规范：证据不足时允许补充信息、暂缓甚至不建议经营，而不是为了返回非空答案强行生成策略。:chatgpt-content-reference{index="1"}

---

# 五、什么时候才应该是 PARTIAL_SUCCESS

这个状态最容易滥用。

我建议定义为：

> **Capability 已经产生至少一个有效、可使用的核心结果，但部分请求输出、对象或证据处理未完成。**

例如自动圈客要求：

```text
100 个候选客户
+
完整排序理由
```

实际：

```text
100个候选客户生成成功
其中8人的部分辅助画像读取失败
```

可以：

```text
PARTIAL_SUCCESS
```

因为主体结果仍然有价值。

---

但：

```text
一个客户都没找到
```

不是 Partial：

```text
NO_RESULT
```

而：

```text
客户名单完全没有生成，
因为客户数据服务挂了
```

是：

```text
FAILED
```

---

# 六、BLOCKED 是最特殊的状态

例如：

```text
Customer D

经营价值：
HIGH

产品适配：
HIGH

养老需求模型：
0.91

↓ Validation

渠道归属：
银保

当前渠道：
个险
```

结果必须：

```text
BLOCKED
```

它不是：

```text
FAILED
```

因为规则服务正常工作了。

甚至可以说：

> **BLOCKED 是一次成功完成的规则裁决。**

但业务动作被禁止。

规范明确规定业务规则结果优先，Agent 只能解释和寻找合法补救路径，不能覆盖裁决。:chatgpt-content-reference{index="2"}

---

# 七、因此 BLOCKED 必须有 Rule Result

建议形成硬不变量：

```text
status == BLOCKED

→ rule_result_refs 不能为空
```

例如：

```python
CapabilityResult(
    ...,
    status=CapabilityStatus.BLOCKED,

    rule_result_refs=(
        "ev_rule_channel_001",
    ),
)
```

对应 T03：

```text
EvidenceType.RULE_RESULT
```

中保存：

```text
rule_id
rule_version
result
reason
effective_period
```

这样：

```text
“为什么被阻断？”
```

最终可以追溯到确定性规则，而不是 Agent 自己写一句：

> 不推荐经营。

---

# 八、Error 应该只服务于真正的 FAILED / PARTIAL_FAILURE

现在正式定义：

```python
class ErrorCategory(str, Enum):
    VALIDATION = "validation"
    DEPENDENCY = "dependency"
    TIMEOUT = "timeout"
    ACCESS = "access"
    INTERNAL = "internal"
```

这里的：

```text
ACCESS
```

一定注意：

这是**技术访问失败**。

比如：

```text
客户数据服务 Token 失效
```

是：

```text
FAILED + ACCESS
```

而：

```text
代理人业务上无权经营客户
```

是：

```text
BLOCKED + RULE_RESULT
```

这两个千万不能混。

---

# 九、CapabilityError

建议第一版：

```python
@dataclass(frozen=True)
class CapabilityError:
    code: str
    category: ErrorCategory

    message: str

    retryable: bool = False

    source: str | None = None
```

例如：

```python
CapabilityError(
    code="CUSTOMER_SERVICE_TIMEOUT",
    category=ErrorCategory.TIMEOUT,
    message="客户数据服务调用超时",
    retryable=True,
    source="customer_profile_service",
)
```

或者：

```python
CapabilityError(
    code="INVALID_OBJECT_SCOPE",
    category=ErrorCategory.VALIDATION,
    message="策略生成要求指定客户对象",
    retryable=False,
)
```

---

# 十、为什么 Error Code 用 str，不用 Enum

这里和 Status 不一样。

Status 是稳定协议：

```text
6种
```

而错误码未来会不断增加：

```text
CUSTOMER_SERVICE_TIMEOUT
MODEL_UNAVAILABLE
KNOWLEDGE_VERSION_NOT_FOUND
INVALID_SCOPE
UPSTREAM_SCHEMA_ERROR
...
```

所以：

```python
code: str
```

更合适。

而：

```python
category: ErrorCategory
```

保持少量、稳定、可用于 Planner 做粗粒度处理。

---

# 十一、不要把原始 Exception 放进 Domain

不要：

```python
CapabilityError(
    exception=exc,
    traceback=...
)
```

这些属于：

```text
Trace / Log
```

Domain Result 最多记录：

```text
错误码
类别
安全摘要
是否建议重试
来源
```

详细 stack trace 继续留给现有 Runtime Trace。

这也避免 CapabilityResult 泄漏：

```text
SQL
服务器地址
Token
客户敏感字段
内部 Prompt
```

规范同样要求日志和页面不能扩大敏感信息暴露。:chatgpt-content-reference{index="3"}

---

# 十二、NEED_INFORMATION 应该返回什么

我们之前 T02 已经有：

```text
MissingInformation
```

这里我建议**复用它，不再重新发明一个 MissingRequirement**。

把原来的：

```python
@dataclass(frozen=True)
class MissingInformation:
    field: str
    reason: str
    impact: str | None = None
    required_before_execution: bool = False
```

视为领域级通用 Value Object。

于是：

```python
CapabilityResult(
    status=CapabilityStatus.NEED_INFORMATION,

    missing_information=(
        MissingInformation(
            field="customer.financial_budget",
            reason="缺少客户当前可投入资金信息",
            impact="无法可靠判断产品方案和经营节奏",
            required_before_execution=False,
        ),
    ),
)
```

---

# 十三、一个小调整：`required_before_execution` 可以保留

它以后会特别有用。

例如：

```text
缺少客户预算
```

可能：

```text
required_before_execution = False
```

可以继续生成一版有假设的策略。

但：

```text
缺少当前执行人身份
```

应该：

```text
required_before_execution = True
```

可以先做某些只读分析，但绝对不能创建任务。

这和当前规范的澄清门槛完全一致：只有缺失会导致明显不同动作、越权或不可逆执行时才必须阻断。:chatgpt-content-reference{index="4"}

---

# 十四、NO_RESULT 返回什么

例如自动圈客：

```text
Opportunity:
养老现金流规划

执行正常

候选客户：
0
```

建议：

```python
CapabilityResult(
    status=CapabilityStatus.NO_RESULT,
    outputs=(),
    errors=(),
)
```

但是仍然可以保留：

```text
evidence_refs
execution_meta
quality
next_action_hints
```

例如：

```text
next_action:
重新评估筛选条件

next_action:
重新执行定向洞察

next_action:
等待数据更新
```

关键不变量：

```text
NO_RESULT.errors == ()
```

正常情况下不能有系统错误。

---

# 十五、FAILED 返回什么

例如：

```text
customer_targeting

调用客户平台失败
```

应该：

```python
CapabilityResult(
    status=CapabilityStatus.FAILED,

    outputs=(),

    errors=(
        CapabilityError(
            code="CUSTOMER_PLATFORM_UNAVAILABLE",
            category=ErrorCategory.DEPENDENCY,
            message="客户平台当前不可用",
            retryable=True,
            source="customer_platform",
        ),
    ),
)
```

硬约束：

```text
FAILED
→ errors 至少一条
```

否则：

```text
FAILED
但为什么失败不知道
```

对 Replan 没有任何意义。

---

# 十六、SUCCESS 的硬约束

```text
SUCCESS
```

意味着：

> 当前 Capability 契约要求的核心结果都已产生。

因此建议：

```text
SUCCESS.errors == ()
```

并且：

```text
required outputs 已满足
```

例如 Insight：

```text
Opportunity 至少一个
```

当然也有一些 Capability 成功返回：

```text
没有需要执行的动作
```

这种情况是否算 Success 还是 No Result，需要由具体 Capability Contract 定义。

但统一原则是：

> **如果“没有找到东西”本身是此次业务请求的自然结果，优先 NO_RESULT。**

---

# 十七、PARTIAL_SUCCESS 必须解释“哪里不完整”

建议不允许：

```python
status=PARTIAL_SUCCESS
```

然后什么信息都不提供。

至少满足一个：

```text
errors 非空

或

missing_information 非空

或

quality.limitations 非空
```

例如：

```python
CapabilityResult(
    status=CapabilityStatus.PARTIAL_SUCCESS,

    outputs=(
        ...
    ),

    errors=(
        CapabilityError(
            code="INTERACTION_HISTORY_UNAVAILABLE",
            category=ErrorCategory.DEPENDENCY,
            ...
        ),
    ),

    quality=ResultQuality(
        completeness=0.85,
        limitations=(
            "部分客户互动记录不可用",
        ),
    ),
)
```

---

# 十八、更新 CapabilityResult

T05 中留下来的两个 `Any` 现在可以正式收口。

建议：

```python
@dataclass(frozen=True)
class CapabilityResult:
    result_id: str
    request_id: str

    capability_id: str
    capability_version: str

    status: CapabilityStatus

    outputs: tuple[CapabilityOutput, ...] = ()

    evidence_refs: tuple[str, ...] = ()
    rule_result_refs: tuple[str, ...] = ()

    missing_information: tuple[MissingInformation, ...] = ()

    quality: ResultQuality | None = None

    errors: tuple[CapabilityError, ...] = ()

    next_action_hints: tuple[NextActionHint, ...] = ()

    execution_meta: CapabilityExecutionMeta | None = None
```

这时候 `CapabilityResult` 已经相当完整了。

# 十九、建议加一层 Contract Validation

不需要做一个：

```text
CapabilityResultValidatorService
```

这么重的东西。

直接：

```python
def __post_init__(self) -> None:
```

或者简单独立校验函数就行。

例如逻辑：

```python
if self.status == CapabilityStatus.FAILED and not self.errors:
    raise ValueError("FAILED result must contain errors")

if self.status == CapabilityStatus.BLOCKED and not self.rule_result_refs:
    raise ValueError("BLOCKED result must reference rule results")

if (
    self.status == CapabilityStatus.NEED_INFORMATION
    and not self.missing_information
):
    raise ValueError(
        "NEED_INFORMATION result must describe missing information"
    )
```

这三条我认为值得从第一版就代码保证。

# 二十、Agent 将来看到六个状态以后该怎么做

T06 暂时不开发 Planner，但可以把语义先确定。

```text
SUCCESS
     ↓
继续 Plan
```

---

```text
PARTIAL_SUCCESS
     ↓
判断缺失部分是否影响后续
     ↓
继续 or Replan
```

---

```text
NEED_INFORMATION
     ↓
能否从可信 Tool / Context 获取？
     ├── 能 → 获取后重新调用
     └── 不能
           ↓
     是否影响关键决策/权限？
           ├── 是 → 问用户
           └── 否 → 明确假设后继续
```

---

```text
BLOCKED
     ↓
停止当前受阻动作
     ↓
保留已确认事实
     ↓
寻找合法替代路径 / Replan
```

Agent **绝对不能**：

```text
BLOCKED
↓
再调用一次看看能不能绕过去
```

除非外部条件已经发生明确变化。

---

```text
NO_RESULT
     ↓
不要把同样参数机械重试
     ↓
调整 Opportunity / 条件 / Plan
或者正常结束
```

---

```text
FAILED
     ↓
retryable?
 ┌───┴────┐
yes       no
↓          ↓
有限重试   fallback / replan / stop
```

这基本就是未来 M3 Replan 的决策基础。

# 二十一、两个特别重要的例子

## 场景 A：圈不到客户

```text
Goal
500W NBEV

↓
Opportunity
养老现金流

↓
Targeting

查询正常
符合客户 = 0
```

结果：

```text
NO_RESULT
```

Agent 下一步可能：

```text
重新洞察
↓
修改 Opportunity
```

而不是：

```text
系统异常，请稍后重试
```

---

## 场景 B：客户特别好，但是不能经营

```text
Targeting
↓
Customer A
价值很高

↓
Validation
↓
银保渠道
```

结果：

```text
BLOCKED

rule_result:
    channel_eligibility_rule_v12

reason:
    客户归属银保渠道
```

Agent 下一步只能：

```text
把客户移出当前个险执行集
↓
重新补充其他候选客户
```

而不能修改：

```text
rule_result = pass
```

这正是规范要求的规则优先。:chatgpt-content-reference{index="5"}

# 二十二、T06 建议确定这些状态不变量

| 编号 | 不变量                                                           |
| ---- | ---------------------------------------------------------------- |
| S-01 | 六种 Status 语义互斥，不使用空结果代替状态                       |
| S-02 | `NO_RESULT` 表示正常执行无业务结果，不属于失败                 |
| S-03 | `NEED_INFORMATION` 表示信息不足，不属于系统失败                |
| S-04 | `BLOCKED` 表示确定性规则阻断，不属于系统失败                   |
| S-05 | `BLOCKED` 必须关联权威 Rule Result                             |
| S-06 | Agent 不得覆盖、修改或绕过 BLOCKED                               |
| S-07 | `FAILED` 必须包含至少一条 Error                                |
| S-08 | Error 描述技术/契约失败，业务裁决不能包装为 Error                |
| S-09 | `SUCCESS` 不应携带 Error                                       |
| S-10 | `PARTIAL_SUCCESS` 必须明确缺失、错误或限制                     |
| S-11 | Retry 行为由上层 Planner/Application 决定，Status 本身不执行重试 |
| S-12 | Raw exception/traceback 不进入 Domain Result                     |

## T06 完成以后，我们终于拥有了一个真正可供 Agent 理解的执行协议

现在：

```text
CapabilityRequest
        ↓
    Capability
        ↓
CapabilityResult
        │
        ├── SUCCESS
        ├── PARTIAL_SUCCESS
        ├── NEED_INFORMATION
        ├── BLOCKED
        ├── NO_RESULT
        └── FAILED
```

主 Agent 不再需要研究：

```text
返回是不是None？
列表是不是空？
有没有exception？
字符串里有没有“失败”？
```

而是获得非常明确的业务语义。

这一步实际上是在为后面 **M3 的 Replan** 打地基。

而按我们原来的 M1 拆解顺序，**下一步 T07 就该正式进入 Plan Contract**：解决 `Plan / PlanStep / CapabilityCall` 到底如何表达，既能让 Agent 动态规划，又不会不小心造出第二个 Workflow Engine。
