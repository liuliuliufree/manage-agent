可以。基于现在已经完成的 `model + agent runtime`，我建议把 M1 定义得非常克制：

> **M1 的目标不是“让智慧经营智能体变聪明”，而是把智慧经营领域中未来所有 Agent 行为都要依赖的稳定业务契约建立起来。**

所以这一阶段尽量**不碰 Prompt、不做真正规划、不写洞察算法、不接真实客户数据**。重点是回答：“未来这些东西在系统里究竟是什么？”

规范已经给出了很明确的基础关系：`Goal → Plan → Capability → Tool`，Plan 是运行时产物；Capability 是通用经营能力；Tool 承担确定性数据、规则、模型、知识和业务执行。:chatgpt-content-reference{index="0"}

我建议把 M1 拆成 **8 个具体任务**。

# M1 最终交付目标

M1 结束以后，我们应该能够纯靠代码构造出这样一个对象关系：

```text
Goal
 │
 └── Plan
      │
      ├── CapabilityCall
      │      │
      │      └── CapabilityResult
      │
      └── Opportunity
             │
             └── Evidence
```

并且这些对象可以：

```text
创建
↓
校验
↓
序列化
↓
互相关联
↓
被测试
```

但暂时**不用让 LLM 自动生成它们**。

# M1-T01：先明确领域层边界

这是第一件事，而且不要直接开始写类。

要先明确：

```text
src/model/
```

负责：

> 怎么调用模型。

```text
src/agent/
```

负责：

> 怎么进行通用 Agent Loop、Tool 调用、Trace。

接下来新增的领域层负责：

> 智慧经营到底在运行什么东西。

概念上应该形成：

```text
Business Layer
    ↓
Agent Runtime
    ↓
Model Runtime
```

而不是：

```text
agent/loop.py
    ↓
开始识别500W
    ↓
开始处理养老客户
```

### 本任务要确定的东西

主要确定：

- Goal 属于业务层；
- Plan 属于业务层；
- Opportunity 属于业务层；
- Capability 属于业务层；
- Evidence 属于业务层；
- Tool 继续属于 Agent Runtime；
- `AgentLoop` 不感知 `开门红 / 客户 / 产品 / NBEV`。

### Done

能画出非常简单的依赖：

```text
经营业务层
    ↓
src/agent
    ↓
src/model
```

并确认：

> **依赖只能向下，`src/agent` 不反向依赖智慧经营业务模块。**

这和目前项目要求的“底层能力不感知具体业务”是一致的。:chatgpt-content-reference{index="1"}

---

# M1-T02：定义 Goal Contract

这是 M1 最重要的对象之一。

规范已经定义了 Goal 至少需要表达的东西，包括：

- 原始自然语言；
- goal type；
- metric；
- target；
- time horizon；
- audience scope；
- product / need context；
- channel / actor；
- constraints；
- success criteria；
- missing information。:chatgpt-content-reference{index="2"}

但是这里不要急着追求一个“完美 Goal Schema”。

第一版应该重点解决三个问题。

### 1. 原始输入必须保留

比如：

```text
当前处于开门红阶段，
目标500W NBEV，
主推御享分红26和御享金越年金。
```

无论之后怎么结构化：

```text
original_request
```

都不能丢。

### 2. 不知道就是不知道

例如没有截止日期：

不要：

```text
time_horizon = "开门红结束"
```

Agent 自己补。

应该：

```text
time_horizon = null

missing_information:
    - time_horizon
```

规范明确要求字段允许为空，但缺失必须显式表达。:chatgpt-content-reference{index="3"}

### 3. Goal 要有版本概念

未来用户可能说：

```text
目标500W
```

后来又说：

```text
改成400W。
```

不能简单修改原对象。

概念上应该允许：

```text
Goal v1
↓
Goal v2
```

这一点以后对 Replan 很重要。

### Done

至少能手工构造：

```text
Goal A:
开门红500W

Goal B:
帮我看看王女士下一步怎么办

Goal C:
最近有什么值得关注的经营机会
```

三种 Goal。

不能因为不是“500W目标”就无法表达。

# M1-T03：定义 Evidence Contract

我建议 **Evidence 比 Opportunity 更早定义**。

因为后面几乎所有东西都会依赖证据：

```text
Opportunity
Strategy
Customer Recommendation
Validation Result
Agent Decision
```

规范反复强调：

> 客户事实、产品知识、规则结果、模型判断、Agent建议必须区分，不能混在一起。:chatgpt-content-reference{index="4"}

所以 Evidence 最重要的职责，不是保存一段文字，而是回答：

```text
这是什么类型的信息？
从哪里来的？
什么时候成立？
哪个版本？
它是事实还是判断？
```

最低限度建议支持这样的语义：

```text
Evidence

type:
    FACT
    RULE
    MODEL_SIGNAL
    KNOWLEDGE
    EXPERIENCE
    AGENT_JUDGEMENT

source

timestamp / effective_time

version

content / reference

quality / confidence
```

注意：

`AGENT_JUDGEMENT`

可以作为证据链中的判断节点，但它绝对不能冒充：

```text
FACT
```

### Done

能明确表达例如：

```text
客户年龄52岁
→ FACT

养老需求评分0.82
→ MODEL_SIGNAL

银保客户不得进入当前个险名单
→ RULE

该客户当前可能存在养老现金流机会
→ AGENT_JUDGEMENT
```

只要这四种东西还能混成一个普通字符串，M1 就还没做好。

---

# M1-T04：定义 Opportunity Contract

有了 Goal 和 Evidence，才定义 Opportunity。

这里要特别注意：

> Opportunity 不是“客户标签”。

例如：

```text
高净值客户
```

不是一个好的 Opportunity。

而：

```text
客户临近退休，但当前长期养老现金流准备不足，
可能存在进一步养老规划空间
```

才接近 Opportunity。

规范已经要求 Opportunity 至少能表达：

- 和 Goal 的关系；
- problem statement；
- evidence；
- eligibility；
- exclusions；
- priority；
- validity；
- candidate logic；
- next actions。:chatgpt-content-reference{index="5"}

### M1 不需要实现什么？

暂时不用解决：

> Opportunity 到底怎么计算出来？

那是 M4。

M1 只回答：

> **一个 Opportunity 一旦被产生出来，它必须长什么样。**

### 一个很重要的测试

把：

```text
开门红
```

从 Opportunity 中全部去掉。

看看结构还能不能成立。

例如：

```text
opportunity_type:
retirement_cashflow_gap
```

应该既可以出现在：

```text
开门红
```

也可以出现在：

```text
日常经营
```

甚至：

```text
年中经营
```

因为规范明确要求 Opportunity 与具体场景解耦。:chatgpt-content-reference{index="6"}

---

# M1-T05：定义 Capability Contract

这是把业务世界和现有 Agent Runtime 接起来的核心。

这里一定要先回答一个问题：

> **Capability 和 Tool 到底有什么不同？**

我建议明确：

```text
Tool
=
一个可被执行的技术/业务能力接口
```

例如：

```text
get_customer_profile

query_customer_population

get_product_knowledge

check_customer_channel
```

而：

```text
Capability
=
Agent试图解决的一类经营问题
```

例如：

```text
directional_insight

customer_targeting

strategy_generation

validation_distribution

tracking_iteration
```

也就是：

```text
Capability
    ↓
可能组织一个或多个 Tool
```

### Capability 输入

规范里已经要求至少关联：

```text
goal_id
plan_id
上下文
对象范围
授权主体
数据时间点
所需输出
约束
```

### Capability 输出

至少应该有：

```text
status
result
evidence
decision_type
quality/confidence
rule_result
error
next_action
```

以及版本信息和审计信息。:chatgpt-content-reference{index="7"}

---

# M1-T06：统一 Capability Status 与错误语义

这个任务看起来很小，但建议单独列出来。

不要让：

```text
Insight
CustomerTargeting
Strategy
Validation
```

将来每个人自己定义状态。

从 M1 就统一：

```text
SUCCESS

PARTIAL_SUCCESS

NEED_INFORMATION

BLOCKED

NO_RESULT

FAILED
```

这是非常有价值的。

因为以后 Agent 才能理解：

### `NO_RESULT`

代表：

> 正常执行，但没有找到结果。

### `NEED_INFORMATION`

代表：

> 信息不足，不是系统错误。

### `BLOCKED`

代表：

> 规则明确不允许继续。

### `FAILED`

代表：

> 系统本身执行失败。

规范特别要求这些情况不能混在一起。:chatgpt-content-reference{index="8"}

### Done

Fake Capability 能分别返回以上六种状态。

但本阶段 Agent 还不需要知道怎么处理。

M3 再做。

# M1-T07：定义 Plan Contract

这时候再定义 Plan。

这里我建议保持极简。

Plan 暂时不要变成复杂工作流 DSL。

Plan 本质上只需要表达：

```text
为了 Goal，
当前准备做什么，
为什么，
以及它们之间有什么依赖。
```

例如：

```text
Plan
 ├── goal_id
 ├── plan_id
 ├── version
 ├── status
 └── steps
```

其中：

```text
PlanStep
```

最核心的是：

```text
step_id

capability

reason

input_context

dependencies

status
```

暂时不要加入大量：

```text
branch
loop
condition
retry_policy
workflow_node
```

因为你已经有 Agent Loop。

如果再把 Plan 自己设计成一个完整 Workflow Engine，会出现：

```text
Agent Loop
+
Workflow Engine
```

两套控制系统。

这正是现在应该避免的过度设计。

### M1 对 Plan 的关键测试

必须能表达：

```text
Plan A

Insight
↓
Targeting
↓
Strategy
```

也能表达：

```text
Plan B

Strategy
↓
Validation
```

也能表达：

```text
Plan C

Insight
```

甚至：

```text
Plan D

Tracking
↓
Insight
↓
Strategy
↓
Targeting
```

这样从数据结构层面就不会把五个 Capability 固化成顺序状态机。

规范明确要求不得假设五种能力全部出现、只出现一次或者按编号顺序执行。:chatgpt-content-reference{index="9"}

# M1-T08：建立 Contract Test，而不是业务功能测试

M1 最后的任务不是开发 Demo，而是“攻击这些抽象”。

我建议至少写下面几类测试。

### Goal Test

```text
缺少期限
→ 合法 Goal
→ missing_information 中存在期限
```

### Opportunity Test

```text
Opportunity 没有 Evidence
→ 不允许成为已确认 Opportunity
```

或者根据最后设计：

```text
必须明确 evidence unavailable
```

### Capability Result Test

```text
status = BLOCKED

必须允许包含：
rule result
reason
```

### Plan Test 1

```text
只包含 strategy_generation
```

合法。

### Plan Test 2

```text
insight
targeting
insight
```

合法。

### Plan Test 3

```text
tracking
insight
strategy
```

合法。

### Plan Test 4

```text
Capability = 未注册能力
```

不合法。

### Evidence Test

```text
MODEL_SIGNAL
```

不能被自动转换成：

```text
FACT
```

# 我建议 M1 明确“不做什么”

这个特别重要，否则这一阶段很容易失控。

**M1 不做：**

- Goal Parser Prompt；
- Planner Prompt；
- LLM 自动生成 Plan；
- 真正的洞察算法；
- 客户圈选；
- 产品推荐；
- 策略生成；
- 渠道规则实现；
- 任务创建；
- 数据库持久化；
- 前端页面；
- 复杂 Workflow DSL；
- 多 Agent。

尤其先不要做持久化。

现在最重要的是先把：

```text
in-memory contract
```

设计正确。

等 M2/M3 运行起来以后，我们才会真正知道哪些状态需要持久化。

# M1 最终验收，我建议就问 7 个问题

| 验收问题                                   | 必须回答 |
| ------------------------------------------ | -------- |
| 任意自然语言经营诉求能否被 Goal 表达？     | 能       |
| 信息缺失是否可以显式存在？                 | 能       |
| 事实、规则、模型和 Agent 判断能否区分？    | 能       |
| Opportunity 是否脱离开门红仍然成立？       | 能       |
| Capability 是否与 Tool 明确区分？          | 能       |
| Plan 是否允许跳过、重复、重排 Capability？ | 能       |
| 整个业务层是否没有反向污染`src/agent`？  | 是       |

全部通过，M1 就可以结束。

**Day 1**：T01 + T02

**Day 2**：T03 + T04
Evidence 和 Opportunity。

**Day 3**：T05 + T06
Capability Contract 和统一 Result。

契约测试、跨场景攻击测试、更新 `architecture.md/current-state.md/dev-log.md`。

> **智慧经营智能体第一次拥有了稳定的“业务语言”。**

而 M2 就可以非常自然地进入：

```text
Natural Language
        ↓
Goal Parser
        ↓
Goal
        ↓
Planner
        ↓
Plan
```

这时才正式开始让 LLM 参与智慧经营决策。

我建议我们接下来就从 **M1-T01 + M1-T02** 开始，把“领域层边界”和 **Goal Contract** 真正定下来。这两个一旦定错，后面的 Plan、Capability 和 Opportunity 都会跟着歪。
