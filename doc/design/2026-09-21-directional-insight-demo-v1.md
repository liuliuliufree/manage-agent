# M4 定向洞察 Demo V1 设计

状态：待确认；单次计划、输出一个优先经营机会已由用户确认，其余为首版推荐方案

创建日期：2026-09-21

## 1. 定位与决策边界

M4 是第一个真正消费业务数据并形成经营判断的 Capability。它解决“在当前 Goal 和当前代理人的可经营范围内，优先探索什么经营机会，以及为什么”，输出一个有证据的 Opportunity，交给后续圈客。

当前 Demo 总范围仍是 Goal 分析 → Opportunity 发现 → 圈客 → 策略制定与执行。M4 只完成其中 Goal → Opportunity，不生成客户执行名单，不制定个性化策略，不创建任务或触达客户。

已确认：

- 每次运行最多一个 Plan，不构建或调用 Replan；无结果就停止。
- M4 首版只发布一个优先经营机会，交给圈客，不要求用户从机会地图中再选择。
- 事实、产品知识和业务规则必须有明确来源及版本；判断和事实分开。
- 渠道与代理人边界不能由模型放宽。
- 2026-09-22 确认标准演示提问：“当前处于开门红阶段，希望完成500W NBEV，主推御享分红26和御享金越年金。”渠道默认个险，操作人为当前代理人，由可信运行上下文注入，不要求用户重复填写。产品提及不代表知识适配已经核实，开门红不自动转换成未经提供的日期。

本文推荐但尚未确认：

- 用版本化合成数据及少量明确业务规则完成首版洞察，不新增洞察 LLM 调用。
- 内部允许比较多个候选方向，只发布排名第一且证据足够的机会。
- 使用透明的分项排序，不构建综合预测分、成交概率或预计 NBEV 模型。

本文是设计讨论稿，不是逐文件施工规格；不锁定未来函数签名、完整数据 Schema 或固定业务阈值。方向确认后再补充供开发模型执行的实施协议与测试细节。旧 roadmap 中先完成 Replan、扩展 Opportunity 全量字段的要求不适用于本首版。

## 2. 当前事实与前置条件

2026-09-21 文件检查确认：

- Domain 已有 Goal、Opportunity、Evidence、CapabilityRequest/Result，无需为了 M4 重建领域对象。
- Opportunity 当前包含 GoalRef、机会类型、问题描述、证据链接及可选优先级和理由；没有圈客 DSL 或预测收益字段。
- Evidence 可表达客户事实、产品事实、经营事实、规则结果和模型信号，并保存来源、时间和限制。
- CapabilityRequest 通过 GoalRef 指向 Goal，通过可信 actor/channel 表达执行主体；请求本身不携带完整 Goal。
- 已有 Tool 协议支持参数校验、调用与结构化结果；不需要引入第二套工具框架。
- 工作区的 Parser、Planner 和执行层正在变化，不能仅依据较早 current-state 的文字判定完成。尚未发现定向洞察业务实现和新首版业务数据集；本次未运行测试。

进入 M4 集成验收前，需要确认 Parser V1、单次 Planner V1、产物流转 V1 已实际完成，尤其是 NO_RESULT 不重规划、输出能保存并按引用读取。数据和规则设计可先行，不能通过伪造成功结果绕开集成前置条件。

## 3. 首版目标与非目标

必须能回答：

1. 这个机会要解决什么经营问题？
2. 为什么与本次 Goal 有关？
3. 哪些数据支持，哪些信息仍缺失或限制判断？
4. 为什么优先于当前其他可评估方向？
5. 后续圈客应核实什么，而不是直接给谁发什么？

首版不做：

- 全市场机会挖掘、任意自然语言规则编译、向量知识库或 RAG 平台。
- 复杂客户评分、机器学习训练、成交概率和 NBEV 贡献预测。
- 根据年龄、收入或家庭阶段单独推断客户已经存在某类需求。
- 为目标金额倒推客户事实、编造保障缺口或投资收益。
- 多个机会并行圈客、用户选机会的会话续接、Replan 和跨运行复用。
- M5 的客户名单及排序、个性化策略，或 M6 的任务创建。
- 新增 InsightAgent、工作流引擎、数据库或通用规则 DSL。

## 4. 用户体验

示例输入可以继续使用“开门红目标500W NBEV，主推御享分红26和御享金越年金”，但产品名称和时间只是 Goal 输入，不是事实依据或实现分支。

推荐展示一张机会说明，而不是产品广告：

| 展示内容 | 说明 |
| --- | --- |
| 优先经营方向 | 基于证据确定的问题，例如“已表达养老现金流需求但尚未完成规划沟通” |
| 与目标的关系 | 该需求方向与本次主推方向或经营诉求相关；不声称足以完成目标金额 |
| 支持依据 | 在当前代理人范围内，由快照实际计算的需求信号规模、相关知识依据和数据时间 |
| 优先理由 | 比较哪些分项后排在其他可评估方向之前 |
| 限制 | 数据为合成演示、需求尚待核实、知识覆盖边界等 |
| 下一步 | 对该机会圈选候选客户并核实条件；不表示这些客户已允许触达 |

这里的标题仅为示例。若数据没有相应支持，不得返回同一标题或固定数量。没有足够证据时显示无可推荐机会及原因，不强行凑出一个结果。

## 5. 输入边界

### 5.1 Goal 与可信运行信息

通过受控应用装配，用 Request.goal_ref 解析本次结构化 Goal，核对版本，不扫描历史运行或另建 Goal 服务。缺少对应 Goal 是装配/技术错误，不请用户提供内部 ID。

使用可信 actor/channel 限定数据范围。分析基准时间由应用提供，可固定为演示快照时间以便复现；必须显示实际使用的时间，不把旧快照解释为实时数据。不能根据“开门红”等原文自行猜测日历日期。

### 5.2 支持的 Goal 范围

- 产品主推型：从已解析的产品提及匹配版本化知识，确定可探索的需求方向。
- 需求探索型：从已支持的需求方向和当前代理人的客户信号寻找机会，可以没有产品和金额。
- 量化目标：保留 metric/target 作为经营目标背景，但不据此预测本机会可以贡献多少 NBEV。

未知产品、歧义别名、无法解释的关键需求或显式客群/渠道约束，不能忽略后返回其他机会。若缺失可由用户补充则返回 NEED_INFORMATION；调用配置缺失则返回 FAILED。明确支持的范围以知识与规则快照为准，不承诺识别任意业务概念。

首版只对有确定性支持的显式约束执行筛选；不支持的关键约束应明确说明。未提供可选金额、产品或时间不能一律阻塞探索请求。

## 6. 最小数据准备

建议使用小型本地版本化快照，生产接入后替换 Tool 内部实现，主 Agent 无需改变调用方式。

| 数据 | 最少需要表达 | 不允许的替代方式 |
| --- | --- | --- |
| 客户/经营事实 | 虚构客户引用、代理人归属、渠道、明确需求信号及观测时间、相关事实来源 | 仅凭人口属性生成需求结论 |
| 产品或需求知识 | 稳定标识、别名、需求关联、适用限制、版本及演示性质 | 把真实产品适配结论写在 Prompt 中 |
| 洞察规则 | 可识别方向、必要证据、信号是否仍可用、比较规则及版本 | 场景名称直接映射固定答案 |
| 分析上下文 | 数据快照标识、规则/知识版本、分析基准时间 | 用系统今天替代数据实际时间 |

演示可准备少量可替换的需求方向，用有明确记录的咨询、需求表达或服务事件作为主要信号。只有浏览、年龄等弱线索时，不能升级成已确认需求；首版建议暂不依靠弱线索单独产生正式机会。

合成数据中的规模由记录计算，不能把展示人数写在规则中。数据应覆盖匹配、无信号、证据不足、过期、非当前代理人、银保渠道及重复记录，形成正常和反例。

真实产品名称若使用合成关联，必须标明“演示知识，不代表真实产品条款或适配结论”。更稳妥的测试默认使用产品甲/乙等虚构名称。业务故事中的产品描述不能单独作为权威知识来源。

本设计不提供真实产品推荐或金融判断；真实产品知识需在后续接入前独立核实。

## 7. 职责与数据流

建议保持一个 directional_insight Capability，内部组合可替换的普通 Tool，不引入新的 Agent Loop。

```text
结构化 Goal + 可信 actor/channel + 分析基准时间
  → 校验支持范围并读取版本化知识
  → 在当前代理人范围内读取和汇总事实
  → 按明确规则形成候选经营问题
  → 检查证据完整性、比较优先级
  → 构造一个 Opportunity 及证据说明
  → 保存对象，发布一个 opportunity 引用
  → 同一 Plan 的后继圈客读取
```

职责边界：

- 知识读取 Tool 提供产品/需求关联及限制，不负责挑选最终客户。
- 事实分析 Tool 完成范围过滤、信号判定和可复现汇总，返回数值及来源。
- Capability 依据受控规则选择优先机会，组织证据及结果。
- Application 构造正式 ID、关联 Goal、保存对象和发布引用。
- 主 Agent 只选择能力及组织整体结果，不理解本地文件结构，不直接改业务规则。

Tool 复用既有稳定协议，参数校验和调用记录不能绕过。采用本地确定性实现即可，不为了“看起来智能”再加一个模型回合，也不为两项本地能力预建插件生命周期。

## 8. 如何形成机会与优先级

首版推荐采用透明的确定性方法：

1. 应用确认 Goal 指向的产品、需求和关键限制能被解释。
2. 先按可信代理人/渠道收窄事实范围，再做聚合；不将其他代理人或银保客户计入机会规模。
3. 对每个已支持方向，检查是否有直接支持该经营问题的有效事实；未知值不能当作不存在需求或已有保障缺口。
4. 用版本化知识判断方向与 Goal 的关联，不将“某产品可关联养老需求”扩张为“某客户一定适合买”。
5. 没有合格证据的方向退出候选，保留简要排除依据。
6. 从证据合格候选中选择一个，构造问题、支持依据、限制和下一步。

优先级建议先比较 Goal 的明确相关性，再比较有直接需求证据的独立客户规模，之后比较信号新近程度。字段定义、窗口和方向顺序应记录在版本化规则中；此处不预设未经验证的阈值或权重。

相同客户在同一方向内去重；不同方向的规模可能重叠，不相加声称总覆盖。可用数据缺失率、无法评估数量应单独展示，不把缺失样本当作负例或虚增置信度。

完全并列时允许稳定的技术顺序保证复现，但应明确“业务指标并列，本次展示其中一个”，不能编造优先性。结果不输出未经校准的概率或神秘总分。

首版建议不增加洞察 LLM 调用。用确定性表述组织已核实字段即可；未来若增加模型，只负责基于给定证据组织语言，不得决定事实数量、权限、产品条款或是否放行。

## 9. 输出与现有契约衔接

### 9.1 一个正式 Opportunity

复用现有 Opportunity：绑定本次 GoalRef，表达经营问题，至少关联真实存在的支持 Evidence。优先级若填写，必须同步提供比较理由；限制性证据使用现有 EvidenceLink 的角色表达。

为满足业务说明，应用保存的机会对象还需携带或关联：Goal 相关性、分析范围/时间、知识和规则版本、关键支持统计、未满足条件和圈客应核实的事项。这些是首版消费者需要的业务说明，不直接扩张 Domain 的核心字段。

推荐以当前运行 Store 中的一个机会业务对象容纳 Domain Opportunity 的序列化内容、可解析的证据记录和最小业务说明。不是将结果 payload 自动合并为 Context，也不是建立第二套 Opportunity 类。精确结构在方案确认后的实施文档中收敛。

### 9.2 Evidence 与可追溯性

- 直接需求记录可表达为 CUSTOMER_FACT；聚合结果表达为有计算来源的 BUSINESS_FACT，不伪装成原始单客户事实。
- 产品关联依据为 PRODUCT_FACT，规则筛选结论为 RULE_RESULT；首版没有模型时不虚构 MODEL_SIGNAL。
- 每条证据保留来源、版本、实际观测或分析时间及适用范围；派生汇总能追溯到输入快照和计算规则。
- Opportunity 的每个 evidence_id 必须能在本次保存的对象或受控事实源解析，不能只生成看起来合法的 UUID。
- Evidence 和 Rule Result 仍为依据或审计，不额外发布成圈客的普通 input_refs。

### 9.3 与产物流转 V1 对齐

无必需前序业务产物，以 Goal 和应用装配的事实源为输入。成功后只发布一个 opportunity 类型输出，对应一个真实保存的对象，遵守每种输出类型最多一个对象的限制。

内部候选不是多个输出，不把机会集合塞进名为单个 opportunity 的对象。结果引用和保存对象的 ID/类型必须一致，后继只通过受控引用读取，不解析 summary 猜经营方向。

完整客户名单和个人联系方式不作为洞察输出。支持证据可关联受控数据范围以供复核，但不能将提前选好的名单包装成机会。

## 10. 与 M5 圈客的交接

M4 交付一个可读取的经营问题及依据，M5 再根据 Goal、机会证据、版本化需求/规则标识动态形成候选条件并执行查询。

为避免 M5 只能解析自然语言，机会业务说明应保留支持判断的需求标识、证据引用与对应规则版本；这些标识来自知识与规则快照，不由模型臆造。它们不是可直接执行的 SQL、表达式或候选名单。

M4 不先建设 candidate_logic DSL，也不要求在 Domain Opportunity 加入完整筛选器。M5 不得以机会标题触发“年龄大于某值”等硬编码分支，更不能重新让模型猜测原有证据。

M4 的圈客交接验收可以使用只读取机会对象并核验内容的消费者替身；不能将这个替身称为已经完成自动圈客。M5 仍需定义并验证实际筛选条件。

## 11. 无结果、缺信息和失败

| 情况 | 建议 Capability 结果 | Demo 后续 |
| --- | --- | --- |
| 合法范围内数据充分且有合格机会 | SUCCESS，恰一个 opportunity | 同一 Plan 可继续圈客 |
| 数据可评估但没有合格方向，包括合法范围内零客户 | NO_RESULT，说明原因和覆盖范围 | 停止，不 Replan |
| 用户关键产品/需求/约束无法唯一解释 | NEED_INFORMATION，结构化缺失 | 提示后结束本次运行 |
| 缺可信身份、Goal 解析关联错误、数据文件损坏或规则配置缺失 | FAILED | 停止，不用空结果掩盖故障 |
| 当前主体被确定性规则禁止分析该范围 | BLOCKED，关联规则证据 | 停止，不放宽条件 |
| 证据覆盖不足以作结论且用户无法补充 | PARTIAL_SUCCESS，仅说明已知信息与限制，不发布机会 | 停止，不自动继续 |

存在部分无效数据但仍有足够有效证据时，可以 SUCCESS 并明确统计范围和遗漏限制；不能把“部分数据缺失”机械等同于整个结果 PARTIAL_SUCCESS。足够证据的条件应由规则定义，而不是靠展示需求决定。

不能静默忽略主推列表中的未知产品后对其余产品返回完整成功；应说明未覆盖内容并在需要完整解释 Goal 时返回缺信息。成功不等于 Goal 金额已达成，也不等于客户已允许执行。

## 12. 最小验收场景

| 场景 | 应看到的行为 |
| --- | --- |
| 产品导向 Goal + 有效演示数据 | 一个相关机会，所有关键结论可回查证据 |
| 无产品、仅探索经营需求 | 根据受支持的需求与数据形成机会，不强制追问产品/金额 |
| 替换阶段或受支持产品 | 不修改通用代码，知识与数据决定不同结论 |
| 调整客户需求信号 | 机会依据、规模或优先方向随数据改变，不固定返回同一机会 |
| 只有年龄或弱浏览信号 | 不编造明确需求或保障缺口 |
| 银保/其他代理人记录混入 | 不进入当前机会统计；存在性本身不导致全量分析被错误阻断 |
| 重复客户与方向重叠 | 单方向去重，跨方向不错误相加 |
| 未知产品、未支持的关键约束 | 明确缺信息或支持边界，不忽略限制 |
| 无信号与数据损坏 | 前者 NO_RESULT，后者 FAILED，二者不能混同 |
| 证据缺失、引用悬空或错误版本 | 不发布正式机会 |
| 排序完全并列 | 稳定选择一个，坦诚说明并列 |
| 成功产物流转 | opportunity 引用可读取实际对象及 Evidence，消费者内容随源数据变化 |
| NO_RESULT / BLOCKED / PARTIAL_SUCCESS | 不发布可继续消费的机会，不触发第二个计划 |
| 目标金额变化 | 保留新目标关联，不伪造客户规模或预测贡献来凑金额 |

离线验证以确定性数据和规则为主，不因缺少新 LLM 调用而降低真实性：真实性来自实际读取、计算、证据关联和结果传递。合成数据结论不能当作真实客户经营效果。

## 13. 取舍与风险

- 一个机会减少产物和交互复杂度，但不能称为全量机会地图。
- 规则方案可解释且易复现，但只覆盖已配置的需求方向；未覆盖的业务问题应诚实返回支持边界。
- 需求信号规模不等于转化概率；首版不估算实现 500W 所需人数。
- 代理人范围过滤是分析数据访问边界，不能替代后续任务创建前的规则复验。
- 将知识、规则和演示数据混成一个固定剧本会损害通用性；必须分别版本化，并用换数据/换 Goal 用例验证。
- Opportunity 的简化 Domain 不能承载所有业务解释，应用机会对象需保留必要说明，但避免重新建设庞大产物元数据体系。

## 14. 待确认事项与成功标准

在进入实施规格前需确认：

1. 是否采用首版无新增洞察 LLM、确定性规则生成一个优先机会的方案。
2. 首批演示知识使用哪些需求方向；标准入口已确认使用御享分红26、御享金越年金，需确定相应知识资料来源，或明确标记合成演示关联；测试仍可使用虚构产品验证通用性。
3. 可用的演示客户事实能支持哪些直接需求信号，以及必要的窗口/证据充分条件。

不以未确认业务阈值阻碍基础设计，也不把这些空白填成看似已验证的规则。本文先确立能力边界和验收方向，确认后再写数据样例、完整输出协议与具体开发清单。

M4 的成功标准：一个已解析 Goal，通过真实运行的业务 Tool 读取版本化演示事实与知识，生成一个有依据、可解释、可存储且能交给圈客读取的 Opportunity；无证据时允许无结果；整个过程不生成第二个计划、不输出未经验证的客户执行结论。
