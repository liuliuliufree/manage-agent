# 前三幕 Mock 数据设计方案

状态：已确认（2026-09-15）

## 1. 问题

Demo 前三幕需要在同一份上下文中完成经营目标理解、多机会洞察和自动圈客。演示结果既要稳定呈现三个候选机会与 86→41→12 的圈客漏斗，也要证明这些结论确实来自原始事实、规则和计算，而不是直接读取预置答案。

本方案定义首套领导演示场景需要提供哪些合成事实、这些事实如何支持三个机会和客户分层、哪些结果必须由确定性逻辑派生，以及如何验证整套数据自洽。

## 2. 已确认事实

- 前三幕共享一次演示运行和同一份不可变数据快照。
- Mock 采用“合成原始数据 + 确定性计算得到固定故事结果”。
- 正常链路不直接 Mock 机会排行、漏斗汇总、客户名单或规则结论。
- 硬边界由普通代码执行；大模型负责目标理解、能力选择和解释组织。
- 除主 Agent 外，数据查询、指标计算和规则判断等业务能力均作为可插拔 Tool。
- Tool 可以由本地函数、外部服务适配器或独立 LLM 调用实现，主 Agent 不感知具体实现。
- 前三幕由主 Agent 消费 Tool 返回的结构化事实和计算结果，并负责形成最终解释与展示文本；首版不额外拆分解释生成 Tool。

## 3. 目标与非目标

### 目标

- 用一份规模适中的合成数据稳定产生故事要求的前三幕结果。
- 让机会指标、推荐理由、漏斗人数和客户解释都可追溯到原始事实。
- 同时覆盖正常入选、硬规则排除、评分降级和边界临界案例。
- 支持替换数据实现而不改变主 Agent 和 Tool 调用协议。
- 为后续策略、执行和事件演示保留 C001、C028 等连续角色。

### 非目标

- 不复刻生产客户、保单、产品和授权系统的完整数据模型。
- 不在首套场景中追求统计代表性或训练机器学习模型。
- 不提前确定数据库、文件格式或持久化方案。
- 不使用真实姓名、手机号、证件号、地址等个人敏感信息。
- 不在本方案中固定代码类名、函数签名或逐文件实现方式。

## 4. 场景总体结构

建议首套场景由四层信息组成：

1. **场景头信息**：确定运行版本、时间基准、随机性和数据来源。
2. **原始业务事实**：模拟外部客户、保单、行为、授权和经营系统提供的数据。
3. **规则与指标口径**：模拟当前生效的硬规则、评分方法和演示用成本参数。
4. **测试期望**：只用于场景校验和自动化测试，不作为正常业务计算输入。

建议初始数据快照包含 120 名合成客户。这个数量足以形成 86 人的重点机会客群，也不会让首版数据维护和页面展示过重。客户可以同时属于多个候选机会，机会规模之和不要求等于客户总数。

场景头信息至少表达：

| 信息 | 设计含义 |
|---|---|
| 场景标识与版本 | 唯一定位本套数据和故事口径 |
| 数据基准时间 | 统一计算“近期”“近 30 天”和授权有效期 |
| 随机种子 | 保证批量合成、并列排序等行为可复现 |
| 数据模式 | 始终明确标注为合成数据 |
| 数据口径版本 | 关联保障缺口、机会指标和客户评分口径 |
| 规则版本 | 关联授权、频控、敏感状态和初步适当性规则 |
| 已知数据质量提示 | 主动表达缺失数据或演示简化项 |

## 5. 原始数据域

### 5.1 经营请求

经营请求表示第一幕中经营人员实际提供的内容，不包含 Agent 已经整理好的结论：

- 原始自然语言目标；
- 分析时间范围；
- 希望改善的经营结果；
- 用户明确提出的数据与经营边界；
- 当前交互主体和请求时间。

故事中的三条边界分别保留原文。系统级硬规则则来自规则快照，两者不能混成一段不可追溯的提示词。

### 5.2 客户基础与家庭责任事实

该数据域只保存机会识别所需的最小画像：

- 合成客户标识；
- 年龄段或演示所需年龄；
- 家庭阶段；
- 被抚养人数或家庭责任级别；
- 收入与持续缴费能力区间；
- 家庭信息最近更新时间；
- 信息由客户主动提供、测算产生或其他授权来源产生；
- 数据用途授权状态和有效期。

不保存姓名、联系方式和精确住址。涉及家庭变化的事实必须带来源、时间和用途授权，避免看起来像 Agent 推测隐私。

### 5.3 保单与保障事实

用于计算保障缺口和保单周年机会：

- 当前有效保单及状态；
- 险种或保障责任类别；
- 当前保障额度；
- 保费与缴费周期；
- 保单生效日和周年日；
- 家庭责任测算所需保障额度；
- 测算口径和版本；
- 是否存在可用于初步匹配的产品范围。

保障缺口由“测算所需额度”和“当前有效保障额度”计算，不在客户数据中额外写入一个不可校验的最终缺口标签。

### 5.4 数据使用与经营授权事实

这一数据用于回答两个直接问题：系统能否使用某项客户信息进行分析，以及当前是否允许围绕相关需求开展经营接触。前三幕只保留：

- 被授权的数据或信息类别；
- 允许的数据用途；
- 是否允许相关经营或营销接触；
- 当前状态；
- 生效与失效时间；
- 授权来源；
- 撤回时间及原因（如有）。

例如，客户主动填写的家庭责任信息可能允许用于保障分析，但并不自动代表客户允许接收营销信息。这两项授权需要分别判断。具体渠道是否可用属于后续策略与执行环节，前三幕暂不展开。

### 5.5 客户行为事件

用于识别主动需求和近期意向：

- 内容打开；
- 保障页面浏览；
- 保障测算开始与完成；
- 主动咨询；
- 家庭信息主动更新；
- 行为发生时间、来源和事件标识；
- 信号有效期或对应的时间衰减口径。

事件本身是原始事实，“主动需求较强”等结论由评分规则派生。

### 5.6 历史触达与负向反馈

用于频控、拒绝和客户打扰判断：

- 触达时间、渠道、用途和结果；
- 是否属于营销触达；
- 明确拒绝、退订或不希望继续联系的事件；
- 事件标识和来源；
- 当前频控窗口内的触达次数。

频控次数原则上从触达事件计算。若 Mock 外部系统只能提供聚合计数，也需要同时说明统计窗口和更新时间，不能把聚合值伪装成事件明细。

### 5.7 敏感状态事实

用于排除当前不适合经营的客户：

- 投诉处理中；
- 理赔处理中；
- 其他经业务确认的暂停经营状态；
- 状态开始、预计结束或复核时间；
- 状态来源。

首版只表达是否阻断当前经营，不扩展生产级投诉或理赔详情。

### 5.8 初步适当性事实

用于第三幕的经营初筛，而不是形成具体产品推荐：

- 持续缴费能力区间；
- 初步风险与需求信息是否完整；
- 当前是否存在可进一步评估的产品范围；
- 必须转专业人员补充确认的事项；
- 数据更新时间和口径版本。

第三幕最多得出“可以开展保障检视”或“当前不宜进入经营”，不能声称客户已经适合购买某一具体产品。

## 6. 三个候选机会的构造

### 6.1 家庭责任变化与重疾保障缺口

基础识别同时依赖：

- 有效且授权用于服务经营的家庭责任信息；
- 家庭责任近期发生更新，或当前家庭责任水平达到业务口径；
- 当前重疾保障低于测算所需保障；
- 数据仍在有效期内。

该机会应覆盖 86 名客户，并在规模、需求强度、预计响应、成本和风险综合比较后排名第一。

### 6.2 临近保单周年的保障回顾

基础识别依赖有效保单和周年时间窗口。客户是否同时存在明显保障缺口可以影响需求强度，但不作为所有客户必须满足的条件。

该机会规模应小于第一类，时间窗口明确、预估触达成本较低，但近期主动需求信号相对较弱，因此不成为首选。

### 6.3 主动了解医疗保障但未完成测算

基础识别依赖近期医疗保障浏览或测算开始事件，并确认尚未完成相应测算。

该机会规模最小、主动意向相对集中、预计响应可以较高，但样本置信度、渠道成本或负反馈风险略高，因此综合排名不超过第一类。

### 6.4 机会指标的派生原则

| 指标 | 建议来源 |
|---|---|
| 客群规模 | 按机会定义从客户明细计数 |
| 需求强度 | 保障缺口、家庭责任、主动行为等标准化贡献 |
| 预计响应 | 根据当前客群中主动行为的覆盖比例、强度和新鲜度形成演示用响应潜力分，不表达为生产预测概率 |
| 触达成本 | 机会规模乘以场景配置的统一单位成本，用于相对比较，不依赖历史经营数据 |
| 风险指标 | 授权完整度、负向反馈、敏感状态和数据质量 |
| 识别置信度 | 数据完整性、时效性、样本基准和证据一致性 |

机会推荐采用版本化的确定性比较口径。具体权重需要业务确认后再固定，但首套数据应避免依赖极小的分数差异，保证合理调整展示精度后第一类机会仍明显领先。

## 7. 第一类机会的圈客分布

建议首套场景固定以下可验证分布：

| 层次 | 人数 | 产生方式 |
|---|---:|---|
| 全部合成客户 | 120 | 场景原始客户数 |
| 第一类机会客户 | 86 | 满足家庭责任与保障缺口基本定义 |
| 可经营客户 | 41 | 通过授权、拒绝、敏感状态、频控和初步适当性硬规则 |
| 高优先级客户 | 12 | 在可经营客户中按需求、主动意向、承接价值和风险排序 |
| 普通可经营客户 | 29 | 通过硬规则但未进入前 12 |

未通过经营初筛的 45 名客户，按页面展示的主要原因建议分布为：

| 主要排除原因 | 人数 |
|---|---:|
| 授权无效或用途不匹配 | 14 |
| 频控窗口内触达过多 | 9 |
| 已明确拒绝相关需求 | 7 |
| 投诉、理赔等敏感状态 | 6 |
| 信息不足或无法通过初步适当性判断 | 9 |
| 合计 | 45 |

客户可以命中多个规则，但漏斗按一套固定优先级归入一个“主要排除原因”，同时保留全部规则命中记录。排除原因的优先级需要与业务和合规人员共同确认；场景校验应保证汇总人数与客户明细一致。

## 8. 优先级评分语义

硬规则只决定客户是否可经营；优先级只在 41 名可经营客户中计算，不能用高分抵消硬规则失败。

建议优先级由以下四类贡献组成：

- **需求贡献**：保障缺口程度、家庭责任水平和信息时效性；
- **主动意向贡献**：近期浏览、测算、主动更新和咨询；
- **承接价值贡献**：保障检视是否有清晰下一步、是否存在可进一步评估的产品范围；
- **风险与疲劳扣减**：接近频控上限、数据缺失、历史负向反馈等非阻断因素。

每个贡献项保存来源事实、分值方向、口径版本和解释标签。第三幕的“圈客优先级分”与第六幕随事件变化的“实时意向分”是两个不同指标，页面和数据中不得混用。

## 9. 锚点角色

### 9.1 C001：完整正向证据链

C001 用于证明系统为什么选择某位客户，建议包含：

- 35 岁，处于家庭责任较高的阶段；
- 近期主动更新家庭信息，且该信息已授权用于服务经营；
- 当前重疾保障显著低于家庭责任测算所需保障；
- 近 30 天两次查看保障内容，并完成一次初步测算；
- 营销用途和演示所需渠道授权有效；
- 近期触达较少，无拒绝、退订、投诉或理赔阻断状态；
- 初步信息支持开展保障检视，但具体产品仍需专业人员确认；
- 在 41 名可经营客户中进入 12 名高优先级客户。

所有描述都必须能定位到对应的原始事实或计算贡献，不另写一个无法追溯的“入选理由”。

### 9.2 C028：执行前状态变化

推荐将 C028 设计为第三幕时通过硬规则并进入高优先级的客户。在第三幕完成后，由场景脚本注入新的外部触达事件，使其在第五幕执行前复检时超过频控限制并被暂缓。

这样可以同时说明：

- 前三幕共享的初始快照没有自相矛盾；
- 高潜力不代表任何时刻都允许触达；
- 第五幕必须基于最新事实重新校验，不能沿用第三幕结果；
- C028 的暂缓来自确定性频控规则，而不是模型改变意见。

第三幕后才发生的预置事件属于后续场景脚本，不进入前三幕的数据快照或圈客计算。

### 9.3 边界角色

除 C001 和 C028 外，建议人工设计少量边界客户：

- 保障缺口明显但无有效营销授权；
- 主动行为较强但已明确拒绝；
- 高分但处于理赔或投诉状态；
- 刚好达到频控上限；
- 刚好未达到高优先级阈值；
- 缺少缴费能力信息，需要转专业人员补充确认；
- 同时属于两个或三个候选机会；
- 数据已过期，不能继续作为家庭责任变化证据。

这些角色用于验证边界，而不是为了丰富页面而增加无关字段。

## 10. 三幕正式产物与 Mock 的边界

### 第一幕产物

从经营请求和规则快照形成结构化经营任务，包括目标、范围、硬边界、可执行动作、必须转人工事项、停止条件和证据来源。

### 第二幕产物

从数据快照、规则和指标口径形成机会组合，包括三个机会的指标、证据、限制、置信度、排序和推荐决定。

### 第三幕产物

从选中机会和客户级事实形成客群筛选结果，包括 86→41→12 漏斗、每位客户的层次、规则命中、评分贡献、入选或排除理由，以及当前允许和禁止的动作。

以上三类正式产物都属于系统计算结果。测试期望可以保存这些结果的关键摘要用于断言，但运行时不得将期望摘要当作 Tool 的正常返回值。

## 11. 合成数据的构造方式

建议采用“人工锚点 + 约束批量生成”的混合方式：

1. 人工维护 C001、C028 和边界角色，保证故事解释自然且证据完整。
2. 其余客户按固定种子和分布约束生成，减少逐条维护成本。
3. 生成后只保存原始事实，不把最终机会标签和圈客结论写回原始客户数据。
4. 每次调整规则或数据后重新运行场景校验，确认人数、排行和锚点结论没有意外漂移。

不建议完全随机生成，因为难以稳定满足业务分布；也不建议手写 120 条完整记录，因为数据容易重复、矛盾且难以维护。

## 12. 场景校验

场景在进入 Demo 前至少通过以下检查：

- 客户、保单和事件标识唯一，所有关联都能解析；
- 所有事件时间不晚于所属快照的基准时间；
- 授权、规则、指标和数据口径均有版本；
- 家庭责任信号具有来源、更新时间和用途授权；
- 保障缺口能够从测算所需额度与当前保障重算；
- 三个机会都能从客户明细独立重算，且第一类排名第一；
- 第一类机会精确产生 86 名机会客户、41 名可经营客户和 12 名高优先级客户；
- 五类主要排除原因合计为 45，且均可追溯到规则命中；
- C001 进入高优先级且完整通过硬规则；
- C028 在第三幕进入高优先级，后续事件未提前污染初始快照；
- 同一场景重复运行得到一致的关键结果；
- 数据中不存在真实个人敏感信息，所有展示明确标注为合成数据。

## 13. 与可插拔 Tool 的关系

Mock 数据源应位于 Tool 实现之后。主 Agent 只看到稳定的能力与结构化结果，不直接读取场景文件或依赖 Mock 专用字段。

前三幕至少涉及以下能力边界：

- 读取经营规则与数据范围；
- 查询客户、保单、授权和行为事实；
- 计算保障缺口和机会指标；
- 比较并推荐候选机会；
- 执行客群筛选、硬规则校验和优先级排序；

首版可以由本地确定性函数承载数据与规则能力。主 Agent 调用这些 Tool 后，根据返回的结构化事实、规则命中和评分贡献形成最终解释。未来接入数据库、指标平台或 LLM 型业务 Tool 时，只替换对应 Tool 的实现。

## 14. 取舍与风险

- 120 名客户便于维护，但不足以代表真实统计规律；页面应将指标表达为演示场景结果。
- 固定漏斗有利于演示稳定，但规则变化可能导致人数漂移；必须用校验器及时暴露，而不是调整汇总数字掩盖问题。
- 预计响应和触达成本只是透明规则产生的演示比较指标，不代表基于真实历史样本训练或校准的预测结果。
- 字段过少会让解释缺乏证据，字段过多会提前固化生产模型；首版只保留前三幕决定实际消费的事实。
- 机会综合排序如果依赖未经确认的权重，会制造虚假精确性；应先确认指标方向和明显领先关系，再确定展示精度。

## 15. 已确认决策

1. 首套场景使用 120 名客户，并固定第一类机会的 86→41→12 分布。
2. 45 名排除客户按 14、9、7、6、9 分布到授权、频控、拒绝、敏感状态和初步适当性五类主要原因。
3. C028 在第三幕进入高优先级，第三幕后因新增触达事件在第五幕被频控暂缓。
4. 第二、第三类机会暂不固定具体人数，只要求规模小于第一类、指标可以比较且能够从客户明细重算。
5. 机会排序先采用透明的规则评分，后续获得真实业务口径后再替换或调整权重。
6. 第一幕故事中的三条边界由经营人员显式输入；系统规则快照补充具体执行参数，但不能覆盖或放宽用户边界。
7. 第三幕页面展示漏斗汇总、12 名高优先级客户和少量有代表性的排除样例，不默认展示全部 86 名客户。
8. 首版场景原始数据采用 CSV 保存，由确定性代码生成；测试期望与业务源数据分目录隔离。

## 16. 成功标准

- 业务人员能仅根据方案判断每类数据为何存在、被哪一幕消费。
- 数据团队可以据此准备合成事实，而不需要预造最终结论。
- 开发人员可以用同一数据快照重算机会、漏斗和客户证据。
- C001、C028 和各类边界客户的故事没有时间或规则矛盾。
- 替换 Mock 数据源或 LLM 解释实现时，主 Agent 的能力调用边界不发生变化。
