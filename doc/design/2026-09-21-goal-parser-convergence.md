# Goal Parser 收敛设计

状态：已确认的完整方向；Demo 首版范围已由独立开发文档收缩

> 2026-09-21 首版范围调整：快速构建时以 [Goal Parser Demo V1 范围与开发说明](2026-09-21-goal-parser-demo-v1.md) 为实施依据。本文中的通用 KEEP/SET/CLEAR 修订、细粒度字段恢复、自动格式修复及两步迁移不再作为首版交付要求。本文保留为后续演进参考，其中“当前事实”是原设计编写时背景，不能替代工作区核实与当前事实文档。

## 1. 文档定位

本文用于收敛当前 Goal Parser 的职责、输入输出语义、Goal 创建与修订规则、澄清门槛和可信边界，为后续独立开发会话提供连续的设计上下文。

本文是已确认设计，不覆盖当前代码、`doc/current-state.md`、`doc/architecture.md` 或 M1 Domain Contract。本文描述后续 Goal Parser 收敛的设计约束；在代码和事实文档完成同步前，不得把本文中的目标状态误写成当前实现事实。

## 2. 当前事实

当前 Goal Parser 位于单一 Application 模块中，已经具备以下能力：

- 使用 `ChatModel` 将自然语言请求解释为结构化业务语义；
- 创建新 Goal，或基于已有 Goal 生成同一 ID 的下一版本；
- 对模糊的泛化业绩指标要求澄清；
- 不向模型提供可信 Runtime Context，由 Application 注入 actor 和 channel；
- 忽略模型生成的活动起止日期，只接受用户原文中的时间表达；
- 产品、需求、客群引用等内容只有能回指用户原文时才会进入 Goal；
- 在 Planner 之前阻断需要澄清的请求。

当前模块同时承担模型请求、Prompt、JSON 解析、字段规范化、原文校验、澄清判断、Goal 构造和 Goal 修订，职责已经过度集中。

当前已知缺口包括：

- 修改已有 Goal 时，`original_request` 会被最新一句修改请求替换；
- 字段缺失、`null`、保留旧值和清空旧值之间没有统一语义；
- 澄清结果主要是自由文本问题，没有把阻塞性缺失写入 Goal 的 `missing_information`；
- Goal 中已有 `assumptions` 契约，但 Parser 尚未建立受控使用方式；
- Metric code 主要依赖模型生成，只对少数歧义表达设置了确定性门禁；
- Goal Parser 没有受限的 JSON 格式修复；
- 模型协议错误、业务语义缺失和需要用户澄清尚未形成清晰的错误边界；
- 澄清后继续、Goal 版本持久化和修改历史不在当前实现范围内。

## 3. 目标与非目标

### 3.1 目标

- 让模型只负责解释用户明确表达的业务语义，不决定可信身份、版本、权限或业务规则。
- 让 Application 以确定性方式完成来源校验、字段规范化、Goal 创建、Goal 修订和澄清门禁。
- 统一新建 Goal 与修改已有 Goal 的字段语义，明确保留、设置和清空的区别。
- 使阻塞性缺失以 `missing_information` 进入 Goal，而不是只存在于澄清文案中。
- 保证 Goal 的原始表达、版本身份和旧版本不可变性符合 M1 Contract。
- 保持 Goal Parser 是一个稳定公共入口，同时拆分内部职责，避免继续扩大单文件。
- 保持与 Planner 和 BusinessAgent 的边界清晰，为后续澄清恢复机制保留稳定输入。

### 3.2 非目标

- 不在本设计中修改 Planner、Replan 或 Capability 契约。
- 不实现 Goal Repository、Event Sourcing 或跨请求会话恢复。
- 不建设完整指标本体、产品知识库或复杂自然语言规则引擎。
- 不自动分解复杂 Goal 或建立子目标贡献模型。
- 不让 Goal Parser 判断客户是否可经营、产品是否适配或任务是否允许分发。
- 不引入工作流框架、Parser 插件框架或多个业务 Parser。
- 不为尚无消费者的字段扩展 M1 Goal Contract。

## 4. 核心职责边界

Goal Parser 的处理过程分为三个阶段：

```text
用户请求 + 可选已有 Goal
              ↓
模型语义解释
              ↓
确定性校验、规范化和修改合并
              ↓
版本化 Goal + 结构化解析结果
```

### 4.1 模型职责

模型只解释用户明确表达的内容，包括：

- 目标意图和目标类型；
- 指标提及、目标值和方向；
- 时间、客群、产品、需求和约束的原始表达；
- 用户是否明确要求修改或移除某个字段；
- 可能存在的歧义及其自然语言说明。

模型不得决定：

- Goal ID 和版本；
- actor、channel、授权主体和权限；
- 业务规则结论；
- 用户未表达的产品、需求、日期或完成事实；
- 是否绕过阻塞性缺失进入 Planner。

### 4.2 Application 职责

Application 负责：

- 校验模型结果是否符合约定结构；
- 将语义内容与用户原文或可信上下文关联；
- 标准化数值、单位、比较方向和受治理的指标代码；
- 对已有 Goal 应用明确的字段修改语义；
- 构造新 Goal 或不可变的新版本；
- 生成结构化 MissingInformation；
- 判断缺失是否阻止 Planner；
- 注入可信 actor 和 channel；
- 区分业务澄清与技术失败。

### 4.3 Domain 职责

M1 Goal Contract 继续负责 Goal 的稳定字段和机器可校验不变量。Application 不创建 LiteGoal、GoalDraft 等第二套领域事实对象；模型语义结果和修改指令属于 Application 临时契约，不成为新的持久领域对象。

## 5. Goal 创建语义

新请求应尽可能形成一个结构化 Goal，即使它尚不完整。未知值保持为空，不得为获得完整对象而猜测事实。

部分 Goal 仍必须满足 M1 Goal Contract 的最小不变量。如果 `goal_type` 等必填语义无法可靠确定，Parser 返回结构化 MissingInformation 和澄清问题，但不创建 Goal、不分配 ID，也不引入 GoalDraft 或占位类型。

当缺少的信息会导致明显不同的行动、越权或不可逆执行时：

- Goal 保留当前已经明确的内容；
- 缺失进入 `missing_information`；
- 解析结果要求澄清；
- BusinessAgent 不调用 Planner。

例如“这个月业绩做到 500W”可以形成包含目标值和时间表达的不完整 Goal，同时把具体指标记录为执行前必须补齐的信息。

当缺失不影响当前阶段时，例如用户只要求发现近期经营机会但没有指定金额或产品，Goal 可以保持相应字段为空并继续规划。

## 6. Goal 修订语义

### 6.1 修改操作

修改已有 Goal 时，不再依赖字段是否出现或 `null` 的隐式含义。每个可修改的顶层业务字段统一明确区分：

- `KEEP`：用户没有修改该字段，保留已有值；
- `SET`：用户明确提供新值，替换已有值；
- `CLEAR`：用户明确要求移除已有值。

这些操作只属于 Application 的解析和合并过程，不进入最终 Goal，也不进入 Domain Schema。

未表达的字段默认为 `KEEP`。只有能够从用户请求确认移除意图时才允许 `CLEAR`。模型提出修改操作后，Application 仍需校验其原文依据和字段一致性。

`SET` 表示该顶层字段合并后的完整目标值，不是开放式局部 Patch。集合字段需要删除其中一项时，模型可以基于可信的已有 Goal 给出删除后的完整值；Application 必须保证没有新增无法回指用户本次请求或已有 Goal 的内容。`CLEAR` 只清空整个顶层字段。首版不引入 `APPEND`、`REMOVE_ITEM` 或任意 JSON Patch；当单项修改无法可靠归并时，应要求澄清。

### 6.2 原始表达

`Goal.original_request` 始终保存创建该 Goal 时的首次请求原文，Goal 修订时不替换它。这里的“首次”不要求请求在业务语义上已经完整；它表示 Goal 身份的创建来源。

后续修改请求应由运行 Trace 或未来专门的 Goal 修订记录保存，不应把“改成 400W”之类的局部表达覆盖为 Goal 的原始目标。当前阶段不因此提前建设 Goal History Repository。

### 6.3 版本

- 创建新 Goal 时生成新 ID，版本从 1 开始；
- 修改 Goal 时保持 ID 并递增版本；
- 旧 Goal 对象保持不变；
- 只要当前已知语义足以构造满足 M1 不变量的 Goal，即使仍有阻塞性缺失，新 Goal 也立即获得正式 ID 和版本 1；解析结果同时标记需要澄清，该版本不得进入 Planner；
- 如果连 `goal_type` 等 M1 必填不变量都无法可靠确定，则不创建 Goal、不分配 ID，也不得用通用类型占位；结构化缺失由解析结果承载；
- 修改已有 Goal 时，只要用户的修改意图通过协议、来源和一致性校验，就生成下一版本。即使该修改引入阻塞性缺失，新版本仍保存修改后的意图和 `missing_information`，但不得进入 Planner；
- 模型协议失败、无原文依据的修改或相互冲突且无法收敛的操作不产生新版本，已有 Goal 保持为最后一个已确认版本。

## 7. 缺失信息与澄清门槛

### 7.1 结构化缺失

影响规划或执行的信息缺失应记录：

- 缺失字段；
- 缺失原因；
- 对后续行动的影响；
- 是否必须在执行前补齐。

澄清问题是 MissingInformation 的用户表达，不是唯一事实源。

### 7.2 阻塞性缺失

首版采用最小、确定性的阻塞规则集。以下缺失将 `required_before_execution` 设为 `true`，并阻止进入 Planner：

- 同一目标值可能对应不同经营指标，或指标与目标值无法可靠关联，且不同解释会产生明显不同的计划；
- 用户要求直接经营、跟进或操作具体对象，但请求和已有可信 Context 都不能可靠识别该对象；
- 用户请求外部写操作，但可信 Runtime Context 中的主体、对象范围或执行前必要控制条件缺失；
- Goal 修改操作相互冲突，无法确定应保留、设置还是清空关键字段；
- 继续规划会造成明显越权风险，或会把不可逆动作建立在未确认的关键语义上。

阻塞性缺失必须停止进入 Planner。

首版直接复用 `MissingInformation.required_before_execution` 作为 Parser 到 BusinessAgent 的阻塞标志，不新增第二个 `required_before_planning` 字段。其语义是：在当前 BusinessAgent 会立即执行 Plan 的前提下，该信息必须在本轮规划执行链开始前补齐。未来若支持“先做安全只读步骤、写操作前再确认”，应在真实消费者出现后另行设计阶段化门禁，不能静默改变本字段语义。

### 7.3 非阻塞性缺失

以下情况通常不应强制澄清：

- 探索经营机会时未指定量化目标；
- 未指定产品或需求方向；
- 未提供精确日期，但当前只需探索或分析；
- 已有 Context 足以支撑用户明确请求的后续动作。

最终门槛由确定性校验决定，模型只能提供语义信号和澄清问题草案。

### 7.4 假设

首版不自动生成假设。`assumptions` 保留为 Domain 能力，但在出现明确消费者和可审计来源前，不允许模型用假设填补阻塞性缺失。

## 8. 可信来源与规范化

### 8.1 可信 Runtime Context

actor 和 channel 继续由 Runtime Context 提供，不发送给模型用于语义生成，也不接受模型输出覆盖。Goal 应记录其可信来源。

### 8.2 原文可追溯

时间、客群、产品、需求和用户约束应能够回指用户原文。模型生成但无法找到原文依据的内容不得升级为 Goal 事实。

规范化值可以不同于原始表达，例如“500W”可以规范为 `500 万元`，但原始表达仍需保留在对应语义或 Goal 的原始请求中。

### 8.3 指标词汇

Metric code 不得依赖模型自由生成。Goal Parser 通过 Application 层只读端口注入一个轻量、可替换、可版本化的指标词汇快照，用于把用户提及和受控别名映射到标准指标。

首个事实源采用仓库内受版本控制的业务配置数据，而不是 Prompt、Python 分支或前端常量。该配置至少携带稳定的 `source_id`、显式业务版本 `version`、标准 metric code、展示名、可接受别名及必要的单位约束。Git 提交历史不能替代业务版本。具体文件格式和路径在实现时按仓库现状确定，不在设计阶段锁死。

指标词汇版本属于解析运行的来源元数据，应进入可观测的解析诊断或 Trace；当前 M1 `Metric` 没有版本字段，因此首版不得为此修改 Goal Contract 或把版本拼进 metric code。未来只有在 Planner、Tracking 或审计成为真实消费者时，才评估 Metric Definition/version 引用。

模型可以提取指标原文，但 Application 只接受词汇快照唯一命中的 code。零命中或多命中均生成结构化 MissingInformation；模型创造的新 code 不得直接进入 Goal。该首版来源可以在未来由平台指标服务适配器替换，而不改变 Parser 公共入口。

### 8.4 时间

Goal Parser 继续优先保留用户的时间原文。精确日期解析需要确定性时间基准和来源，在该能力建立前，不采信模型自行生成的活动起止日期。

## 9. 输出与 BusinessAgent 边界

Goal Parser 的稳定输出需要区分：

- 已创建 Goal；
- 已修订 Goal；
- 需要澄清；
- 技术失败。

输出至少应携带：

- 当前可构造的 Goal；
- 是否需要澄清；
- 结构化 MissingInformation；
- 面向用户的澄清问题；
- 必要的非敏感诊断信息。

BusinessAgent 的规则是：只要存在 `required_before_execution=true` 的 MissingInformation，就返回澄清结果且不调用 Planner；否则将 Goal 交给 Planner。新建或成功修订的 Goal 以自身 `missing_information` 作为结构化缺失事实源，解析结果只做同一信息的便捷投影。Goal 因 M1 不变量无法构造时，或已有 Goal 的修改没有任何字段通过来源/一致性校验而不产生新版本时，解析结果直接承载本次解析缺失；后者返回的旧 Goal 仍只代表上一个已确认版本，不吸收本次失败修改。调用方必须按解析状态和缺失门禁处理，不能仅凭存在 Goal 就进入 Planner。

本设计不定义澄清后的自动恢复协议，但要求澄清响应保留足够的 Goal 身份和缺失信息，使未来能够建立稳定恢复入口。

## 10. 模型协议与失败边界

### 10.1 格式修复

允许最多一次严格受限的格式修复，只用于 JSON 语法或无歧义的协议结构问题。修复请求必须要求保留原响应中的业务字符串、数值、修改操作和空值语义，不得补充用户未表达的字段；修复结果需要重新经过完整协议、来源和确定性业务校验。第二次仍不合法时返回协议失败，不再重试。

以下问题不能通过格式修复处理：

- 用户没有表达的产品、需求或事实；
- 无法确定的指标；
- 相互冲突的修改操作；
- 违反可信来源或字段一致性的值。

### 10.2 结果分类

- 用户信息不足属于业务澄清，不属于系统失败；
- 模型返回无法解析或不符合协议的内容属于协议失败；
- 确定性校验发现单个模型字段无法回指用户原文、可信已有 Goal 或受治理词汇时，默认按字段拒绝，不让该字段进入 Goal。过滤后仍能安全表达请求且缺失非阻塞时继续；关键字段因此缺失或用户修改意图无法可靠落地时要求澄清；只有输出整体不可用、无法满足 M1 最小不变量，或受限修复后仍违反模型协议时才作为协议失败；
- 内部异常不得作为原始异常文本直接暴露给 Domain 或用户。

## 11. 内部组织方案

将当前单一 Goal Parser 模块调整为 `src/application/goal_parser/` 内部包，同时保持一个统一公共入口。

内部职责至少分为：

- 服务编排和模型调用；
- Application 层解析结果与修改语义；
- Prompt；
- 确定性校验和澄清门禁；
- Goal 创建与修订合并。

具体文件名和数量在实现前根据现有代码进一步确认。不得把拆包演变成多个业务 Parser、动态插件系统或字段级文件碎片。

公共导入路径应保持兼容，现有调用方不应因为内部拆包而被迫感知实现结构。

## 12. 迁移原则

分两步实施并分别验证：

1. 先进行内部职责拆分，保持现有外部行为和公共导入兼容；
2. 再引入明确修改语义、结构化 MissingInformation、原始表达保留和确定性校验调整。

结构调整与行为调整应避免混在同一个不可区分的变更中。迁移期间不得创建第二套 Goal 或绕过 M1 Domain Contract。

第一步是等价重构：公共导入路径、调用签名、现有行为和测试基线保持兼容。第二步才引入行为变化，并用新增契约测试明确差异。两步可以处于同一开发里程碑，但必须具有可独立审查和验证的变更边界。

行为变化后需要同步检查：

- `doc/current-state.md` 中 Goal Parser 当前能力和限制；
- `doc/architecture.md` 中目录、职责和数据流；
- `dev-log.md` 中功能变更和验证结论。

## 13. 验收场景

后续实现至少应覆盖以下行为：

1. 明确的量化经营请求生成完整 Goal。
2. 泛化“业绩”目标生成部分 Goal、结构化 MissingInformation 和澄清问题。
3. 阻塞性缺失时 Planner 不被调用。
4. 非阻塞字段缺失时允许继续规划。
5. 单字段修改只改变用户明确修改的内容。
6. 用户明确移除产品、时间、客群或约束时能够执行 CLEAR。
7. 未修改字段保持已有值。
8. Goal 新版本保留创建请求的 `original_request`，旧版本不变。
9. actor 和 channel 只能来自可信 Runtime Context。
10. 模型臆造的产品、需求、日期和身份不会进入 Goal。
11. 未知或歧义 Metric code 不会被模型自由创造后直接采信。
12. 非法 JSON 最多执行一次纯格式修复，业务歧义不得通过修复绕过。
13. 非 Demo 产品和非开门红场景无需修改 Parser 代码即可处理。
14. 现有公共导入和 BusinessAgent 调用边界保持兼容，或有明确迁移说明。

## 14. 风险与取舍

- 显式修改操作提高一致性，但会增加模型输出协议复杂度，需要更多协议测试。
- 返回部分 Goal 能保留结构化缺失，但调用方必须同时识别澄清状态，不能仅凭存在 Goal 就进入 Planner。
- 过度依赖原文字面匹配会误拒绝合理规范化；完全信任模型又会引入臆造，需要在原文证据和规范化词汇之间保持边界。
- 指标词汇可以阻止模型创造 code，但若过早建设完整本体会扩大当前范围。
- 保留首次 `original_request` 符合原始目标语义，但后续修改的审计来源仍需由 Trace 或未来修订记录承担。

## 15. 已确认决策

| 编号 | 决策 | 主要理由 |
| --- | --- | --- |
| D-01 | `original_request` 固定保存 Goal 创建请求原文，修订不覆盖 | 保持 Goal 身份来源稳定；后续修改由 Trace 或未来修订记录审计 |
| D-02 | 修改统一使用顶层字段级 `KEEP / SET / CLEAR` | 消除字段缺失、`null`、保留和清空之间的歧义，同时避免首版引入通用 Patch DSL |
| D-03 | 需要澄清时尽可能返回带 MissingInformation 的部分 Goal | 保留已经确认的结构化语义，让缺失成为领域事实而不只是一句问题 |
| D-04 | 可满足 M1 不变量的不完整新 Goal 立即获得正式 ID 和版本 1；否则不创建 Goal | 不引入 GoalDraft，也不为获得 ID 而伪造 `goal_type` |
| D-05 | 合法修订即使引入阻塞性缺失也生成下一版本；协议失败或无依据修改不生成版本 | 新版本保存用户最新有效意图，旧版本仍不可变；失败输出不得污染版本链 |
| D-06 | 首版采用 7.2 节的最小确定性阻塞规则集 | 先覆盖会改变计划、造成越权或支撑不可逆动作的关键缺失，不扩大成业务规则引擎 |
| D-07 | 首个指标词汇事实源为带显式业务版本的仓库配置，经只读端口注入；版本记入解析诊断或 Trace，不进入当前 Goal Contract | 阻止模型自由创造 code，同时保留未来替换为平台服务的能力 |
| D-08 | 最多允许一次纯格式或无歧义协议结构修复 | 提高模型协议韧性，但不允许借修复补造业务语义 |
| D-09 | 无可信依据的字段先按字段拒绝，再按剩余语义决定继续、澄清或协议失败 | 避免单个可选字段污染拖垮整个请求，也不让关键字段缺失被静默忽略 |
| D-10 | 先完成公共入口兼容的等价拆包，再实施行为修改，两步独立审查和验证 | 降低结构迁移与语义变化相互掩盖的风险 |

上述决策关闭本文原有全部待确认事项。后续实现中若发现 M1 Contract 无法承载某项决策，应先按 M1 演进评审清单证明真实消费者和契约缺口，再修订设计；不得在 Parser 内另建持久事实模型规避 Domain Contract。

## 16. 成功标准

- 新会话只阅读当前事实源、M1 Contract 和本文即可理解 Goal Parser 的问题、边界和已确认方向。
- 模型解释、确定性校验、Goal 合并和澄清门禁具有清晰职责边界。
- Goal 创建和修改不存在依赖字段缺失或 `null` 的模糊语义。
- 阻塞性缺失能够结构化保存，且不会进入 Planner。
- Goal 原始表达、可信身份和不可变版本不会因模型输出或局部修改而丢失。
- 内部代码不再集中于单一大文件，同时公共入口保持稳定。
- 新场景、产品和指标扩展不要求把业务事实写入 Prompt 或复制一套 Parser。
