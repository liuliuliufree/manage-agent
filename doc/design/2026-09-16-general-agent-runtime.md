# 通用经营 Agent 运行机制

状态：已确认（2026-09-16）

## 问题

当前演示内容覆盖前三幕，但旧应用层把这段故事误建模成固定工作流：专用 Agent 类要求按顺序形成三类产物，工具之间也互相检查调用顺序，前端预创建三个幕次。这样会让后续故事不得不绕过或扩张一个并不存在的阶段模型，也削弱了模型观察结果后自主选择下一步的能力。

## 目标

- 一次 Agent 运行对应一个可观察 Trace，Trace 由实际发生的多个 Turn 构成。
- 模型根据用户目标和 Tool 描述自主选择能力、观察结果并继续行动。
- 所有业务和外部能力采用统一 Tool 协议，并能被运行时自动发现。
- 确定性业务结论继续由普通代码或可靠外部能力产生，模型不重算硬规则。
- 前端展示真实执行过程，不以幕次、工具数量或工具名称建立固定状态机。
- 当前前三幕数据继续作为最小闭环样例，但不成为代码组织边界。

## 非目标

- 不追求完全自治，不允许模型覆盖合规硬规则或确定性结果。
- 不为尚未出现的后续故事提前设计完整领域模型或复杂工作流引擎。
- 不引入多 Agent、LangGraph 或动态插件生命周期系统。
- 本次不实现跨请求会话记忆、持久化、认证和生产部署治理。

## 边界与职责

- Agent Core 负责消息历史、多 Turn 循环、Tool 调用、事件和终止原因，不感知业务。
- 经营 Agent 负责组合模型、稳定提示词、自动发现的 Tool 和单次运行上下文，不编排固定业务步骤。
- `manage/tools/` 下的 Tool 描述使用业务语义说明使用时机。Tool 之间不以“必须先调用某工具”的内存标志限制模型；依赖的数据由每个 Tool 自己显式参数化并可靠加载。稳定提示词归属于 `manage/prompts/`。
- Tool 内部可以复用确定性服务。授权、拒绝、频控、敏感状态、适当性和评分等规则结果不得由模型覆盖。
- 提示词只定义角色、权限、事实来源和安全边界，不嵌入固定答案、固定机会或固定工具顺序。
- 前端只消费通用 Trace、Turn、Tool 和文本事件；当前三个主要 Tool 自然形成与前三幕相似的展示，后续 Tool 使用同一机制。

## 不变量

- 一个请求的 Tool 缓存和产物只属于该 Trace。
- 所有模型可见 Tool 名称唯一，参数在执行前通过 JSON Schema 校验。
- 模型每次 Tool 调用及结果都写入 Trace，并作为后续 Turn 的消息上下文。
- 达到最大 Tool Turn 后，循环只要求模型形成最终答复，不替模型执行预设业务步骤。
- 模型或数据不可用时明确返回失败，不用固定故事模板伪造已完成的分析。

## 取舍

移除应用层的必经步骤后，模型可能选择不足或给出不完整答案。当前通过清晰 Tool 描述、稳定权限提示词、完整 Trace 和评测来改善，而不是恢复固定工作流。对未来真正需要保证的评分关键路径，可以在具体业务入口增加显式、可验证的代码约束，但不得把演示幕次本身当成业务不变量。

## 成功标准

- 模型可以从任意合适 Tool 开始，也可以在无需数据时直接回答。
- 新增一个 Tool 模块后，无需修改 Agent 工具清单和前端步骤模型。
- 当前合成数据的确定性结果保持不变。
- HTTP 流能展示实际 Trace、Turn 和 Tool 生命周期。
- 代码和文档不再把前三幕称为实现阶段或通用流程。
