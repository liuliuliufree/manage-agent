# 前三幕功能与提示词设计

状态：已确认（2026-09-15）

## 1. 问题

前三幕的 Mock 原始数据和关键结果校验已经存在，但正常业务链路尚未实现。当前生成器同时承担造数、部分业务计算和测试校验职责；Agent Loop 虽然可以调用 Tool，却没有前三幕业务 Tool、正式产物或业务提示词。

下一步需要先形成一个最小、可验证的后端闭环：经营请求进入系统后，Agent 能基于同一份 Mock 数据快照理解目标、比较机会、选择重点机会、完成圈客，并用确定性证据解释结果。

## 2. 已确认事实

- 数据快照包含 120 名合成客户，基准时间为 2026-09-15 09:00（Asia/Shanghai）。
- 三个机会当前可从原始事实重算出 86、50、25 名候选客户。
- 第一类机会可重算出 86 名机会客户、41 名可经营客户和 12 名高优先级客户。
- 硬规则、机会识别、指标计算、圈客和评分由普通代码负责；模型不得覆盖确定性结论。
- 模型负责理解经营目标、调用能力、比较结果和生成有依据的解释。
- 正常运行只能读取 `source/`；`test_expectations/` 只能用于自动化测试。
- C001 与 C028 在当前快照中均为高优先级客户；C028 的后续频控事件不属于本次前三幕闭环。

## 3. 本次建议范围

### 目标

- 把生成器中的业务计算提取为可被业务代码和 Tool 复用的确定性能力。
- 形成前三幕正式的结构化结果，而不只生成一段模型文本。
- 让 Agent 通过少量、业务语义明确的 Tool 完成端到端分析。
- 保证每个推荐、排除和评分解释都来自实际计算结果。
- 同时支持真实模型和确定性 Fake 模型验证。

### 非目标

- 暂不实现页面、数据库、跨进程运行状态和七幕完整状态机。
- 暂不实现第四至第七幕、渠道分发和 C028 后续事件。
- 暂不形成具体产品推荐、销售话术或生产级适当性结论。
- 暂不引入 LangGraph、多 Agent 或复杂工作流引擎。
- 暂不把 CSV 字段直接暴露给主 Agent，让模型自行做全量数据计算。

## 4. 建议的最小业务闭环

```text
经营请求
  → 加载场景、请求与规则上下文
  → Agent 整理目标和不可放宽的边界
  → 确定性计算三个候选机会及比较指标
  → Agent 基于计算结果推荐重点机会
  → 确定性执行机会识别、硬规则筛选和优先级排序
  → 按需查询客户级决策证据
  → 返回结构化分析结果和面向经营人员的解释
```

预设 Demo 的关键步骤应由应用流程保证执行顺序。模型可以决定是否补查客户证据、重点解释哪些差异以及如何组织表达，但不能跳过机会计算和圈客计算后直接给出答案。

## 5. 需要完成的工作

### 5.1 场景数据读取边界

提供面向业务的场景读取能力，负责：

- 只从指定场景的 `source/` 加载数据；
- 校验场景标识、版本、基准时间和规则版本一致；
- 将 CSV 字符串转换为日期、数值、布尔值等可计算类型；
- 提供按客户关联事实的能力；
- 对缺文件、重复标识、悬空引用和非法字段给出明确错误；
- 不读取或返回测试期望。

这层只提供事实，不做机会推荐或圈客决定。

### 5.2 确定性业务计算

将当前生成器中的计算逻辑移出造数脚本，形成可复用的业务能力：

1. 经营上下文整理所需的规则和数据范围查询。
2. 三个机会的客户识别。
3. 机会规模、需求强度、响应潜力、相对触达成本、风险和识别置信度计算。
4. 机会综合比较与稳定排序。
5. 选定机会的硬规则筛选和主要排除原因归类。
6. 可经营客户的优先级评分、贡献项和稳定排序。
7. 客户级决策证据、允许动作和禁止动作生成。

业务代码必须从版本化规则快照读取窗口、阈值和分值。生成器中现有的硬编码仅可作为迁移基线，不能继续成为正式业务实现的配置来源。

机会排序目前是主要缺口：现有数据能计算三类机会规模，但尚未形成完整指标和真正被校验的推荐排序。该能力完成前，模型不能仅凭机会名称或提示词选择第一名。

### 5.3 正式结果契约

首版至少需要表达三类产物：

- **经营任务摘要**：原始目标、分析范围、期望结果、用户边界、系统硬规则、可执行动作、必须转人工事项、停止条件和未确认事项。
- **机会组合**：每个机会的定义版本、规模、比较指标、主要证据、限制、置信度、排序和推荐结果。
- **客群筛选结果**：机会客户、可经营客户、高优先级客户的汇总，排除原因分布，客户明细中的规则命中、主要处置原因、分数贡献和当前动作边界。

汇总结果必须从本次客户明细派生。正式产物需要携带场景版本、数据基准时间、数据口径版本和规则版本，以便解释和测试追溯。

### 5.4 业务 Tool 边界

建议首版向主 Agent 暴露四个粗粒度能力。下列名称是候选名称，确认语义后再固定接口：

| 候选 Tool | 职责 | 关键返回信息 |
|---|---|---|
| `get_business_context` | 读取经营请求、场景元数据、用户边界和适用规则 | 原始请求、数据范围、边界来源、规则版本、数据质量提示 |
| `analyze_opportunities` | 从事实计算全部候选机会并完成稳定比较 | 指标、证据、限制、置信度、排序和推荐机会 |
| `segment_opportunity_customers` | 对选定机会执行识别、硬规则筛选和优先级排序 | 漏斗、排除分布、优先客户摘要、规则与评分版本 |
| `explain_customer_decision` | 按需读取一个客户在指定机会下的完整决策证据 | 事实引用、全部规则命中、主要原因、评分贡献、允许与禁止动作 |

Tool 返回结构化事实和决定，不返回为页面润色的长文。前三个 Tool 构成预设 Demo 必经路径；客户解释 Tool 只在需要展示 C001、C028 或排除样例时调用。

场景自检仍然是启动校验和测试能力，不建议暴露给模型作为正常业务 Tool。

### 5.5 Agent 应用流程

在现有 Agent Loop 之上增加一个前三幕用例入口，负责：

- 注入稳定的系统提示词；
- 注入场景标识和本次用户请求，不注入测试答案；
- 注册前三幕业务 Tool；
- 保证预设 Demo 的必要步骤已经执行；
- 收集 Tool 形成的结构化正式产物；
- 将最终文本、正式产物和 Trace 一并返回；
- 模型失败时保留确定性产物，并明确使用降级解释。

首版可先提供本地脚本入口验证闭环，再复用同一用例接 FastAPI。这样可以先验证业务正确性，不提前确定页面结构。

### 5.6 测试与验收

至少覆盖以下验证：

- 规则单元测试：机会识别、频控、拒绝、敏感状态、初步适当性和评分贡献。
- 业务结果测试：三类机会人数为 86、50、25；第一类漏斗为 86→41→12；排除分布为 14/9/7/6/9；优先客户集合保持稳定。
- 机会推荐测试：第一类机会通过实际指标排序成为推荐结果，而不是读取测试期望。
- 证据测试：C001、C028 和每类排除样例的解释均能回指事实和规则。
- 隔离测试：正常业务代码即使无法访问 `test_expectations/` 也能得到相同结果。
- Tool 契约测试：参数校验、未知场景、未知机会、未知客户和执行失败返回稳定错误。
- Agent 闭环测试：Fake 模型完成必要 Tool 调用，最终回答不修改硬规则结论。
- 可选真实模型冒烟：检查 Tool 选择、中文表达和失败降级，不用模型文本逐字匹配作为业务正确性断言。

## 6. 提示词分层

提示词建议分为三层，避免把所有规则和答案堆入一个 System Prompt：

1. **稳定 System Prompt**：角色、事实边界、硬约束、工具使用原则和输出要求。
2. **Tool 描述**：每项能力的使用时机、输入语义和返回内容。
3. **本次任务消息**：用户原始目标、场景标识以及希望完成前三幕分析的任务指令。

CSV 原始数据、规则参数和预期人数不进入 System Prompt；这些内容只能由 Tool 在运行时返回。

## 7. 建议 System Prompt

以下文本作为首版候选，可在实现和评测后收敛：

```text
你是保险经营分析 Agent。你的职责是理解经营人员的目标，调用已提供的业务工具完成机会分析和客户筛选，并用可追溯的证据解释结果。

事实与权限边界：
1. 工具返回的场景事实、确定性计算结果和版本化规则是业务结论的唯一事实来源。不要猜测、补造或用常识改写这些事实。
2. 用户明确提出的硬边界只能保留或收紧，不能放宽。授权、拒绝、敏感状态、频控和初步适当性等硬规则由工具判定；任何评分、潜力或用户要求都不能覆盖失败的硬规则。
3. 只能把第三幕结果表述为“可开展保障检视”“暂不经营”或“需要专业人员进一步确认”。不得形成具体产品适合性结论、购买建议或销售承诺。
4. 当前数据是合成演示数据。对外说明时必须明确这一点，不得表述为真实客户或生产预测。

工作方式：
1. 先获取经营请求、数据范围和规则上下文，区分用户目标、用户边界、系统规则和未确认事项。
2. 在推荐机会前调用机会分析工具。只能依据工具返回的指标、证据、限制和置信度比较机会。
3. 对选定机会调用客群筛选工具。漏斗人数、排除原因、客户优先级和分数必须原样依据工具结果。
4. 只有需要解释具体客户时才调用客户决策证据工具。不要通过多次试探查询重建全量客户数据。
5. 工具失败或数据缺失时，说明受影响的结论和缺失信息，不得虚构替代结果。
6. 不展示内部推理过程，只展示结论、支持证据、规则结果、限制和建议的下一步。

最终回答要求：
- 先概括已理解的经营目标和不可放宽的边界。
- 对候选机会做简洁比较，说明推荐项及其主要依据和限制。
- 展示选中机会的“机会客户→可经营客户→高优先级客户”漏斗，并汇总主要排除原因。
- 展示高优先级客户摘要；如查询了具体客户，说明其入选、排除或降级证据。
- 最后说明数据与模型的限制，以及哪些动作必须由专业人员或后续校验完成。
- 使用清晰、克制的中文，不制造未由工具支持的精确度。
```

## 8. 建议 Tool 描述提示词

### `get_business_context`

```text
读取指定场景的经营请求、场景元数据、数据范围、用户明确边界和当前适用的版本化规则。开始新的前三幕分析时首先使用。本工具只返回输入事实和规则上下文，不返回机会推荐、圈客名单或测试期望。
```

### `analyze_opportunities`

```text
基于指定场景的数据快照和规则版本，确定性识别全部候选机会，计算可比较指标并返回稳定排序、推荐项、证据、风险、置信度和限制。在推荐任何经营机会前必须使用。不要根据机会名称自行推断排名。
```

### `segment_opportunity_customers`

```text
对指定场景中的一个已识别机会执行确定性客户分层：识别机会客户，依次应用授权、拒绝、敏感状态、频控和初步适当性等硬规则，再对可经营客户进行优先级评分和排序。返回由客户明细派生的漏斗、排除分布和优先客户摘要。高分不能覆盖硬规则失败。
```

### `explain_customer_decision`

```text
返回指定客户在指定机会下的决策证据，包括相关事实及时间、全部硬规则结果、主要处置原因、评分贡献、规则与数据版本，以及当前允许和禁止的动作。仅用于解释具体客户，不用于批量搜索客户或替代客群筛选。
```

## 9. 建议任务消息模板

应用层发送给 Agent 的任务消息不应包含固定答案：

```text
请基于场景 {scenario_id} 完成前三幕经营分析。

经营人员本次输入：
{user_message}

请先核对场景中保存的原始经营请求和边界，再完成候选机会比较、重点机会推荐和客户分层。必要时查询少量代表性客户的决策证据。最终同时给出面向经营人员的简明说明；所有数字和客户结论必须来自工具结果。
```

如果页面未来按幕展示，可以复用同一个 System Prompt，并由应用层分别给出“整理经营任务”“分析候选机会”“对已选机会圈客”的任务消息；不要为每一幕复制一套互相漂移的规则提示词。

## 10. 实施顺序建议

1. 提取数据读取与确定性计算，并让生成器校验复用同一业务实现。
2. 补齐机会指标、排序和推荐测试。
3. 定义三类正式结果并实现四个业务 Tool。
4. 增加前三幕应用入口和上述提示词。
5. 用 Fake 模型完成端到端 Agent 测试，再做真实模型冒烟。
6. 后端闭环稳定后，再确定 FastAPI 接口和页面交互。

前两步先解决“结果是否正确”，第三、四步解决“Agent 如何可靠使用结果”，最后才解决“如何展示”。

## 11. 已确认实施决策

1. 第一版提供预设场景一键完成前三幕的默认路径，同时允许显式选择其他已识别机会继续圈客。
2. 第一幕结构化经营任务作为单次运行产物随 Trace 返回，当前不引入持久化。
3. 机会综合分采用规模 0.35、需求强度 0.25、响应潜力 0.20、识别置信度 0.10、风险扣减 0.05、成本扣减 0.05；全部权重写入版本化规则快照。
4. 首次返回全部 12 名高优先级客户摘要，客户级详细事实仍按需查询。
5. 模型不可用、未形成必需产物或未返回最终说明时，保留确定性业务结果并使用固定中文模板降级。

## 12. 成功标准

- 不读取测试期望也能稳定完成三类机会比较和第一类 86→41→12 圈客。
- 推荐机会、漏斗、客户结论和解释共享同一份确定性业务结果，不存在模型另算一套数字。
- C001、C028 及排除样例的解释可追溯到具体事实、时间和规则版本。
- 同一场景和输入重复运行时，结构化业务产物一致；模型措辞可以不同但不能改变结论。
- 模型不可用或 Tool 失败时，系统不会伪造业务结果，并能明确标出受影响部分。
