# 智慧经营智能体对话页面设计

状态：已确认（2026-09-16）

创建日期：2026-09-16

## 1. 目的与范围

将现有前端调整为以聊天为中心的单页界面。本文件记录已确认的页面目标、展示逻辑和验收标准。

用户已明确的约束：

1. 初始页面中间放置聊天输入框，上方显示“智慧经营智能体”；页面顶部不放 Logo 和后端连接说明。
2. 智能体回答在左侧，用户提问在右侧。
3. 一次请求中的中间模型说明可见，工具调用详情默认折叠、点击展开；最后一次模型输出以 Markdown 渲染。
4. 页面不向用户展示 Turn 概念。

本次不改变 Agent 的业务行为、工具选择、数据计算和请求接口，不新增会话记忆、侧边栏、历史管理或复杂工作流。界面中的多条问答记录不意味着后端已支持跨请求记忆。

## 2. 已核实的当前事实

核实依据为当前 `web/src/App.tsx`、`web/src/types.ts`、`web/src/chatStream.ts`、`web/package.json` 和 `src/manage/api.py`。

- 前端使用 React、TypeScript 和 Vite，已有流式请求、发送和停止生成能力。
- 初始页面有欢迎消息，顶部包含品牌标记、经营 Agent 标题及后端接口提示。
- 工具输入与结果当前默认展开，页面直接显示 Turn 编号与数量。
- 模型文本按内部 Turn 保存；最终文本当前作为普通文本展示。当前依赖中没有 Markdown 渲染组件。
- API 已提供 `trace`、`turn`、`tool`、`delta`、`done`、`error` 事件。文本有归属编号，工具有调用标识、归属编号、状态、输入与结果。
- API 不提前标记某段流式文本是否为最终回答；正常完成事件提供实际执行数量。异常通过错误事件结束。
- 本文中的“思考说明”指模型通过普通文本通道公开输出的分析摘要或行动说明。当前接口未提供独立的内部推理通道，页面不生成或补造这类内容。

## 3. 页面布局

### 3.1 初始状态

页面采用简洁的单列布局。标题和输入框组成一个整体，位于主要可视区域中央，标题在输入框上方。

```text
┌──────────────────────────────────────────┐
│                                          │
│                                          │
│             智慧经营智能体               │
│                                          │
│       ┌──────────────────────────┐       │
│       │ 输入经营目标或问题…  [发送]│       │
│       └──────────────────────────┘       │
│                                          │
└──────────────────────────────────────────┘
```

- 顶部留白，不设置品牌导航、Logo、连接指示灯或“后端接口”等说明。
- 初始状态不插入智能体欢迎消息，也不放执行过程占位卡片，以保持标题和输入框的视觉中心。
- 输入框支持多行；发送按钮在输入区域右侧。空白输入不可发送。
- 键盘操作提示可以低对比度放在输入框下方。
- 当前使用合成演示数据这一事实，可在输入区下方保留一行弱提示“当前使用合成演示数据”；不与后端连接状态混写，也不占据页面顶端。

### 3.2 开始对话后

首次发送成功触发请求后，页面切换为消息列表加底部输入区。初始居中大标题退场，不占据消息区域；智能体消息可以使用“智慧经营智能体”作为角色名称。

```text
┌──────────────────────────────────────────┐
│                         ┌──────────────┐ │
│                         │ 用户的问题   │ │
│                         └──────────────┘ │
│ 智慧经营智能体                           │
│ 我会先了解经营目标与现有约束。           │
│ ▸ 查询经营背景                  已完成   │
│ 接下来比较各个机会的表现。               │
│ ▸ 分析经营机会                  已完成   │
│                                          │
│ 最终回答正文，按 Markdown 排版           │
│ ……                                       │
│                                          │
│       ┌──────────────────────────┐       │
│       │ 输入经营目标或问题…  [发送]│       │
│       └──────────────────────────┘       │
└──────────────────────────────────────────┘
```

上述文字仅演示布局，不能作为预置回答或固定工具顺序。

- 用户消息右对齐，使用柔和底色气泡；智能体消息左对齐，以宽松正文排版承载较长内容。
- 一次请求对应一条智能体消息，内部连续呈现公开说明、实际工具调用和最终正文。不能把每次内部模型调用拆成不同角色消息。
- 过程说明和最终正文使用同一左侧阅读起点，最终正文的字号、颜色和间距层级高于过程信息。
- 消息区域居中并限制阅读宽度；用户气泡更窄，长问题正常换行。最终表格或代码块不能把整页撑宽。
- 输入区在对话状态保持底部可用，不遮挡消息末尾；窄屏下缩减留白，保留左右角色区分。

## 4. 一次回答的展示逻辑

### 4.1 中间说明

- 将真实收到的模型公开说明随流追加，默认可见。
- 每段说明后呈现属于该段的实际工具调用，按实际发生顺序组织。
- 不显示“Turn 1”“第几轮”“共几轮”等编号、计数或替代性技术分组标题。可以用留白形成自然段落。
- 允许没有公开说明就调用工具，允许同一段说明关联多个工具，也允许直接回答且不调用工具。
- 不要求前端补齐“说明 + 工具”的固定模板，不填充虚构的分析文字。

### 4.2 工具调用

每次调用对应一条可折叠记录，初始收起。摘要行包含展开指示、工具标题和状态，例如“查询经营背景 · 执行中”。优先使用事件提供的可读标题，没有标题时使用工具名称；不维护固定的业务工具列表。

| 状态 | 收起时 | 展开时 |
| --- | --- | --- |
| 执行中 | 工具标题、执行中标识 | 已收到的输入参数，以及“等待返回结果” |
| 已完成 | 工具标题、已完成标识 | 输入参数与实际返回结果 |
| 失败 | 工具标题、调用失败标识 | 已有输入和真实错误信息或结果 |

- 点击摘要行切换展开状态，支持键盘操作。
- 展开仅改变已有数据的可见性，不重新发起工具调用或网络请求。
- 工具开始时即可展开查看已知参数，不必等待完成。
- 流式更新和运行结束不得重置用户已选择的展开状态；每次新调用独立默认收起，即使名称相同也不能合并。
- 工具结果用适合结构化数据的格式展示，长内容在详情区域内滚动，不将大段 JSON 自动铺满聊天区域。
- 调用失败的状态始终可见，但详情仍由用户控制。单个工具失败不自动等同于整个请求失败，模型可能继续处理。

### 4.3 最终回答与流式过渡

现有接口只有在后续工具事件或正常结束事件到达后，才能明确一段文本的用途。因此展示需要允许当前文本从“正在生成”自然转为过程说明或最终回答。

- 当前正在输出的文本只出现一份，持续可见；可从流式阶段就使用 Markdown 排版，以便直接回答也能即时阅读。
- 如果这段文本随后出现工具调用，则将其作为过程说明，在后面接上工具摘要行，不把它复制为最终答案。
- 如果开始了下一段模型输出，前一段留在过程区域，新文本继续流式显示。
- 正常完成后，依据完成事件中的归属信息，将最后一段模型文本确认为最终正文。它不能同时出现在过程区域和正文区域。
- 最终正文不需要“最终 Turn”等标签，也无需强制添加“最终回答”标题；尊重模型自身的内容标题。
- 没有工具调用的直接回答仅展示正文，不出现空的执行过程容器。
- 中间过程在完成后仍可阅读，工具详情保持各自展开状态，不自动展开全部数据。

Markdown 至少支持标题、段落、换行语义、列表、加粗、引用、链接、行内代码、代码块和表格。流式片段暂时缺少闭合标记时，允许暂时按普通文本显示；后续内容补齐后更新排版，不报错、不丢字、不重复文本。

Markdown 渲染应使用适合 React 的成熟解析能力，不用正则拼接 HTML。默认不执行原始 HTML、脚本或危险链接。具体库由实现时选择，仅引入满足正文渲染需要的轻量依赖。

## 5. 运行状态与输入交互

| 场景 | 页面行为 |
| --- | --- |
| 请求已发送，尚无内容 | 左侧显示简短“正在处理…”状态，不预建工具或过程步骤 |
| 文字生成中 | 增量显示内容，发送按钮切换为停止按钮 |
| 工具执行中 | 真实工具摘要显示执行中，已有说明保持可读 |
| 正常完成 | 停止生成状态消失，恢复发送能力 |
| 用户停止 | 保留已生成内容，显示“已停止生成”；不将停止包装成正常完成 |
| 请求失败或连接中断 | 保留已收到内容，显示简短错误提示，恢复输入和发送能力 |
| 流关闭但未收到结束事件 | 视为未完整结束，不能静默标记为成功 |

- 错误或停止时，部分文本留在原位置，不能再复制到另一处作为最终答案；尚在运行的工具应显示已中断或状态未确认，不能继续无限转动或伪装成功。
- 保持一次只运行一个请求。生成过程中保留当前禁止提交新请求的行为，不引入并行问答。
- Enter 发送，Shift + Enter 换行；中文输入法选词确认不能误触发送。
- 用户在底部阅读时随新内容跟随滚动；用户上滚查看历史或展开数据时，不强行拉回底部。可提供“回到最新”入口。
- 消息追加或布局切换不应清空既有记录；刷新后的持久化不在本次范围。

## 6. 视觉与可访问性建议

- 整体采用浅色背景、深色正文和一个克制的强调色，工具过程使用较弱的视觉层级。
- 页面只突出输入和回答，避免仪表盘卡片、复杂装饰、固定步骤进度条及技术状态栏。
- 工具展开按钮、发送和停止按钮有清晰的悬停、焦点和禁用状态，图标按钮具有可访问名称。
- 工具状态同时使用文字表达，不能仅靠颜色区分。
- 正文长词、代码和表格有局部溢出处理；移动端输入区适应软键盘，关键操作保持可达。
- 屏幕阅读器收到适度的状态提示，不因每个流式字符变化反复朗读全部历史。

## 7. 系统边界与不变量

- 前端继续消费现有 SSE 事件。内部保留 Trace、Turn 和工具调用标识，用于正确归属与更新，但这些技术编号不出现在普通页面中。
- 一次请求中的文本与工具只能更新该请求的智能体消息，后续请求不能覆盖历史结果。
- 工具输入和返回结果来自真实事件；UI 不重算业务指标、不伪造工具执行、不固化工具数量和执行顺序。
- 不为视觉上的“思考过程”新增推理接口，不强制模型输出隐含推理，不改变后端业务运行机制。
- 后端连接故障通过本次请求的错误状态表达，无需常驻后端连接说明。
- 原始工具详情仍可查看，以保留当前可观察性；折叠只影响呈现。

## 8. 已确认的交互取舍

除四项初始要求外，以下交互建议也随本设计一并确认：

- 首次发送后将输入框移至底部，居中大标题退场。
- 保留低对比度的合成演示数据提示。
- 过程文字始终可见，仅工具输入和结果默认折叠；本次不增加整个过程区域的总折叠开关。
- 当前流式文本先即时渲染，再根据实际事件确定其属于过程还是最终正文。代价是后续工具到来时可能有轻微的视觉层级变化；需要保持文本位置稳定，避免明显跳动。

本文不锁定组件拆分、CSS 参数、函数签名和具体依赖版本。后续实现应依据确认后的交互结果选择最小修改范围。

## 9. 验收标准

1. 初次打开时，中心区域仅以“智慧经营智能体”和聊天输入框为主体；没有顶部 Logo、后端连接说明或预置欢迎消息。
2. 发送后用户消息在右侧，智能体所有过程及正文在左侧，底部输入区可持续使用。
3. 使用包含多次模型输出和工具调用的事件流时，真实公开说明逐段可见，工具详情全部默认收起，点击可查看输入和结果。
4. 同一段多个工具、同名工具重复调用及无说明的工具调用均正确显示，不丢失、不串位、不预置固定步骤。
5. 展开一个执行中的工具后，结果到达仍保持展开；其他工具仍收起。完成后也不重置展开状态。
6. 最终回答的标题、列表、加粗、表格、代码块和链接正确渲染；生成中可阅读，结束后只出现一份正文。
7. 直接回答、没有中间说明、中文输入法输入、长文本、长表格和窄屏布局均可正常使用。
8. 页面可见文案不出现 Turn、轮次编号、Trace ID 或执行总轮数。
9. 工具失败、网络异常和用户停止均保留已有内容，并显示真实状态；非正常结束不展示成功状态。
10. 用户上滚时不会被新内容强制拉回底部；返回底部后可继续跟随。
11. 后续实现完成时，通过前端类型检查与生产构建，并用可控事件流验证文本归属、工具展开状态和中断行为；浏览器检查初始页、对话页、展开详情、Markdown 与窄屏。未实际执行的检查须明确记录。
