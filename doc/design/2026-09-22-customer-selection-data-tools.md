# 第二幕自动圈客：Mock 数据评估与工具设计

状态：已实现（2026-09-22）。已按确认边界发布共享 v2 快照、两个 Tool、圈客 Capability 装配与离线/真实模型验证；两幕真实模型场景已由单 Plan 的第一幕 handler 发布正式 Opportunity 并直接交给第二幕，第一幕 handler 尚未下沉为可复用 Application 模块。

创建日期：2026-09-22。

实现校准（2026-09-22）：活跃数据为 `insight_demo_v2/2.0`（50 位客户、117 条行为）；实现入口为 `src/application/customer_selection.py`，公共装配导出位于 `src/application/__init__.py`。圈客成功发布 `selection_result` 和优先集合 `customer_set`；人工标注只由 `scripts/evaluate_customer_selection_model.py` 读取。完整离线测试 74 项通过，真实模型独立标注评测 7/7 通过。另一次真实模型两幕场景得到优先 2、进一步了解 4、持续关注 4、排除 40；以上结果不代表可复用第一幕 Application 能力、策略或生产链路已完成。

## 1. 已确认的故事与边界

承接第一幕的一个优先经营机会，从相关信号找到具体客户，分为优先沟通、进一步了解、持续关注。只有明确表达自身相关需求的客户进入优先沟通层，并交给第三幕制定策略。浏览、活动、一般咨询不能独立支持这一层。

名单后重点展开一位优先客户，展示关联机会、需求原话、时间、来源、入选理由和待核实信息。第二幕不做具体产品匹配，不按老客、新客分别展开，不预测成交或 NBEV。Demo 样本保证有符合条件的客户，不扩展无人入选的故事分支。

本次仅核对实际文件并设计补充方案，不生成新快照、不实现工具、不运行模型评估，不改变单 Plan 和执行前确定性权限校验边界。

| 故事要求 | 现有依据 | 判断 |
| --- | --- | --- |
| 找到具体客户 | 50 位客户有稳定 ID、虚构称呼、年龄和归属 | 足够，不必补保单、资产或健康数据 |
| 展示相关行为 | 115 条事件有客户关联、主题、类型、时间和素材引用 | 足够作为原始证据底座 |

本次按非空 JSONL 行重算：115 条事件、主窗口 105 条；近期有 question 的客户 15 位，有 explicit_interest 的客户也是 15 位；前者全部在后者中。这不能证明没有进一步了解层，但说明按现有标签直接分层缺少独立的一般咨询组。

C021 当前回访原话为：“我希望进一步了解退休后补充收入的安排，先把领取条件和限制讲清楚。”它能支持进一步了解的兴趣，不足以稳健断言客户已提出自己的收入安排目标。8 位退休收入主题的 explicit_interest 客户不能直接报告为 8 位明确需求客户。

## 3. 最小 Mock 补充方案

### 3.1 保留底座，发布共同消费的新快照

复用 50 位客户、5 个主题、素材目录、90 天窗口及来源结构。不必增加婚姻、收入、资产、健康、保单、新老客标签或真实联系方式；family_stage 可以继续未知。

建议以现有快照为底稿发布新版本，第一幕和第二幕使用同一版本。不要第一幕使用旧统计、第二幕偷偷叠加新事实，也不覆盖原版后继续沿用旧版本号和指纹。

重写少量演示表达，并增加必要的后续记录；不为保持 115 条或 15 个兴趣客户而牺牲语义。实际生成时同步重新计算数量、统计、manifest、README 和依赖旧配额的验证预期。本设计不预报新名单人数。

### 3.2 需覆盖的表达样本

下表是建议合成的事实，不是现有事实或预填运行结果。客户编号仅表示可复用的样本，业务逻辑不得按编号判断。

| 用途 | 可用客户 | 建议的虚构表达 | 要验证的区别 |
| --- | --- | --- | --- |
| 单客展开主角 | C021 | 我想给自己安排一份退休后的补充收入，希望能持续领取。目前这件事还没定下来，想先把可选方式和限制了解清楚。 | 有自身目标、未完成安排及沟通诉求 |
| 另一位明确需求客户 | C022 | 我想现在开始为自己未来退休后的生活准备一份补充收入，具体什么时候开始领取还没想好。 | 不同年龄也可有需求，领取时间保持未知 |
| 一般咨询 | C023 | 我只是想弄清楚领取规则，暂时没有确定要为自己做这类安排。 | 问题具体不等于明确自身需求；未确定也不自动等于拒绝 |
| 为他人询问 | C024 | 我是替朋友问问退休收入安排有哪些方式，我自己目前没有这方面的计划。 | 不能将朋友需求算给客户本人 |
| 需求后撤回 | C025 | 先表达为自己准备退休收入，较晚记录：这件事今年先不考虑了，暂时不继续安排。 | 早期正向不能覆盖后续明确撤回 |
| 另一机会方向 | C029 | 我想重新梳理自己家庭的长期保障安排，先确认要考虑哪些事项，目前还没有整理清楚。 | 支持家庭保障沟通，不推导保障缺口或传承需求 |
| 无关反馈对照 | 独立评测样本 | 先明确退休收入需求，后来仅表示暂不考虑医疗保障。 | 不能用任意较晚否定覆盖所有机会 |

其余浏览、活动、跨主题、历史和无行为样本继续复用。新增表达应有自然差异，不只替换称呼，也不凭年龄补写退休状态。主角展开不必增加预算、目标收入金额或已购保障；没有提供的内容保持未知。

“没有找到后续否定”只表示已提供记录中未发现，不代表掌握客户完整历史。

### 3.3 事实与评测标注分开

运行时以原始表达、时序、来源和版本为依据，不在客户档案预填优先级、潜在机会、推荐产品或有效需求结论。

statement_kind 保持来源侧人工编码的含义，不将 explicit_interest 全量升级为明确需求。新文本与旧类别不符时应校准编码，不为维持统计强行贴标。

另外准备人工评测标注：是否表达自身需求、对应原文片段、机会关联、撤回/已解决/歧义及预期分层。标注与业务数据隔离，模型和主 Agent 不读取答案，也不能作为运行时返回表。首版模型建议不读取 statement_kind，只看原始表达和行为上下文，避免分类捷径。

若未来要求确定性证明明确需求，需要经确认的结构化事实或人工复核；模型原话解读不能伪装为确定性事实。

## 4. 工具建议

复用现有 Tool 协议，新增两个工具职责。以下名称用于讨论，不锁定代码位置、函数签名或 Schema。不增加圈客 Agent、工作流引擎或插件基础设施。

### 4.1 客户证据查询：query_customer_evidence

职责：受控读取客户档案和行为明细，支持取候选证据及按客户展开，不判断经营价值。

概念输入是受控主题范围、观察窗口或已授权客户引用。代理人、渠道、版本及允许访问范围由可信配置绑定，模型不能指定任意代理人、路径、SQL 或代码。

输出客户标识与称呼、必要基础信息、按时间排列的原始事件、素材标题、原话、来源、快照版本和覆盖/缺失/截断说明。浏览与活动不能生成不存在的客户原话。

当前只有 50 位客户，建议完整读取当前代理人授权快照，内部按客户组织后分批评估，避免只按主题编码召回而漏掉跨主题表达。若先筛选候选，也须读取候选在窗口内的完整行为链，包括负向记录；历史单独标明。

不能只把正向表达送入模型，不能对截断证据声称无后续否定。完整读取仅针对当前小规模受控快照，生产召回与分页策略延后设计。

### 4.2 潜在机会评估模型：assess_customer_opportunity

职责：判断客户证据是否支持本次机会、支持到什么程度，并给出可核对的经营建议。它是内部调用模型的 Tool，不是能自主规划或调用其他工具的子 Agent。

输入概念：本次正式 Opportunity 及其解释/证据、受控客户证据引用和观察时点。工具从同一运行解析真实对象，不能让主 Agent 改写的摘要替代客户原文。第一幕正式产物尚未集成时，只能用明确标识的评测输入验证，不能称完整链路已实现。

| 输出内容 | 含义 |
| --- | --- |
| 机会关联 | 相关、不相关或无法判断，说明与当前机会的关系 |
| 需求状态 | 明确自身需求、主动了解、仅关注、当前否定/已解决，或证据不足/冲突 |
| 正向及反向证据 | 输入事件引用和逐字片段，支持、限制、反向分开 |
| 需求摘要 | 仅概括有原文支持的目标，不补预算、缺口或购买意向 |
| 建议层级及理由 | 三层建议或本次不入选，附可理解的依据 |
| 待核实项 | 本次需求理解所缺信息，不提前生成产品方案 |
| 推断来源 | 模型标识、提示/评估口径版本、时间、输入快照及调用记录 |

不输出产品推荐、成交概率、价值分或预计 NBEV。首版用可解释类别，不引入未经校准的综合评分。换机会、阶段或主题仍使用相同职责，不设养老或产品专用分支。

内部复用现有模型调用层。独立模型调用用于隔离客户级判断、方便替换与评测；主 Agent 不必了解供应商或提示细节。每位客户证据要完整，分批规模在实现前依据实际上下文决定。

### 4.3 模型建议与确定性校验

模型负责语义理解；程序负责结构、引用、访问范围、时间范围和分层不变量。

优先沟通的建议约束：与当前机会相关、有明确自身需求的模型解读及有效原文引用、无未解决的相关否定/冲突，且证据包完整。只有一般咨询或浏览时，即使模型建议优先，也不能直接通过约束。

程序能验证引用真实、属于该客户、逐字片段存在，以及声明类别与层级一致；不能仅凭字符串匹配证明模型语义必然正确。需求解读仍标记为模型信号，依赖独立评测验证准确性，不宣称规则引擎已确定客户真实需求。

相关但未明确需求的主动咨询归进一步了解，仅浏览/活动归持续关注。明确否定、已解决、无关或无法判断不强塞进三个正向层级，内部保留不入选原因。同主题较晚撤回不能忽略，不同主题否定不互相覆盖，无法解释的冲突不进入优先层。

模型失败、引用非法、证据缺失不能用预制名单补成功，沿用现有停止语义。Demo 保证有明确需求是样本要求，不是跳过验证的授权，不扩展无人入选的展示分支。

## 5. 控制流与第三幕交接

一个有证据的 Opportunity → 查询实际客户证据 → 模型评估机会关联与需求 → 确定性校验并分层 → 展示名单及一位优先客户 → 只交接优先客户。

圈客 Capability 负责结果组织与正式发布；两个 Tool 分别读取事实和产生模型建议。模型工具不另建正式 Opportunity 替换第一幕机会，不生成新 Plan，不把其他主题发现自动升级为新经营路径。

展示保留全部三层；给第三幕的 customer_set 只包含优先客户，附机会解释/引用、需求证据、入选理由及待核实项。第三幕不能从展示名单自行扩大范围。

现有输入解析只读取直接依赖发布产物，不自动回溯祖先。圈客必须把第三幕所需解释和证据随客户集合明确交接，或由 Plan 显式声明所需直接依赖，不能假设第三幕凭空获得第一幕上下文。

展开客户从实际优先集合选择。Demo 可以配置希望展示的样本，但必须先确认其仍在集合中，不强行入选。同层排序尚未确认，可先稳定展示，不称价值排名。

## 6. 成功标准与验证边界

- 数据：来源、客户关联、时序和指纹一致；两幕同版本；原话清楚区分自身需求与一般了解；生成后重算实际统计。
- 模型：以独立标注验证自身需求、一般咨询、为朋友询问、仅浏览、后续撤回、已解决、无关否定和跨主题证据，不能只验证 JSON 合法。
- 行为变化：删除需求或改为一般咨询后不能凭 ID、年龄或旧标签继续入选；新增相关撤回应改变结果；无关否定不能机械覆盖；多次浏览不重复计人。
- 展示及交接：需求、理由可回指原话/时间/来源；区分事实和模型判断；无产品匹配与 NBEV 预测；展开客户来自实际结果；只有优先集合进入第三幕。
